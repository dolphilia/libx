# 外部公式文書の取得・整形・定本化・翻訳パイロット計画

- 作成日: 2026-08-11
- 最初の対象: GLFW公式ドキュメント
- 最初の翻訳先: 日本語
- 根拠原則: `docs/spec/PROJECT_PRINCIPLES.md`
- ステータス: 実施中（フェーズ5、日本語14/36ページを原文照合済み）

## 1. 目的

外部プロジェクトの公式文書を取得し、libx向けMarkdown／MDXへ整形し、翻訳元言語の定本として配置・設定し、翻訳・確認・公開するまでの実作業を複数のパイロットで調査する。

各パイロットでは、必要だった人の判断、機械化できる処理、失敗、例外、所要時間、成果物を逐次記録する。複数プロジェクトで共通する手順と固有処理を分離し、最終的に`docs/guides/`配下の一つの標準運用ガイドへ統合する。

## 2. 成果物

### パイロット中

- プロジェクト別の取得元・版・ライセンス記録
- 原文の網羅性を確認する文書インベントリ
- 上流文書とlibx文書の対応表
- 変換・翻訳・レビューの逐次作業記録
- 自動化候補と未解決事項
- libx上でビルド可能な英語定本と日本語翻訳

### パイロット終了後

- `docs/guides/UPSTREAM_DOCUMENT_IMPORT_AND_TRANSLATION_GUIDE.md`（予定）
- 必要と判明した取得・変換・翻訳状態検査スクリプト
- 必要な場合は翻訳追跡メタデータの仕様とADR

## 3. 記録と作業領域

Gitで継続管理する記録は`docs/notes/document-import/<project>/`へ置く。取得した上流リポジトリ、生成HTML、変換途中の大量ファイルは`.tmp/document-import/<project>/`へ置き、検証済みの最終文書だけを`apps/<project>/src/content/docs/`へ移す。

```text
docs/notes/document-import/glfw/
├── README.md
├── SOURCE_MANIFEST.md
├── CONTENT_MAP.md
├── WORK_LOG.md
└── REVIEW_CHECKLIST.md

.tmp/document-import/glfw/
├── 01-source/
├── 02-extracted/
├── 03-normalized/
├── 04-translation/
└── 05-reports/
```

この分離により、外部取得物や失敗した変換を公開アプリへ混入させず、判断と由来だけをGitで追跡できる。

## 4. GLFWパイロットの前提

調査時点の公式`latest`ページはGLFW 3.5.1を示すが、`latest`は将来別版を指す。取得時に次を固定するまで、3.5.1を確定定本として扱わない。

- 正式リリース番号とタグ
- タグが指すコミットSHA
- ソースアーカイブまたはGit取得元
- 公式HTMLの取得日時
- 対象ファイルのチェックサム
- ライセンス全文と著作権表示

GLFWの文書はDoxygenで生成される。内容取得の優先順位は次とする。

1. 固定した正式リリースのリポジトリ内文書ソースと公開ヘッダー
2. 同じ版の公式生成HTML（リンク、アンカー、表示、網羅性の照合）
3. 公式リリースノート、版履歴、配布アーカイブ

公式サイト: [GLFW latest documentation](https://www.glfw.org/docs/latest/)  
公式リポジトリ: [glfw/glfw](https://github.com/glfw/glfw)  
ライセンス: [GLFW License](https://www.glfw.org/license)

GLFWはzlib/libpngライセンスを掲示している。複製・翻訳では、由来を誤認させず、変更版であることを明示し、ライセンス通知を保持する。実際の採用前に固定したリリース内のライセンスファイルと文書ソースへの適用範囲を再確認する。

## 5. 対象範囲

最低限、公式ドキュメント入口から到達できる次の領域をインベントリへ含める。

- Introduction
- Release notes、version history
- Getting started
- Introduction to the API
- Window、Context、Vulkan、Monitor、Inputの各ガイド
- Compiling GLFW、Building applications
- API reference
- Moving from GLFW 2 to 3
- Guarantees and limitations
- Standards conformance
- 文中から参照される図、コード例、定数、型、関数、関連ページ

「網羅」はページを無条件に複製することではない。公式入口、Doxygenページ一覧、文書ソース、公開ヘッダーの四者を照合し、採用、統合、除外の理由を`CONTENT_MAP.md`へ記録した状態を指す。

フォーラム投稿、Issue、非公式チュートリアル、検索結果だけで見つかる第三者資料は定本へ含めない。必要な場合は参考資料として別に扱い、ライセンスを個別確認する。

## 6. 実施フェーズ

### フェーズ0: 取得条件と法的条件の固定

1. 公式リリースを特定する。
2. タグ、コミットSHA、取得URL、取得日時、チェックサムを記録する。
3. ライセンスと必要な帰属・変更表示を確認する。
4. 対象範囲と除外範囲を承認する。

完了条件:

- `SOURCE_MANIFEST.md`の必須項目が埋まっている。
- 版とライセンスが曖昧なまま本文変換を始めていない。

### フェーズ1: 原文取得とインベントリ作成

1. 固定したリリースを`.tmp/document-import/glfw/01-source/`へ取得する。
2. Doxygen文書ソース、公開ヘッダー、画像、生成HTMLを分類する。
3. 公式ナビゲーションとファイル一覧を照合する。
4. 各文書を採用、統合、参照のみ、除外に分類する。
5. 欠落リンク、生成専用ページ、重複説明を記録する。

完了条件:

- 全対象が`CONTENT_MAP.md`のいずれかの分類に入っている。
- 「チュートリアル・ガイド・リファレンス」の欠落有無を説明できる。

### フェーズ2: libxサイト構造の決定

候補プロジェクトIDは`glfw`とする。版ディレクトリは固定した上流版に対応するID（例: `v3.5.1`）を使用し、英語を定本、日本語を翻訳として構成する。

1. `CONTENT_MAP.md`でカテゴリ、順序、安定スラッグを確定する。
2. APIリファレンスを1シンボル1ページにするか、公式モジュール単位にするか比較する。
3. 将来版でURLを維持できる粒度を選ぶ。
4. `create-project.js`のdry-runまたは構造確認後、テンプレートからサイトを作成する。
5. 言語、版、カテゴリ、ライセンス設定を検証する。

初期カテゴリ案は次とするが、インベントリ完了前に確定しない。

```text
01-overview/
02-getting-started/
03-guides/
04-reference/
05-migration-and-history/
```

完了条件:

- URLと文書粒度の決定理由が記録されている。
- 空のサイトが個別ビルドできる。

### フェーズ3: 英語定本の変換・整形

1. Doxygen構文を標準Markdown／MDXへ変換する。
2. 見出し階層、コードフェンス、表、注記、画像、内部リンクを正規化する。
3. C識別子、定数、関数シグネチャ、コード例を原文どおり保持する。
4. Doxygenアンカーとlibxの安定スラッグの対応を記録する。
5. 自動変換後にページ単位で原文と照合する。
6. Frontmatterと必要な`licenseSource`を付与する。

定本化では意味を要約・補筆しない。ナビゲーション上の分割・統合やMarkdown表現の変更は可能だが、変更内容を記録し、GLFW公式文書そのものと誤認させない。

完了条件:

- 英語ページが全件ビルドできる。
- 外部・内部リンク、コード、画像、帰属表示を検査できる。
- `CONTENT_MAP.md`から各英語ページへ追跡できる。

### フェーズ4: 英語を翻訳元の定本として設定

`project.config.jsonc`では少なくとも次を満たす。

- `language.default`と`licensing.sourceLanguage`を`en`にする。
- `language.supported`へ`en`と`ja`を登録する。
- 固定した上流版を`versioning.versions`へ登録する。
- GLFWの名称、原著作者、zlib/libpng、固定版の出典URLを`licensing.sources`へ登録する。
- 全カテゴリの英語・日本語表示名を設定する。

上流リビジョンや原文ハッシュを既存Frontmatterへ独自追加しない。パイロット中は`SOURCE_MANIFEST.md`と`CONTENT_MAP.md`で追跡し、複数パイロットで必要性が確認された場合に共有スキーマとして設計する。

### フェーズ5: 日本語翻訳

1. 技術用語集と表記規則を先に作る。
2. 英語と同じカテゴリ、スラッグ、ファイル順を作る。
3. 計画した順序で一ページずつ、見出し、本文、注記、画像代替テキストを翻訳する。
4. API名、識別子、コード、URL、数値条件は不用意に翻訳しない。
5. 原文の規範語（must、should、may等）の強さを維持する。
6. 現段階では翻訳機、翻訳API、ローカル翻訳モデル、一括翻訳スクリプトを使用しない。
7. 未翻訳や判断保留を黙って省略せず、作業記録へ残す。

完了条件:

- 英語と日本語の対応表が完成している。
- 日本語だけで手順を実行しても技術的意味が変わらない。
- 欠落がある場合、システムが許容し、進捗として記録されている。

### フェーズ6: 確認とプレビュー公開

確認を次の四層に分ける。

1. 構造: 設定、カテゴリ、対応ページ、サイドバー、リンク
2. 技術: API、コード、版、プラットフォーム条件、規範表現
3. 言語: 日本語の明確さ、用語統一、原文との対応
4. 表示・法務: ブラウザ表示、モバイル、アクセシビリティ、帰属、変更表示

個別ビルド、選択的ビルド、リポジトリ整合性検査に合格してからPreviewへデプロイする。Previewで代表ページだけでなく、文書入口、各カテゴリ、APIリファレンス、404、言語切替、版切替を確認する。

Productionへの公開は別の明示的判断とし、パイロットの途中成果を自動的に本番公開しない。

### フェーズ7: 振り返りと標準化

1. `WORK_LOG.md`から実作業と所要時間を集計する。
2. 手作業を「必要な判断」「機械的反復」「GLFW固有処理」に分類する。
3. 自動化候補を安全性、再利用性、効果で優先順位付けする。
4. 次の外部プロジェクトで同じ記録様式を使う。
5. 複数パイロットで再現した手順だけを標準ガイドへ昇格する。

## 7. 逐次記録の規則

取得、変換、配置、設定、翻訳、レビューの各まとまりについて、作業前後に`WORK_LOG.md`へ記録する。

必須項目:

- 日時と担当
- フェーズと目的
- 入力の版・ファイル・URL
- 実行コマンドまたは手作業
- 出力先
- 判断した内容と理由
- 成功・失敗・検証結果
- 実作業時間
- 自動化できそうな部分
- 次の作業と未解決事項

大量の同型ページは一件ずつ同じ説明を書かず、変換バッチと例外ページを分けて記録する。

## 8. 中断条件

次の場合は本文の取得・変換・公開を進めず、判断を記録して停止する。

- リリース版、出典、ライセンス適用範囲が確定できない。
- 公式文書とリポジトリ内ソースが同じ版として対応しない。
- 変換で規範的意味、コード、APIシグネチャを保持できない。
- 原文との対応を追跡できない編集が必要になる。
- Previewで帰属、リンク、言語切替、主要ページ表示に問題がある。
