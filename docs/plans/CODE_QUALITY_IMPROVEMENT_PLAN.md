# コード品質改善計画

## 1. 背景と目的

リポジトリ全体のコードレビューと現状確認により、ドキュメントサイトの入口URL、共有CSS、Service Worker、設定参照、静的検査、回帰テストに改善余地が見つかった。

本計画の目的は、次の状態を段階的に実現することである。

- 各ドキュメントサイトのトップページから、必ず実在するページへ遷移できる。
- 共有UIが構文エラーなくビルドされ、モバイル・デスクトップ双方で意図した表示になる。
- サイドバーJSONのオフラインキャッシュが安定して動作する。
- プロジェクト設定の参照名と型定義が一致し、設定したデフォルト言語が反映される。
- `pnpm lint` がエラーなしで完了し、主要なURL生成処理を自動テストで保護できる。
- 通常ビルドで検出される警告を分類し、意図しない警告を残さない。

## 2. 対象範囲

### 対象

- `templates/docs-site`
- `apps/sample-docs`
- `apps/test-verification`
- `packages/ui`
- `packages/project-config`
- `packages/content-utils`
- ルートの検査・テスト用スクリプト

### 対象外

- ドキュメント本文の翻訳品質改善
- UIデザインの全面刷新
- デプロイ基盤の変更
- `sites/landing` のページ構成変更

対象外の問題を作業中に発見した場合は、本計画へ無理に含めず、別課題として記録する。

## 3. 優先順位

| 優先度 | 課題 | 主な影響 |
| --- | --- | --- |
| P1 | ドキュメントサイトのトップページが存在しないURLへリダイレクトする | サイト入口から404になる |
| P1 | `Sidebar.astro` のCSSに余分な閉じ括弧がある | 共有UIのCSS構文エラー、意図しない適用範囲 |
| P2 | Service Workerがキャッシュ書き込みを待たない | オフラインキャッシュが不安定になる |
| P2 | 標準テンプレートが存在しない `defaultLocale` を参照する | 設定したデフォルト言語を無視する |
| P2 | `pnpm lint` がエラー終了する | CIや変更時の品質ゲートとして利用できない |
| P3 | URL生成・設定・キャッシュに回帰テストがない | 同種の不具合を再検出できない |
| P3 | ビルド時の警告と大量のデバッグログが残る | 本当に重要な警告を見落としやすい |

## 4. 実施方針

- P1を最初に解消し、各段階で個別ビルドを実行する。
- 3アプリに重複する実装は、まず同一仕様へ修正して挙動を安定させ、その後に共通化する。
- 共有パッケージの変更は標準テンプレートだけでなく、`sample-docs` と `test-verification` でも検証する。
- 修正とリファクタリングを同じ差分に詰め込まず、問題単位でコミット可能な大きさに保つ。
- 警告を無条件に抑制せず、原因を解消できない場合のみ理由をコメントまたは計画書へ記録する。

## 5. 実施ステップ

### フェーズ1: ベースラインの固定

   - `pnpm --filter=apps-test-verification build`
2. 各アプリのビルド成果物から、生成された `/{version}/{lang}/index.html` の一覧を取得する。

4. 作業前後で比較する警告を次の分類に分ける。
   - CSS構文警告
   - Viteの動的import警告
   - ブラウザ向けバンドルへの `node:*` モジュール混入警告
   - MDX/KaTeXコンテンツ警告

完了条件:

- 修正前の失敗・警告件数と再現手順が明確になっている。

### フェーズ2: トップページとデフォルト言語の修正

対象ファイル:

- `templates/docs-site/src/pages/index.astro`
- `apps/sample-docs/src/pages/index.astro`
- `apps/test-verification/src/pages/index.astro`
- `templates/docs-site/src/pages/[version]/index.astro`
- 必要に応じて `packages/content-utils/src/dynamic-navigation.ts`

実施内容:

1. ルートページのリダイレクト先を `/{lang}/` ではなく、実在する `/{version}/{lang}/` または最初の文書URLに変更する。
2. 最新バージョンの判定は、可能な限り既存の `generateRedirectUrl()` / `getLatestVersion()` を再利用し、3アプリで同じ規則に統一する。
3. 対象言語に文書がない場合のフォールバック順を明文化する。
   1. 対象言語の最新バージョンにある最初の文書
   2. 設定されたデフォルト言語の最新バージョンにある最初の文書
   3. 設定上の最新バージョンのインデックス
4. `templates/docs-site/src/pages/[version]/index.astro` の `projectConfig.defaultLocale` を `projectConfig.defaultLang` に修正する。
5. `return Astro.redirect()` より後ろにある、実行されないクライアント側リダイレクトコードとmeta refreshを整理する。ブラウザ言語検出を残す場合は、静的リダイレクトと競合しない独立した設計にする。

検証:

- 各アプリのルート `index.html` に含まれる遷移先が、同じビルド成果物内に存在することをスクリプトで検査する。
- `defaultLang` を一時的に英語以外へ変更した検証用設定でも、バージョンページが正しい言語へ遷移することを確認する。
- ベースURL付きとローカルビルドの両方で、先頭・末尾スラッシュが重複しないことを確認する。

完了条件:

- 3アプリのトップページから404にならない。
- 標準テンプレートが設定されたデフォルト言語を使用する。
- リダイレクト先の決定規則が3アプリで一致する。

### フェーズ3: 共有サイドバーCSSの修正

対象ファイル:

- `packages/ui/src/components/Sidebar.astro`

実施内容:

1. モバイル用 `@media (max-width: 48em)` の括弧対応を修正する。
2. `.sidebar-title` と `.close-button` を意図したメディアクエリ内へ戻す。
3. デスクトップでモバイル用閉じるボタンが表示・適用されないことを確認する。
4. LTRとRTLのモバイルオーバーレイ方向を確認し、既存のRTL対応を壊さないようにする。

検証:

- 3アプリの個別ビルドで `Unexpected "}"` が出ない。
- 画面幅48em未満でサイドバーの開閉、オーバーレイ、閉じるボタンを確認する。
- 48em以上でデスクトップ用サイドバーの表示を確認する。
- `dir="rtl"` のページで開閉方向と境界線を確認する。

完了条件:

- CSS構文警告が0件になる。
- モバイル限定スタイルがデスクトップへ漏れない。

### フェーズ4: Service Workerの堅牢化と重複整理

対象ファイル:

- `templates/docs-site/public/sw.js`
- `apps/sample-docs/public/sw.js`
- `apps/test-verification/public/sw.js`
- `apps/*/src/layouts/MainLayout.astro`
- 共通化する場合は `scripts/` または共有アセット生成用ファイル

実施内容:

1. 正常レスポンスの `cache.put()` を `await` または `event.waitUntil()` で完了保証する。
2. オフラインかつキャッシュがない場合は、`undefined` ではなく明示的な503レスポンスを返す。
3. GET以外のリクエストを処理対象外にする。
4. `response.ok`、レスポンスタイプ、必要に応じて同一オリジンを確認してからキャッシュする。
5. `activate` 内の `clients.claim()` を待機対象へ含める。
6. キャッシュ名の更新規則を決め、挙動変更時にはバージョンを更新する。
7. 3つの同一ファイルを手作業で維持しないよう、次のいずれかに統一する。
   - 共通テンプレートから各アプリへ生成・コピーするスクリプト
   - ビルド時に共通ソースを各出力先へ配置する処理

検証:

- 初回オンライン取得後、キャッシュに対象JSONが保存される。
- オフライン時にキャッシュ済みJSONを取得できる。
- オフラインかつ未キャッシュ時に503が返る。
- キャッシュ名更新後に古い `sidebar-cache-*` のみが削除される。
- サイドバー以外のリクエストに影響しない。

完了条件:

- キャッシュ書き込みとフォールバックが決定的に動作する。
- 3アプリのService Worker実装に差分が生じない仕組みがある。

### フェーズ5: lint・型定義・設定スキーマの整理

対象ファイル:

- `apps/test-verification/src/layouts/DocLayout.astro`
- `packages/project-config/src/config-schema.ts`
- `packages/project-config/src/config.ts`
- lintで `no-explicit-any` が報告される共有パッケージとUIコンポーネント

実施内容:

1. `DocLayout.astro` のインラインスクリプトで、`define:vars` と関数引数の役割を整理し、未使用変数エラーを解消する。
2. `ProjectConfig` に実際に利用している `licensing` などの設定項目を型として追加し、UI側の `projectConfig: any` を具体型へ置き換える。
3. 設定バリデーションを浅い存在確認から、少なくとも次を検査する形へ強化する。
   - `supported` の各要素が文字列である。
   - `default` が `supported` に含まれる。
   - バージョンの `id`、`name`、`date` が妥当である。
   - `translations` にフォールバック言語が存在する。
   - `date` を `Date` に変換した結果が有効である。
4. `any` は設定オブジェクト、Astro props、コレクションエントリの順に具体型へ置換する。
5. 一度に全警告を直して大きな差分にせず、パッケージ単位で進める。

検証:

- `pnpm lint` が終了コード0になる。
- 各ワークスペースのTypeScript/Astroチェックを実行できるスクリプトを追加し、型エラーがないことを確認する。
- 不正なJSONC設定を与えたテストで、読み込み時に対象フィールドを示すエラーになることを確認する。

完了条件:

- lintエラー0件。
- 残す `any` がある場合、理由と境界が明確になっている。
- 実行時設定と公開型の主要項目が一致する。

### フェーズ6: 回帰テストと品質ゲートの追加

対象候補:

- `packages/content-utils` のURL生成・ナビゲーション
- `packages/project-config` のJSONC読み込みと変換
- Service Workerのレスポンス戦略
- ビルド成果物のリンク整合性
- ルート `package.json`

実施内容:

1. リポジトリの既存構成と相性のよいテストランナーを選定し、ルートに `test` スクリプトを追加する。
2. 最低限、次の単体テストを追加する。
   - `buildDocumentPath()` の `version-first` / `locale-first`
   - 最新バージョンと最初のページの選択
   - ベースURLの正規化
   - JSONCコメント除去と設定変換
   - 不正な設定値の拒否
3. ビルド後のスモークテストを追加する。
   - ルートリダイレクト先のファイルが存在する。
   - サイドバーJSONから参照される主要ページが存在する。
   - HTML内の内部リンクに未解決の `..` や重複ベースURLがない。
4. CI相当のローカルコマンドを1つにまとめる。
   - 推奨: `pnpm check` = lint + typecheck + test + 選択的ビルド/スモークテスト

完了条件:

- URLまたは設定の回帰を自動テストで検出できる。
- `pnpm check` がローカルとCIの共通品質ゲートとして利用できる。

### フェーズ7: ビルド警告とログの整理

対象ファイル:

- `packages/config/src/index.ts`
- `packages/project-config/src/config-loader.ts`
- `scripts/plugins/remark-link-transformer.js`
- `apps/*/src/pages/**/*.astro`
- `apps/*/public/sw.js`

実施内容:

1. `remark-link-transformer.js` のCommonJS/ESM境界を整理し、Nodeの実験的警告を解消する。
2. 変数を使った動的importがViteの解析対象になる理由を確認し、サーバー専用コードの分離または明示的な `vite-ignore` の妥当性を判断する。
3. ブラウザ用バンドルから `node:path` と `node:fs/promises` を参照する設定ローダーを切り離す。
4. `console.log` を次の基準で整理する。
   - 通常ビルドでは文書ごとのログを出さない。
   - 警告とエラーは対象ファイル・URLを含める。
   - 詳細ログは環境変数または `--verbose` 指定時だけ出す。
5. KaTeXなどコンテンツ由来の警告は、コード問題と分離して対象文書を修正するか、既知の警告として一覧化する。

完了条件:

- 通常の個別ビルドに、コード起因の未対応警告が残らない。
- ビルドログから重要な警告を容易に判別できる。

## 8. リスクと対策

| リスク | 対策 |
| --- | --- |
| リダイレクト修正でローカルと本番のベースURLがずれる | `baseUrl` の有無を含むテーブル駆動テストを追加する |
| 共通CSS修正が全アプリのレイアウトへ影響する | 3アプリ、LTR/RTL、モバイル/デスクトップの組み合わせで確認する |
| Service Worker更新後も古いWorkerが残る | キャッシュ名を更新し、更新・再読み込み手順を検証する |
| 設定バリデーション強化で既存JSONCが拒否される | 全設定ファイルを先に走査し、移行が必要な値を洗い出す |
| `any` の一括置換で差分が肥大化する | パッケージ単位で型を導入し、公開型から順に狭める |
| テスト導入がビルド時間を増やす | 単体テストと重いビルドスモークテストを分ける |
