# Awesomeリスト群の取得・定本化・翻訳パイロット計画

- 作成日: 2026-08-20
- 対象起点: [`sindresorhus/awesome`](https://github.com/sindresorhus/awesome)
- サイトID: `awesome`（Awesome系リストを一つのアプリへ集約する）
- 初回版ID: `v2026-08-20`
- 定本言語: 英語
- 最初の翻訳先: 日本語
- ステータス: フェーズ0〜6完了、フェーズ7着手中。固定ライセンス本文を確認できた365ページを単一`apps/awesome`へ統合し、旧6分割アプリは削除済み。人手による内容レビューは最終フェーズ10へ延期
- 根拠: `docs/spec/PROJECT_PRINCIPLES.md`、`docs/guides/UPSTREAM_DOCUMENT_IMPORT_AND_TRANSLATION_GUIDE.md`

## 0. 計画レビューの結論

本計画は、対象範囲、法的条件、正本と翻訳の分離、品質ゲート、公開後の更新方針までを一貫して扱っており、大規模パイロットの基本計画として妥当である。一方、初版には実作業時に担当者が判断しなければならない箇所が残っていたため、2026-08-20のレビューで次を拘束的な実行規則として補った。

- 探索は幅優先で行い、25取得元ごと、および深さが一段増えるごとにチェックポイントを保存する。
- 作業日のAsia/Tokyoの日付を版IDに使い、取得日時はUTC、内容はコミットSHAとハッシュで固定する。
- 取得、判定、生成、レビューの状態を機械可読ファイルへ保存し、中断後に完了済みバッチから再開する。
- 外部リポジトリのコードやスクリプトは実行せず、必要なMarkdownとライセンス資料だけを取得する。
- ライセンス、除外、ページ分割の判断は、判断者、根拠、日時を記録し、暗黙の判断を残さない。
- 全件処理の前に10件以下の縦断パイロットを完了し、誤探索、誤除外、帰属、性能の各ゲートを通す。
- 通常ページは一リスト一ページとし、既定の分割候補基準を超えたページだけを実測後に分割する。
- 翻訳と公開の全体完了条件を分け、部分的なPreviewは許可するが、全件翻訳済みと誤認させるProduction公開はしない。
- 英語定本の全文照合、除外結果の内容確認、日本語の技術・表現確認は途中工程へ分散せず、生成、翻訳、機械検査、Preview検証がすべて完了した後の最終フェーズでまとめて行う。ライセンス、適格性、公開可否の判断は安全ゲートであり、この延期対象には含めない。
- Awesome系の公開単位は`apps/awesome`一つとする。上位分類はアプリ分割ではなく、単一アプリ内のコンテンツ境界、URL、サイドバー、検索索引、必要に応じたビルド区画として扱う。
- 372ページを通常のAstro content collectionへ一括投入した検証では、`_astro_data-layer-content.*.js`が32,260 KiBとなり、デプロイ上限25,600 KiBを超えた。このため、全件を同じcollectionへ戻すだけの統合は禁止し、軽量ルート目録と遅延コンテンツ読込を先に実証する。

この計画内で「記録する」とした判断は、指定されたJSONまたはMarkdown成果物へ書かれて初めて完了とみなす。口頭判断や作業ログだけでは次工程へ進めない。

## 1. 目的

`sindresorhus/awesome`を入口として、そこから参照される独立したAwesomeリスト群を再現可能なスナップショットとして取得し、広告・寄付案内などリスト本文と無関係な要素を除いた英語定本を作成する。その後、英語定本と対応する日本語翻訳を一ページずつ作成・照合し、libxで検証・公開できる状態にする。

三例目のパイロットとして、GLFWとLuaでは扱わなかった次の条件を検証する。

- 数百以上の独立したGitHubプロジェクトを一つの文書集合として固定し、一つの`awesome`サイトから公開する。
- 単一リリース番号を持たず、各取得元が別々の時点で更新される文書を版管理する。
- リストから別のリストへの参照をグラフとして探索し、循環と重複を排除する。
- 取得元ごとに異なるライセンス、著作者、既定ブランチ、READMEパスを管理する。
- 広告・スポンサー・寄付案内を除外しつつ、主題としての商用サービスや広告関連リストを誤って消さない。
- 大量のページ、リンク、検索索引、翻訳状態を、手書きの進捗数に依存せず管理する。
- 上流更新時に変更された定本だけを再翻訳・再レビューできるようにする。

本計画では、取得と翻訳を急いで同時進行しない。最初に対象集合、ライセンス、ページ粒度、成果物予算を固定し、英語定本の品質ゲートを通過した範囲から日本語翻訳へ進む。

## 2. 調査時点で確認した前提

2026-08-20の計画調査時点で、起点リポジトリには次の性質がある。

- `readme.md`はPlatforms、Programming Languages、Securityなど多数の分類から、独立したリストへリンクする索引である。
- 起点READMEのリスト本文より前には、作者のアプリ、支援案内、スポンサー紹介など、今回の定本対象としない要素がある。
- 公式の[Awesome manifesto](https://github.com/sindresorhus/awesome/blob/main/awesome.md)は、単なる収集ではなく推薦できる項目のキュレーションであること、主題を明確にすること、項目の理由を説明すること、目次とカテゴリを持つことを求めている。
- manifestoは、ライセンス未指定の場合は複製・配布・派生物作成が原則として許可されないことを明記し、CC0を推奨している。
- 起点リポジトリ自体は[CC0 1.0 Universal](https://github.com/sindresorhus/awesome/blob/main/license)である。
- 起点のライセンスはリンク先の独立リポジトリへ自動的には適用されない。各取得元のライセンスを個別に確認する必要がある。

したがって、「起点から到達できる」という事実だけで定本へ複製してはならない。対象リストとしての適格性と、翻訳・改変・再配布の法的条件は別々に判定する。

## 3. 採用する版管理方式

### 3.1 URL用版ID

初回スナップショットの版IDは、固定済みの`v2026-08-20`とする。

```text
apps/awesome/src/awesome-content/v2026-08-20/en/
apps/awesome/src/awesome-content/v2026-08-20/ja/
```

この形式を選ぶ理由は次のとおりである。

- Awesomeリスト群全体には共通のリリース番号がない。
- libxの現行版探索は`v`で始まり数字をハイフンで連結したIDを扱える。
- 人が取得時点を理解でき、時系列で並べられる。
- 同じ日の再取得が必要な場合は`v2026-08-20-2`のように連番を付けられる。

版IDの日付だけを再現性の証拠にはしない。日付は表示・URL用識別子であり、内容を固定する正本は次項のロックファイルとする。

初回版IDは起点コミットを固定したAsia/Tokyoの日付ですでに確定しているため、統合日や公開日に合わせて変更しない。同じ探索を日付をまたいで継続しても版IDは変更しない。`retrievedAt`はUTCのISO 8601で記録する。

### 3.2 スナップショットの正本

すべての取得元を機械可読な`SOURCES.lock.json`へ固定する。各レコードは最低限、次を持つ。

```json
{
  "sourceId": "github-owner-repository-path",
  "parentSourceId": "sindresorhus-awesome-readme",
  "discoveryDepth": 1,
  "repository": "owner/repository",
  "defaultBranch": "main",
  "commitSha": "40-character SHA",
  "documentPath": "README.md",
  "documentSha256": "SHA-256",
  "licenseSpdx": "CC0-1.0",
  "licensePath": "license",
  "licenseSha256": "SHA-256",
  "retrievedAt": "ISO 8601",
  "status": "included",
  "decisionId": "license-decision-id",
  "normalizerVersion": "git commit or package version"
}
```

ロック完了後、ファイル全体を正規化してSHA-256を計算し、`SOURCE_MANIFEST.md`へスナップショット識別子として記録する。版ID、ロックファイルハッシュ、起点コミットSHAの三つが一致した集合だけを同じ版として扱う。

スナップショットは公開後に上書きしない。次回取得は新しい日付の版を追加する。

ロック中に上流HEADが変わっても、すでに記録したコミットを追従更新しない。各取得元は、発見時に解決したコミットを固定するため、全リポジトリが同一秒の状態であることは要求しない。代わりに、起点コミット、各取得元の固定コミット、発見順、取得日時を一つのロックファイルに閉じた状態を「一スナップショット」と定義する。

## 4. 対象範囲と探索停止規則

### 4.1 必ず棚卸しする対象

1. 起点リポジトリの固定コミットにある`readme.md`のリスト本文。
2. 起点READMEのカテゴリ配下で、Awesomeリストとして登録されているリンク先。
3. 直接対象となったリストが、`Related Awesome Lists`など明確なリスト間ナビゲーションから参照する下位リスト。
4. 同じリポジトリ内でリスト本文の一部として分割されているMarkdown文書。
5. 各取得元のライセンス、著作者、README、目次、寄与規約など、採否と変換に必要な資料。

### 4.2 リスト間リンクの判定

リンク先を再帰探索の対象にするのは、次の複数条件から「独立したキュレーションリスト」と判定できる場合に限る。

- 起点または取得済みリストの、リスト間参照を目的とする領域からリンクされている。
- 主文書がMarkdownまたは変換可能な構造化文書である。
- 主題の説明、複数の項目、カテゴリまたは目次を持つ。
- Awesome badge、`awesome-list`トピック、リポジトリ名などの補助的根拠がある。
- リンク先が個別製品、記事、書籍、ツール、企業サイトではない。

名称に`awesome`を含むだけでは採用しない。逆に、起点から直接登録されているリストは、リポジトリ名に`awesome`がなくても候補に含める。

### 4.3 再帰探索

- ノードの一意性は最終的な`repository + documentPath`で判定する。
- リダイレクト、リポジトリ移転、既定ブランチ変更を正規URLへ解決する。
- 訪問済みノードを再取得せず、親子関係だけを辺として追加する。
- 循環参照は正常なグラフとして記録し、エラーにしない。
- 通常のリスト項目が指す製品、ライブラリ、記事、データセットなどは取得せず、外部リンクとして保持する。
- 深さごとの新規候補数、累計文書数、ライセンス未確定数をレポートする。
- 候補数が見積もりを大幅に超えた場合も無言で打ち切らず、対象判定の誤りと単一アプリ内のコンテンツ区画・索引分割の必要性を確認する。

探索は幅優先で行い、URL発見順を安定ソートしてから処理する。一バッチは最大25取得元とし、各バッチ後に`DISCOVERY_STATE.json`、候補一覧、辺一覧、失敗一覧を原子的に更新する。深さが一段増えるごとに規模レポートを確認し、次のいずれかなら管理者レビューまで探索を停止する。

- 直前の深さより新規候補数が2倍を超えた。
- 累計候補数が1,000件、または想定公開ページ数が2,000ページを超えた。
- GitHub以外、HTMLのみ、巨大生成物など、既存の取得方式で扱えない候補が全候補の10%を超えた。
- リスト間リンクの誤判定率が、レビュー標本で2%を超えた。

安全停止は対象の打ち切りを意味しない。判定規則または単一アプリ内のコンテンツ区画方針を記録してから同じ状態ファイルを使って再開する。候補キューが空になり、未分類ノードが0件となった時点を探索完了とする。

探索は「リストからリストへの辺」だけで閉包を求める。すべての外部リンクを辿るWebクローラーにはしない。

### 4.4 対象外

- 個々のリスト項目が指すソフトウェア、記事、書籍、動画、企業サイトの本文。
- Issue、Pull Request、Discussion、SNS投稿。
- GitHubがページへ付加するナビゲーション、スター数、フォーク数などのUI。
- リスト本文と無関係な広告、スポンサー紹介、寄付・資金援助の依頼、作者自身の製品宣伝。
- README内のバッジ画像、CI状態、スター履歴グラフなど、定本の理解に不要な装飾。
- 翻訳・改変・再配布の根拠を確認できない文書。

対象外でも、発見した事実と除外理由はインベントリへ残す。

### 4.5 取得の安全性と信頼性

- 外部リポジトリをビルドせず、package script、GitHub Actions、サブモジュール、実行ファイルを実行しない。
- 原則としてGitHub APIと固定コミットのRaw URLから、対象Markdown、ライセンス、必要最小限の画像メタデータだけを取得する。
- `javascript:`、`data:`、`file:`など公開文書に不要なURLスキーム、埋め込みスクリプト、イベント属性を拒否する。
- シンボリックリンク、Git LFSポインタ、サイズ上限超過ファイルは自動展開せず`review`へ送る。
- 1文書の取得上限は既定で5 MiBとする。超過時は分割文書の有無を調査し、管理者承認なしに上限を引き上げない。
- GitHub APIの認証情報を使う場合は環境変数から読み、URL、ログ、ロックファイル、Git管理ファイルへ保存しない。
- APIのレート制限値とリセット時刻を記録し、指数バックオフ付きで再試行する。403、429、5xxを無限再試行しない。
- 取得応答はコミットSHAとハッシュをキーに一時キャッシュし、同じ入力を再取得しない。
- 削除、非公開化、DMCA、取得不能は失敗理由を記録し、推測したミラーへ自動切替しない。

## 5. 法的条件と帰属

### 5.1 リポジトリ単位の判定

各候補を本文変換前に次へ分類する。

| 状態 | 意味 | 処理 |
| --- | --- | --- |
| `included` | 翻訳・改変・再配布条件を満たす | 定本化へ進む |
| `metadata-only` | 索引上の存在は記録できるが本文を複製できない | 起点索引から原文へリンクするだけにする |
| `pending-license-review` | ライセンスや適用範囲が不明 | 本文取得後の公開処理を停止する |
| `excluded` | 条件不適合、対象外、取得不能 | 理由を記録して除外する |

ライセンスファイルがない場合、GitHubの表示やREADMEの曖昧な文言から許可を推定しない。ライセンスがあっても、文書・データへ適用されるか、翻訳と改変が許されるか、表示・通知・継承条件が何かを確認する。

判定結果は`LICENSE_DECISIONS.json`へ保存し、`decisionId`、対象コミット、検出したライセンス、文書への適用根拠、許可される処理、必要な表示、判断者、判断日時、備考を持たせる。自動検出したSPDX値だけで`included`へ昇格させず、初出のライセンス種別は管理者が一度承認する。同一条件の後続取得元だけ、承認済みルールを再利用できる。

法的条件に合理的な疑義がある場合は、公開を優先せず`pending-license-review`に留める。本計画は法的助言の代替ではないため、管理者が判断できない条件は専門家確認または`metadata-only`を選ぶ。

### 5.2 出典レジストリ

現行の`project.config.jsonc`は少数の`licensing.sources`を直接列挙する設計である。数百以上の取得元を手作業で同ファイルへ書くと、設定が巨大化し、ロックファイルと二重管理になる。

大量投入前に、次の方式を優先して小規模実証する。

1. `project.config.jsonc`にはサイト既定とレジストリ参照だけを持たせる。
2. `SOURCES.lock.json`から、検証済みの出典レジストリを機械生成する。
3. 各英語ページと翻訳ページは安定した`licenseSource` IDだけを参照する。
4. 文書最下部の出典パネルは、そのIDから取得元、固定コミット、著作者、ライセンス、原文URLを表示する。
5. 未知ID、欠落ライセンス、翻訳ページとのID不一致をビルド前に失敗させる。

この変更は共有設定スキーマと帰属UIへ影響するため、実装前にADRでレジストリ形式、配置場所、公開API、移行方法を承認する。ロックファイルを手書き設定の代用品として二重入力しない。

## 6. 広告・寄付案内などの除外方針

### 6.1 除外するもの

- リストの主題と関係のないアプリ・サービスの宣伝。
- スポンサー名、スポンサー広告、広告枠。
- GitHub Sponsors、Patreon、Open Collectiveなどへの支援依頼。
- 作者個人のSNS、ニュースレター、採用、商品販売への誘導。
- リスト本文ではないバッジ列やキャンペーン画像。

### 6.2 誤除外を避ける規則

単語だけで削除しない。`Advertising`、`Open Source Supporters`、`Software Patreons`、`Web Monetization`などは、リストの主題または正規項目である可能性がある。

除外判定は次を組み合わせる。

- 文書内の位置がタイトル前後の定型ブロックか。
- 目次や主要カテゴリから参照されるか。
- リストの説明した主題に含まれるか。
- 同じ形式の項目が複数並ぶキュレーション本文か。
- 支援・宣伝を目的とする見出しまたは画像リンクか。

自動分類は`include`、`exclude`、`review`の三値を返す。曖昧なものを自動削除しない。

### 6.3 除外記録

`EXCLUSIONS.json`に次を保存する。

- 出典IDと固定コミット。
- 元文書内の見出しまたは行範囲。
- 除外断片のSHA-256。
- 分類理由。
- 自動判定か手動承認か。
- 再取得時に同じ断片かどうか。

定本から除外した内容を完全に忘れず、上流更新時に除外規則がリスト本文を侵食していないか再検証できるようにする。

## 7. 作業領域と記録

Git管理する記録は次とする。

```text
docs/notes/document-import/awesome/
├── README.md
├── SOURCE_MANIFEST.md
├── SOURCES.lock.json
├── DISCOVERY_STATE.json
├── LICENSE_DECISIONS.json
├── CONTENT_MAP.md
├── CONTENT_MAP.json
├── CONTENT_PARTITIONS.json
├── URL_MIGRATIONS.json
├── EXCLUSIONS.json
├── BATCH_STATUS.json
├── TRANSLATION_GUIDE.md
├── MANUAL_TRANSLATION_PLAN.md
├── WORK_LOG.md
├── REVIEW_CHECKLIST.md
├── SINGLE_APP_ARCHITECTURE.md
└── RETROSPECTIVE.md
```

既存の`SITE_SHARDS.json`は分割検証時点の移行入力として保持するが、統合後の配置正本にはしない。`CONTENT_PARTITIONS.json`はカテゴリから単一アプリ内のURL・本文・索引区画への割当、`URL_MIGRATIONS.json`は旧検証URLから正規URLへの対応、`SINGLE_APP_ARCHITECTURE.md`は方式選定とasset実測を記録する。

取得物と中間生成物はGit管理しない。

```text
.tmp/document-import/awesome/
├── 01-source/
│   ├── repositories/
│   └── responses/
├── 02-inventory/
├── 03-normalized/
├── 04-translation/
├── 05-reports/
└── 06-preview/
```

ただし、`.tmp`は再現性を支える保管場所ではない。`included`と確定した取得元の変換前Markdownとライセンス資料は、スナップショット単位の決定的な圧縮アーカイブへまとめ、アーカイブのSHA-256、保存場所、復元手順、保持期間を`SOURCE_MANIFEST.md`へ記録する。圧縮後25 MiB以下ならGit管理を第一候補とし、超える場合はデプロイ対象外の永続ストレージをADRで選ぶ。`metadata-only`、`pending-license-review`、`excluded`の本文は永続アーカイブへ含めず、一時取得物を判定後に破棄する。

公開対象は検証済み成果物だけに限定する。

```text
apps/awesome/
├── src/awesome-content/v2026-08-20/
│   ├── en/<category-id>/
│   └── ja/<category-id>/
├── src/generated/
│   ├── awesome-routes.json
│   └── awesome-sources/
├── public/sidebar/
└── public/search/awesome/
```

`src/awesome-content`という名前は実装スパイク時の既定案であり、重要なのは全ページを現在の単一`docs` collectionへ登録しないことである。公開Markdown、軽量ルート目録、出典レジストリ、サイドバー、検索索引は、すべて`CONTENT_MAP.json`と`SOURCES.lock.json`から決定的に生成する。`apps/awesome-*`を正本にせず、統合完了後の公開コンテンツの正本は`apps/awesome`だけとする。

進捗の正本は`SOURCES.lock.json`、英語・日本語の実ファイル集合、検査結果とする。READMEや計画書へ完了数を重複して手入力しない。

`BATCH_STATUS.json`は各バッチの`discovered`、`locked`、`normalized`、`canonical-validated`、`translated`、`translation-validated`、`human-reviewed`状態と、入力ハッシュ、出力ハッシュ、検査結果を持つ。フェーズ9までは機械検査済みを表す`*-validated`だけを更新し、`human-reviewed`は最終フェーズ10でのみ更新する。後工程へ進めるのは直前状態が完了したバッチだけとする。失敗したバッチは一時出力を破棄でき、確定済みバッチを再生成しない。

## 8. ページ構造と粒度

### 8.1 初期構造案

起点READMEの上位分類をlibxのカテゴリへ対応させる。例:

```text
01-overview/
02-platforms/
03-programming-languages/
04-front-end-development/
05-back-end-development/
...
```

正式なカテゴリ数、順序、英日表示名は、固定した起点READMEのインベントリから生成し、手作業で別管理しない。

### 8.2 ページ粒度

- 起点索引は、入口ページと上位分類ページへ分割する。
- 通常のリンク先リストは、原則として一つの主文書を一つのlibxページにする。
- 非常に大きいリストだけ、上流のH2カテゴリ単位で分割する。
- 一つの項目を一ページにはしない。
- 同じリストが複数分類から参照される場合、本文ページを複製せず一つの正規ページへ集約する。
- 分割後も、上流見出し、項目順、リンク、説明の対応を追跡できるページマップを生成する。

分割しきい値は取得後に、原文バイト数、項目数、見出し数、表示時間、翻訳単位、検索索引、生成ファイル数を測って決める。推測だけで全リストを細分化しない。

迷った場合の既定値として、正規化後本文が400 KiB、リスト項目が1,500件、H2が80件のいずれかを超えたページを「分割候補」とする。候補は直ちに分割せず、未分割ページの実ブラウザ測定と翻訳量・最終レビュー対象量の機械集計を確認する。分割する場合は上流H2境界だけを使い、採否と測定結果を`CONTENT_MAP.md`へ記録する。

### 8.3 安定URL

- 正規URLはすべて`/docs/awesome/<version>/<lang>/<category-id>/<page-id>`配下とし、上位分類ごとにproject slugを変えない。
- ページIDは初回採用時に固定し、リポジトリ名変更だけで変更しない。
- 同名リポジトリは所有者を含む安定IDで区別する。
- 上流のカテゴリ移動は、可能な限り既存ページURLを維持し、索引上の所属だけを更新する。
- 検証用の`/docs/awesome-web/`などが共有または公開されていた場合は、`SITE_SHARDS.json`と`CONTENT_MAP.json`から旧URL・新URL対応表を生成し、統合先へリダイレクトする。未公開URLなら、対応表だけを移行記録として残す。

### 8.4 単一アプリ内のコンテンツ境界

単一アプリ化の主案は、全本文を一つのAstro content collectionへ格納せず、ビルド時に次の二層へ分ける方式とする。

1. 全ページ共通の軽量目録: URL、タイトル、版、言語、カテゴリ、ページID、出典ID、本文モジュールキーだけを持つ。`getStaticPaths()`、サイドバー、前後移動、進捗集計はこの目録を読む。
2. ページ本文: Markdownをページ単位の遅延`import()`として解決し、対象ページの描画時だけロードする。本文モジュールが一つの巨大なdata-layer assetへ再結合されないことをビルド成果物で検査する。

Awesome専用ルートは、既存の`CollectionEntry<'docs'>`へ依存する汎用ルートをそのまま複製せず、軽量目録のメタデータと遅延ロードした`Content`、見出しを`DocLayout`へ渡す。frontmatterは生成時に既存`docsSchema`と同等以上の規則で検証し、未知フィールド、重複URL、欠落出典ID、目録と本文の不一致をビルド前に失敗させる。

出典レジストリ、サイドバー、検索索引も上位分類単位のJSONへ分割し、入口にはカテゴリ名、件数、索引参照だけを持たせる。分類はナビゲーションと成果物の境界であり、別アプリや別project slugにはしない。

最初に入口、最大ページ、各分類から一ページずつを使う統合スパイクを作り、次を確認する。

- `apps/awesome`だけで全正規URLを生成できる。
- 最大生成ファイルが警告値20 MiB未満で、デプロイ上限25,600 KiBを超えない。
- 本文の合計増加に比例して単一JS assetが増大しない。
- サイドバー、検索、前後移動、言語切替、版切替、出典表示が分類境界を越えて動作する。

遅延import方式でも巨大assetが残る場合の代替案は、`apps/awesome`パッケージ内でカテゴリ別にAstroビルドし、最後に一つの`dist/docs/awesome/`へ原子的に統合する方式とする。各区画は同じ設定、レイアウト、URL目録を共有し、統合処理はHTML・asset・サイドバー・検索索引のパス衝突と欠落を検出する。この代替案でも`apps/awesome-*`は作らない。主案・代替案の採否と実測値はADRおよび`SITE_BUDGET_DECISION.md`へ記録する。

## 9. インポータと機械検査

### 9.1 コマンド境界

Awesome用処理は一つの巨大スクリプトにせず、少なくとも次へ分ける。

```text
discover-awesome-sources   対象グラフの発見と分類
lock-awesome-sources       コミット、文書、ライセンスの固定
import-awesome-lists       Markdown正規化と一時出力
validate-awesome-canonical 定本の完全性検査
validate-awesome-translation 英日構造比較
report-awesome-progress    実ファイルから進捗・規模を報告
plan-awesome-partitions    カテゴリ、URL、内部コンテンツ区画の決定的な割当
publish-awesome            単一apps/awesomeへの目録・本文・索引の安全な生成
validate-awesome-assets    巨大単一asset、URL重複、区画欠落の検査
```

各書き込みコマンドは`--dry-run`、`--check`、明示的な入力・出力を持ち、安全出力基盤を使う。

実装場所は`scripts/importers/awesome/`、公開コマンドはルート`package.json`の`awesome:*`スクリプトへ統一する。各コマンドは、同一入力で二度実行したときに二度目の確定差分が0となることを必須とする。出力は一時ディレクトリで完全検証してからディレクトリ単位で置換し、処理中断時に既存成果物を部分更新しない。

### 9.2 定本変換

- HTMLを取得せず、可能な限り固定コミットのRaw Markdownを入力にする。
- タイトル、主題説明、目次、カテゴリ、リスト項目を保持する。
- 広告等の除外後に空見出しを残さない。
- GitHub相対URLを、固定コミットまたは適切な外部URLへ解決する。
- 通常のリソースURLは無断で別サイトへ置換しない。
- Markdownのリンクラベル、説明、強調、インラインコードを保持する。
- GitHub専用HTML、画像、details、表、脚注はCommonMark／GFMで意味を保てる形式へ正規化する。
- 原文を要約、評価、補筆しない。

### 9.3 必須検査

- 発見候補が`included`、`metadata-only`、`pending-license-review`、`excluded`のいずれかに分類されている。
- すべての`included`に固定コミット、文書ハッシュ、ライセンス証拠がある。
- 同じ取得元を重複ページ化していない。
- 定本の見出し、項目、URL、コード、画像代替テキストの対応を説明できる。
- 除外断片が`EXCLUSIONS.json`と一致する。
- 未処理HTML、壊れたMarkdown、相対GitHub URL、未知の出典IDがない。
- 内部リンク、フラグメント、外部リンクの形式が有効である。
- 再実行時に差分がない。
- 失敗時に既存定本を変更しない。

### 9.4 最終人手内容レビューの標本規則

機械検査だけでは、項目説明の欠落や広告の誤判定を完全には証明できないため、次を最低基準とする。この標本レビューは途中フェーズでは実施せず、全コンテンツの生成、翻訳、機械検査、Preview検証が完了した後のフェーズ10で一括実施する。

- `exclude`と`review`に分類された断片は100%人手確認する。
- 新しいMarkdown構造、ライセンス種別、除外パターンが初めて現れたページは100%確認する。
- 残りは25取得元の各バッチから最低3ページ、または10%の多い方を原文と全文照合する。
- 標本で項目欠落、URL変更、順序変更、誤除外が一件でも見つかった場合、そのバッチを完了にせず、規則修正後に全件を再検査する。
- 外部URLの到達不能は、URL文字列が原文と一致していれば定本欠陥と混同しない。恒久的404、リダイレクト、レート制限、検査不能を別々に報告する。

標本の選定方法、対象ページ、確認者、結果は`REVIEW_CHECKLIST.md`へ記録する。

### フェーズ0: 計画・判定規則・法務ゲートの固定

1. 本計画の対象定義と探索停止規則を承認する。
2. 起点リポジトリの取得日時、コミット、README、ライセンスを固定する。
3. ライセンス分類、広告等の除外基準、曖昧時の中断規則を確定する。
4. 出典レジストリ拡張のADRを作成・承認する。

完了条件:

- 起点だけを試験入力にして、対象・除外・ライセンス判定を再現できる。
- ライセンス未確認の本文を`apps/`へ置かない仕組みがある。

### フェーズ1: 対象グラフの発見と規模測定

1. 固定した起点READMEから直接リスト候補を抽出する。
2. 候補URLを正規化し、GitHubリポジトリ、文書パス、既定ブランチを解決する。
3. 直接候補から構造の異なる標本を選び、そのリスト間リンクを一段だけ抽出して分岐数と誤判定率を測る。
4. ライセンス、アーカイブ状態、取得可否、文書形式を予備分類する。
5. 直接候補数、標本の分岐数、リポジトリ数、原文容量、リンク数、想定ページ数を報告する。

完了条件:

- 起点からの直接候補が機械可読インベントリにあり、標本から再帰探索の規模を推定できる。
- 通常のリソースリンクを誤ってクロールしていない。
- 想定英語ページ数、日本語追加後のページ数、ビルド・ファイル数を試算できる。

この段階では再帰探索を完了させない。判定器を縦断パイロットで検証する前に、誤った規則でグラフ全体を取得しないためである。

### フェーズ2: 小規模縦断パイロット

起点と、構造・規模・ライセンスが異なる代表リストを合計10取得元以下で選ぶ。

代表例に含める条件:

- CC0など文書向けライセンス。
- MIT等、文書適用範囲の確認が必要な例。
- ライセンス未指定で`metadata-only`となる例。
- 広告・寄付案内を含む例。
- 大きな単一README、分割Markdown、相対リンク、画像、表を含む例。

この集合で、取得、ロック、除外、定本化、出典表示、日本語一ページ、部分翻訳ビルドまで縦断する。

完了条件:

- 出典レジストリと帰属UIが複数ライセンスを正しく表示する。
- 自動除外が正規のリスト項目を消していない。
- 翻訳0件、部分翻訳、代表ページ翻訳済みの各状態でビルドできる。
- 一ページあたりの取得・判定・整形・翻訳量と、最終人手レビュー対象量を機械的に見積もれる。

### フェーズ3: 単一アプリ構造と成果物予算の確定

1. 既存の`apps/awesome`を統合先とし、`apps/awesome-*`の内容、設定、URL、出典を機械的に棚卸しする。
2. `SITE_SHARDS.json`を別サイト配置表として使うのをやめ、同じカテゴリ割当を単一アプリ内のURL・本文・索引区画へ変換する`CONTENT_PARTITIONS.json`（名称はADRで確定）を生成する。
3. 入口、最大ページ、各分類から一ページずつを使い、軽量ルート目録とページ単位の遅延import方式を実装する。
4. `v2026-08-20`、英語定本、日本語対応、カテゴリ表示名、単一出典レジストリ、分類横断ナビゲーションを設定する。
5. スパイクに全372英語ページを投入し、最大asset、検索索引サイズ、ビルド時間、配信ファイル数、メモリ使用量を測る。
6. 主案がasset上限を満たさない場合だけ、`apps/awesome`内のカテゴリ別ビルドと衝突検査付き統合を実証する。
7. ページ粒度のしきい値を実測から確定する。ビルド内部区画を理由に、同じリスト本文を複製・細分化しない。
8. 入口、中央値付近、最大候補の三ページについて、初回表示とキャッシュ済み表示を各5回測定し中央値を記録する。
9. 同一内容を最小限の静的HTMLで表示した基準ページ、および既存のGLFWかLuaの同程度ページと相対比較する。
10. 変換前入力アーカイブの圧縮後容量を測り、Git管理か永続ストレージかを確定する。
11. 統合ビルドとURL移行表の検証後に限り、分割アプリを削除対象として列挙する。削除自体は差分確認と管理者承認後に行う。

成果物予算は現行のデプロイ検査に従い、20,000ファイルを実効上限、12,000で警告、18,000で停止とする。現在の統合成果物を差し引いた余裕も評価する。

完了条件:

- `apps/awesome`だけが公開プロジェクトとなり、固定ライセンス根拠を持つ`included`全英語ページが`/docs/awesome/`配下の一意なURLへ対応している。
- 最大生成ファイルが20 MiB未満で、デプロイ上限25,600 KiBに余裕を持って合格する。例外的に20 MiB以上を採用する場合は増加予測と根拠を管理者が記録する。
- 全文検索索引、サイドバー、出典レジストリが過大な単一JSONにならず、上位分類単位でロードできる。
- `pnpm build:selective --projects=awesome`だけで完全なAwesome成果物を生成できる。
- 主案または代替案の再実行で差分がなく、区画ごとのページ漏れ、重複URL、asset衝突が0件である。
- 旧分割URLの扱いと、`apps/awesome-*`を安全に廃止できる条件が記録されている。
- 測定端末、ブラウザ、ネットワーク、キャッシュ条件、比較対象、中央値が記録され、最大候補ページに著しい回帰がない。
- `.tmp`を削除しても、固定入力アーカイブと記録だけから同じ英語定本を再生成できる保管方針がある。

ここで著しい回帰とは、同じ測定条件で既存libx比較ページより初回表示中央値が20%を超えて遅い、または同一内容の最小静的HTMLより2倍を超えて遅い状態を指す。該当した場合は、原因を解消するか、内容量による不可避な差と採用理由を管理者が記録するまで完了にしない。

### フェーズ4: 全取得元の固定と法務レビュー

1. パイロットで承認した判定器を使い、幅優先探索を候補キューが空になるまで再開する。
2. 各発見バッチで既定ブランチHEADを一度だけ解決し、そのコミットを固定する。
3. コミットSHA、文書パス、文書ハッシュ、ライセンスをロックする。
4. ライセンス条件、著作者、通知、原文URLをレビューする。
5. `pending-license-review`を0件にする。解決できないものは`metadata-only`または`excluded`へ確定する。
6. `SOURCES.lock.json`を閉じ、全体ハッシュを記録する。

完了条件:

- 探索キューが空で、全ノードと辺が記録され、安全停止の未解決事項がない。
- 公開候補の全取得元に再現可能な固定情報と法的根拠がある。
- 取得作業中の上流更新が同じスナップショットへ混入していない。

### フェーズ5: 英語定本の一括生成と機械検査

1. ロック済み原文を一時領域へ取得する。
2. 除外候補を三値分類し、公開可否を確定できない曖昧項目だけを安全判断として手動判定する。
3. ページマップに従いMarkdownを生成する。
4. 構造、リンク、出典、除外、再現性を検査する。
5. 小さなバッチごとに原文と定本の構造・URL・件数・ハッシュを機械照合し、合格したバッチだけ`canonical-validated`へ進める。

完了条件:

- `included`の全対象が定本ページまたは定本内の明示項目へ対応する。
- `metadata-only`と`excluded`の本文が混入していない。
- 英語定本の全ページが個別・選択的ビルドできる。
- 外部リンクは取得時点のURLとして追跡され、失敗とリダイレクトが報告される。

### フェーズ6: 日本語翻訳準備

#### 翻訳支援モデルの利用方針

翻訳APIの継続利用には厳しいレート・利用制限があり、低精度なローカルLLMでは本計画の品質を安定して満たせない。この禁止は利用形態と品質保証に基づくものであり、LLM一般を禁止するものではない。

| 区分 | 対象 | 方針と理由 |
| --- | --- | --- |
| 使用しない | Google翻訳、DeepLなどの翻訳API | API制限が厳しく、全365ページを継続して翻訳する運用を安定して維持できない。 |
| 使用しない | 翻訳品質を担保できないローカルLLM | 技術文書・Markdown構造を含む翻訳の品質を安定して保証できない。 |
| 使用しない | 入出力を無検査で量産する一括翻訳スクリプト | ページごとの構造・保護対象・内容上の問題を検出できない。 |
| 使用できる | Codex、Claude、Geminiなどの高性能LLM | 継続的に翻訳でき、十分な翻訳品質を期待できるため禁止対象ではない。担当者が一ページずつ確認し、保護規則と機械検査に通す補助として用いる。 |

高性能LLMを使う場合も、最大10ページのバッチ、ページごとの構造検査、未解決事項の最終レビューキュー記録を必須とし、フェーズ10の人手内容レビューを省略しない。

1. 実際の定本から用語、カテゴリ名、定型説明を抽出する。
2. プロジェクト名、製品名、URL、コード、ライセンス名、リポジトリ名の保護規則を定める。
3. 一ページの完了条件とレビュー記録を`MANUAL_TRANSLATION_PLAN.md`へ確定する。
4. 起点入口、短いリスト、大きいリストを一件ずつ試訳し、翻訳手順と保護規則が実行可能か確認する。この時点では内容レビュー済みと扱わない。
5. リンク集合・項目数・順序の英日比較を実装する。

完了条件:

- 用語と文体が代表三種で成立する。
- リスト項目を追加・削除・並べ替えずに翻訳できる。
- 翻訳API、品質を担保できないローカルLLM、無検査の一括生成スクリプトを使用せず、Codex・Claude・Geminiなどの高性能LLMを使う場合にも一ページ単位の確認・構造検査を実施する手順が再現できる。

### フェーズ7: 日本語逐次翻訳

翻訳は次の順で進める。

1. 起点の入口、概要、上位カテゴリ索引。
2. 短く中心性の高い代表リスト。
3. Platforms、Programming Languagesなど、用語を安定させやすい技術カテゴリ。
4. 専門性の高いComputer Science、Health and Social Scienceなどのカテゴリ。
5. 大規模リスト、複雑な表・画像・分割文書を持つ例。
6. 下位リストと例外ページ。

各ページは一ページずつ翻訳し、構造、リンク集合、項目数、順序、保護対象を機械検査して`translation-validated`まで進める。原文との意味照合と日本語表現の確認はフェーズ10まで行わない。未完成の初稿は`.tmp/document-import/awesome/04-translation/`へ置き、`apps/awesome`へ混入させない。

翻訳は最大10ページを一バッチとする。各バッチで用語集への追加と構造差分を閉じてから次へ進む。判断が必要な技術・分野用語は推測で確定せず、最終レビュー課題として記録する。

### フェーズ8: 全体機械検査

1. 英日ファイル集合、出典ID、見出し、項目数、リンクURL、順序、コードを比較する。
2. 未翻訳、英語混入、未知の出典ID、重複URL、欠落ページを機械検出する。
3. 広告除外IDと除外箇所が英日で一致することを機械検査する。
4. 個別、選択的、統合ビルドとデプロイ成果物予算を検査する。
5. 人手判断が必要な箇所をカテゴリ、ページ、該当位置、理由つきで最終レビューキューへ固定する。

### フェーズ9: 表示・Preview・運用準備

1. 入口、各上位カテゴリ、短いページ、最大ページ、分割ページ、metadata-only項目、404を確認する。
2. デスクトップ、モバイル、キーボード、RTL影響、長いURL、折返し、目次、サイドバー、前後移動を確認する。
3. 検索索引の生成時間、容量、初回検索応答を確認する。
4. 個別、選択的、統合ビルドとデプロイ成果物予算に合格させる。
5. Previewで主要URL、分類をまたぐナビゲーション、未知URLの404、帰属、外部リンク、言語・版切替を確認する。
6. 旧分割URLをリダイレクト対象にした場合は、全対応表を機械検査する。
7. 更新差分、レビュー失効、再生成、ロールバックの運用手順を確認する。
8. GLFW、Lua、Awesomeを比較し、共通処理とAwesome固有処理の暫定振り返りを記録する。

Previewには対象件数、英語定本件数、日本語完了件数、除外件数、metadata-only件数、スナップショットIDを明示する。日本語が全件揃う前のPreviewは検証用とし、Productionの日本語版として公開しない。

### フェーズ10: 最終人手内容レビュー・公開承認

1. 9.4の標本規則に従い、英語定本と固定原文を全文照合する。
2. `exclude`と`review`断片を確認し、広告等の誤除外・除外漏れがないことを確定する。
3. 日本語全ページについて、推薦理由、対象範囲、制限、否定、固有名詞、技術・分野用語、自然な日本語を確認する。
4. 最終レビューキューをすべて解消し、対象バッチを`human-reviewed`へ更新する。
5. 標本で欠陥が見つかった場合は該当バッチを差し戻し、修正後に機械ゲートと人手レビューを再実行する。
6. レビュー結果、既知の制約、次回取得頻度、改善点を最終記録へ反映する。
7. すべての内容レビューと公開品質ゲートの合格後、管理者の明示承認を得てProductionへ公開する。

このフェーズより前に、人手による内容品質の合格判定やProduction公開を行わない。フェーズ10は本計画の最終フェーズであり、完了後に続く実施フェーズは設けない。

## 11. 翻訳のページ完了条件

一ページを完了とするには、次をすべて満たす。

- 対応する英語定本が固定済みである。
- 見出し構造とリスト階層が一致する。
- リスト項目数と順序が一致する。
- 全URL、アンカー、インラインコード、リポジトリ名が保持されている。
- タイトル、主題説明、カテゴリ、項目説明、リンクラベルの翻訳が完了している。
- 固有名詞を一般名詞として誤訳していない。
- 推薦の強さ、対象範囲、制限、否定、比較条件を原文と照合した。
- 英語と同じ`licenseSource`を参照する。
- 構造検査、内部リンク検査、ページビルドに合格する。
- フェーズ10で技術・分野レビューと日本語レビューが完了し、`human-reviewed`になっている。

全体完了数は実ファイルと検査結果から生成する。

### 11.1 英語定本の全体完了条件

- 探索キューが空で、全候補の分類が確定している。
- `pending-license-review`が0件である。
- `included`の全取得元が定本または分割された定本ページへ一意に対応している。
- 変換前入力、ロックファイル、除外記録、ページマップ、生成物のハッシュが対応している。
- 全バッチが`canonical-validated`で、機械検査に合格している。
- `.tmp`を空にした状態から再生成し、確定済み定本との差分が0になる。

### 11.2 日本語版の全体完了条件

- 英語定本の全体完了条件を満たしている。
- 翻訳対象の全ページが本節のページ完了条件を満たす。
- 未翻訳、英語混入、機械検査エラーが0件である。
- 英日間のページ集合、見出し、項目、URL、順序、出典IDの検査に合格する。
- 日本語の全カテゴリが`translation-validated`である。

### 11.3 パイロット全体の完了条件

- 英語定本と日本語版の全体完了条件を満たす。
- フェーズ10の英語定本標本レビュー、日本語内容レビュー、最終レビューキューの解消が完了し、全対象バッチが`human-reviewed`である。
- 選択的ビルド、統合ビルド、実ブラウザ表示、Preview、Production確認に合格する。
- スナップショットの対象数、除外数、ライセンス別件数、ページ数、翻訳数、性能、既知の制約が記録されている。
- `RETROSPECTIVE.md`とlibx実装上の改善点を分けて記録している。
- 次回スナップショットで同じ作業を再開できる運用手順がある。

## 12. 上流更新時の方針

公開済みスナップショットは変更しない。新しいスナップショットでは次の差分を作る。

- 追加・削除されたリスト。
- 取得元コミットの変更。
- 原文Markdownの正規化前・正規化後ハッシュの変更。
- ライセンス変更。
- 広告等の除外断片変更。
- 見出し、項目、URL、説明の追加・削除・移動。

正規化後の英語定本ハッシュが完全一致するページだけ、日本語翻訳のレビュー状態を引き継げる。英語が変わったページは翻訳を自動更新せず、未翻訳または要再レビューとして扱う。古い日本語を新しい英語版のURLで黙って表示しない。

取得頻度は初回パイロット終了後に決める。常時追従ではなく、翻訳とレビューを完了できる間隔で明示的なスナップショットを作成する。

## 13. 品質ゲート

パイロットで実装したAwesome固有の`check:content`をルート品質ゲートへ接続する。単一アプリ生成器の実装後は、最低限、次を順に実行する。

```bash
pnpm awesome:publish --check
pnpm awesome:validate-assets
pnpm --filter=apps-awesome check:content
pnpm awesome:validate-translation-complete
pnpm --filter=apps-awesome build
pnpm build:selective --projects=awesome
pnpm check:links
pnpm check:integrity
pnpm test:runtime
pnpm check:deployment-assets
pnpm test:smoke
git diff --check
```

公開前には`pnpm check`と本番用統合ビルドも実行する。

## 14. 中断条件

- 起点コミットと対象集合を固定できない。
- 通常のリソースリンクとリスト間リンクを安全に区別できない。
- ライセンス未確認の本文が定本へ混入する。
- 広告除外が正規リスト項目を削除する。
- 原文の項目、URL、順序、説明との対応を追跡できない。
- 出典レジストリが手書き設定との二重管理になる。
- 想定ページ数、検索索引、ビルド時間、配信ファイル数が予算を超え、単一アプリ内の区画方式が未決定である。
- 全件統合によって25,600 KiBを超える単一assetが再発する、または本文総量に比例して単一assetが増え続ける。
- URLや出典IDが統合時に衝突し、決定的な解決規則がない。
- 全取得元を一つのスナップショットとして固定する途中で、異なる時点の内容が無記録で混在する。
- 自動翻訳により項目、URL、Markdown構造、推薦の意味が変更される。
- 部分翻訳を英語本文で黙って補完する必要が生じる。

## 15. 計画改訂後に最初に着手する作業

発見、縦断パイロットの機械ゲート、単一アプリ化、旧分割アプリ削除まで完了済みである。次は途中の内容レビューへ戻らず、フェーズ4以降を順に進める。

1. 全取得元の固定情報と法的根拠を確定し、`pending-license-review`を解消する。
2. 英語定本を一括再生成し、構造・URL・件数・ハッシュの機械ゲートを完了する。
3. 翻訳規則を固定し、日本語全ページを`translation-validated`まで進める。
4. 全体機械検査、統合ビルド、Preview、運用手順を完了する。
5. 未解決の内容判断を最終レビューキューへ集約する。
6. すべての前工程が完了してから、フェーズ10で初めて人手内容レビューを実施する。

## 16. 単一アプリ移行ランブック

次の担当者は、既存の分割成果物を先に移動・削除せず、以下の順で移行する。

1. 現在の`SOURCES.lock.json`、`CONTENT_MAP.json`、`SITE_SHARDS.json`と各アプリのファイル一覧・ハッシュを保存する。
2. 旧project slugから`awesome`配下の新URLへの一対一対応を生成し、未割当、重複、複数割当を0件にする。
3. 単一の出典レジストリを生成し、全ページの`licenseSource`が解決できることを確認する。
4. `apps/awesome`の一時出力へロック済み`included`全英語ページを生成し、元の正規化済みMarkdownとの本文ハッシュ一致を確認する。
5. サイドバー、検索索引、前後移動、カテゴリ入口を生成し、カテゴリ境界をまたぐ先頭・末尾ページを確認する。
6. `pnpm build:selective --projects=awesome`とasset上限検査を行い、Previewで代表URLと必要な旧URLリダイレクトを確認する。
7. 同一入力から再生成して差分0を確認する。
8. ここまで合格してから、`apps/awesome-*`、分割アプリ用package設定、分割サイドバー、分割公開スクリプトを削除候補としてレビューする。
9. 削除後にルートの選択的ビルド、統合ビルド、リンク、整合性、デプロイasset検査を再実行する。

各作業日の終了時には、`WORK_LOG.md`へ「完了したバッチ」「失敗・保留理由」「最後に成功した検査」「次に実行する一手」の四点を記録する。これにより、別の日や別の担当者でも状態ファイルと一行目の次作業から再開できる。
