# libx 正式原則準拠改善計画

- 作成日: 2026-08-11
- 根拠文書: `docs/spec/PROJECT_PRINCIPLES.md`
- 入力資料: `docs/notes/PROJECT_PRINCIPLES_COMPLIANCE_AUDIT.md`
- ステータス: 実施完了（2026-08-11）

## 1. 目的

正式原則準拠状況の再調査で確認したP0からP3の課題を、公開物を壊さず、検証可能な小さい変更単位で解消する。

本計画の完了時には、次の状態を目指す。

- サイト単位の選択的ビルドが、対象外サイトの生成物を変更・削除しない。
- ローカルとCIが同じ品質ゲートを使い、検査失敗時にはデプロイを停止する。
- 管理CLIが設定の正本を守り、変更予定の確認、dry-run、失敗時の復旧を提供する。
- BCP 47ロケール、言語・版の欠落、RTL、アクセシビリティを通常の利用経路として扱う。
- ライセンス、設定、ディレクトリ、生成物の明確に測れる整合性を自動検査する。
- レガシー設定経路と重複実装を減らし、公開APIと所有責務を明確にする。
- 読者性能と管理者性能を、再現可能な条件と予算で継続測定する。

## 2. 計画の原則

1. P0を他の変更から分離し、最初に修正する。
2. 不具合修正には、修正前に失敗し修正後に成功する回帰テストを付ける。
3. 正本を増やさない。設定、言語、URL、生成物の所有者を決めてから移行する。
4. 共有パッケージの変更は、正規テンプレートと全配信アプリで検証する。
5. 破壊的な処理は対象を列挙し、dry-run、原子的置換、失敗時復旧の順に安全性を高める。
6. リファクタリングと挙動変更を可能な限り別の変更単位にする。
7. 各フェーズを単独で完了・公開できる状態にし、後続フェーズを待たずに価値を確定する。

## 3. 対象範囲

### 対象

- 統合・選択的ビルドと生成物の配置
- GitHub Actionsとルート品質ゲート
- プロジェクト、言語、版、文書を管理するCLI
- 設定スキーマ、設定ローダー、言語レジストリ、URL解決
- 共有UI、RTL、アクセシビリティ、欠落言語・版の処理
- ライセンス設定とFrontmatter参照整合性
- テンプレートと配信アプリの共通シェル
- ワークスペース依存関係、package exports、ツールチェーン
- 読者性能、生成性能、品質レポート
- 監査で確認した主要文書の参照切れと現状不一致

### 対象外

- UIデザインの全面刷新
- ドキュメント本文の翻訳品質や内容そのものの改稿
- 配信基盤の移行
- サイトより細かい単位の選択的ビルド
- 古いAPIや設定形式を外部利用者向けに長期間維持すること

作業中に対象外の問題を見つけた場合は、実装へ混ぜず調査メモまたは別計画へ記録する。

## 5. 実施フェーズ

### フェーズ0: ベースラインと作業境界の固定

目的:

- 修正前の挙動、性能、生成物、既存差分を記録し、後続作業の比較基準を作る。

実施内容:

1. `pnpm check`、format検査、全体ビルド、サイト別ビルドの結果を記録する。
2. `dist/` の所有区分を次のように定義し、機械可読な検査へ利用できる形にする。
   - landingが所有するルートHTMLとルートアセット
   - 各ドキュメントサイトが所有する `dist/docs/{project}`
   - 将来追加する他サイトの所有領域
3. 代表的なLTR、RTL、ハイフン付きロケール、言語・版欠落の組合せをテストケースとして固定する。
4. ビルド時間、最大メモリ、代表ページのLCP・CLS・転送量を参考値として再記録する。
5. 既存の `CODE_QUALITY_IMPROVEMENT_PLAN.md` と `RTL_SUPPORT_PLAN.md` の完了事項を確認し、同じ問題を再実装しない。

完了条件:

- 修正前後を比較できる検証記録がある。
- `dist/` の各領域について所有者が説明できる。
- 後続フェーズで使う代表ケースが自動テストまたは検証表に列挙されている。

### フェーズ1: 選択的ビルドの公開安全性を回復する

対象候補:

- `scripts/build-selective.js`
- 統合出力のコピー・同期処理
- 生成物スモークテスト

実施内容:

1. `landing` の選択的ビルド前後で `dist/docs/**` の内容とハッシュが変わらない回帰テストを先に追加する。
2. landingを一時ディレクトリへビルドし、landing所有ファイルだけを `dist/` へ同期する。
3. `dist/` 全体を削除対象にせず、削除・置換対象を所有マニフェストまたは明示的な一覧から決定する。
4. コピー途中の失敗時には既存公開物を維持し、成功時だけ置換を確定する。
5. 次の組合せを検証する。
   - landingのみ更新
   - 文書サイト1件のみ更新
   - 複数文書サイトを更新
   - 存在しないサイトIDを指定
   - ビルドまたはコピー途中で失敗

完了条件:

- landingのみの更新で `dist/docs/**` が追加・変更・削除されない。
- 文書サイト1件の更新で他サイトの生成物が変わらない。
- 失敗後も更新前の公開可能な成果物が残る。
- この保証をCIで自動検出できる。

### フェーズ2: 品質ゲートと再現可能な開発環境を整える

対象候補:

- `package.json`
- `pnpm-lock.yaml`
- `.prettierrc`
- `.github/workflows/cloudflare-pages-deploy.yml`
- `README.md`、`docs/guides/*`

実施内容:

1. `prettier-plugin-astro` を正規の開発依存へ追加し、format検査を復旧する。
2. lintとformatの `continue-on-error` を除去する。
3. CIの正規品質ゲートを `pnpm check` に統一し、デプロイをその成功へ依存させる。
4. 軽量な検査と重いビルド検査をジョブとして分離しても、最終ゲートでは両方を必須にする。
5. `packageManager` とNodeの対応範囲を宣言し、README、CI、ローカルのpnpm系統を揃える。
6. 実在するMarkdownリンクを検査し、監査で確認した参照切れとREADMEの現状不一致を修正する。
7. コード例中の架空リンクを実ナビゲーションのリンク検査から除外する。

完了条件:

- クリーンな環境で依存導入後、`pnpm prettier --check .` と `pnpm check` が成功する。
- lint、format、型、テスト、必須ビルドのいずれかが失敗するとデプロイへ進まない。
- CIと文書が同じNode・pnpm条件を示す。
- 主要文書の実リンクに参照切れがない。

### フェーズ3: 管理CLIとロケール処理を安全にする

対象候補:

- `scripts/add-language.js`
- `scripts/create-version.js`
- `scripts/create-document.js`
- `scripts/document-utils.js`
- `scripts/build-integrated.js`
- `scripts/build-selective.js`
- `@docs/i18n` と設定読込API

実施内容:

1. プロジェクトのコンテンツ言語追加と、landing UI自体の対応言語追加を別の操作として定義する。
2. `projects.config.jsonc` の存在しない `supportedLangs` を正本として扱う処理を廃止する。
3. ロケール検証を共有APIへ集約し、`en`、`ar`、`zh-Hans`、`zh-Hant`、`pt-BR`を同じ経路で扱う。
4. HTMLまたはURLの後処理にある `[a-z]+` 前提を廃止し、構造化されたURL生成へ寄せる。
5. `add-language`、`create-version`、`create-document` に次を共通導入する。
   - 変更対象と予定差分の表示
   - `--dry-run`
   - 非対話実行時の引数検証
   - 一時領域での準備
   - 全検証成功後の確定
   - 失敗時のロールバック
6. 同じ意味の設定を複数ファイルへ書く必要がある操作は、共有更新APIを通す。
7. CLIの成功、入力拒否、途中失敗、再実行をテストする。

完了条件:

- dry-runではファイル内容とGit差分が変化しない。
- ハイフン付きロケールの言語・文書追加とURL生成が成功する。
- 途中失敗後に設定だけ、またはコンテンツだけが残らない。
- 同じ引数で再実行した場合の結果が予測可能である。
- 操作後の設定、ディレクトリ、landing表示情報が整合する。

### フェーズ4: 読者安全性、国際化、アクセシビリティを保証する

対象候補:

- `packages/ui`
- `packages/i18n`
- `packages/versioning`
- `packages/theme`
- 各サイトの共有レイアウト
- プロジェクト設定スキーマと文書Frontmatter検査
- ブラウザスモークテスト

実施内容:

1. Lighthouseで確認した問題を修正する。
   - `aria-hidden` 配下のフォーカス可能な操作要素
   - コードコメントのコントラスト
   - タスクリストのチェックボックス名
2. 共有UIの固定日本語 `aria-label` を翻訳キーへ移し、表示言語とアクセシブル名を一致させる。
3. 物理方向CSSを分類し、意味上固定でないものを論理プロパティへ変更する。
4. 言語ごとに利用可能な版の対応表をビルド時に生成し、存在しないサイドバーへの確認要求をなくす。
5. 欠落時のUI規則を定義する。
   - 選択不能な版・言語をリンクとして表示しない。
   - 暗黙に別言語へ遷移しない。
   - フォールバックする場合は読者へ明示する。
6. 配信サイトではライセンス、原著者、出典、既定sourceを必須にする。
7. `sourceLanguage` と対応言語、Frontmatterの `licenseSource` とsource IDの参照整合性を検査する。
8. デスクトップ・モバイルの英語とアラビア語を対象に、キーボード操作、アクセシビリティ、自動404検出を行う。

完了条件:

- 監査で確認した3種類のアクセシビリティ失敗が解消する。
- アラビア語ページに日本語固定のアクセシブル名がない。
- 欠落している言語・版を閲覧しても、存在しないサイドバー要求やコンソールエラーが発生しない。
- ライセンス設定または参照が不正なサイトは品質ゲートで失敗する。
- LTRとRTL、デスクトップとモバイルの主要操作が成立する。

### フェーズ5: 設定契約と生成物の正本を確立する

対象候補:

- `packages/project-config`
- `packages/config`
- `packages/i18n`
- `config/global-defaults.jsonc`
- `scripts/jsonc-utils.js`
- 各アプリの `public/sidebar` と `public/sw.js`
- landing設定

実施内容:

1. 次の参照整合性を共有スキーマまたは検証器へ追加する。
   - version IDの一意性
   - `isLatest` がちょうど1件
   - 既定言語が対応言語に含まれる
   - 全対応言語の表示名と必要な翻訳
   - 設定上の版・言語とディレクトリの対応
   - `projectSlug`、アプリID、公開URL、landing装飾IDの対応
   - ライセンスsource参照
2. `defaultLang` と `language.default` のどちらを正本にするか決定し、読み書き経路を一本化する。
3. 言語一覧、表示名、方向、fallbackを言語レジストリから提供する。
4. JSONC解析と既定値解決を共有実装へ集約する。
5. サイドバーとService Workerについて次を決定する。
   - Git追跡するなら、すべての正式ビルド入口で再生成し、生成後差分がないことをCIで検査する。
   - Git追跡しないなら、依存するすべてのビルド入口で生成を必須化する。
6. 存在しない `libx-docs` landing装飾など、検査で確認した孤立設定を削除する。
7. 正本や生成物追跡方針を変更する判断はADRへ記録する。

完了条件:

- 明確に測れる設定不整合が `pnpm check` で検出される。
- 言語一覧、JSONC解析、既定言語解決にそれぞれ説明可能な正本が一つだけある。
- どの正式ビルド入口でも古いサイドバーやService Workerを配信しない。
- 設定上の孤立参照がない。

### フェーズ6: 公開API境界と重複実装を整理する

対象候補:

- `packages/project-config`
- `packages/config`
- `packages/content-utils`
- `packages/ui`
- `packages/i18n`
- `packages/versioning`
- `templates/docs-site`
- `apps/*`

実施内容:

1. レガシー設定APIの全参照を分類し、現行 `ProjectConfig` APIへの移行順を決める。
2. レイアウト、ページ、UI、content-utilsを現行APIへ移し、リポジトリ内参照が0件になった互換コードを削除する。
3. 設定読込、ルートリダイレクト、静的パス生成、レイアウト骨格のうち、安定した共通責務を共有パッケージへ移す。
4. サイト固有の見た目や内容はslot、Props、設定として残し、共通化のための条件分岐を増やしすぎない。
5. Vite aliasによる `src` 直参照を廃止し、必要なサブパスをpackage exportsへ定義する。
6. Astro依存を同一系統へ揃える。共有パッケージで実行時所有が不要ならpeer dependency化する。
7. 依存境界変更ごとにテンプレートと全配信アプリをビルドする。

完了条件:

- リポジトリ内部に廃止対象の設定API参照がない。
- 公開APIを迂回するワークスペース向け `src` aliasがない。
- Astroの対応バージョン方針がpackage manifest間で一貫する。
- テンプレートと実サイトの共通シェル変更を1か所で適用できる。
- 全アプリの静的ルートと表示が移行前と同等に保たれる。

### フェーズ7: 性能を継続測定可能な契約にする

対象候補:

- 性能測定スクリプト
- 大規模文書フィクスチャ
- CIの定期・手動実行ジョブ
- 品質レポート
- 性能測定ガイド

実施内容:

1. 読者性能の代表ページを定義する。
   - 軽量な通常文書
   - 長文、コード、画像を含む重い文書
   - LTRページ
   - RTLページ
2. 管理者性能の代表ケースを定義する。
   - 1サイトの選択的ビルド
   - landingのみのビルド
   - 全体ビルド
   - 大規模文書群のサイドバー生成
3. 比較対象を用意する。
   - 最小限の静的HTML
   - 類似ドキュメントジェネレーター
   - 改善前または直近安定版のlibx
4. 本番環境を優先し、ローカルではCPU、回線、キャッシュ、測定回数を固定して中央値を使う。
5. 最初は観測値として収集し、安定後に次の予算を設定する。
   - LCP、CLS、必要に応じてINP
   - HTML、CSS、JavaScript、画像の転送量
   - リクエスト数
   - サイト別・全体ビルド時間
   - 最大メモリ
6. 閾値超過時には対象ページ、変更量、比較対象との差をレポートする。
7. 性能、アクセシビリティ、内部リンク、ライセンス、設定整合性を一つの品質レポートとして参照できるようにする。

完了条件:

- 同じ条件で繰り返せる測定コマンドと手順がある。
- 読者性能と管理者性能が別々に記録される。
- 最小静的HTMLを含む相対比較結果がある。
- 合意した予算を超える回帰を自動検出できる。
- 大規模化の兆候をサイト分割判断へ利用できる。

## 6. 推奨する変更単位

次の順で、個別にレビュー、検証、取り消しができる変更へ分ける。

1. landing選択ビルドの保全テスト
2. landing出力同期の修正と失敗時復旧
3. Prettier依存とCI必須ゲートの修正
4. ツールチェーン固定と主要文書修正
5. 共有ロケール検証とBCP 47対応
6. `add-language` の正本修正とdry-run
7. `create-version` / `create-document` の原子的更新
8. 欠落言語・版対応表と不要な404の解消
9. アクセシビリティ修正とUI文言のi18n化
10. ライセンス参照整合性検査
11. 設定・ディレクトリ・landing参照整合性検査
12. 生成物の正本と再生成経路の統一
13. レガシー設定APIの利用箇所ごとの移行と削除
14. package exports、Astro依存、共通サイトシェルの整理
15. 性能フィクスチャ、比較計測、予算、品質レポートの導入

各変更では、実装と同時に関連テストと文書を更新する。

## 7. 検証マトリクス

| 変更領域 | 必須検証 |
| --- | --- |
| 選択的ビルド | 対象サイト更新、対象外ハッシュ不変、途中失敗時復旧 |
| CI・依存 | クリーンインストール、format、`pnpm check`、失敗ジョブからのデプロイ停止 |
| 管理CLI | dry-run、成功、入力拒否、途中失敗、再実行、Git差分確認 |
| ロケール | `en`、`ar`、`zh-Hans`、`pt-BR`、言語・版欠落 |
| 共有UI | LTR/RTL × デスクトップ/モバイル × キーボード操作 |
| ライセンス | 正常参照、存在しないsource、未対応sourceLanguage、必須値欠落 |
| 設定 | 重複版、最新版0件/複数、孤立ID、ディレクトリ不一致 |
| 生成物 | 正式ビルド入口ごとの再生成、生成後差分、古い成果物の不在 |
| 公開API | 全ワークスペース型検査、テンプレートと全配信アプリのビルド |
| 性能 | 固定条件の複数回測定、中央値、比較対象、予算超過検出 |

## 9. ADRが必要な判断

次の項目は実装前に選択肢と影響を整理し、既存原則の単純な適用で決まらない場合はADRとして承認する。

1. `dist/` 直下の所有マニフェストと原子的置換方式
2. `defaultLang` / `language.default` の正本と移行方法
3. サイドバー、圧縮済みサイドバー、Service WorkerをGit追跡するか
4. 共有パッケージにおけるAstroのdependency / peerDependency方針
5. サイトシェルを共有する公開APIの境界
6. 性能予算、測定環境、比較対象、回帰時の停止条件

ADRは `docs/adr/README.md` の保存場所、テンプレート、承認手順に従う。

## 10. リスクと対策

| リスク | 対策 |
| --- | --- |
| `dist/` 同期変更で古いlandingアセットが残る | 所有マニフェストを使い、追加だけでなく安全な削除もテストする |
| CI必須化で既存開発が一時的に停止する | 依存不足と既知の失敗を先に直し、ゲート化を独立した変更にする |
| CLIの原子化が複雑になる | 計画生成、検証、一時領域、確定の4段階へ共通化する |
| 厳格な設定検証が既存サイトを拒否する | 全設定を事前走査し、既存データ修正と検証導入を同じ変更にする |
| UI修正がLTRまたはRTLの一方を壊す | 言語と画面幅の検証マトリクスを自動化する |
| レガシーAPI削除の差分が肥大化する | 利用層ごとに現行APIへ移し、参照0件を確認してから削除する |
| 共通化でサイト固有要件が表現しにくくなる | 安定した責務だけを共有し、見た目とコンテンツは拡張点として残す |
| 性能計測がCIノイズで不安定になる | 観測期間を設け、複数回の中央値と許容幅を使ってから必須化する |

## 12. 進捗記録方法

各変更単位またはフェーズの完了時に、別の実施記録へ次を残す。

- 実施日と対象フェーズ
- 解消した監査項目ID
- 変更ファイルと責務
- 実行した検証コマンド、ブラウザ条件、結果
- 修正前後の差または測定値
- 残課題、既知の制約、次の変更単位
- 作成・更新したADRと文書

チェックボックスは、実装と必須検証が完了した項目だけを更新する。計画変更が必要になった場合は、監査項目との対応関係を維持したまま理由を記録する。
