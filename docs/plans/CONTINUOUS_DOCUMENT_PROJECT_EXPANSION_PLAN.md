# 公式文書の継続追加・更新計画

## 1. 目的と運用の正本

Libxは、公式文書の原文コピーと日本語訳を、無理なく読める範囲で提供する。原文の意味を保ち、詳しい情報や元サイト固有の機能は原典へのリンクで補う。原文自体の完全性・技術的正しさの保証や、元サイトの機能・外観の完全再現を採用条件にしない。対象は通常のドキュメントサイトとし、別計画のコンテンツは混在させない。

本書は共通の実行手順を定める。案件名、作業場所、進捗、実行履歴は本書へ追記せず、次の正本で管理する。

| 情報 | 正本 |
| --- | --- |
| 件数上限・採点・確認間隔・モデル・公開方針 | [POLICY.json](../notes/project-expansion/POLICY.json)の現行設定。`changes` は履歴 |
| 候補・選定根拠 | [CANDIDATES.json](../notes/project-expansion/CANDIDATES.json) |
| 作業状態・担当・作業場所・次の操作 | [OPERATIONS.json](../notes/project-expansion/OPERATIONS.json) |
| 原資料・ページ進捗・レビュー証拠 | 各案件の台帳から参照するファイル |
| 実行結果・全体進捗 | `docs/notes/project-expansion/runs/` と台帳から生成する `REPORT.md` |

最新のユーザー指示とAGENTS.mdに従い、方針変更時は本書とPOLICYを揃える。履歴や個別の作業メモを現行手順として適用しない。

## 2. 作業の選択と候補の採用

優先順位は、確認済みの重大不具合、着手済み案件の完了と既存修正・更新、新規追加、余力での定期確認とする。公開可能な案件は完了工程として速やかに公開する。

新規着手はPOLICYの件数上限・保守優先条件と台帳検査に従う。停止・証拠失効中の案件も作業枠に数える。長期保留で枠を外す場合は、理由・復帰条件・保存成果物・配信対象からの除外を記録する。

候補は「公式プロジェクト・固定版・収録範囲」の組で評価する。有効な候補があれば再調査せず、不足時に公式文書、関連技術、パッケージ情報などから補充する。採用には次の条件をすべて満たす必要がある。

- 利用条件と、帰属・通知・変更表示などの履行方法を確認できる。
- 掲載範囲と、原典を参照する範囲を読者に示せる。利用ガイドなど意味のまとまった範囲で採用でき、全API・全資料の収録は必須にしない。
- 対象版と入力をコミットまたは配布物のハッシュで固定できる。
- 原文に説明不足や古い記述があっても、掲載部分に読む価値があり、不足する情報の参照先を示せる。
- 代表ページで本文・コード・表などの意味を保って読める。表示機能は静的な表現や原典リンクに置き換えられる。
- 掲載範囲と提供方式を簡素にし、バッチ処理で作業量を管理できる。文書量の多さや専用変換の必要性だけで見送らない。

対象版の日本語資料を必要な範囲で調べ、追加価値・実用性・読みやすさ・保守性・方式の再利用性をPOLICYに従って採点する。最低点は各項目3/5相当の60点、追加価値・実用性は各3点以上とする。保守性はLibxで提供する簡素な方式の負荷で評価し、元サイトの全機能維持を見積もらない。採用前の根拠照合は1回とし、上記条件の不明点だけを解消する。見送りには再開条件を残し、原文の不備・表示再現・過大な保守見積もりで保留した候補は、この基準で既存証拠を使って再評価する。

文書専用ライセンスが見つからない場合は、POLICYの注釈付き本体ライセンス適用方針を用いる。確認先・固定ライセンス・適用判断・通知を保存し、明示的な文書条件や第三者素材の条件を優先する。根拠や条件履行が未確定の案件は保留する。

## 3. 実行手順

1. **再開する。** 本書、POLICY、作業台帳、対象案件の進捗を確認し、現在のファイルと証拠を照合する。既存作業場所を再利用し、有効な工程から続ける。履歴は必要な箇所だけ読む。
2. **入力を固定する。** 版・取得元・取得日・ハッシュ・利用条件と文書一覧を保存する。原文から定本・訳文への対応を記録し、原資料を再取得なしでも確認できるようにする。
3. **定本を作る。** 新規サイトは正規テンプレートと作成器を使う。固定入力から同じ定本を再生成できるようにし、掲載範囲の説明・図表・コード・注意書きの意味を保つ。元サイトの独自JS・ツールチップ・実行デモ等は移植を必須とせず、必要な説明を静的表示または原典リンクで補う。新しい方式は代表ページで試してから広げる。
4. **翻訳・レビューする。** 下記のバッチ方式で翻訳、別パスの内容確認、修正を進める。出典・非公式翻訳の説明・Libxの編集注記は共通フッターへ置き、原著者の本文や通知と区別する。
5. **検証・統合する。** 必要な機械検査と代表表示を確認し、最新の共有状態へ対象差分だけを統合する。統合で影響した検査を再実行する。
6. **公開・記録する。** 完了条件を満たした案件を公開し、配信結果と次の作業を保存する。下記の区切りで計画に伴う変更をコミットし、`origin`へpushする。続行可能なら次のバッチまたは案件へ進む。

簡略化した機能、未収録の範囲、確認できた原文の不備は出典・編集注記に短く示し、対応する原典へリンクする。機能省略に伴って説明や例を黙って消さず、全体を再現したと表示しない。

新版は別の版として追加し、既存版を黙って置き換えない。同じ固定原文の誤訳・変換不具合は変更履歴を残して修正する。上流に変更がなければ確認日時と `no-change` を記録し、再翻訳しない。

## 4. 作業単位と品質確認

**1バッチは関連する5〜10ページ、または原文3,000〜6,000語程度を目安**とする。長文は意味のまとまった節に分け、検証作業は成果が明確な単位にまとめる。規模は難易度と手戻りを見て調整し、件数ノルマにしない。

草稿は随時保存する。作成後に別パスで、掲載範囲の原文との対応、訳文の意味、日本語の読みやすさを1回確認する。原文そのものの技術監査や全サンプルの実行試験は求めず、見つかった原文の問題は短く注記する。同じ担当でよく、別担当の承認は必須にしない。機械検査だけで内容レビュー済みとしない。

修正後は変更箇所と依存する説明だけを再確認する。合格済みの節を組み立てる場合は、全節の存在・順序・境界・参照を確認して証拠を引き継ぐ。旧証拠を書き換えず、元の確認範囲と現行本文の関係を残す。未読・未検証を合格にしない。

| 変更範囲 | 必要な確認 |
| --- | --- |
| 内容・関連入力に変更なし | 有効なレビューと検査証拠を再利用 |
| 本文・訳文の変更 | 変更箇所と意味上の依存、構造・リンク、バッチ末尾の対象ビルド |
| 注記の配置・整形・リンクのみ | 本文保全、限定差分、該当リンク・表示 |
| 変換器・ページ構成 | 再生成差分と影響範囲の内容・構造・参照・代表表示 |
| 共有UI・設定・テンプレート | 関連テスト、テンプレートビルド、複数アプリの回帰確認 |

入力・検査実装・設定・依存・出力が同じ検査は繰り返さない。検査・ビルド・台帳更新はバッチ末尾にまとめる。全体検査を毎ページ実行したり、記録専用の仕組みを増やしたりしない。

表示は代表ページで、原文・訳文が読めること、表・コード・図の意味が分かること、原典へ移動できることを確認する。Libxの主要導線は提供しているものを確認し、共通UIが不変なら既存証拠を使う。元サイトとの外観・操作の一致や全ページ×全表示幅の巡回は求めず、掲載範囲の構造・リンク検査と分ける。

Libxの変換・翻訳による意味の欠落・重大誤訳、閲覧や原典参照を妨げる破損、必要な通知不足は解消する。原文自体の説明不足・誤記、代替手段のある未再現機能、軽微な表示差、任意のバッジの障害は注記・原典リンクで補い、採用や公開を止めない。無関係な既存エラーは失敗として残し、独立して進められる作業を続ける。

## 5. 完了と公開

状態は `planned → source-locked → canonical-ready → translating → content-reviewed → verified` で管理する。状態名だけで完了を判断せず、以下の成果を確認する。

- `content-reviewed`: 確定した収録範囲の全ページに翻訳と有効な全文内容レビューがある。
- `verified`: 上記に加え、利用条件の履行、再生成一致、掲載範囲の構造・リンク検査、ビルド、可読性と主要導線、統合、台帳との一致を満たす。必要な配布資料と提供範囲・制限の案内がある。原典全体の完全性や元サイトの機能再現は要求しない。
- `published`: 検証済み成果物の本番配信が成功している。配信後確認の結果・問題は別に記録する。

**公開できる状態になったら、その都度の承認確認なしで公開デプロイする。** 検証済み案件を公開待ちとして登録し、現行成果物と証拠を照合して、必要な限定差分のpush・外部Preview・Productionまで進める。公開待ち上限までためず、既存の検証済み未公開案件も処理する。

公開先は統合Cloudflare Pages、ローカル開発・検証はAstroとする。Cloudflare Workersは使わない。公開候補には対象の検証済み変更だけを含め、他案件やユーザーの未完了変更を混在させない。

公開後は主要URL、言語/版切替、出典、404を確認し、成果物との対応・公開URL・配信ID・確認結果を記録する。配信失敗は未公開のまま原因と再開条件を残し、解消後に再試行する。明示的な作業・公開停止指示を優先する。定期実行の設定は別途指示がある場合のみ行う。

## 6. 記録と中断・再開

起動時の台帳検査と操作方法は[運用READMEの再開操作](../notes/project-expansion/README.md#再開操作)を使う。既存のスキーマと競合検出を維持し、同じ入力の全検査を重ねない。設定上のモデルと確認できた実モデルを区別し、ローカルLLMは使わない。

ページ別に原文・定本・訳文のハッシュ、確認範囲、指摘と修正、モデル・日時を保存する。run・台帳・REPORTはバッチ末尾、終了・引継ぎ時にまとめて更新する。記録は「完了範囲、再利用証拠、検査結果、未完了と理由、次の操作」を基本とし、証拠を重複保存しない。

**バッチ完了、案件完了、公開後の記録完了、中断・終了・引継ぎなど、作業の区切りで、計画によって生じたファイルの追加・変更・削除をまとめてコミットし、作業ブランチを`origin`へpushする。** 原資料・草稿・定本・訳文、生成器・設定、検査証拠、run・台帳・REPORTなどの追跡対象を含め、公開待ちの変更だけに限定しない。毎ページのコミットは求めず、関連する変更をレビュー可能な単位にまとめる。公開後に生じた記録の変更も次の区切りで保存する。

コミット前に差分と必要な検証結果を確認し、この計画の対象変更だけを明示的に選ぶ。他案件やユーザーの未完了変更、依存物・ビルド出力・一時ファイル・秘密情報を混在させない。pushで外部Previewや公開が起動し得るため配信workflowと対象差分を確認し、未確認の草稿・途中成果は配信対象から除外した保存用ブランチへpushする。公開用ブランチには公開条件を満たした対象差分だけを含める。

コミット・pushは都度の承認確認なしで行うが、明示的な作業・公開停止指示を優先する。停止中の保存は許可された範囲に限る。コミットID・push先・成否と、未保存の変更があれば理由・再開操作をrun・台帳・REPORTへ記録する。push失敗を成功と扱わず、条件不変のまま繰り返さない。

中断時は最後の有効な状態と未確認範囲を保存する。再開時に失効した範囲だけへ戻り、他者の変更を巻き戻さない。競合は再読込し、ロックは担当とプロセス終了を確認して扱う。同じ外部障害を条件不変のまま再試行しない。

報告は日本語で、完了範囲、現在の状態、公開結果、重大な残件、次の操作を簡潔に示す。進捗は完了した文書や解消した問題で測り、検査回数・証拠数を成果にしない。定期的に作業時間と手戻りを振り返り、重複確認や記録の負担を減らす。
