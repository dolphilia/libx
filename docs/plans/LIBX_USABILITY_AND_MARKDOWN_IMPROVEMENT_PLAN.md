# libx使いやすさ・閲覧性・Markdown改善実装計画

- 作成日: 2026-08-11
- 入力資料: `docs/notes/document-import/lua/USABILITY_AND_MARKDOWN_IMPROVEMENTS.md`
- 関連資料: `docs/notes/document-import/lua/LIBX_IMPLEMENTATION_IMPROVEMENTS.md`
- 根拠原則: `docs/spec/PROJECT_PRINCIPLES.md`
- ステータス: 完了（2026-08-11）
- 実装記録: [libx使いやすさ・閲覧性・Markdown改善 実装記録](../notes/LIBX_USABILITY_AND_MARKDOWN_IMPROVEMENT_IMPLEMENTATION.md)

## 1. 目的

Lua 5.5.1文書パイロットで確認した管理操作、本文表示、Markdown変換、共通UIの問題を、上流追従、多言語構造、軽い静的配信、サイト単位の選択的ビルドを維持したまま改善する。

本計画の完了時には、次の状態を目指す。

- 管理者向けガイドのコード例が、実際の公開APIと一致し、継続的に検査される。
- `.md`と`.mdx`が、文書発見、ナビゲーション、検索、言語・版切替で同等に扱われる。
- Luaインポータが、意味だけでなく読みやすい段落・定義構造を再現可能に生成する。
- 本文CSS、UIラベル、ページメタデータが、すべてのサイトと言語で一貫する。
- 定義、注意書き、API項目、出典状態を、移植性とno-JS表示を損なわず表現できる。
- 大規模サイトで、ページ名、見出し、API識別子から目的の箇所へ到達できる。
- 共通レイアウトとスキーマの修正を、サイトごとの手作業で反映しなくてよい。
- 任意機能のアセットが、不要なサイトのファイル数と表示性能へ影響しない。

## 2. 実施原則

1. 不具合修正には、修正前に失敗し修正後に成功する回帰テストを付ける。
2. 定本の技術的意味、上流アンカー、コード、リンクを表示改善のために変更しない。
3. 英語定本と翻訳は可能な限り同じ構造変換を使い、片方だけへ装飾を追加しない。
4. CommonMark／GFMを基礎とし、MDXと独自記法は必要な場合だけ使う。
5. 本文はJavaScriptなしでも読める状態を完了条件に含める。
6. 共有UIまたはテーマの変更は、Luaだけでなくテンプレートと全配信アプリで確認する。
7. リファクタリング、本文再生成、表示変更を可能な限り別の変更単位にする。
8. 検索索引と任意アセットはサイト・版・言語の境界を越えて無条件に読み込まない。
9. 各フェーズを単独で完了、検証、公開、ロールバックできるようにする。
10. 複数の合理的な方式がある変更は、試作と計測後にADRで採用方式を決める。

## 3. 対象範囲

### 対象

- サンプル文書と管理者向けMarkdown／MDX執筆ガイド
- Luaインポータの空白、インライン要素、定義的列挙、manページ変換
- `.md`／`.mdx`を扱うコンテンツ発見、検査、ナビゲーション処理
- `packages/ui`、`packages/theme`、`packages/i18n`
- 各サイトとテンプレートの`DocLayout.astro`、`MainLayout.astro`、コンテンツスキーマ
- ページtitle、description、canonical、`hreflang`、出典・翻訳状態
- ページ内目次、サイト内検索、APIシンボル探索
- コード、表、定義リスト、注意書き、API項目の意味的表現
- KaTeXを含む任意機能の生成ファイル数と読込境界
- 実装に対応するガイド、仕様、ADR、検証記録

### 対象外

- Lua本文の技術内容を上流と異なる内容へ改稿すること
- 日本語訳を自動翻訳で再生成すること
- 全サイトのデザインを一度に刷新すること
- すべての文書をMDXへ移行すること
- 1 APIシンボル1ページへの一律分割
- 配信基盤の移行
- サイトより細かい選択的ビルド保証
- 本計画と独立した進捗マニフェスト、上流更新差分、翻訳レビュー失効の実装

最後の項目群は[Luaパイロットから得た実装改善案](../notes/document-import/lua/LIBX_IMPLEMENTATION_IMPROVEMENTS.md)で別途管理する。本計画が必要とする場合は、その公開APIを利用するが、同じ機能を重複実装しない。

## 5. 実施フェーズ

### フェーズ0: ベースラインとfixtureの固定

目的:

- 後続変更が内容、表示、性能を意図せず変えていないと判断できる基準を作る。

実施内容:

1. 次の代表ページを検証対象として固定する。
   - Luaの通常説明ページ
   - 長いC APIページ
   - Luaとluacのman由来ページ
   - 表、引用、画像、コード、数式、Tabs、Alertを含むsample-docsページ
   - 英語、日本語、RTL言語のページ
2. Markdown要素を一ページで確認できる小さい表示fixtureを`test-verification`へ追加する。
3. `.md`と`.mdx`で同じ見出し、リンク、前後移動、言語・版切替を持つruntime fixtureを追加する。
4. Luaの問題箇所を含むインポータ入力・期待出力fixtureを切り出す。
5. 次の基準値を記録する。
   - サイト別ページ数、ファイル数、容量、ビルド時間
   - 初期JavaScript、CSS、最大アセット、KaTeXファイル数
   - 代表ページのFCP、LCP、CLS、横overflow
   - C APIページの見出し数と目次項目数
6. デスクトップ、モバイル、印刷、no-JSの確認項目をブラウザ検証表へ追加する。

完了条件:

- 後続フェーズが参照するページ、fixture、測定条件が固定されている。
- `.md`／`.mdx`、LTR／RTL、通常ページ／長大ページを自動または手動で再現できる。
- 現在のファイル数と読者性能を、変更後と同じ条件で比較できる。

成果物候補:

- `tests/runtime/`のMarkdown／MDX契約fixture
- `tests/smoke/`の代表ページ宣言
- `docs/notes/`の実装前ベースライン

### フェーズ1: 表示・執筆・変換契約の修復

#### 1.1 執筆例を実行可能な契約にする

実施内容:

1. `@docs/ui`の実際のexportとPropsを正本として、サンプル文書の`Tab`、`CodeWindow`、`Alert type`、`Card type`などの不整合を修正する。
2. ガイドに載せる主要例を、実際にビルドするMDX fixtureへ移す。
3. コードフェンスの例とfixtureの差異を検出する方法を追加する。自動生成が過剰なら、少なくとも公開exportと主要prop名を検査する。
4. 未検証のアクセシビリティ保証など、実装と検査で裏付けられない記述を修正する。
5. 未知のvariantを黙って既定表示する挙動を、型・schema・テストのいずれかで検出する。

完了条件:

- ガイド掲載の主要なMDX例が実際にビルドされる。
- 存在しないexportまたは主要propを例示すると品質ゲートが失敗する。
- 日本語版と英語版の例が同じ公開APIを使用する。

#### 1.2 本文ルートとテーマCSSを統一する

実施内容:

1. 正式な本文ルートクラスを`.sl-markdown-content`とし、テーマの対象を統一する。
2. 移行のために`.article-content`を一時的に受ける場合は、削除条件をテストと文書へ記録する。
3. 段落、見出し、リスト、リンク、引用、コード、表、画像、focus、印刷、モバイル規則をfixtureで確認する。
4. block quoteの引用装飾が、通知や出典へ誤用されないようにする。
5. CSS変更前後の画像差分を確認し、意図した変更だけを承認する。

完了条件:

- 代表的な本文要素に共通テーマが適用される。
- Lua、GLFW、sample-docs、テンプレートで本文表示契約が同じである。
- LTR、RTL、モバイル、印刷で内容が欠落または横overflowしない。

#### 1.3 Luaインポータの可読性を修正する

実施内容:

1. インラインtext、code、link、punctuation間の空白正規化規則を定義する。
2. 演算定数の列挙、manオプション、環境変数を、中間表現上の用語・説明として保持する。
3. 英語定本を再生成し、アンカー、リンク、コード、識別子、見出しが変化していないことを検査する。
4. 日本語訳は自動翻訳しない。生成規則に対応する書式変更だけを適用し、定本と一項目ずつ構造照合する。
5. `--check`、`--dry-run`、一時生成、検査後置換を維持する。
6. 連続空行、記号だけの段落、短い断片段落、未処理定義を品質レポートへ追加する。

完了条件:

- `LUA_OPADD`等の説明が一つの読みやすい項目として生成される。
- manオプションと説明が意味的に関連付けられる。
- 上流538アンカー、内部リンク、コード、識別子の既存不変条件を満たす。
- 同じ入力から差分なく再生成できる。

#### 1.4 `.md`と`.mdx`の契約を正式化する

実施内容:

1. `.md`を外部定本、翻訳、通常文書の第一選択、`.mdx`を明示的なUI拡張と定義する。
2. コンテンツ発見、サイドバー、前後移動、リンク変換、言語・版切替、検索入力、Frontmatter検査が両形式を同じ経路で処理するようにする。
3. `.md`と`.mdx`を名前付きで列挙する重複glob、正規表現、条件分岐を共有APIへ集約する。
4. `PROJECT_PRINCIPLES.md`と執筆ガイドの「MDX標準」を、実装契約と一致する表現へ改定する。
5. 原則文書の変更は、管理者レビューを受けてから確定する。

完了条件:

- `.md`／`.mdx`のruntime fixtureがすべて同じ品質ゲートを通る。
- 片方だけを処理する実装が検査で検出される。
- 定本を表示都合だけでMDXへ変換する必要がない。
- 原則、ガイド、実装が同じ役割分担を説明する。

フェーズ1全体の公開条件:

- 4作業を別の変更単位で検証できる。
- Luaの全定本・翻訳検査、テンプレート、全配信アプリのビルドが成功する。
- URL、アンカー、ライセンス帰属、言語・版切替に回帰がない。

### フェーズ2: 多言語UIとページ状態の整備

#### 2.1 共通UIラベルをi18nへ移す

実施内容:

1. `Alert`、`ContentNotice`、`AnchorHeading`と関連コンポーネントの固定文字列を棚卸しする。
2. visible labelとaccessible nameを`@docs/i18n`の同じ言語から取得する。
3. コンポーネントの`lang`伝播を共通レイアウトから保証する。
4. 未翻訳キーのfallback規則を既存i18n契約へ合わせる。
5. 英語、日本語、アラビア語でDOMとアクセシビリティツリーを検査する。

完了条件:

- 英語・アラビア語ページの共通UIに日本語固定ラベルがない。
- visible labelとaccessible nameの言語がページ言語と一致する。
- 未対応言語でもコンポーネントが壊れず、fallbackを説明できる。

#### 2.2 ページメタデータを正しく出力する

実施内容:

1. `DocLayout`から`MainLayout`へ、Frontmatterのtitleとdescriptionを渡す。
2. サイト表示名、版、ページ名を含むtitle生成規則を定義する。
3. canonical URLを正規のbase URLと現在のパスから生成する。
4. 実在する翻訳・版だけに`hreflang`を出す。
5. Open Graphの最小項目を静的に生成する。
6. 入口、文書、404で異なるメタデータ契約をruntime testで検査する。

完了条件:

- 全文書ページでFrontmatterのdescriptionがHTMLへ反映される。
- 存在しない言語・版のcanonical／`hreflang`を出さない。
- titleとURLがLua、GLFW、sample-docsでサイトを正しく識別する。

#### 2.3 出典と翻訳状態を生成表示へ移す

実施内容:

1. 現在のFrontmatterと将来の進捗マニフェストから取得可能な、source、upstream version、converter version、review status、reviewed hashを整理する。
2. 本文のblock quoteとは別の`SourceStatus`表示を共通UIとして試作する。
3. 定本と翻訳の照合ハッシュが異なる場合だけ再確認通知を表示する。
4. 法的帰属、上流の技術的問題、libxの変換・翻訳問題の報告先を分ける。
5. 既存の各ページにある出典段落は、同じ情報を生成表示できることを確認してから段階的に除去する。

完了条件:

- 出典、版、翻訳状態を本文の手書き引用へ依存せず確認できる。
- block quoteが引用として表示される。
- 出典情報を除去したページでもライセンス帰属が維持される。
- 状態情報の正本をFrontmatterと別マニフェストへ二重入力しない。

### フェーズ3: 技術文書の意味的Markdown拡張

目的:

- 標準Markdownで不足する少数の意味構造を、移植性、静的表示、多言語対応を保って補う。

決定ゲート:

本実装前に、次を比較するADRを作成して管理者の承認を受ける。

- remark directiveを使う方式
- GFM風の追加構文を使う方式
- インポータが直接意味的HTMLを生成する方式
- MDXコンポーネントを明示importする方式

ADRでは、構文の可読性、標準Markdownでの劣化、Astro依存、翻訳差分、生成HTML、アクセシビリティ、ビルド性能を比較する。

最小実装:

1. note、tip、warning、danger
2. definition list／option list
3. source／translation status

後続候補:

4. API entry、signature、stack effect
5. figure、caption
6. code group
7. 数式

実施内容:

1. 構文と生成HTMLをfixtureで固定する。
2. 未知のdirective、必須属性欠落、入れ子違反をビルド時に検出する。
3. UIラベルをページ言語から生成する。
4. 色だけに依存せず、印刷と高コントラストでも種類を識別できるようにする。
5. JavaScriptなしのHTMLへ同じ意味を残す。
6. 外部定本へ適用する場合はインポータで決定的に生成し、翻訳と同じ構造を検査する。

完了条件:

- ADRが承認されている。
- 最小3構造がMarkdownとMDXの両方で同じHTML契約を生成する。
- no-JS、モバイル、印刷、LTR／RTL、支援技術で意味が保たれる。
- サイト固有のimportを各定本ページへ追加しない。
- 未対応Markdown処理系でも、少なくとも本文内容を失わない劣化方法がある。

### フェーズ4: 目次と検索による探索改善

#### 4.1 ページ内目次を内容に応じて表示する

実施内容:

1. 見出しがないページでは目次領域と`data-has-toc`を出さない。
2. ページまたはサイト設定で、目次の最小深さ、最大深さ、表示上限を指定できるようにする。
3. 長い目次を折りたたむか、APIシンボル索引へ切り替える閾値をLuaで計測する。
4. モバイルの「このページの内容」を、本文を押し下げない形で実装する。
5. 現在位置追跡を`IntersectionObserver`で試作し、既存scroll方式と処理時間・安定性を比較する。
6. イベント、observer、DOM差し替え時の解除をテストする。

完了条件:

- 目次なし、通常目次、長大目次がそれぞれ適切なUIになる。
- C APIページで目的のシンボルへ到達できる。
- モバイルでサイドバーまたは目次が本文閲覧を妨げない。
- no-JSでも見出しと通常のアンカーリンクは利用できる。

#### 4.2 サイト別静的検索を試作・導入する

試作範囲:

- Luaの`v5-5-1/en`と`v5-5-1/ja`
- ページtitle、description、見出し、明示アンカー、API識別子
- API識別子の完全一致、見出し一致、本文一致の順の評価

実施内容:

1. 索引生成をサイト・版・言語単位に分離する。
2. 検索操作まで索引と検索コードを遅延読込する。
3. キーボードだけで起動、入力、結果移動、終了できるUIを作る。
4. 存在しない翻訳結果を現在言語の結果として表示しない。
5. 索引ファイル数、非圧縮・圧縮容量、生成時間、初回検索時間を記録する。
6. 全文格納、語彙索引、外部検索ライブラリを比較し、採用方式をADRへ記録する。
7. Luaで予算を満たした後、GLFWとsample-docsへ展開する。

完了条件:

- Luaのページ名、章見出し、`lua_absindex`などのAPI名から正しいURL・アンカーへ到達できる。
- 初期表示で全検索索引を読み込まない。
- 選択的ビルドで対象サイトの索引だけを更新する。
- サイト・版・言語別の索引サイズと生成時間に承認済み予算がある。
- 検索機能が無効または読込失敗でも通常ナビゲーションが使える。

### フェーズ5: 共通レイアウトとスキーマの集約

目的:

- サイト横断修正の反映漏れを防ぎ、新規サイトが設定とコンテンツを中心に構成されるようにする。

#### 5.1 ずれの自動検出

1. テンプレートと生成直後サイトの共通ファイル一覧を宣言する。
2. 意図しない差異をruntime testまたはintegrity checkで検出する。
3. サイト固有差分には理由と所有者を記録する。

#### 5.2 コンテンツスキーマの共有

1. 同一の`content/config.ts`から共通schemaとloaderの責務を抽出する。
2. サイト固有Frontmatter拡張を合成できるfactoryを提供する。
3. Lua、GLFW、sample-docs、test-verification、テンプレートを段階的に移行する。
4. schemaのエラー文が、対象ファイル、項目、期待値を示すようにする。

#### 5.3 レイアウトの共有

1. パッケージ化、Astro layout合成、テンプレート生成・同期の三案を小さい試作で比較する。
2. package boundaryとAstro依存への影響をADRへ記録する。
3. `MainLayout`、`DocLayout`の順に、安定した骨格を共有する。
4. サイト固有の内容は設定、Props、slotで注入し、サイトID条件分岐を共有側へ増やさない。
5. 各サイトのコピーを一度に削除せず、移行済みサイトごとに全ルートを比較する。

完了条件:

- 同じスキーマまたはレイアウト修正を複数アプリへ手作業で複製しない。
- テンプレートから作ったサイトが共有契約を自動的に利用する。
- サイト固有の上書き箇所と理由を列挙できる。
- Lua、GLFW、sample-docs、test-verificationのURL、表示、ビルドが移行前と同等である。
- パッケージ境界のADRが承認されている。

### フェーズ6: 補助機能と成果物最適化

#### 6.1 コードと表

1. コードのcopyを任意の小さい補助機能として追加し、元コードのbyte列を維持する。
2. 言語名、ファイル名、折返し切替は、メタデータがある場合だけ表示する。
3. 表を横スクロール可能な意味的wrapperへ変換する。
4. caption、見出しセル、focus時の操作性を検査する。
5. printとno-JSでは通常の`pre`、`code`、`table`として読めるようにする。

#### 6.2 KaTeXと任意アセット

1. KaTeXの`woff2`、`woff`、`ttf`が必要な対象ブラウザを確認する。
2. `woff2`限定案を互換性、ファイル数、容量で比較する。
3. 数式を使うサイトだけへCSSとフォントを出力する。

1. Luaの通常文書とC APIで、本文幅、1行の文字数、行高、見出し間隔を測る。
2. 英語、日本語、アラビア語、コード、表で比較する。
3. CSS tokenだけを小さく変更し、主観評価とFCP／LCP／CLSを記録する。
4. 実測で改善しない一括変更は採用しない。

完了条件:

## 10. ロールバック方針

- 各フェーズを独立した変更単位にし、後続機能を戻さず個別に取り消せるようにする。
- Lua定本の再生成前に`--check`と`--dry-run`を行い、生成失敗時は既存ファイルを置換しない。
- URLとアンカーは互換性契約とし、表示改善のロールバックでも変更しない。
- 検索は通常ナビゲーションから独立させ、索引生成または読込に問題があれば検索だけを無効化できるようにする。
- 新しいdirectiveを定本へ大量適用する前に、旧Markdownへ決定的に戻せる変換または限定した試行範囲を用意する。
- 共通レイアウト移行中は、未移行サイトの既存経路を維持し、サイトごとに戻せるようにする。
- フォント削減は互換性検査で問題があれば従来形式へ戻し、他の改善と結合しない。
