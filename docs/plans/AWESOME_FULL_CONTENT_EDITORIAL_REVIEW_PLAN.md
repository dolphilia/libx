## 完成ページの編集方針

### タイトルと序文

タイトルは単一H1とし、製品名や主題が分かる簡潔な表記にする。既存の `Awesome <主題>` は自然であれば維持するが、表記を揃えること自体を目的にしない。frontmatterのtitleと本文H1を対応させる。

序文は原則1段落、1〜3文。主題の説明と、実際に何を探せるかを書く。必要な対象範囲や制約も短く含める。単なる「○○の資料や関連プロジェクトを集めました」から、そのリストに固有の内容へ書き直す。全ページに同じ文型を強制しない。短いリストや案内ページでは1文でもよい。descriptionも同じ範囲を説明し、検索結果に適した簡潔な文章にする。

たとえば今回確認したWhisperの内容なら、日本語の序文案は「Whisperによる音声の文字起こしに使えるアプリ、CLIツール、ライブラリ、派生モデルをまとめています。導入の参考になる記事や動画、APIサービスも探せます。」となる。英語版も同じ収録範囲を説明する。これは編集例であり、本文への反映は実行工程で行う。

「最新」「最高」「網羅的」「厳選」「安全」など、根拠のない評価を補わない。原文が古い時点の事実を述べている場合は、その時点や対象版を保ち、現在の事実として書き換えない。

### 本文の基本形

基本形は、タイトル、序文、必要なら短い前提・凡例、H2/H3で分類したリストである。項目はリンク付きの名称と、用途や違いが分かる説明を中心にする。比較表、教材、参考文献主体のページは、その情報構造が有用なら維持する。無理にすべてを同じ箇条書きに変えない。

本文の項目と分類順は原則維持する。名称、URL、技術的意味、利用条件、対応環境、警告、数値、否定、比較対象を保存する。上流に説明がない項目へ推測で説明を足さない。説明のない正当な項目は、欠落した翻訳と区別して記録する。

内容確認の基準はその版の固定原文と既存の取得証拠とする。不明な用語やリンクの役割は一次資料で補足確認できるが、最新情報への更新はこの編集作業へ混ぜない。リンク切れを理由に項目を消したり、推測したURLへ置換したりしない。修正が必要なリンクは根拠を別途記録する。

日本語は序文・注意書きを自然なです・ます調、項目説明を簡潔な体言止めまたは常体を基本とし、同一ページの並列項目で揃える。プロジェクト名、API、コマンド、コード、標準化された識別子は維持する。一般的な見出しや「公式サイト」「ソースコード」「デモ」「資料を読む」などの案内は翻訳する。書籍・論文・記事の正式題名は原題を残せるが、その説明は日本語で提供する。英語が残っているだけで未翻訳と判定しない。

### 除く情報と残す情報

| 情報 | 原則 | 例外と確認事項 |
| --- | --- | --- |
| 手動目次、カテゴリへのジャンプ一覧、Back to top | 本文から除く。ON THIS PAGEを使う | 概念の説明や外部資料の一覧まで目次扱いしない。深い見出しは階層またはtoc設定を確認 |
| スポンサー、寄付、広告、作者の別製品の宣伝 | 誘導ブロックを除く | 有料製品や作者自身の製品でも、通常の収録項目として主題に適合するものは残す |
| コントリビューター一覧、謝辞、投稿方法、行動規範 | リスト運営の案内として除く | 収録対象の選定条件、教材の著者名、帰属表示に必要な情報は該当箇所や出典欄へ残す |
| リスト自体のLicense節、ライセンス画像 | 本文から除き、Libxの出典・ライセンス欄へ集約 | 既存の証拠・通知・必要な帰属がそこで確認できることを先に検証する |
| 個々の項目のライセンス、料金、OS、実装言語、制約 | 選択に必要な情報として残す | Selfhostedのライセンス凡例も該当。リスト自体のLicense節とは別物 |
| ロゴ、バッジ、スクリーンショット、GIF、埋め込み動画 | 表示を除く | 画像だけにある有用な内容は文章・表・通常リンクへ置換して保つ |
| 装飾絵文字、顔文字、星、過剰な太字・区切り線・空行 | 除く | 有料・非推奨・外部依存などを表す記号は意味を短いテキストへ変換 |
| Unicodeや絵文字そのものの説明・コード例 | 教材としての内容を保つ | 装飾とは区別。画像はコードポイント、文字名、テキスト例、原資料へのリンクへ置換 |
| コミュニティ、関連リスト、教材や図表へのリンク | 主題の資料として有用なら残す | リスト作者への支援やフォローだけを目的とする誘導は除く |
| 警告、非推奨、メンテナンス状況、収録条件 | 読者に必要な位置へ残す | 古い情報を現在の保証へ変えない。記号を消す際に意味も消さない |

画像を単に `[画像]` や「関連資料です」へ置き換えて完了にしない。内容を損なわずに文字化できない場合は、具体的な不足を記録し、そのページを未完了として個別判断する。画像表示を残すことを自動的な例外にしない。資料としての画像ファイルへの通常リンクは、埋め込み画像とは区別する。

`metadata-only` は「元のリストで何を探せるか」と「Libxには本文を収録していないこと」を簡潔に伝え、原文へ案内する。資料が不足する場合は、既存情報以上の説明を作らない。既存の収録可否やlicenseSourceを翻訳担当の判断で変更しない。

## 例外の判断手順

ページごとに、対象が「資料を選ぶための内容」「リストの運営案内」「出典・帰属」「装飾」「コード・文字等の実例」のどれかを、周辺の文脈と固定原文から判断する。見出し名やキーワードだけで自動削除しない。コードブロック内の `# Show commits of all contributors` のような文字列も、見出しや貢献者節と誤認しない。

1. 読者が資料を選ぶ・理解するために必要なら保持する。冗長なら意味を保って要約する。
2. 必要な意味を画像・記号が担う場合は、文章・表へ置換する。
3. Libxの共通表示と同じ役割なら、情報が共通表示に実在することを確認して本文から除く。
4. 運営案内・宣伝・装飾なら除く。ブロックに混在する有用な条件は救い出す。
5. 根拠が足りなければ保留し、疑問を具体化する。判断可能な別ページは進める。

判断は `keep`、`rewrite`、`remove`、`relocate`、`textualize`、`needs-decision` のいずれかとし、該当ブロック、理由、原文証拠、英日での反映、検証結果を記録する。例外は「このページは特殊」とだけ記録せず、対象範囲と残す意味を明記する。

通常の編集判断はCodexが行う。ユーザーへの確認は、依頼範囲を変更する判断や、証拠を調べても解消できない内容上の選択に限る。ページごとの翻訳承認や全件の人手レビューを必須工程にしない。

## 既存基盤と先に解決する課題

自動目次は [Awesomeルート](../../apps/awesome/overview/src/pages/[version]/[lang]/[...slug].astro) がAstroの見出しを取得し、既定でH2/H3から生成する。デスクトップとモバイルの両方に表示する。ページの `toc` 設定で深さなどを指定できる。ReactのH3/H4、Unicodeの複数H1のようなページは、手動目次の削除と合わせて意味に沿った階層へ調整し、実際の生成HTMLで確認する。

出典は [DocumentProvenance.astro](../../packages/ui/src/components/DocumentProvenance.astro) がlicenseSourceから取得し、原文・ライセンスへのリンクと帰属文を表示する。本文のLicense節を除く前に、該当ページの設定、表示、既存の通知情報を照合する。足りない情報は出典データ・共通表示側へ追加する工程を設ける。ライセンス本文、取得時の証拠、上流の著作権情報は削除対象にしない。

既存の [序文整理計画](AWESOME_DOCUMENT_TITLE_INTRODUCTION_NORMALIZATION_PLAN.md) は序文以降の本文を原則固定し、テンプレートによる序文生成を行った。本計画は本文全体と個別の序文へ対象を広げるため、同計画の本文不変条件・定型文生成規則を今回の工程へそのまま適用しない。旧計画と実績は履歴として保持する。

再import差分の既存記録では、旧版241件、新版242件が停止対象となっている。内訳は旧版で冒頭134件・保持本文107件、新版で冒頭135件・保持本文107件である。この値は既存の `INTRODUCTION_IMPORT_DRIFT.json` の記録値であり、今回の再実行結果ではない。**先にimportやpublishを実行して現在の本文を上書きしてはいけない。**

既存の [翻訳検査](../../scripts/importers/awesome/validate-awesome-translation.mjs) は英日間の見出し階層、リスト構造、URL順序、コード等を比較するが、正しい意味や自然さを保証しない。また、英日で同じ項目を誤って消しても対応検査だけでは検出できない。新工程では「編集前からの内容保全」と「編集後の英日対応」を別々に検証する。

## Codexによる実行体制と成果物

GPT-6.1 Solを計画進行・編集・翻訳・レビューの標準とする。実行時に利用可能なモデル名を確認し、実際に使用したモデルを記録する。選べない場合はその制約を報告し、ローカルLLMへ自動で切り替えない。Ollama、ローカル翻訳モデル、従来のLLM呼び出し翻訳スクリプトは今回の工程では使用しない。ファイル列挙、差分比較、AST解析、ハッシュ計算、ビルドには通常のローカルスクリプトを使う。

進行担当は作業台帳から未完了ページを選び、Codexが編集する。同じCodexでレビューする場合も、編集を終えてから、原文と成果物を読み直す別のパスを必須にする。ここでの「レビュー済み」はAIによる内容レビューであり、`human-reviewed` と記録しない。機械検査の合格とも区別する。

実行時に以下を追加する。名称は新設予定であり、現時点では存在しない。

| 成果物 | 保存先と役割 |
| --- | --- |
| 全件台帳と進捗 | `docs/notes/document-import/awesome/editorial/INVENTORY.json`。版、sourceId、owner、slug、英日パス、収録種別、ハッシュ、担当、状態 |
| 編集規則と用語 | 同ディレクトリの `EDITORIAL_GUIDE.md` と `TERMS.json`。本計画を実務用に具体化し、例外例を収録 |
| ページ別の判断とレビュー | 同ディレクトリの `<version>/<sourceId>.json`。段落・項目対応、除外理由、保留、編集とレビューの実行記録、検査証拠 |
| 再現用編集データ | 同ディレクトリの `overlays/<version>/`。入力ハッシュに結び付けた差分と、その適用順序 |
| バッチ履歴と引継ぎ | 同ディレクトリの `WORK_LOG.md`。対象、結果、問題、次の未完了ID、再開手順 |

作業単位は `snapshot + sourceId` の英日1組。台帳で実ファイルとroute manifestを突き合わせ、欠落、重複、孤立ファイルを検出する。機械検出の警告がないページも全件台帳に含める。

状態は `inventoried → classified → edited-en → translated-ja → content-reviewed → verified` とする。根拠不足は `needs-decision`、検査や再現に失敗したものは `blocked`、入力や出力のハッシュが変わったものは `stale` にする。変更のないページも本文を読み、変更不要の理由と確認ハッシュを残してからverifiedにする。中断時は最後の完了段階を保存し、再開時にハッシュを再照合する。

## 実行工程と完了条件

### フェーズ0 全件棚卸し

実ファイル、両版のロック、content map、route manifest、所有子設定を照合する。全文・案内・入口を分類し、ページの長さ、表・HTML・RST由来構文、画像、手動目次、広告候補、英語残存、テンプレート置換候補、見出し異常を記録する。検出は優先順位付けに使い、合否や削除の確定には使わない。

作業開始前のGitリビジョン、英日本文ハッシュ、既存検査結果を保存する。既存不具合と今回の回帰を区別する。入力資料が一時ディレクトリにしかないものは、固定コミットと既存ハッシュで復元できるか確認する。

完了条件は、台帳の件数と実ファイルが一致し、全件に処理単位と分類が割り当てられ、未確認のファイルがないことである。

### フェーズ1 編集を失わない再生成経路と検査

現在のGit管理下の本文を編集前の基準として固定する。既存の再import差分をページごとに分類し、上流固定入力から現行本文に至る必要な修正を再現用差分として保持する。本計画の差分はその後段へ適用する。日本語も既存翻訳からの差分と入力ハッシュを保持し、LLMの再呼び出しを再生成の条件にしない。

`固定入力 → 既存修正の再現 → 今回の英語編集 → 公開用英語` と、`固定した既存翻訳 → 今回の日本語編集 → 公開用日本語` を、版ごとに再現できるようにする。日本語成果物には対応する編集後英語のハッシュを持たせる。差分の入力不一致では停止し、曖昧に適用しない。`.tmp` は作業領域とし、そこだけに正本や編集結果を置かない。

既存import、publish、序文正規化、レビュー同期の経路を調べ、個別序文と本文編集が巻き戻らないよう統合する。既存の検査を単純に無効化せず、新しい編集段階を明示して適用先を分ける。既存EXCLUSIONSは履歴として保持し、新判断記録を既存バリデーターが扱えない形式のまま混入させない。

追加する機械検査は、無記録の項目・URL・コード・警告の消失、英日の対応漏れ、リンクとアンカー、画像と装飾の残存、空見出し、frontmatter・検索用説明の不整合、古いレビュー証拠を検出する。HTML表、参照形式リンク、コード、RST由来構文も扱う。正規表現だけで節を削除しない。

内容保全には編集前の全項目へ安定IDを付け、入力ハッシュ、節、項目位置、主リンク、付随リンクを保存する。URLだけでは同一リンクの重複項目を区別できないため、位置も識別に使う。各IDに保持・変更・除外の行先を必ず与え、追加項目も根拠を要求する。英日で同じ項目を消した場合や、リスト以外の段落・表の意味欠落も確認対象にする。

警告記号の文字化はコードの改変とは分ける。たとえばSelfhostedのインラインコード内の警告記号を英語と日本語で別のテキストにすると、現行のコード完全一致検査に抵触する。記録済みの表示用トークンだけを対応表で比較し、プログラムのコード・識別子・数値の一致検査は維持する。URL除去も除外ブロックの記録との対応を要求し、英日差分を丸ごと許容しない。

見出し変更では既存アンカーと参照元を列挙する。残す節は必要に応じて従来IDを別名として保ち、削除節への既知のリンクは適切な行先へ更新または除去する。新しい見出しでビルドできただけでは互換性確認済みとしない。

完了条件は、両版の代表入力と小規模な編集fixtureを別の作業領域へ再生成し、期待する成果物と一致し、二度実行して差分が増えず、想定外の入力変更で停止することである。フェーズ2では実際の編集済みパイロット全件でもこの確認を行う。これにより、基盤整備の完了条件が次工程の編集完了へ循環依存しないようにする。

### フェーズ2 多様なページでパイロット

今回調べた最新版10組に、過去版のWhisper・Unicodeの2組を加えた12組を最初の対象とする。棚卸しでRST由来ページや複雑なHTML表がこの集合に含まれない場合は、それぞれ最低1組追加する。単純なページだけで方式を確定しない。

1. 固定原文、現在の英語、日本語を最後まで読む。長文は節単位で分割し、全節を読んだ範囲を台帳に残す。metadata-onlyは転載対象外の本文全体を翻訳・レビュー対象にせず、案内の根拠と案内ページ全体を確認する。
2. 本文を分類し、英語の除外・保持・文字化と個別序文を確定する。
3. 編集後英語に対して日本語を見直す。既存訳を活用しても、未変更箇所を含めて全項目を確認する。
4. 原文と編集後英語の差分、編集後英語と日本語、単独で読んだ日本語の自然さを順にレビューする。
5. 機械検査、該当子アプリのビルド、ローカルAstroプレビューで確認する。

レビュー記録には、原文・英日成果物のハッシュ、確認した節と項目IDの範囲、意味上の指摘と修正内容、残した英語表現の理由、レビュー実行日時・使用モデルを残す。「全文確認済み」の一文だけでは証拠としない。分割した範囲の和がページ全体を覆い、抜けがないことを機械的にも確かめる。出力が途中で省略された読み取りは未読として扱う。

完了条件は、全対象がverifiedになり、12組以上の成果物から編集ガイドと検査を修正できたことである。計画に従った結果が冗長、画一的、意味欠落になるなら、展開前に規則を直す。

### フェーズ3 最新版の全件処理

672組を所有子と難易度で小バッチへ分ける。通常は3〜5組、長大なリストは1組を目安とし、1回で全文を読み切れない場合は節単位に分割する。ページ数だけで負荷を揃えない。Unicodeの意味欠落、Pythonの広告、Selfhostedの未翻訳凡例など、問題が明確なものから優先するが、最終的には警告のないページもすべて処理する。

各バッチで英語編集、日本語、内容レビュー、検査を終えてから次へ進む。長いページは、分割レビュー後に序文・凡例・用語・分類・項目数の全体整合性を再確認する。進行担当はverified件数だけでなく、未着手、レビュー待ち、保留、失効も報告する。

完了条件は最新版672組すべてのverifiedと、無記録の欠落がないことである。所要日数は事前に断定せず、パイロットで得た長さ別の処理実績から見積もる。

### フェーズ4 過去版の全件処理

旧版365組も独立に確認する。入力内容と文脈が同じ箇所は新版の編集判断や訳文を再利用できるが、版別の全項目対応と最終確認は省略しない。新しい項目、仕様、説明を旧版へ持ち込まない。旧版固有の情報は旧版の固定原文と照合する。

完了条件は旧版365組がverifiedで、両版合計1,037組の台帳に未着手や保留が残らないことである。

### フェーズ5 全体検証と公開候補の確定

両版のcontent map、routes、localized routes、サイドバー、検索、レビュー証拠を正規の生成経路で更新する。全7子アプリをビルドし、ページの自動目次、出典欄、言語切替、版切替、内部リンクを検証する。代表的な表示確認だけで全件の内容レビューを代替しない。

生成HTMLの全件検査で目次の対象とリンク先、画像残存、出典欄を確認する。実ブラウザーでは全7子アプリ・両言語・両版をカバーするサンプルに加え、H1/H3/H4の修正、長大な表、metadata-onlyなどの例外をデスクトップとモバイルで確認する。見つかった共通不具合は同じ構造を持つ全ページへ検査を広げる。

次のコマンドは既存の確認手段である。実行時にはフェーズ1の整合化を先に完了し、両版に対して実施する。新設検査のコマンド名は実装時に台帳へ記録する。

```bash
pnpm awesome:validate-records --snapshot=v2026-08-23
pnpm awesome:validate-canonical --snapshot=v2026-08-23
pnpm awesome:validate-translation --snapshot=v2026-08-23 --require-complete
pnpm awesome:publish --snapshot=v2026-08-23 --check
pnpm awesome:audit-machine --snapshot=v2026-08-23 --check
pnpm build:selective --projects=awesome/web
pnpm build:selective --group=awesome
```

上記の `v2026-08-23` を `v2026-08-20` に替えた検査も行う。`awesome:publish` は公開用ファイルの生成器であり、Cloudflareへのデプロイを意味しない。バッチでは影響子を、最終段階ではグループ全体をビルドする。基盤変更時は関連するruntime/unitテストと、共有パッケージを使う複数アプリも確認する。

ローカル検証の完了と外部公開は別状態で記録する。この依頼で行うのは計画書までであり、外部公開は実行しない。将来公開する場合も統合Cloudflare Pagesを使用し、Workersは開発・検証を含め使用しない。公開時には、その時点のユーザー指示に従って公開候補の差分と検証結果を提示する。

## 受け入れ基準と中断からの復帰

各ページは次をすべて満たしてverifiedとする。

- 全文収録ページは固定原文・英語・日本語の全節と全項目を確認し、未読部分がない。metadata-onlyは案内の根拠と英日案内全文を確認している。
- 序文が主題と実際の収録範囲を説明し、本文とdescriptionが整合する。
- 手動目次、広告、不要な運営案内、埋め込み画像、装飾を除き、必要な意味を失っていない。
- 項目、主要リンク、利用条件、数値、コード、教材例の変更には根拠と判断記録がある。
- 日本語の意味欠落、汎用文による代替、説明ラベルの未翻訳、不自然な訳が未解決で残らない。
- 見出し、アンカー、表、参照リンク、自動目次、出典表示が機能する。
- 再生成した内容が一致し、英日対応・内容保全の検査と現在のハッシュに対するAI内容レビューが合格している。

既存の `human-reviewed` や自動証拠レビューの記録から、今回の内容レビュー済み状態をコピーしない。文言修正後は対象ページのレビューを失効させ、見出し・URL変更なら参照元のリンク検査もやり直す。

判断不能や検証失敗は対象ページと依存バッチだけを止め、他の作業は継続する。中断時は確定した英日差分、未解決点、検査結果、次の処理IDを保存する。ロールバックは当該バッチの本文と編集データ・生成物・状態記録を対応させて戻し、既存のユーザー変更や他バッチを巻き戻さない。

全件完了は1,037組すべてのverified、未解決0件、両版の再生成一致、全7子アプリの検証完了で判定する。対象件数が開始時から変わった場合は、理由と追加・削除の根拠を明記して分母を更新する。集計上の除外によって未処理ページを隠さない。
