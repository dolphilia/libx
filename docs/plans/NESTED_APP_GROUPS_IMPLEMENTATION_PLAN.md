# 入れ子型アプリグループの実装・Awesome移行計画

- 作成日: 2026-09-05
- ステータス: 基本実装・Awesome移行・品質CI・Pagesプレビュー検証済み。独立Workersの外部検証は未完了、本番切替は未実施。
- 採用根拠: ユーザーによる一段の入れ子案の採用指示
- 対象: アプリ検出、設定、CLI、共通閲覧UI、出力統合、CI、Awesome移行
- 関連調査: [大規模ドキュメント調査](../notes/AWESOME_AND_LARGE_DOCUMENT_SCALING_RESEARCH.md)
- 根拠原則: [libx正式原則](../spec/PROJECT_PRINCIPLES.md)

## 1. 目的と完了の定義

`apps/<group>/<project>/`を正式にサポートし、独立した子アプリを一つの閲覧サイトとして表示する。グループ所属はディレクトリ構造から推論し、文書・翻訳・設定・出典の正本をファイルで管理する。従来の`apps/<project>/`も継続して利用できるようにする。

基本実装の完了は、単独アプリと入れ子アプリが混在する状態で、個別／グループ／全体ビルド、グループのナビ・検索、既存URLの保持、Awesomeの移行、通常の品質ゲートが成立した時点とする。実装完了と本番切替完了は別々に記録する。

独立デプロイは後続段階として計画する。初期段階の統合Pages配信では「変更appだけのビルド」を実現するが、「変更appだけの独立した公開」まで実現したとは扱わない。

## 2. 採用する構造と対象外

```text
apps/
├── awesome/
│   ├── group.config.jsonc
│   ├── README.md
│   ├── overview/
│   │   ├── package.json
│   │   ├── astro.config.mjs
│   │   └── src/
│   ├── web/
│   │   └── ...
│   ├── languages/
│   │   └── ...
│   └── data/
│       └── ...
├── lua/
│   ├── package.json
│   └── src/
└── glfw/
    └── ...
```

子アプリ名と分割数は例示であり、Awesomeの内容・容量の棚卸し後に確定する。

- グループは`group.config.jsonc`で識別する。親にはアプリの`package.json`、`astro.config.mjs`、`src/`を置かない。
- アプリは`package.json`と正規のプロジェクト設定など既存の必須構造で検証する。
- グループ内の直下アプリだけをメンバーとする。グループの再入れ子は認めない。
- グループ設定とアプリ必須ファイルが同じ階層にある場合はエラーとする。
- README、生成用ディレクトリ等をアプリと誤検出しない。アプリを装った不完全なディレクトリは黙って無視せず診断する。
- シンボリックリンクで所属を表現しない。対象パスがリポジトリ外へ逃げる構造は拒否する。
- 複数グループへの所属、任意階層、R2必須化、リクエスト時のMarkdown変換、本文のSPA化、一リスト一appの強制は今回の対象外。

平坦案は移行コストが小さいが、直下の増加と所属設定の分離が残る。今回の要件では、所属を構造で表せる入れ子案を採用する。横断的な分類・関連文書集は、将来必要になれば所属とは別の参照機能で扱う。

## 3. 設定・識別子・公開パスの契約

### 3.1 グループ設定

次を初期スキーマ案とする。名称は実装時に既存設定体系と整合させるが、所属を二重管理しないという契約は維持する。

```jsonc
{
  "schemaVersion": 1,
  "name": { "ja": "Awesomeリスト", "en": "Awesome Lists" },
  "entry": "overview",
  "order": ["overview", "web", "languages", "data"],
  "versioning": { "mode": "shared" }
}
```

- IDは親ディレクトリ名、所属は実ディレクトリから導出する。`members`を別途手書きしない。
- `entry`は存在する子アプリ名を一つ指定する。
- `order`は表示順のみを表す。重複・存在しない名前はエラー。未指定メンバーはID順で後置し、隠さない。
- 公開ルートの既定は`/docs/<group>`とし、変更が必要な場合だけ既存paths体系に沿った明示設定を許す。
- `versioning.mode`は`shared`または`independent`。既定は`independent`、Awesomeは`shared`とする。
- グループ名・入口・共通ナビ設定は親が所有する。本文・出典・ページの翻訳状態は子が所有する。
- 言語・版の可用性は各子のページ目録から計算する。group設定から存在しないページを推測しない。
- 設定継承はフィールド単位で規定し、任意の再帰的マージは導入しない。グループの出典設定で子の帰属を上書きしない。

### 3.2 共通アプリ一覧

ファイルシステム探索を一か所へ集約する。Node CLIとAstro設定から利用でき、Astroに依存しないモジュールを既存`packages/project-config`の公開境界に追加することを第一候補とする。TypeScriptの事前ビルドなしで既存Nodeスクリプトから使用できる構成にする。

```text
id             awesome/web
directory      <repo>/apps/awesome/web
groupId        awesome
packageName    apps-awesome-web（package.jsonから取得）
projectSlug    web（パスの一セグメント）
publicBase     /docs/awesome
outputDirectory <repo>/apps/awesome/web/dist
```

単独アプリのIDは従来の`lua`等を維持する。`awesome/web`のような内部IDを、単一セグメント前提の`projectSlug`へ流用しない。package名はIDから毎回推測せず実ファイルから取得し、リポジトリ全体の重複を検査する。新規生成では`apps-<group>-<child>`を候補にし、単独appとの名前衝突時もエラーにする。

CLI入力は共通一覧のIDへ解決してから使い、`../`、絶対パス、曖昧な子名を受理しない。子プロセスはpackage名を引数として渡し、文字列をそのままシェルへ連結しない。設定キャッシュは実ディレクトリをキーにし、同名の子が別グループにいても混線しないことを検証する。

### 3.3 公開出力の所有

物理パスを変えてもAwesomeの既存URLを維持する。

```text
物理位置: apps/awesome/web/src/...
公開URL: /docs/awesome/<version>/<lang>/<category>/<page>/
```

各appは公開パス、所有app、ファイル位置、ハッシュ、サイズ、依存アセットを持つ出力目録を生成する。入口・共通一覧はoverview、本文は各所有app、グループナビ・検索はグループ生成処理が所有する。グループの404・版入口・言語入口の所有者も一つに固定する。

CSS／JSは`/docs/awesome/assets/<child>/...`など所有app別の名前空間を基本とし、共有化は参照とハッシュを確認してから行う。末尾スラッシュ、index表現、URLエンコードを正規化した後で、本文・予約パス・アセットの衝突を検査する。同一内容でも複数所有は原則エラーにし、暗黙の上書きを禁止する。

同じ`baseUrl`を全子へ設定するだけの実装や、結合後HTMLへの広範な文字列置換に依存しない。ビルド時にcanonical・内部リンク・資産URLを正しく生成し、公開パス解決を一元化する。

## 4. 変更対象の棚卸し

以下は着手時の主要対象。各フェーズで`apps/*`、`apps-`、`../../`、固定アプリ配列等を検索し、残存箇所を再点検する。

| 領域 | 主なファイル・処理 | 変更方針 |
| --- | --- | --- |
| workspace | `pnpm-workspace.yaml`、ルート`package.json` | `apps/*/*`を追加し、dev/build/previewのfilterも子を対象にする |
| 設定 | `packages/project-config`、`scripts/global-defaults.js` | 共通一覧、root解決、グループ設定、内部IDと公開パスの分離 |
| 検出・一覧 | `packages/landing/src/project-detector.ts`、`projects-loader.ts`、`project-url.ts` | 共通一覧を使い、所属appのカードをグループ一件へ集約 |
| ビルド・統合 | `build-integrated.js`、`build-selective.js`、`selective-output.js` | 目録による所有パスの統合・置換・削除 |
| 索引・ナビ | `build-sidebar*.js`、`build-search-index.js` | 対象appの生成とグループ集約を分離 |
| 管理CLI | `create-project.js`、`create-document.js`、`create-version.js`、`add-language.js`、`document-utils.js` | 階層に依存せず対象を解決し、dry-runも対応 |
| 同期・検査 | `sync-docs-layouts.js`、`sync-service-workers.js`、`validate-repository-integrity.js`、`validate-category-structure.js` | 共通一覧と契約で検査し、親をアプリ扱いしない |
| UI | 正規テンプレート、`packages/ui`、`packages/versioning` | 所有appと閲覧グループを区別、グループ目録で遷移先解決 |
| Awesome | `scripts/importers/awesome/`、専用ルート・生成目録 | 固定`apps/awesome`参照を廃止し、分割先への生成を一本化 |
| CI・検証 | `.github/workflows/`、runtime/smoke/performance | 入れ子の追跡生成物、単独ビルド、グループ出力、成果物再利用 |

アプリ内のprebuild、Astro plugin import、tsconfigのextends、CSS、public資産、プロジェクト推定も相対パス監査対象にする。深さの数だけ`../`を増やす方針を既定にせず、workspaceパッケージの公開APIまたは共通root解決を使う。設定ファイル自身を起点とする正当な相対参照は維持できる。

## 5. グループ閲覧の実装契約

各子から本文を横断importせず、ページ目録だけを集約する。目録には公開URL、安定した文書ID、所有app、版、言語、カテゴリ、表示名、検索メタデータ、翻訳可用性を持たせる。ナビ・検索のschemaVersionを検査し、不足目録を黙って欠落扱いにしない。

- トップページはグループ一件を表示する。所属appを重複掲載せず、単独appは現状を維持する。
- ヘッダー・ホーム・パンくずはグループの文脈を使う。本文・目次・出典は所有appの文脈を使う。
- 大規模ナビは共有JSONを取得し、初期HTMLには現在地、局所ナビ、静的一覧へのリンクを残す。全体ナビを各HTMLへ複製しない。
- 検索は版・言語内でグループ全体を対象とする。Awesomeの既存メタデータ検索を無断で全文検索へ変えない。分割索引でも全体の検索漏れ・順位・重複を検査する。
- `shared`では子が宣言する版の対応を検査し、新版は対象メンバーの成果物が揃ってから公開目録へ載せる。文書が特定版に存在しないことと、生成物の欠損を区別する。
- `independent`では現在のappの版選択を維持し、無関係な版番号を共通化しない。
- 言語／版切替は文書IDとページ目録から解決する。欠落時は適切な一覧へ誘導し、別言語を同言語として表示しない。
- 前後リンク、内部リンク、出典、canonical、404、アクセシビリティを横断で検証する。
- Service WorkerとCacheStorageはグループ／app／環境の所有範囲を定義し、他appのキャッシュを削除しない。オフライン時にHTMLとナビの不整合から復帰できるようにする。

## 6. ビルド・公開の操作契約

以下は操作契約の例。実装済みかどうかと検証範囲は、各フェーズのチェック項目と実施記録で管理する。

```bash
pnpm build:selective --projects=awesome/web
pnpm build:selective --group=awesome
pnpm create:project --group=awesome web "Web Lists" "Web関連リスト"
```

グループ引数とapp引数は初期版では同時指定不可とし、対象解決後にpackage名・公開所有範囲を表示する。グループIDを既存`--projects`へ曖昧に解釈する互換処理は追加しない。従来の`--projects=lua`は維持する。

CLIはrootやapp内などcwdによらず同じ対象を解決する。グループ追加の生成操作も用意し、手動作成時と同じスキーマ・必須構造に収束させる。

| 変更 | 必要な処理 |
| --- | --- |
| 一子appの本文 | 対象appのビルド・目録生成。目録差分があれば関連索引も更新 |
| タイトル・カテゴリ・URL | 対象app、グループのナビ・検索・ルート、影響する隣接／参照元 |
| 所属・表示順 | グループ目録・入口。HTMLに埋め込む情報が変わるappも対象 |
| 共通レイアウト・変換器 | 依存するappを再ビルド |
| 新版・言語追加 | 対象版／言語を持つappとグループ可用性を検証 |
| 子app削除 | 所有目録から旧出力を削除し、参照・ナビ・リダイレクトを更新 |

本フェーズの生成単位は子app。一リストの変更でもその所属appは全体ビルドする。リスト単位の増分変換は別の最適化である。グループ目録の集約で未変更appの本文再ビルドを要求しない。

選択出力は所有目録に従って対象だけを置換する。従来の`dist/docs/<app名>`全消去をグループへそのまま適用しない。ステージで全検証を終えてから切り替え、途中失敗時は既存出力を保全する。

クリーンCIで全体を公開する場合、同じ入力ハッシュに対応する検証済み未変更成果物を復元する。復元できなければ必要appをビルドし、不完全な集合で公開しない。検証とデプロイで同一artifactを使用し、環境で公開設定が異なる場合は設定別に一度生成する。

## 11. 実行順序と移行判定

フェーズ番号だけで作業を進めず、次の境界で成果物を確認する。既存の実装途中の変更はこの順序に沿って検証し、未完了の項目を完了扱いにしない。

| 境界 | 必要な成果物・証拠 | 次へ進む条件 |
| --- | --- | --- |
| 基盤導入 → 実データ移行準備 | 共通一覧・CLI・テンプレートと小規模グループの検証結果 | 単独appを維持し、子単独・グループ・全体の対象が一致する |
| 生成器対応 → ファイル移動 | 全sourceIdの所有割当、生成器のcheck、出典・翻訳検査 | 旧配置でも結果が変わらず、未知の取得元・所有先違反で停止する |
| ファイル移動 → 統合検証 | 移行前後の全件照合、各子の出力目録 | 本文・出典・URL・本文アンカーの意図しない差分がゼロ |
| 統合検証 → 公開準備 | CI成果物、ブラウザー検証、性能比較、復旧用成果物 | キャッシュなしでも完全生成でき、失敗時に従前の出力を保持する |
| 統合公開 → 独立公開の判断 | 公開処理だけの所要時間・転送量・失敗記録 | ビルド短縮後も公開コストが問題として残り、運用増加に見合う |

変更は各境界でレビュー可能な差分に分ける。ファイル移動と本文改訂、Cloudflare構成変更を一つの差分へ混在させない。工数はAwesome専用生成器の固定パス監査と小規模試作の完了後に見積もり直す。未検証の段階で一括移行の日程や削減率を固定しない。

### 11.1 Awesomeの初期分割と一リスト単位の扱い

[分割候補の棚卸し](../notes/nested-app-migration/partition-inventory.json)に基づき、初期候補は `overview`・`web`・`languages`・`systems`・`science`・`creative`・`community` の7子とする。[全子の個別計測](../notes/nested-app-migration/partition-build-comparison.json)で時間・最大RSS・出力容量を確認し、この7子を初期構成として確定した。各1回の標本値であり性能上限の保証にはしない。第2節の構造例にある `data` は一般的な例示であり、確定した移行先ではない。

一リストの独立ビルドが必要になった場合は、そのリストを同じグループ直下の専用子appへ切り出せる設計とする。例えば `apps/awesome/web/` にある特定取得元を `apps/awesome/react/` へ移し、公開URLを保持する。`apps/awesome/web/react/` のような再入れ子は導入しない。

少数の子にまとめる初期構成では、一リスト変更時も所属子全体が生成単位になる。すべてのリストを個別ビルド可能にする場合は、子app数を増やすか、別途リスト単位の増分変換を実装する必要がある。まず更新頻度・負荷の高い取得元だけを専用子にすることで、管理量と再生成コストを調整する。

取得元から子への割当は [awesome-source-owners.json](../../config/awesome-source-owners.json) を正本とする。表示カテゴリ、版、翻訳言語、出典ロックはそれぞれの役割を維持する。新規取得元の無指定フォールバックを禁止し、割当変更時は旧所有者の残存本文・出力も検査する。

### 11.3 独立配信の設計を確定する前の確認

Cloudflare Pagesのモノレポ対応は、同じリポジトリから複数のプロジェクトを構成できる仕組みである。これだけでは一つの公開パスへ自動統合されないため、libxのグループ表示・URL所有と公開先の振り分けは別に設計する。[公式Monorepos資料](https://developers.cloudflare.com/pages/configuration/monorepos/)

Workers Static AssetsはWorkerからアセットbindingを通じて取得できる。子ごとの配信先と入口Workerを組み合わせる案では、子への接続、パス保持、404、キャッシュ、リリースの整合性を小規模プレビューで検証してから採用する。これは本計画の設計候補であり、入れ子採用に伴って自動的に配信方式を変更するものではない。[公式Static Assets設定資料](https://developers.cloudflare.com/workers/static-assets/binding/)

公式資料の確認日は2026-09-05。フェーズ7の着手時には料金・上限・ルーティング仕様を再確認し、その時点の設定と検証結果を記録する。

子appの単独ビルドと、グループ全体を閲覧するプレビューを分けて用意する。子appの開発サーバーだけでは他の子の本文を提供できないため、通常のグループ閲覧確認には統合出力のプレビューを使う。開発時の振り分けサーバーは、統合プレビューの待ち時間が問題になる場合の追加機能とする。
