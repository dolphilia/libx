# ADR-0001: libxの正式原則を採用する

- ステータス: 承認
- 日付: 2026-08-11
- 提案者: リポジトリ管理者
- 承認者: リポジトリ管理者
- 置換対象: `docs/notes/PROJECT_PRINCIPLES.md`
- 置換元: なし

## 背景

libxには開発原則の改訂案と、リポジトリ調査から作成したコンセプト・方向性の草稿が存在していた。しかし、文書の位置、主要用語、翻訳構造、性能評価、選択的ビルド、互換性、ADR運用、原則違反の自動検出範囲が未確定だった。

今後の設計・実装判断に共通して使用できる正式原則と、その判断履歴を残すADR運用を確立する必要がある。

## 決定

次を決定する。

1. 既存の原則文書を、`docs/spec/PROJECT_PRINCIPLES.md` の正式原則へ置き換える。
2. 文書の追加・編集・翻訳・レビュー・公開を担う役割の総称を「管理者」とする。
3. 全言語で可能な限り同一構造を目指すが、システムはやむを得ない欠落を許容する。
4. 性能では、実際にブラウザでページを開いたときの表示時間を最重要指標とする。本番測定を優先し、ローカル測定では類似ジェネレーター、静的HTML、変更前のlibxなどとの相対比較を行う。
5. 選択的ビルドの保証単位はサイトとする。サイトが恒常的に重い場合は分割の兆候として扱う。
6. リポジトリ内で使用されていない古いAPI、設定形式、互換コードは廃止してよい。
7. ADRは `docs/adr/` に保存し、連番、共通テンプレート、管理者承認を用いる。
8. 原則違反の自動検出は、ディレクトリ、ファイル、設定、リンク、生成物など明確に測定できる範囲に限定する。

## 判断理由

- 正式原則を仕様として配置することで、調査メモや作業案と区別できる。
- 「管理者」は、実際の運用責任を執筆だけに限定せず表現できる。
- 同一言語構造は管理を単純にするが、翻訳進捗や言語固有事情による欠落は現実に発生する。
- 読者が体感する表示時間が、表示性能の最終的な価値である。
- サイト単位の境界は理解・検証・復旧が容易であり、過度に複雑な文書単位増分処理を避けられる。
- 未使用の互換コードを残さないことで、設定と実装の理解コストを抑えられる。
- 自動検出を客観的な項目へ限定することで、形式的な規則が設計判断を誤って代替することを防げる。

## 検討した代替案

### 既存原則と新草稿を併存させる

- 利点: 移行作業が少ない。
- 欠点: どちらが正本か不明確になり、内容の不一致が拡大する。
- 採用しなかった理由: 一つの正式な判断基準が必要なため。

### 文書・言語単位の増分ビルドを正式な保証にする

- 利点: 巨大サイトの一部変更を高速化できる可能性がある。
- 欠点: 依存関係、キャッシュ、生成物整合性が複雑になり、管理・復旧コストが増える。
- 採用しなかった理由: サイト分割の方がlibxの独立ビルド構造と整合し、境界も明確なため。

### すべての原則を自動検出する

- 利点: レビュー負担を減らせる可能性がある。
- 欠点: 可読性や管理者体験のような文脈依存の判断を、粗い形式規則へ変えてしまう。
- 採用しなかった理由: 客観的に測定できる項目と人が判断する項目を分けるため。

## 影響

### 良い影響

- 原則の正本と参照先が明確になる。
- 性能、ビルド境界、互換性に関する判断が一貫する。
- 重要な判断を後から追跡できる。

### 悪い影響・トレードオフ

- 単一サイトが巨大化した場合、文書単位増分生成ではなくサイト分割を検討する必要がある。
- 外部利用が確認されていない旧APIは、長期互換性より保守性を優先して削除される。

### 影響する範囲

- リポジトリ全体の設計、実装、文書、レビュー、運用

## 移行方法

- 旧 `docs/notes/PROJECT_PRINCIPLES.md` を削除する。
- 正式原則を `docs/spec/PROJECT_PRINCIPLES.md` に配置する。
- 文書内の「作者」を、役割定義に従い「管理者」へ改める。
- `docs/adr/` とテンプレートを追加し、文書索引と既存参照を更新する。

## 検証方法

- 旧原則と草稿への参照が残っていないことを検索する。
- 正式原則に8件の決定が反映されていることを確認する。
- ADRの保存場所、テンプレート、承認手順が相互にリンクされていることを確認する。
- Markdown差分に構文上の不整合がないことを `git diff --check` で確認する。
