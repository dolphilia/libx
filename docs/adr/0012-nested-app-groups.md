# ADR-0012: 一段の入れ子型アプリグループを採用する

- ステータス: 承認
- 日付: 2026-09-05
- 提案者: リポジトリ管理者・Codex
- 承認者: リポジトリ管理者（会話で入れ子案を採用し、実装計画全体の実行を指示）
- 置換対象: なし（従来の単独アプリを維持し、グループを追加）
- 置換元: なし

## 背景

Awesomeは一つの閲覧サイトとしての利便性がある一方、単一アプリの生成が重くなった。各リスト群を平坦なapps直下へ増設すると、管理者が見通すディレクトリ数が増える。ファイルを正本とし、構造から所属を推論し、アプリ単位に処理を分離するlibxの原則を維持したい。

## 決定

`apps/<group>/<project>/`を一段だけサポートする。グループ親は`group.config.jsonc`を持ち、Astroアプリを兼ねない。入口も子アプリとする。従来の`apps/<project>/`は維持する。

所属はディレクトリ配置を正本とし、設定に同じメンバー一覧を持たせない。設定は表示名、入口、順序、共通版の扱い等を表す。内部アプリID、package名、公開URLは分離する。Awesomeの既存公開URLを保持する。

各子は本文を独立生成する。軽量目録からグループのナビ・検索・公開ルートを組み立て、全本文を再集約してビルドしない。大規模ナビは共有データとして取得し、静的な一覧へのno-JS経路を残す。出典は各文書を所有するアプリの情報を用いる。

共通アプリ検出・パス解決を一元化し、管理CLI、検査、ビルド、一覧表示で使う。通常の単独アプリを変更なしで利用できることを互換性条件とする。

## 判断理由と代替案

平坦appsと別のグループ定義は導入しやすいが、直下の増加と所属定義の分離が残る。任意階層は探索・命名・設定を複雑にするため採用しない。一段の入れ子は安定した所属をファイル構造で示せる。横断的な複数分類は将来別機能として扱う。

R2への移行やリスト単位の増分変換は必須にしない。まず子アプリ単位の静的生成と既存統合配信を成立させる。独立配信は後続段階で要件・実測に応じて検証する。

## 影響

workspace、固定階層の相対パス、出力先、管理CLI、CIを改修する。グループ移動にはディレクトリ移動が必要になる。共有目録の変更は関連索引や参照元へ波及するため、app分割だけで全ての更新が独立するわけではない。

ADR-0003の設定正本を維持し、グループ情報を追加する。ADR-0008の検索範囲をグループ所属時にはグループ・版・言語へ拡張する。ADR-0009のテンプレート同期はナビ供給の拡張点を通して適用する。ADR-0011の出典ロック正本は保持し、生成先を各所有アプリへ分ける。

## 移行・検証・復旧

[実装計画](../plans/NESTED_APP_GROUPS_IMPLEMENTATION_PLAN.md)に従い、検出、CLI、公開目録、UI、選択統合、Awesome移行の順に進める。移行前の本文ハッシュ・出典ID・全URLを保存し、移動時に本文編集や翻訳を混ぜない。

単独／入れ子の混在、同名子、設定不正、公開パス衝突、個別ビルド、グループ検索、版・言語欠落、失敗時保全を検証する。旧公開artifactと移行前Git状態を保持し、設定・生成器・本文配置を一組で復旧する。
