<div class="contents rapidjson-document">&#10;<div class="textblock"><p><a class="anchor" id="autotoc_md67"></a></p>&#10;<p>This section records some design and implementation details.</p>&#10;<h1 class="doxsection"><a class="anchor" id="Architecture"></a>&#10;Architecture</h1>&#10;<h2 class="doxsection"><a class="anchor" id="autotoc_md68"></a>&#10;SAX and DOM</h2>&#10;<p>The basic relationships of SAX and DOM is shown in the following UML diagram.</p>&#10;<div class="image">&#10;<img src="/docs/rapidjson/assets/v1-1-0/architecture.png" alt="">&#10;<div class="caption">&#10;Architecture UML class diagram</div></div>&#10;    <p>The core of the relationship is the <span class="tt"><a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/047-classrapidjson_1_1_handler/" title="Concept for receiving events from GenericReader upon parsing. The functions return true if no error o...">Handler</a></span> concept. From the SAX side, <span class="tt">Reader</span> parses a JSON from a stream and publish events to a <span class="tt"><a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/047-classrapidjson_1_1_handler/" title="Concept for receiving events from GenericReader upon parsing. The functions return true if no error o...">Handler</a></span>. <span class="tt">Writer</span> implements the <span class="tt"><a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/047-classrapidjson_1_1_handler/" title="Concept for receiving events from GenericReader upon parsing. The functions return true if no error o...">Handler</a></span> concept to handle the same set of events. From the DOM side, <span class="tt">Document</span> implements the <span class="tt"><a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/047-classrapidjson_1_1_handler/" title="Concept for receiving events from GenericReader upon parsing. The functions return true if no error o...">Handler</a></span> concept to build a DOM according to the events. <span class="tt">Value</span> supports a <span class="tt">Value::Accept(<a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/047-classrapidjson_1_1_handler/" title="Concept for receiving events from GenericReader upon parsing. Even <span class="tt">Reader</span> and <span class="tt">Writer</span> have no dependencies between them. This provides flexibility to chain event publisher and handlers. As shown in the above tables, each JSON type contains redundant <span class="tt">kXXXType</span> and <span class="tt">kXXXFlag</span>. This design is for optimizing the operation of testing bit-flags (<span class="tt">IsNumber()</span>) and obtaining a sequential number for each type (<span class="tt">GetType()</span>).</p>&#10;<p>String has two optional flags. <span class="tt">kCopyFlag</span> means that the string owns a copy of the string. <span class="tt">kInlineStrFlag</span> means using <a class="el" href="#ShortString" title="Short-String Optimization">Short-String Optimization</a>Short-String Optimization.</p>&#10;<p>Number is a bit more complicated. For normal integer values, it can contains <span class="tt">kIntFlag</span>, <span class="tt">kUintFlag</span>, <span class="tt">kInt64Flag</span> and/or <span class="tt">kUint64Flag</span>, according to the range of the integer. The optimization idea is given as follow. Excluding the <span class="tt">flags_</span>, a <span class="tt">Value</span> has 12 or 16 bytes (32-bit or 64-bit) for storing actual data. Instead of storing a pointer to a string, it is possible to store short strings in these space internally. For encoding with 1-byte character type (e.g. <span class="tt">char</span>), it can store maximum 11 or 15 characters string inside the <span class="tt">Value</span> type.</p>&#10;<table class="markdownTable">&#10;<tbody><tr class="markdownTableHead">&#10;<th class="markdownTableHeadNone">ShortString (Ch=char)  </th><th class="markdownTableHeadNone"></th><th class="markdownTableHeadCenter">32-bit  </th><th class="markdownTableHeadCenter">64-bit  </th></tr>&#10;<tr class="markdownTableRowOdd">&#10;<td class="markdownTableBodyNone"><span class="tt">Ch str[MaxChars]</span>  </td><td class="markdownTableBodyNone">String buffer  </td><td class="markdownTableBodyCenter">11  </td><td class="markdownTableBodyCenter">15  </td></tr>&#10;<tr class="markdownTableRowEven">&#10;<td class="markdownTableBodyNone"><span class="tt">Ch invLength</span>  </td><td class="markdownTableBodyNone">MaxChars - Length  </td><td class="markdownTableBodyCenter">1  </td><td class="markdownTableBodyCenter">1  </td></tr>&#10;<tr class="markdownTableRowOdd">&#10;<td class="markdownTableBodyNone"><span class="tt">unsigned flags_</span>  </td><td class="markdownTableBodyNone"><span class="tt">kStringType kStringFlag ...</span>  </td><td class="markdownTableBodyCenter">4  </td><td class="markdownTableBodyCenter">4  </td></tr>&#10;</tbody></table>&#10;<p>A special technique is applied. Instead of storing the length of string directly, it stores (MaxChars - length). This make it possible to store 11 characters with trailing <span class="tt">\0</span>.</p>&#10;<p>This optimization can reduce memory usage for copy-string. It can also improve cache-coherence thus improve runtime performance.</p>&#10;<h1 class="doxsection"><a class="anchor" id="InternalAllocator"></a>&#10;Allocator</h1>&#10;<p><span class="tt"><a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/005-classrapidjson_1_1_allocator/" title="Concept for allocating, resizing and freeing memory block.">Allocator</a></span> is a concept in RapidJSON: </p><div class="fragment"><div class="line"><span class="keyword">concept </span><a class="code hl_class" href="/docs/rapidjson/v1-1-0/en/02-reference/005-classrapidjson_1_1_allocator/">Allocator</a> {</div>&#10;<div class="line">    static const bool kNeedFree;    <span class="comment">//!&lt; Whether this allocator needs to call Free().</span></div>&#10;<div class="line"> </div>&#10;<div class="line">    <span class="comment">// Allocate a memory block.</span></div>&#10;<div class="line">    <span class="comment">// \param size of the memory block in bytes.</span></div>&#10;<div class="line">    <span class="comment">// \returns pointer to the memory block.</span></div>&#10;<div class="line">    void* Malloc(size_t size);</div>&#10;<div class="line"> </div>&#10;<div class="line">    <span class="comment">// Resize a memory block.</span></div>&#10;<div class="line">    <span class="comment">// \param originalPtr The pointer to current memory block. It allocate but do not free memory. This is suitable for building a DOM tree.</p>&#10;<p>Internally, it allocates chunks of memory from the base allocator (by default <span class="tt">CrtAllocator</span>) and stores the chunks as a singly linked list. When user requests an allocation, it allocates memory from the following order:</p>&#10;<ol type="1">&#10;<li>User supplied buffer if it is available. (See <a class="el" href="/docs/rapidjson/v1-1-0/en/01-guide/04-dom/" title="DOM">User Buffer section in DOM</a>)</li>&#10;<li>If user supplied buffer is full, use the current memory chunk.</li>&#10;<li>If the current block is full, allocate a new block of memory.</li>&#10;</ol>&#10;<h1 class="doxsection"><a class="anchor" id="ParsingOptimization"></a>&#10;Parsing Optimization</h1>&#10;<h2 class="doxsection"><a class="anchor" id="SkipwhitespaceWithSIMD"></a>&#10;Skip Whitespaces with SIMD</h2>&#10;<p>When parsing JSON from a stream, the parser need to skip 4 whitespace characters:</p>&#10;<ol type="1">&#10;<li>Space (<span class="tt">U+0020</span>)</li>&#10;<li>Character Tabulation (<span class="tt">U+000B</span>)</li>&#10;<li>Line Feed (<span class="tt">U+000A</span>)</li>&#10;<li>Carriage Return (<span class="tt">U+000D</span>)</li>&#10;</ol>&#10;<p>A simple implementation will be simply: </p><div class="fragment"><div class="line"><span class="keywordtype">void</span> SkipWhitespace(InputStream&amp; s) {</div>&#10;<div class="line">    <span class="keywordflow">while</span> (s.Peek() == <span class="charliteral">' '</span> || s.Peek() == <span class="charliteral">'\n'</span> || s.Peek() == <span class="charliteral">'\r'</span> || s.Peek() == <span class="charliteral">'\t'</span>)</div>&#10;<div class="line">        s.Take();</div>&#10;<div class="line">}</div>&#10;</div><!-- fragment --><p>However, this requires 4 comparisons and a few branching for each character. This was found to be a hot spot.</p>&#10;<p>To accelerate this process, SIMD was applied to compare 16 characters with 4 white spaces for each iteration. Currently RapidJSON only supports SSE2 and SSE4.2 instructions for this. And it is only activated for UTF-8 memory streams, including string stream or <em>in situ</em> parsing.</p>&#10;<p>To enable this optimization, need to define <span class="tt">RAPIDJSON_SSE2</span> or <span class="tt">RAPIDJSON_SSE42</span> before including <span class="tt"><a class="el" href="/docs/rapidjson/v1-1-0/en/02-reference/154-rapidjson_8h/" title="common definitions and configuration">rapidjson.h</a></span>. Some compilers can detect the setting, as in <span class="tt">perftest.h</span>:</p>&#10;<div class="fragment"><div class="line"><span class="comment">// __SSE2__ and __SSE4_2__ are recognized by gcc, clang, and the Intel compiler.</span></div>&#10;<div class="line"><span class="comment">// We use -march=native with gmake to enable -msse2 and -msse4.2, if supported.</span></div>&#10;<div class="line"><span class="preprocessor">#if defined(__SSE4_2__)</span></div>&#10;<div class="line"><span class="preprocessor">#  define RAPIDJSON_SSE42</span></div>&#10;<div class="line"><span class="preprocessor">#elif defined(__SSE2__)</span></div>&#10;<div class="line"><span class="preprocessor">#  define RAPIDJSON_SSE2</span></div>&#10;<div class="line"><span class="preprocessor">#endif</span></div>&#10;</div><!-- fragment --><p>Note that, these are compile-time settings. Running the executable on a machine without such instruction set support will make it crash.</p>&#10;<h3 class="doxsection"><a class="anchor" id="autotoc_md70"></a>&#10;Page boundary issue</h3>&#10;<p>In an early version of RapidJSON, <a href="https://code.google.com/archive/p/rapidjson/issues/104">an issue</a> reported that the <span class="tt">SkipWhitespace_SIMD()</span> causes crash very rarely (around 1 in 500,000). After investigation, it is suspected that <span class="tt">_mm_loadu_si128()</span> accessed bytes after <span class="tt">'\0'</span>, and across a protected page boundary.</p>&#10;<p>In <a href="http://www.intel.com/content/www/us/en/architecture-and-technology/64-ia-32-architectures-optimization-manual.html">Intel® 64 and IA-32 Architectures Optimization Reference Manual</a>, section 10.2.1:</p>&#10;<blockquote class="doxtable">&#10;<p>To support algorithms requiring unaligned 128-bit SIMD memory accesses, memory buffer allocation by a caller function should consider adding some pad space so that a callee function can safely use the address pointer safely with unaligned 128-bit SIMD memory operations. The minimal padding size should be the width of the SIMD register that might be used in conjunction with unaligned SIMD memory access. </p>&#10;</blockquote>&#10;<p>This is not feasible as RapidJSON should not enforce such requirement.</p>&#10;<p>To fix this issue, currently the routine process bytes up to the next aligned address. After tha, use aligned read to perform SIMD processing. Also see <a href="https://github.com/miloyip/rapidjson/issues/85">#85</a>.</p>&#10;<h2 class="doxsection"><a class="anchor" id="LocalStreamCopy"></a>&#10;Local Stream Copy</h2>&#10;<p>During optimization, it is found that some compilers cannot localize some member data access of streams into local variables or registers. Experimental results show that for some stream types, making a copy of the stream and used it in inner-loop can improve performance. For example, the actual (non-SIMD) implementation of <span class="tt">SkipWhitespace()</span> is implemented as:</p>&#10;<div class="fragment"><div class="line"><span class="keyword">template</span>&lt;<span class="keyword">typename</span> InputStream&gt;</div>&#10;<div class="line"><span class="keywordtype">void</span> SkipWhitespace(InputStream&amp; is) {</div>&#10;<div class="line">    internal::StreamLocalCopy&lt;InputStream&gt; copy(is);</div>&#10;<div class="line">    InputStream&amp; s(copy.s);</div>&#10;<div class="line"> </div>&#10;<div class="line">    <span class="keywordflow">while</span> (s.Peek() == <span class="charliteral">' '</span> || s.Peek() == <span class="charliteral">'\n'</span> || s.Peek() == <span class="charliteral">'\r'</span> || s.Peek() == <span class="charliteral">'\t'</span>)</div>&#10;<div class="line">        s.Take();</div>&#10;<div class="line">}</div>&#10;</div><!-- fragment --><p>Depending on the traits of stream, <span class="tt">StreamLocalCopy</span> will make (or not make) a copy of the stream object, use it locally and copy the states of stream back to the original stream.</p>&#10;<h2 class="doxsection"><a class="anchor" id="ParsingDouble"></a>&#10;Parsing to Double</h2>&#10;<p>Parsing string into <span class="tt">double</span> is difficult. The standard library function <span class="tt">strtod()</span> can do the job but it is slow. By default, the parsers use normal precision setting. This has has maximum 3 <a href="http://en.wikipedia.org/wiki/Unit_in_the_last_place">ULP</a> error and implemented in <span class="tt">internal::StrtodNormalPrecision()</span>.</p>&#10;<p>When using <span class="tt">kParseFullPrecisionFlag</span>, the parsers calls <span class="tt">internal::StrtodFullPrecision()</span> instead, and this function actually implemented 3 versions of conversion methods.</p><ol type="1">&#10;<li><a href="http://www.exploringbinary.com/fast-path-decimal-to-floating-point-conversion/">Fast-Path</a>.</li>&#10;<li>Custom DIY-FP implementation as in <a href="https://github.com/floitsch/double-conversion">double-conversion</a>.</li>&#10;<li>Big Integer Method as in (Clinger, William D.&nbsp;How to read floating point numbers accurately. Vol. 25. No. 6. ACM, 1990).</li>&#10;</ol>&#10;<p>If the first conversion methods fail, it will try the second, and so on.</p>&#10;<h1 class="doxsection"><a class="anchor" id="GenerationOptimization"></a>&#10;Generation Optimization</h1>&#10;<h2 class="doxsection"><a class="anchor" id="itoa"></a>&#10;Integer-to-String conversion</h2>&#10;<p>The naive algorithm for integer-to-string conversion involves division per each decimal digit. We have implemented various implementations and evaluated them in <a href="https://github.com/miloyip/itoa-benchmark">itoa-benchmark</a>.</p>&#10;<p>Although SSE2 version is the fastest but the difference is minor by comparing to the first running-up <span class="tt">branchlut</span>. And <span class="tt">branchlut</span> is pure C++ implementation so we adopt <span class="tt">branchlut</span> in RapidJSON.</p>&#10;<h2 class="doxsection"><a class="anchor" id="dtoa"></a>&#10;Double-to-String conversion</h2>&#10;<p>Originally RapidJSON uses <span class="tt">snprintf(..., ..., "%g")</span> to achieve double-to-string conversion. This is not accurate as the default precision is 6. Later we also find that this is slow and there is an alternative.</p>&#10;<p>Google's V8 <a href="https://github.com/floitsch/double-conversion">double-conversion</a> implemented a newer, fast algorithm called Grisu3 (Loitsch, Florian. And in most of cases it produces the shortest (optimal) string representation.</p>&#10;<p>The header-only conversion function has been evaluated in <a href="https://github.com/miloyip/dtoa-benchmark">dtoa-benchmark</a>.</p>&#10;<h1 class="doxsection"><a class="anchor" id="Parser"></a>&#10;Parser</h1>&#10;<h2 class="doxsection"><a class="anchor" id="IterativeParserImplementation"></a>&#10;Implementation</h3>&#10;<p>Based on the parsing table, a direct(or conventional) implementation that pushes the production body in reverse order while generating a production could work.</p>&#10;<p>In RapidJSON, several modifications(or adaptations to current design) are made to a direct implementation.</p>&#10;<p>First, the parsing table is encoded in a state machine in RapidJSON. States are constructed by the head and body of production. State transitions are constructed by production rules. Besides, extra states are added for productions involved with <span class="tt">array</span> and <span class="tt">object</span>. In this way the generation of array values or object members would be a single state transition, rather than several pop/push operations in the direct implementation. This also makes the estimation of stack size more easier.</p>&#10;<p>The state diagram is shown as follows:</p>&#10;<div class="image">&#10;<img src="/docs/rapidjson/assets/v1-1-0/iterative-parser-states-diagram.png" alt="">&#10;<div class="caption">&#10;State Diagram</div></div>&#10;    <p>Second, the iterative parser also keeps track of array's value count and object's member count in its internal stack, which may be different from a conventional implementation. </p>&#10;</div></div>
