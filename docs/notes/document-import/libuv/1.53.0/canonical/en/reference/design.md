<article class="libuv-document" id="furo-main-content" role="main">&#10;<section id="design-overview">&#10;<span id="design"></span><h1>Design overview<a class="headerlink" href="#design-overview" title="Permalink to this heading">¶</a></h1>&#10;<p>libuv is cross-platform support library which was originally written for <a class="reference external" href="https://nodejs.org">Node.js</a>. It’s designed&#10;around the event-driven asynchronous I/O model.</p>&#10;<p>The library provides much more than a simple abstraction over different I/O polling mechanisms:&#10;‘handles’ and ‘streams’ provide a high level abstraction for sockets and other entities;&#10;cross-platform file I/O and threading functionality is also provided, amongst other things.</p>&#10;<p>Here is a diagram illustrating the different parts that compose libuv and what subsystem they&#10;relate to:</p>&#10;<a class="reference internal image-reference" href="/docs/libuv/assets/v1-53-0/architecture.png"><img alt="Picture of libuv architecture" class="align-center" src="/docs/libuv/assets/v1-53-0/architecture.png" style="width: 765.0px; height: 369.75px;"/></a>&#10;<section id="handles-and-requests">&#10;<h2>Handles and requests<a class="headerlink" href="#handles-and-requests" title="Permalink to this heading">¶</a></h2>&#10;<p>libuv provides users with 2 abstractions to work with, in combination with the event loop:&#10;handles and requests.</p>&#10;<p>Handles represent long-lived objects capable of performing certain operations while active. Some examples:</p>&#10;<ul class="simple">&#10;<li><p>A prepare handle gets its callback called once every loop iteration when active.</p></li>&#10;<li><p>A TCP server handle that gets its connection callback called every time there is a new connection.</p></li>&#10;</ul>&#10;<p>Requests represent (typically) short-lived operations. These operations can be performed over a&#10;handle: write requests are used to write data on a handle; or standalone: getaddrinfo requests&#10;don’t need a handle they run directly on the loop.</p>&#10;<p>Guidelines for dealing with handles and requests:</p>&#10;<ol class="arabic simple">&#10;<li><p>If <cite>uv_foo_init()</cite> succeeds in initializing the handle, you must call&#10;<a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/handle/#c.uv_close" title="uv_close"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_close()</span></code></a>. If the handle’s init function errors, you don’t&#10;need to do anything.</p></li>&#10;<li><p>Only handles are closed, not requests. For example, <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/tcp/#c.uv_tcp_t" title="uv_tcp_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_tcp_t</span></code></a>&#10;is a handle, <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/stream/#c.uv_write_t" title="uv_write_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_write_t</span></code></a> is a request.</p></li>&#10;<li><p>The handle’s memory can only be reclaimed or reused from inside the&#10;<a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/handle/#c.uv_close_cb" title="uv_close_cb"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_close_cb</span></code></a> or afterwards, not before.</p></li>&#10;<li><p>Most handles have init + start/stop functions; some handles don’t.&#10;Example: <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/tcp/#c.uv_tcp_t" title="uv_tcp_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_tcp_t</span></code></a> vs. <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/process/#c.uv_process_t" title="uv_process_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_process_t</span></code></a>; <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/process/#c.uv_spawn" title="uv_spawn"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_spawn()</span></code></a>&#10;combines handle initialization and process start into one.</p></li>&#10;<li><p>Requests are closed automatically when they complete, or when they are&#10;cancelled with <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/request/#c.uv_cancel" title="uv_cancel"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_cancel()</span></code></a>.</p></li>&#10;<li><p>No additional cleanup is needed except for <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/fs/#c.uv_fs_t" title="uv_fs_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_fs_t</span></code></a> and&#10;<a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/dns/#c.uv_getaddrinfo_t" title="uv_getaddrinfo_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_getaddrinfo_t</span></code></a> requests. For <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/fs/#c.uv_fs_t" title="uv_fs_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_fs_t</span></code></a>, call&#10;<a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/fs/#c.uv_fs_req_cleanup" title="uv_fs_req_cleanup"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_fs_req_cleanup()</span></code></a> once you are done with it; for&#10;<a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/dns/#c.uv_getaddrinfo_t" title="uv_getaddrinfo_t"><code class="xref c c-type docutils literal notranslate"><span class="pre">uv_getaddrinfo_t</span></code></a>, that’s <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/dns/#c.uv_freeaddrinfo" title="uv_freeaddrinfo"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_freeaddrinfo()</span></code></a>.</p></li>&#10;<li><p>The request’s memory can only be reclaimed or reused from that point onward.</p></li>&#10;</ol>&#10;</section>&#10;<section id="the-i-o-loop">&#10;<h2>The I/O loop<a class="headerlink" href="#the-i-o-loop" title="Permalink to this heading">¶</a></h2>&#10;<p>The I/O (or event) loop is the central part of libuv. It establishes the content for all I/O&#10;operations, and it’s meant to be tied to a single thread. One can run multiple event loops&#10;as long as each runs in a different thread. The libuv event loop (or any other API involving&#10;the loop or handles, for that matter) <strong>is not thread-safe</strong> except where stated otherwise.</p>&#10;<p>The event loop follows the rather usual single threaded asynchronous I/O approach: all (network)&#10;I/O is performed on non-blocking sockets which are polled using the best mechanism available&#10;on the given platform: epoll on Linux, kqueue on OSX and other BSDs, event ports on SunOS and IOCP&#10;on Windows. As part of a loop iteration the loop will block waiting for I/O activity on sockets&#10;which have been added to the poller and callbacks will be fired indicating socket conditions&#10;(readable, writable hangup) so handles can read, write or perform the desired I/O operation.</p>&#10;<p>In order to better understand how the event loop operates, the following diagram illustrates all&#10;stages of a loop iteration:</p>&#10;<a class="reference internal image-reference" href="/docs/libuv/assets/v1-53-0/loop_iteration.png"><img alt="Picture of libuv loop iteration" class="align-center" src="/docs/libuv/assets/v1-53-0/loop_iteration.png" style="width: 343.5px; height: 642.0px;"/></a>&#10;<ol class="arabic">&#10;<li><p>The loop concept of ‘now’ is initially set.</p></li>&#10;<li><p>Due timers are run if the loop was run with <code class="docutils literal notranslate"><span class="pre">UV_RUN_DEFAULT</span></code>. All active timers scheduled&#10;for a time before the loop’s concept of <em>now</em> get their callbacks called.</p></li>&#10;<li><p>If the loop is <em>alive</em>  an iteration is started, otherwise the loop will exit immediately. So,&#10;when is a loop considered to be <em>alive</em>? If a loop has active and ref’d handles, active&#10;requests or closing handles it’s considered to be <em>alive</em>.</p></li>&#10;<li><p>Pending callbacks are called. All I/O callbacks are called right after polling for I/O, for the&#10;most part. There are cases, however, in which calling such a callback is deferred for the next&#10;loop iteration. If the previous iteration deferred any I/O callback it will be run at this point.</p></li>&#10;<li><p>Idle handle callbacks are called. Despite the unfortunate name, idle handles are run on every&#10;loop iteration, if they are active.</p></li>&#10;<li><p>Prepare handle callbacks are called. Prepare handles get their callbacks called right before&#10;the loop will block for I/O.</p></li>&#10;<li><p>Poll timeout is calculated. Before blocking for I/O the loop calculates for how long it should&#10;block. These are the rules when calculating the timeout:</p>&#10;<blockquote>&#10;<div><ul class="simple">&#10;<li><p>If the loop was run with the <code class="docutils literal notranslate"><span class="pre">UV_RUN_NOWAIT</span></code> flag, the timeout is 0.</p></li>&#10;<li><p>If the loop is going to be stopped (<a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/loop/#c.uv_stop" title="uv_stop"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_stop()</span></code></a> was called), the timeout is 0.</p></li>&#10;<li><p>If there are no active handles or requests, the timeout is 0.</p></li>&#10;<li><p>If there are any idle handles active, the timeout is 0.</p></li>&#10;<li><p>If there are any handles pending to be closed, the timeout is 0.</p></li>&#10;<li><p>If none of the above cases matches, the timeout of the closest timer is taken, or&#10;if there are no active timers, infinity.</p></li>&#10;</ul>&#10;</div></blockquote>&#10;</li>&#10;<li><p>The loop blocks for I/O. At this point the loop will block for I/O for the duration calculated&#10;in the previous step. All I/O related handles that were monitoring a given file descriptor&#10;for a read or write operation get their callbacks called at this point.</p></li>&#10;<li><p>Check handle callbacks are called. Check handles get their callbacks called right after the&#10;loop has blocked for I/O. Check handles are essentially the counterpart of prepare handles.</p></li>&#10;<li><p>Close callbacks are called. If a handle was closed by calling <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/handle/#c.uv_close" title="uv_close"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_close()</span></code></a> it will&#10;get the close callback called.</p></li>&#10;<li><p>The loop concept of ‘now’ is updated.</p></li>&#10;<li><p>Due timers are run. Note that ‘now’ is not updated again until the next loop iteration.&#10;So if a timer became due while other timers were being processed, it won’t be run until&#10;the following event loop iteration.</p></li>&#10;<li><p>Iteration ends. If the loop was run with <code class="docutils literal notranslate"><span class="pre">UV_RUN_NOWAIT</span></code> or <code class="docutils literal notranslate"><span class="pre">UV_RUN_ONCE</span></code> modes the&#10;iteration ends and <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/loop/#c.uv_run" title="uv_run"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_run()</span></code></a> will return. If the loop was run with <code class="docutils literal notranslate"><span class="pre">UV_RUN_DEFAULT</span></code>&#10;it will continue from the start if it’s still <em>alive</em>, otherwise it will also end.</p></li>&#10;</ol>&#10;<div class="admonition important">&#10;<p class="admonition-title">Important</p>&#10;<p>libuv uses a thread pool to make asynchronous file I/O operations possible, but&#10;network I/O is <strong>always</strong> performed in a single thread, each loop’s thread.</p>&#10;</div>&#10;<div class="admonition note">&#10;<p class="admonition-title">Note</p>&#10;<p>While the polling mechanism is different, libuv makes the execution model consistent&#10;across Unix systems and Windows.</p>&#10;</div>&#10;</section>&#10;<section id="file-i-o">&#10;<h2>File I/O<a class="headerlink" href="#file-i-o" title="Permalink to this heading">¶</a></h2>&#10;<p>Unlike network I/O, there are no platform-specific file I/O primitives libuv could rely on,&#10;so the current approach is to run blocking file I/O operations in a thread pool.</p>&#10;<p>For a thorough explanation of the cross-platform file I/O landscape, check out&#10;<a class="reference external" href="https://blog.libtorrent.org/2012/10/asynchronous-disk-io/">this post</a>.</p>&#10;<p>libuv currently uses a global thread pool on which all loops can queue work. 3 types of&#10;operations are currently run on this pool:</p>&#10;<blockquote>&#10;<div><ul class="simple">&#10;<li><p>File system operations</p></li>&#10;<li><p>DNS functions (getaddrinfo and getnameinfo)</p></li>&#10;<li><p>User specified code via <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/threadpool/#c.uv_queue_work" title="uv_queue_work"><code class="xref c c-func docutils literal notranslate"><span class="pre">uv_queue_work()</span></code></a></p></li>&#10;</ul>&#10;</div></blockquote>&#10;<div class="admonition warning">&#10;<p class="admonition-title">Warning</p>&#10;<p>See the <a class="reference internal" href="/docs/libuv/v1-53-0/en/reference/threadpool/#threadpool"><span class="std std-ref">Thread pool work scheduling</span></a> section for more details, but keep in mind the thread pool size&#10;is quite limited.</p>&#10;</div>&#10;</section>&#10;</section>&#10;</article>
