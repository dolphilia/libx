# GLFWパイロットから得たlibx実装改善案

- 作成日: 2026-08-11
- 対象: libx本体、サイト生成、外部文書インポート、翻訳検査
- 位置付け: GLFWパイロットから得た改善候補と実装記録。P0は2026-08-11に実装・検証済み。P1以降は引き続き候補であり、この文書自体は実装承認を意味しない。

## 1. 評価基準

改善案は次の順に優先する。

1. 定本や翻訳を失う危険を下げる。
2. 誤った文書を公開する危険を下げる。
3. 次のパイロットで同じ手作業や不具合を繰り返さない。
4. libxの原則である単一設定、言語欠落許容、サイト単位の選択的ビルド、軽量な配信を保つ。
5. GLFW固有の事情を、実証前に共通機能へ過剰一般化しない。

## 2. 優先度P0: 次のパイロット前に対応する

### 2.1 インポータを安全な生成パイプラインにする

実装状況: 完了。共通の安全出力処理とGLFWインポータCLI、失敗時保持・読み取り専用差分・出力境界のテストを追加した。

現状の`scripts/importers/import-glfw-3.5.1.mjs`は、固定された入力・出力パスを使い、既存の英語出力ディレクトリを`rmSync`した後に直接再生成する。途中失敗時に定本が部分生成状態となり、意図しない入力や版へ再利用できない。

改善案:

- `--source`、`--output`、`--check`、`--dry-run`を持つCLI契約を定める。
- 一時ディレクトリへ全件生成し、検査成功後だけ出力を原子的に置き換える。
- 上書き対象を実パスで表示し、リポジトリ外やプロジェクトルートへの逸脱を拒否する。
- 未処理Doxygen命令、変換不能リンク、欠落画像が一件でもあれば置換しない。
- 同じ入力から同じ出力が得られることをハッシュで検査する。
- 翻訳ディレクトリには一切書き込まないことを契約としてテストする。

完了条件:

- 変換途中で例外を発生させても既存定本が変わらない。
- `--check`で差分の有無だけをCIから判定できる。
- 実行前後の対象ファイル一覧とハッシュを記録できる。

### 2.2 翻訳構造・リンク検査を共通化し、Markdown構文木を使う

実装状況: 完了。設定から対象を解決するMarkdown／MDX構文木検査を追加し、0件・部分・全件・余分・壊れたアンカー・表記差のテストを追加した。

`validate-glfw-translation.mjs`と`validate-glfw-links.mjs`はGLFW、`v3-5-1`、英語、日本語、URL形式をハードコードし、正規表現でMarkdownを解析している。今回の検査には有効だったが、入れ子の括弧を含むリンク、別のコードフェンス、MDX要素、参照リンクへ拡張しにくい。

改善案:

- `project.config.jsonc`と対象版・言語からルートを解決する共通コマンドを作る。
- Markdown／MDX構文木とFrontmatterパーサーを使い、コード、リンク、HTMLアンカー、画像、見出しをノード単位で比較する。
- 「全言語で同一であるべき要素」と「翻訳対象要素」を明示的な規則に分ける。
- 途中用の`--allow-missing`と公開前の欠落不可モードを共通機能として維持する。
- 結果を人向け表示とJSONの両方で出力する。

完了条件:

- GLFW固有のパスやライセンスIDなしで36ページの現行検査結果を再現できる。
- 0件、部分翻訳、全件翻訳、余分な翻訳ページ、壊れたアンカーのテストがある。
- Markdown構文の違いを本文の不一致として誤検出しない。

### 2.3 プロジェクト固有検査を通常の`check`へ接続する

実装状況: 完了。サイト任意の`check:content`規約をルートへ接続し、GLFWでは定本差分と共通翻訳・リンク検査を読み取り専用で実行する。

現在、GLFWの構造・内部リンク検査は手動で`node scripts/importers/...`を実行する必要があり、ルート`package.json`の`check`や`apps/glfw/package.json`のスクリプトに含まれない。翻訳後に検査を実行し忘れても通常のCIでは検出できない。

改善案:

- 各サイトが任意の`check:content`を公開できる規約を設ける。
- ルートの整合性検査が対象サイトの`check:content`を発見・実行する。
- GLFWでは構造、内部リンク、未処理命令、ライセンス参照を一つの読み取り専用コマンドへまとめる。
- ビルド前にファイルを書き換える同期処理と、検査処理を分離する。

完了条件:

- `pnpm --filter=apps-glfw check:content`で必要な静的検査がすべて走る。
- ルートCIで翻訳ファイルの欠落、コード改変、壊れた内部リンクを検出できる。
- 検査がソースや生成物を書き換えない。

### 2.4 版ID・スラッグの正規化を設定読込時に検証する

実装状況: 完了。小文字英数字と単一ハイフンの共有検証器を設定、作成コマンド、リポジトリ整合性検査で使用し、正規化・衝突・ディレクトリ不一致を検査する。

`v3.5.1`がAstroで`v351`へ正規化され、ディレクトリと設定を`v3-5-1`へ変更する必要があった。現状はGLFWインポータのコメントと運用ガイドに知識があり、設定スキーマによる強制ではない。

改善案:

- `project.config.jsonc`の版IDとコンテンツディレクトリ名に、安全な文字集合を定義する。
- 入力IDとAstro正規化後IDが異なる場合、設定読込または整合性検査で失敗させる。
- 正規化後の重複、言語名・カテゴリ名との衝突も検査する。
- サイト作成・版追加スクリプトでも同じ検証関数を使う。

完了条件:

- `v3.5.1`のような不安全IDをビルド前に具体的な修正例付きで拒否する。
- 設定、ディレクトリ、生成URLの版ID不一致を検出する。

### 2.5 言語欠落状態を共有UIの回帰テストへ加える

実装状況: 完了。実在ページから言語・版候補を導出し、0件・部分・全件で入口、セレクター、サイドバー、前後移動、不存在リンクを検査する。

日本語が0ページの時、版セレクターへ空の版配列が渡り、ビルドが失敗した。`VersionSelector.astro`は空配列なら描画しないよう修正されたが、0件・部分・全件の状態を保証する自動テストがない。

改善案:

- 翻訳0件、1ページだけ、全件の小さなフィクスチャを作る。
- 版セレクター、言語切替、サイドバー、前後移動、サイト入口を各状態でテストする。
- 対応ページがない言語へ切り替える場合の挙動を仕様化する。黙った本文フォールバックは行わない。
- 欠落状態のビルド成功と、存在しないリンクを生成しないことを回帰テストにする。

完了条件:

- 0件・部分・全件の各フィクスチャがビルドできる。
- 言語・版UIが空配列や欠落ページで例外を投げない。
- 欠落時の利用者向け挙動が文書化されている。

### 2.6 統合成果物へ明示的な404ページを生成する

実装状況: 完了。多言語かつキーボード操作可能な統合`404.html`を追加した。ローカルおよびCloudflare PagesのHTTP状態検査結果は後掲の実装記録に残す。

Production公開後、存在しない`/docs/glfw/__deployment-check-not-found__/`がHTTP 404ではなく、ルートの言語リダイレクトHTMLをHTTP 200で返した。統合`dist/`に明示的な404ページがないため、Cloudflare PagesのSPAフォールバックが働いている。

改善案:

- 統合ビルドで多言語対応の`404.html`を生成する。
- 404ページからトップ、言語別入口、文書サイト一覧へ戻れるようにする。
- 存在しないルート、文書サイト、版、言語、文書の各URLがHTTP 404を返すことをデプロイ前後に検査する。
- 既存ページのクライアント側ナビゲーションやルートリダイレクトを壊さないことを確認する。

完了条件:

- ローカルプレビューとCloudflare Pagesの両方で未知URLがHTTP 404になる。
- 404レスポンスがルートのcanonical URLや言語リダイレクトを誤って返さない。
- 404ページがキーボード操作と主要言語で利用できる。

## 3. 優先度P1: 次の二つのパイロットで整備する

### 3.1 インポート作業一式をスキャフォールドする

今回、記録ディレクトリ、一時領域、チェックリスト、用語表、作業ログを手動で作成した。次回は`create-import-pilot`のようなコマンドで標準構造だけを生成する。

生成対象は文書テンプレートと空の作業領域に限定し、上流形式に固有の判断は埋め込まない。運用メタデータはランタイム設定と混同せず、プロジェクト別の一つのインポートマニフェストへまとめる。libxの公開時設定は引き続き`project.config.jsonc`を正本とする。

### 3.2 進捗と対応表の重複をなくす

README、パイロット計画、対応表、翻訳計画へ進捗数を手書きしたため、14/36や34/36という古い値が残った。英語・翻訳ファイル集合とレビュー状態の一つのマニフェストから、進捗表と要約を生成または検証する。

完了条件は、文書内の進捗数が実ファイル数と異なる場合にCIが失敗することとする。

### 3.3 公開前ブラウザ確認をスモークテスト化する

今回のブラウザ確認は代表4ページを手動で行った。次をサイト共通のPlaywright等のスモークテストとして用意する。

- 入口、各カテゴリ、最大ページ、APIリファレンス、404
- 言語・版切替と欠落時の挙動
- 帰属・変更表示
- コード・表・画像の横方向オーバーフロー
- キーボード操作と主要なアクセシビリティ検査
- コンソールエラーと失敗リクエスト

サイトごとの差は代表URLの宣言だけに留める。

### 3.4 外部リンク検査を内部リンク検査から分離して追加する

現行GLFW検査は内部ページとアンカーだけを対象とし、レビュー表の外部リンク確認は未完である。外部リンクはネットワーク変動を伴うため、通常CIの決定的検査と分ける。

- 通常CI: URL構文、許可プロトコル、英日間の外部URL一致。
- 定期／公開前検査: HTTP到達性、リダイレクト、恒久的な404。
- 一時障害と恒久障害を区別し、結果をキャッシュする。

### 3.5 上流更新の差分取り込みを設計する

今回のインポータは3.5.1の全英語定本を再生成するが、将来版でどの原文ページが変わり、どの翻訳を再照合すべきかを追跡できない。

改善案:

- 上流ファイルと生成ページの対応、入力ハッシュ、変換器版を記録する。
- 新版取得時に追加、変更、削除、移動、アンカー変更を報告する。
- 変更された英語ページに対応する翻訳だけを「再照合必要」にする。
- 手修正した定本と再生成結果の差分を明示し、無言で上書きしない。

## 4. 優先度P2: 複数パイロット後に判断する

### 4.1 共通の来歴・レビュー状態スキーマ

ページ単位の上流URL、入力ハッシュ、変換器版、翻訳状態、最終照合日には価値がある。ただしFrontmatterへ項目を増やすと全サイトへ恒久的な負担を課す。次の異なる形式のパイロットでも必要性を確認し、Frontmatter、サイドカーマニフェスト、生成レポートのどこを正本とするかADRで決める。

### 4.2 上流形式別アダプターを持つ共通インポータ基盤

Doxygenのアンカー、`@snippet`、グループHTML変換は再利用可能だが、他形式へそのまま適用できない。まず共通部分を「取得物検証」「安全な出力」「Markdown検査」「差分報告」に限定し、Doxygen変換はアダプターとして残す。二つ以上の上流形式で共通性を確認してからAPIを固定する。

### 4.3 規範表現・重点レビュー支援の一般化

`report-glfw-translation-review-hotspots.mjs`はmust、not、unless、before等の候補抽出に有効だったが、行単位の正規表現で誤検出も多い。構文木で自然言語ノードだけを対象にし、プロジェクト別の危険語、API条件、用語表を設定できるレビュー支援へ発展させる。自動合否には使わず、人の照合順を決める補助とする。

### 4.4 サイト別の成果物予算を検査する

文書数と翻訳言語が増えると、容量より先にファイル数やビルド時間が問題になりうる。サイト別にページ数、静的ファイル数、総容量、最大ファイル、ビルド時間を記録し、警告・失敗しきい値を設定する。選択的ビルドの保証単位はサイトとし、予算を超える場合はサイト分割の兆候として扱う。

## 5. 推奨実施順

1. 安全な一時生成と`--check`をインポータへ追加する。
2. 共通翻訳構造検査を作り、GLFW専用検査と結果を比較する。
3. `check:content`規約を作り、ルートCIへ接続する。
4. 版ID検証、言語欠落フィクスチャ、明示的な404ページを追加する。
5. 次のパイロット用スキャフォールドと進捗の単一正本を導入する。
6. ブラウザ・外部リンク・上流差分検査を公開前工程へ追加する。
7. 二つ目以降のパイロット結果を踏まえ、来歴スキーマと共通インポータAPIをADRで決める。

## 6. 今回は実装しないもの

- 翻訳APIやローカルモデルによる訳文の自動生成。
- 未翻訳本文を定本言語で黙って表示するフォールバック。
- 1シンボル1ページへの機械的分割。
- 一つのGLFWパイロットだけを根拠にした、全上流形式共通の変換API。
- Preview／Productionへの自動公開。

これらは現在の品質判断、欠落許容方針、ファイル数抑制、管理者による公開承認と矛盾するか、根拠がまだ不足している。

## 7. P0実装記録

- 安全な出力: `scripts/importers/safe-import-output.js`と`import-glfw-3.5.1.mjs`。`--source`、`--output`、`--check`、`--dry-run`、一時生成、検査後置換、SHA-256マニフェストを実装した。
- 共通コンテンツ検査: `scripts/content-validation.js`と`validate-translated-content.mjs`。GLFW英語36件・日本語36件と内部リンク6,274件をエラー0件で検査した。
- 通常検査: ルートとGLFWの`check:content`を追加し、定本再生成差分、画像差分、構造、コード、アンカー、内部リンクを読み取り専用で検査した。
- ID: `packages/project-config/src/content-id.js`を設定読込、プロジェクト・版作成、整合性検査で共有した。`v3.5.1`は`v3-5-1`の修正例付きで拒否する。
- 欠落許容: `buildAvailableLanguagePaths`と`collectAvailableVersionIds`により、実在する対応ページだけを切替候補にする。sample-docsの翻訳0件・部分翻訳とGLFWの全件翻訳をビルド・スモークテストした。
- 404: `sites/landing/src/pages/404.astro`から統合`dist/404.html`を生成し、リダイレクトや誤ったルートcanonicalを含まないことを検査した。ローカルPages環境とCloudflare Pages Productionの双方で、未知のルート・サイト・版・言語・文書がHTTP 404になることを確認した。
