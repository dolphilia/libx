# GLFW文書インポート・翻訳パイロット総括

- 総括日: 2026-08-11
- 対象: GLFW 3.5.1公式文書の取得、Markdown化、英語定本化、日本語翻訳
- 対象外: Preview／Production公開、第三者校閲、全端末・アクセシビリティ確認

## 1. 結果

## 2. 実施した流れ

1. 正式版、タグ、コミット、配布物、チェックサム、ライセンスを固定した。
2. Doxygen入力文書、生成ページ索引、APIグループ、構造体、画像を棚卸しした。
3. 上流物を採用、参照、除外に分類し、libxの配置先とページ粒度を決めた。
4. テンプレートから`apps/glfw`を作成し、英語定本用の設定を一つの`project.config.jsonc`へ集約した。
5. GLFW固有インポータでDoxygen Markdownと生成HTMLをMarkdownへ正規化した。
6. 英語を定本、日本語を翻訳先とし、欠落を許容した状態でサイトを先に成立させた。
7. 翻訳サービスとローカルモデルを小規模に評価し、品質上の理由から不採用とした。
8. 用語、順序、ページ単位の完了条件、レビュー指針を定め、英語定本から36ページを逐次翻訳した。
9. 構造、リンク、ビルド、代表ページのブラウザ表示を段階的に検証した。

詳細な時系列と判断は`WORK_LOG.md`、取得証拠は`SOURCE_MANIFEST.md`、上流との対応は`CONTENT_MAP.md`に記録している。

## 3. 得られた知見

### 3.1 「最新」ではなく再現可能な版を定本にする

公式`latest`は入口の確認には使えるが、将来参照先が変わる。タグ、コミット、配布物のSHA-256、配布物内の版表示、公式HTMLを相互照合して初めて、更新時にも差分を説明できる定本になる。取得元URLだけでは証拠として不足する。

### 3.2 網羅性はページ数ではなく分類可能性で示す

Doxygenには同じ内容の文書ソースビュー、ファイルビュー、グループビューがあり、すべてを複製すると重複とファイル数だけが増える。公式入口、生成設定、ページ索引、公開ヘッダーの四者を照合し、全上流物を採用、統合、参照、除外のいずれかへ分類することで、複製しないものを含めて網羅性を説明できた。

### 3.3 上流の意味単位を保つページ粒度が更新しやすい

APIを1シンボル1ページにせず、Doxygenのグループ単位に保った。これにより、アンカーと上流分類を追跡しやすくしながら、ファイル数とナビゲーションの膨張を抑えられた。ページ粒度は表示上の好みだけでなく、上流差分、リンク安定性、デプロイ成果物数、多言語の同期コストで決める必要がある。

### 3.4 原資料、変換途中、公開成果物を分離する価値は大きい

取得物と失敗した変換を`.tmp/document-import/glfw/`、判断と証拠を`docs/notes/document-import/glfw/`、検証済み成果物を`apps/glfw/`へ分けた。機械翻訳初稿を棄却した際にも公開対象と混同せず、進捗を正しく0へ戻せた。途中成果物を公開ディレクトリへ直接作る運用は避けるべきである。

### 3.5 欠落翻訳を許容する設計は逐次作業の前提になる

日本語が0ページ、部分翻訳、全件翻訳の各状態を実際に通過した。欠落を英語で黙って埋めず、存在する日本語だけを表示できるため、36ページが完成するまでサイト全体を保留する必要がなかった。一方、翻訳先に版が一件もない場合に版セレクターへ空配列が渡り、ビルドが失敗した。欠落許容はコンテンツ探索だけでなく、言語・版・ナビゲーションの全UIで保証する必要がある。

### 3.6 URL用IDは表示名と分け、生成器の正規化前に検証する

表示名`GLFW 3.5.1`をそのまま版ID`v3.5.1`へ使うと、AstroのコンテンツID正規化で`v351`となった。版IDを`v3-5-1`へ変更して解決した。人向け表示名と機械用IDを分け、ディレクトリ作成前に正規化後の衝突や変化を検出する必要がある。

### 3.7 英語定本の不備を翻訳で補修してはならない

翻訳中に未展開のDoxygen `@snippet`が見つかった。日本語だけへコードを補うのではなく、インポータを修正して英語定本を再生成し、その後に翻訳した。翻訳は定本の欠陥を隠す工程ではなく、定本の問題を上流工程へ戻す検査にもなる。

### 3.8 翻訳生成と機械検査は分けて判断する

翻訳サービスはレート制限で継続性を欠き、4B・12Bのローカルモデルは規範表現、否定、処理順序、Markdown不変要素を破壊した。特にmustを許可へ弱める、beforeの順序を逆転する例は、自然な日本語だけを読んでも見逃しうる。この時点で訳文生成を自動化しない判断は妥当だった。

一方、ファイル集合、コード、インラインコード、URL、アンカー、識別子、リンク先の比較は有効だった。自動化の境界は「文章を生成するか」ではなく、「正誤を決めるための意味判断を代替するか」で引くべきである。

### 3.9 正規表現による検査は有用だが、完全な意味検査ではない

専用検査は欠落、コード改変、リンク切れなどを早期に検出したが、規範表現の強さ、条件の作用範囲、自然な誤訳は検出できない。また、Markdownを文字列として扱う限り、コードと本文、入れ子構造、複雑なリンクの判別には限界がある。構造検査への合格は翻訳品質の十分条件ではない。

### 3.10 小さい単位で定本照合と検査を閉じる方が安全である

ページ全体を翻訳し、原文照合と機械検査を終えてから次ページへ進む方法は、途中状態と完了状態を明確にした。入口、ガイド、中核API、定数・構造体、履歴の順に進めたことで、先に用語と文体を固め、後半の反復を安定させられた。

### 3.11 記録も単一の進捗源を必要とする

翻訳作業中、パイロット計画、README、対応表、翻訳計画に同じ進捗数が重複し、一部が古い14/36や34/36のまま残った。成果物の検査は成功していても、説明文書の不一致は管理判断を誤らせる。進捗はファイル集合と検査結果から生成し、各文書では参照する形が望ましい。

## 4. 有効だったもの

- 取得前に版とライセンスを固定し、本文処理の開始条件にしたこと。
- `SOURCE_MANIFEST.md`、`CONTENT_MAP.md`、`WORK_LOG.md`、`REVIEW_CHECKLIST.md`を役割別に分けたこと。
- 変換を再実行可能なインポータへ残し、手修正だけで英語定本を作らなかったこと。
- 翻訳欠落をエラーにする最終検査と、欠落を許容する途中検査を分けたこと。
- コード、URL、アンカー、識別子を英日で完全一致させたこと。
- 失敗した機械翻訳を成果として残さず、評価結果と不採用理由だけを記録したこと。
- 個別サイトだけをビルドし、他サイトを巻き込まず反復できたこと。

## 5. 改善すべき作業方法

### 次のパイロットから行う

1. 作業開始時に記録一式をテンプレートから生成し、進捗の正本を一つにする。
2. インポータは公開ディレクトリへ直接上書きせず、一時出力、差分確認、原子的置換の順にする。
3. 変換直後に未処理ディレクティブ、HTMLリンク、コード、画像、アンカーを自動検査する。
4. 版IDとスラッグをサイト作成前に検証する。
5. 0件・部分・全件の翻訳状態を最初にテストする。
6. 翻訳前に代表ページ一件で用語、完了条件、レビュー記録の粒度を確定する。
7. ブラウザ確認項目を手作業メモではなく再実行可能なスモークテストへ寄せる。

### 複数パイロット後に判断する

- 上流ファイル、ハッシュ、変換器版をページ単位で持つ共通来歴スキーマ。
- Doxygen以外にも適用できる共通インポータ基盤。
- 翻訳レビュー状態をFrontmatterへ持たせるか、外部マニフェストで管理するか。
- 翻訳支援モデルを再評価する条件と共通評価セット。

一つのパイロットだけでGLFW固有処理を共通仕様へ昇格しない。次はDoxygen以外の形式、または異なる文書構造を持つプロジェクトで同じ手順を試し、再現した部分だけを標準化する。

## 6. 残っている公開前ゲート

取得から翻訳までは完了したが、公開作業は完了していない。次の項目は`REVIEW_CHECKLIST.md`に従って別工程として扱う。

- 英語定本と日本語訳の独立した第三者校閲

## 7. 結論

このパイロットで、libxの「固定した定本を中心に、言語欠落を許容しながら、サイト単位で軽く構築する」という方向性が実作業でも成立することを確認できた。難所はMarkdownの生成そのものより、上流範囲の確定、由来の保持、ページ粒度、定本の品質、翻訳の意味保証にあった。

今後は訳文生成の自動化を急がず、人が判断すべき箇所を明確にしたまま、取得、差分、構造、リンク、進捗、表示確認の機械化を先に進める。これが今回もっとも再利用価値の高い知見である。
