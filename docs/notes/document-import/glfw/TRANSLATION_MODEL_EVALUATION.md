# GLFW翻訳モデル評価

- 評価日: 2026-08-11
- 対象言語: 英語から日本語
- 対象モデル: TranslateGemma 4B、12B、27B
- 実行環境: Apple M1 Pro（10コア）、ユニファイドメモリ16GB、Ollama
- ステータス: 評価完了、不採用

## 管理者判断

2026-08-11、現段階ではGoogle等の翻訳機も、Ollama等で動かすローカル翻訳モデルも、GLFW日本語版の作成工程へ採用しないと決定した。

評価では、自然に見える訳でも規範表現や処理順序を変える重大誤訳があり、Markdown構造の破損も発生した。これらを安全に補う自動化基盤を先に開発するより、英語定本、用語、ページ構造、レビュー手順をページ単位の逐次翻訳で確立する方を優先する。

この判断に伴い、次を実施した。

- OllamaのTranslateGemma 4B・12Bを削除した。
- HomebrewのOllama常駐サービスを停止した。
- 評価用のモデル実行・機械翻訳スクリプトをリポジトリ成果物から削除した。
- 機械翻訳由来の日本語初稿を`apps/glfw`から外し、日本語進捗を0/36ページへ戻した。
- 退避した試験初稿は`.tmp/document-import/glfw/04-translation/rejected-machine-drafts/`に置き、公開・翻訳進捗・翻訳元として扱わない。

今後は`MANUAL_TRANSLATION_PLAN.md`と`TRANSLATION_GUIDE.md`に従い、英語定本から一ページずつ翻訳・原文照合する。

## 1. 目的

GLFW 3.5.1の英語定本から日本語初稿を作る工程をローカルモデルへ任せられるかを、次の三点に分けて判断する。

1. 原文の意味、条件、否定、規範表現を保持できるか。
2. API識別子、コード、URL、Markdown構造を保持できるか。
3. 全文書へ適用できる速度と資源消費か。

「自然な日本語を生成できること」と「技術文書を安全に自動生成できること」は別の合格条件として扱う。

## 2. 比較対象

Ollama配布版のモデル容量とコンテキスト表示は次のとおりである。

| モデル | Ollama上の容量 | この端末での位置付け |
| --- | ---: | --- |
| TranslateGemma 4B | 3.3GB | 実用速度で実測可能 |
| TranslateGemma 12B | 8.1GB | 実測可能だが4Bより低速 |
| TranslateGemma 27B | 17GB | モデル本体だけで物理メモリ16GBを超える |

出典: [Ollama TranslateGemma model library](https://ollama.com/library/translategemma)

Googleのモデルカードに掲載された55言語平均は次のとおりである。MetricXは低いほど、COMETは高いほどよい。

| 指標 | 4B | 12B | 27B |
| --- | ---: | ---: | ---: |
| WMT24++ MetricX | 5.32 | 3.60 | 3.09 |
| WMT24++ COMET | 81.6 | 83.5 | 84.4 |
| WMT25 MQM | 記載なし | 7.94 | 5.86 |

出典: [Google TranslateGemma model card](https://huggingface.co/google/translategemma-27b-it#benchmark-results)、[TranslateGemma Technical Report](https://arxiv.org/abs/2601.09012)

この公式値は55言語または10言語の集計であり、GLFW固有の英日技術翻訳品質を直接保証しない。ローカル評価では同じ原文を各モデルへ与え、人が意味を確認する。

## 3. 評価方法

一時的な評価スクリプトで、実文書に現れる問題を短い12ケースへ固定した。スクリプトは不採用決定後に削除した。

- must、should、mayの強度
- 条件、否定、until、unless、orの作用範囲
- Wayland固有条件、配列の有効期間、座標単位
- GLFW API名と変数名
- Markdown見出し、インラインコード、リンク、コードフェンス

各ケースには人手で作成した基準訳を添えた。モデルにはOllamaが案内する英語から日本語への公式形式のプロンプトを使い、temperatureを0とした。速度はモデルをロード済みの状態でも測る。

実ページについては、英語と日本語の次の不変条件を機械比較する。

- ファイル、コードブロック、インラインコード
- HTMLアンカー、Markdownリンク先、URL
- `GLFW*`、`glfw*`、`Vk*`、`VK_*`識別子
- ライセンス参照、内部リンク先、保護トークン残存

## 4. 4Bの結果

### 4.1 短文

モデルをロード済みの2回目は12ケースを約12.4秒で処理した。多くの文は自然で、API名、Markdown、コードも短いケースでは保持した。一方、公開を妨げる意味上の誤りがあった。

| ケース | 出力の要点 | 判定 |
| --- | --- | --- |
| must | 「メインスレッドからのみ呼び出す必要があります」 | 許容 |
| should | 「必ずウィンドウを破棄してください」 | 強すぎる。推奨を義務へ変更 |
| must not | 「呼び出すことはできません」 | 禁止を能力上の不可能表現へ変更 |
| before | 「GLFWを初期化する前に、ウィンドウを作成してください」 | 順序が逆転する重大誤訳 |

とくに最後の例は、原文の「ウィンドウを作成する前にGLFWを初期化する」と逆である。流暢さだけでは検出できない。

### 4.2 実ページ

5ページを4Bで生成した時点で、厳格な構造検査に2ページが不合格となった。検出した問題は次のとおりである。

- 保護トークンの一部を重複して本文へ残した。
- Markdown見出しを翻訳した後、原文見出しをコードフェンス内へ追加した。
- コードブロック数とインラインコード数を変えた。
- API識別子を欠落させた。
- Markdownリンク先を変えた。

短文ではMarkdownを保持できても、長い文書を段落単位で繰り返し処理すると失敗確率が蓄積する。この実装のまま4BへMarkdownを渡す方式は不採用とする。

## 5. 12Bの結果

### 5.1 訳質

12Bは、4Bが順序を逆転させたbeforeの文を「ウィンドウを作成する前に、GLFWを初期化します」と正しく訳した。unless条件、座標単位を含む文も4Bより明確だった。

一方、12Bにも公開を妨げる誤りがあった。

| ケース | 4B | 12B | 判断 |
| --- | --- | --- | --- |
| must | 「呼び出す必要があります」 | 「呼び出すことができます」 | 12Bは義務を許可へ反転 |
| should | 「必ず破棄してください」 | 「破棄する必要があります」 | 両方とも推奨より強い |
| must not | 「呼び出すことはできません」 | 同趣旨 | 両方とも禁止を能力上の不可能表現へ変更 |
| before | 順序を逆転 | 正しい順序 | 12Bが改善 |
| API名 | 原文どおり | 原文にないバッククォートを追加 | 12Bが構造を変更 |
| 見出し | エラーコールバック | エラーハンドラ | 12Bが用語を変更 |

固定12ケースのうち、12Bは自動構造検査で11件に合格し、API名へ原文にないインラインコード記号を追加した1件に不合格となった。短文であっても、モデルサイズを上げれば構造が必ず安定するわけではない。

### 5.2 速度

12Bの初回ロードを含む最初のケースは約20.2秒だった。ロード後の残り11ケースは合計約24.6秒、平均約2.23秒だった。4Bは12ケース合計約11.5秒、平均約0.96秒であり、この端末では12Bが約2.3倍遅い。

短文の差であり、文書全体の所要時間を直接示す値ではない。

## 6. 27Bの扱い

27BのOllama配布物は17GBであり、この端末の物理メモリ16GBをモデル本体だけで超える。OS、推論ランタイム、KVキャッシュの余地がなく、スワップ前提の測定は通常運用の速度を表さないため、ローカル実測対象から外す。

公式集計では27Bが最良だが、12Bから27Bへの改善は、MetricXで3.60から3.09、COMETで83.5から84.4である。Googleも27Bを単一H100またはTPU向け、12Bを一般的なノートPC向けと位置付けている。

出典: [Google公式ブログ](https://blog.google/innovation-and-ai/technology/developers-tools/translategemma/)

## 7. 自動化の判断

評価だけを見れば、モデルを初稿補助に限定する案はあり得る。しかし、管理者判断として現段階では採用しない。翻訳モデルの選定、Markdown抽出・再挿入、複数モデル比較といった仕組みも、現在の開発対象にしない。

重点レビュー候補の抽出は`scripts/importers/report-glfw-translation-review-hotspots.mjs`として試作した。GLFW英語定本から1,395件を抽出し、そのうちmust not、should not、cannot、unless、until、before／afterを含む303件を高優先度に分類した。

この抽出は翻訳を生成しないため、逐次翻訳のレビュー計画に利用する。安全に測れる構造検査、リンク検査、用語候補抽出は継続する。

## 8. 次の判断

次は`MANUAL_TRANSLATION_PLAN.md`の順序で一ページずつ翻訳する。各ページは定本との原文照合、構造検査、用語検査を終えてから完了とする。数ページを完了した時点で、実際の所要時間とレビュー負荷を振り返り、計画だけを調整する。翻訳機・ローカルモデルの再評価は、この逐次翻訳手順が安定した後に管理者が別途決定した場合に限る。
