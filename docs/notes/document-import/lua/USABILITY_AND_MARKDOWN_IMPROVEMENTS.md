# Luaパイロット後の使いやすさ・閲覧性・Markdown改善調査

- 作成日: 2026-08-11
- 対象: libxの管理操作、共通UI、文書表示、Markdown／MDX、外部文書インポート
- 位置付け: Lua 5.5.1パイロット完了後の追加調査。実装候補の採用や着手をこの文書だけで決定するものではない。

## 1. 結論

Luaパイロットにより、libxは56ページの英語定本と56ページの日本語訳を一つのサイトとして取得、生成、検査、公開できることを確認した。一方で、ページ数と文書形式の種類が増えたことで、次の改善余地が明確になった。

1. **変換後の意味だけでなく、読みやすさも検査対象にする必要がある。** Luaの定義的な列挙では、インライン要素の間に過剰な空行が入り、内容は正しくても走査しにくい箇所が残った。
2. **現在のテーマCSSの相当部分がLua本文へ適用されていない。** 本文は`.sl-markdown-content`だが、多くの本文スタイルは`.article-content`だけを対象としている。
3. **Markdownを定本の第一選択、MDXを明示的な拡張手段として定義し直す必要がある。** Luaパイロットは`.md`を大量文書の定本として使えることを示した一方、既存機能には`.mdx`だけを想定した漏れがあった。
4. **標準Markdownだけでは、定義リスト、API項目、注意書き、出典情報などの技術文書表現が不足する。** ただし、定本へサイト固有のコンポーネント記法を大量に埋め込むのではなく、移植しやすい軽量記法を意味的なHTMLへ変換する方がよい。
5. **サンプル文書を実装の契約として検査できていない。** 存在しないコンポーネント名や実装と異なるプロパティがコード例に残っている。
6. **大規模文書向けの探索手段が不足している。** サイドバーとページ内目次だけでは、API名や用語から目的の箇所へ到達しにくい。
7. **サイトごとの複製が、改善の反映漏れを起こしやすい。** レイアウトとコンテンツスキーマは複数サイトとテンプレートに同一または近似したコピーがある。

最初に取り組むべきなのは、新しい装飾機能の追加ではない。**既存の表示契約と執筆契約を正し、MarkdownとMDXを全処理で同等に扱い、Lua変換の読みづらい出力を再現可能に直すこと**である。その後、検索、技術文書用の意味的表現、ページ状態表示を追加するのが安全である。

## 2. 調査範囲と判断基準

次を確認した。

- [Luaパイロット総括](./RETROSPECTIVE.md)と[既存の実装改善案](./LIBX_IMPLEMENTATION_IMPROVEMENTS.md)
- Luaの代表的な定本・翻訳ページ、C APIリファレンス、manページ
- `DocLayout.astro`、`MainLayout.astro`、共通UI、テーマCSS
- サンプル文書のMDX執筆ガイドと実際のコンポーネント公開API
- サイトテンプレート、各アプリのコンテンツスキーマ、統合ビルド成果物

候補は[プロジェクト原則](../../../spec/PROJECT_PRINCIPLES.md)に照らし、次を満たすものを優先する。

- 上流の意味、アンカー、コード、言語間の構造対応を壊さない。
- JavaScriptを必須にせず、静的HTMLだけでも本文を読める。
- 一つのサイトだけを選択して生成・検査できる。
- サイト追加時のコピーや設定箇所を増やさない。
- ファイル数、転送量、ビルド時間を測定できる。
- 欠落翻訳を許容しつつ、存在しない言語ページへリンクしない。

## 3. 確認できた具体的な改善点

### 3.1 インポータ出力の空白正規化

[C APIの日本語ページ](../../../../apps/lua/src/content/docs/v5-5-1/ja/03-c-api/07-functions-and-types-a-c.md)では、演算定数の説明が次のような形になっている。

```markdown
- **`LUA_OPADD`**
  
  ：加算（
  
  `+`
  
  ）を実行します。
```

HTML上のインライン要素とテキストノードが、Markdown変換時に独立した段落へ分かれた結果である。リンク、識別子、意味は保たれているため既存の構造検査は通るが、読者には一つの短い説明が複数行へ散って見える。

対策は手作業の整形ではなく、Luaインポータへ次を追加することである。

- インライン要素の前後にある空白と改行を、文脈を見て一つの空白または空白なしへ正規化する。
- 定義的な列挙を「用語」と「説明」の構造として中間表現へ保持する。
- punctuation、code、linkが混在するfixtureを用意し、生成Markdownをgolden testで比較する。
- 連続空行、記号だけの段落、極端に短い連続段落を品質レポートへ出す。

### 3.2 manページの構造表現

[luaコマンド](../../../../apps/lua/src/content/docs/v5-5-1/ja/06-tools/02-lua-command.md)では、オプション名と説明が連続した太字段落として表現されている。視覚上は読めるが、用語と定義の関係がHTMLの構造に残らず、支援技術、CSS、将来の索引生成から扱いにくい。

標準Markdownには広く合意された定義リスト構文がないため、次のいずれかを共通機能として用意する余地がある。

- GFMに近い記法を維持した定義リスト拡張
- `OptionList`／`DefinitionList`へ変換する軽量directive
- インポータの中間表現から`<dl><dt><dd>`を生成するrehype処理

説明文が長い技術文書では、表に変換すると狭い画面で読みにくくなる。第一候補は意味的な`dl`であり、表は列比較が必要な場合だけ使う。

### 3.3 本文クラスとテーマCSSの不一致

[LuaのDocLayout](../../../../apps/lua/src/layouts/DocLayout.astro)は本文を`.sl-markdown-content`で囲む。一方、[Starlight上書きCSS](../../../../packages/theme/src/css/starlight-overrides.css)の段落、リスト、リンク、引用、表、画像、印刷、モバイル向け規則の多くは`.article-content`だけを対象とする。

このため、テーマに定義された読みやすさの調整が、実際のLua本文へ一貫して適用されない。まず本文ルートの公開契約を一つに決め、CSSを`:where(.sl-markdown-content)`などへ統一する必要がある。移行中に二つのクラスを受ける場合も、最終的な標準クラスを明記する。

変更時は代表ページだけでなく、段落、入れ子リスト、コード、表、引用、画像、LTR／RTL、印刷を含む視覚回帰fixtureで確認する。

### 3.4 執筆ガイドとコンポーネントAPIのずれ

[MDX執筆ガイド](../../../../apps/sample-docs/src/content/docs/v2/ja/04-reference/02-mdx-authoring.mdx)と[文書追加ガイド](../../../guides/DOCUMENT_ADDITION_GUIDE.md)には、現在の[UI公開API](../../../../packages/ui/src/components/index.ts)と一致しない例がある。

- `Tab`をimportしているが、公開名は`TabItem`である。
- `CodeWindow`をimportしているが、公開コンポーネントに存在しない。
- `Alert type="tip"`などを例示するが、実装は`variant="info|success|warning|error"`である。
- `Card type="warning"`を例示するが、Cardの契約と一致しない。
- コンポーネント一覧に、公開APIにない名前または異なる名前が含まれる。

コードフェンス内の例はビルドされないため、サイト全体のビルド成功だけでは検出できない。これは管理者が文書どおりに操作して失敗する問題であり、優先度は高い。

対策は次のとおりである。

- 実行可能なMDX fixtureを正本にし、ガイドの例をそこから参照または生成する。
- 公開exportと主要Propsを検査するコンポーネント契約テストを追加する。
- 未知のvariantを黙って既定値表示にせず、開発・ビルド時に検出する。
- アクセシビリティ対応などの品質主張は、対応する自動検査または確認記録を伴う場合だけ掲載する。

### 3.5 MarkdownとMDXの役割が未確定

Luaの英語定本と日本語訳は`.md`で成立した。これは、外部文書を小さい差分で保ち、任意コードの混入を避け、別の処理系でも読めるという利点がある。一方で、Luaパイロット中には前後移動の走査が`.mdx`だけを対象としていた不具合が見つかった。

次の契約を正式化するのがよい。

- **`.md`**: 外部から取り込む定本、翻訳、通常文書の第一選択。CommonMark／GFMを基礎とする。
- **`.mdx`**: UIコンポーネントまたは式が本当に必要な手書き文書でのみ選ぶ。
- サイドバー、前後移動、リンク、検索、言語切替、版切替、Frontmatter検査は両形式を同等に扱う。
- 表示上の都合だけで定本を`.mdx`へ変換しない。

プロジェクト原則にある「MDX標準」という表現は、この実績を踏まえて「Markdownを基礎とし、MDXを互換な拡張として扱う」方向へ見直す余地がある。

### 3.6 注意書きと引用の意味が混在する

Luaの各ページは、上流出典と改変内容をblock quoteで記載している。テーマはblock quoteを斜体と装飾引用符で表示するため、出典通知が引用文のように見える。また、同じ長い文章が全ページへ入り、翻訳対象と差分を増やしている。

次のように分離する方がよい。

- block quoteは引用に限定する。
- 出典、上流版、変換器版、翻訳状態、確認日をページメタデータから共通パネルへ生成する。
- 定本ハッシュと翻訳照合ハッシュが異なる場合だけ「再確認が必要」と表示する。
- ライセンス帰属はフッターに保ち、技術内容の報告先と翻訳の報告先を分ける。

### 3.7 共通UIのラベルが日本語に固定されている

[Alert](../../../../packages/ui/src/components/Alert.astro)、[ContentNotice](../../../../packages/ui/src/components/ContentNotice.astro)、[AnchorHeading](../../../../packages/ui/src/components/AnchorHeading.astro)には、日本語のラベルまたはスクリーンリーダー文言が直接書かれている。英語ページでも日本語のaccessible nameになり得る。

共通コンポーネントは`lang`を受け、`@docs/i18n`からラベルを取得する必要がある。翻訳がない言語では明示した既定言語へフォールバックし、見た目に出ない文言も言語検査の対象にする。

### 3.8 目次と探索

Luaの通常ページは現在、深さ2の見出しだけをページ内目次に出す。C APIページではAPI項目が同じ深さに大量に並ぶ一方、幅75em未満では右目次自体が表示されない。目次の有無もレイアウト側で常に真としている。

大量文書向けには次が必要である。

- 見出しがないページでは目次領域を出さない。
- ページまたはサイト単位で目次の深さと上限を設定する。
- 長い目次を折りたたむ、絞り込む、またはAPIシンボル索引へ切り替える。
- モバイルで本文を妨げない「このページの内容」UIを用意する。
- scrollイベントによる全見出し走査は、必要なら`IntersectionObserver`へ置き換え、イベント解除も行う。

さらに、56ページと多数のAPI識別子を持つLuaサイトでは全文検索の効果が高い。検索は全サイトを一つの巨大索引にせず、**サイト・版・言語単位の静的索引**としてビルドし、操作時に遅延読込するのがlibxの方針に合う。見出し、明示アンカー、API名の完全一致を優先し、索引ファイル数、容量、生成時間へ予算を設ける。

### 3.9 APIリファレンス向けの表現

Lua C APIは、関数名、スタック効果、Cシグネチャ、説明が規則的に繰り返される。現在の見出し、短い段落、コードフェンスでも読めるが、長いページの走査性を改善できる。

候補は次のとおりである。

- API名と複数の上流アンカーを持てる`ApiEntry`構造
- シグネチャとスタック効果の意味的なラベル
- 見出しリンクとコードのコピーボタン
- `since`、非推奨、エラー、yield可否など、上流に明示された情報だけのバッジ
- ページ内シンボル絞り込み

これらはインポータの中間表現から決定的に生成し、英語だけまたは日本語だけへ手動追加しない。JavaScriptが無効でも、通常の見出し、コード、説明として読める構造にする。

### 3.10 ページメタデータと検索エンジン向け情報

[MainLayout](../../../../apps/lua/src/layouts/MainLayout.astro)は各文書の`description`を受け取らず、すべてのページへ固定のdescriptionと`| Docs`というtitleを設定する。Frontmatterにはページごとの説明があるため、その情報が表示層で失われている。

ページtitle、description、サイト名、版、canonical URL、Open Graph、存在する翻訳だけの`hreflang`を共通レイアウトへ渡すべきである。これは検索結果だけでなく、タブ、履歴、ブックマーク、共有時の識別性を改善する。

### 3.11 レイアウトとスキーマの複製

調査時点で、GLFW、Lua、sample-docs、テンプレートの`DocLayout.astro`は同一であり、GLFW、Lua、テンプレートの`MainLayout.astro`も同一だった。`content/config.ts`もGLFW、Lua、テンプレートで同一である。Lua中に見つかったハイフン付き版IDの修正も複数コピーへ反映する必要があった。

段階的な対策は次のとおりである。

1. まず、テンプレートと生成サイトの共通ファイルが意図せずずれた場合に検査で失敗させる。
2. コンテンツスキーマを`createDocsCollection()`のような共有factoryへ移す。
3. 共通レイアウトをパッケージ化し、サイト固有部分はslotまたは設定で差し込む。
4. サイト固有の上書きが必要な場合だけ、差分と理由を明示する。

最終的には、新しいサイトが主に設定、コンテンツ、必要な固有アセットだけを持つ状態が望ましい。

### 3.12 成果物のファイル数

確認した統合成果物は799ファイルだった。このうちKaTeXフォントは、`woff2`、`woff`、`ttf`を合わせて300ファイル存在する。Lua自体が数式を必要とするためではなく、数式コンポーネントを含む別サイトの任意機能が統合成果物全体へ影響している。

Cloudflare Pagesのファイル数を意識するなら、次を検証する価値がある。

- 現行ブラウザ向けに`woff2`だけで十分か。
- KaTeXを使用するサイトだけへアセットを含められるか。
- 同一フォントがサイトやページごとに重複していないか。
- 数式未使用サイトの選択的ビルドへ数式アセットを持ち込まないか。

削減前後は、サイト別ファイル数、容量、表示時間、ブラウザ互換性で測定する。単に容量が小さいという理由だけで、ファイル数の多さを見逃さない。

## 4. 推奨するMarkdown表現モデル

Markdownの表現力を増やす場合は、次の三層を分ける。

### 4.1 基礎層

CommonMark／GFMの見出し、段落、リスト、リンク、コード、表、画像、引用を使う。定本と翻訳はこの層だけでも意味が通る状態を保つ。

### 4.2 技術文書の意味層

標準Markdownで不足する次の構造だけを、限定したdirectiveまたは変換器で補う。

- note、tip、warning、danger
- definition list、option list
- API entry、signature、stack effect
- figure、caption
- code group
- 数式
- source／translation status

構文、生成HTML、アクセシビリティ、Markdown非対応環境での劣化方法を仕様化する。追加する種類は少なく保ち、似たコンポーネントを増やさない。

### 4.3 表示層

共通UIとテーマが意味層を表示する。色やアイコンだけに意味を依存せず、RTL、印刷、高コントラスト、reduced motionを扱う。必要なJavaScriptはコピーや絞り込みなどの補助機能に限定する。

この分離により、翻訳者は内容へ集中でき、表示変更のために全Markdownを編集せずに済む。

## 6. 推奨実施順

1. サンプル文書の誤ったAPI例を修正し、実行可能なcomponent fixtureを追加する。
2. 本文ルートクラスを統一し、代表的なMarkdown要素の視覚回帰fixtureを作る。
3. Luaインポータの空白正規化と定義構造を直し、英語定本と日本語訳を同じ生成規則で再検査する。
4. `.md`を第一級の定本形式として文書化し、`.md`／`.mdx`共通fixtureを拡充する。
5. Alert等のAPIとi18nを整理し、技術文書directiveの小さい仕様をADRで決める。
6. Frontmatterを使うページメタデータと、生成型の出典・翻訳状態パネルを実装する。
7. サイト・版・言語単位の静的検索を試作し、Luaで索引サイズと探索性を測る。
8. 共通スキーマ、共通レイアウトの順にコピーを減らす。
9. 目次、API索引、コード補助、KaTeXアセットを、測定結果に基づいて改善する。

## 7. 今すぐ採用しない方がよい案

- すべての定本をMDXへ変換し、表示コンポーネントを各ページへ直接importすること。
- 読みやすさを理由に、上流にない注記や意味を自動で追加すること。
- 全サイト・全版・全言語の検索索引を初期表示時に読み込むこと。
- APIシンボルを無条件に一シンボル一ファイルへ分割すること。
- JavaScriptがないと本文、目次、コード、注意書きが読めないUIにすること。
- 英語にしかない拡張構造を翻訳ページへ黙ってフォールバック表示すること。
- 実測せずに文字サイズ、余白、アニメーションを一括変更すること。

## 8. 成果を測る指標

改善後は、機能の有無だけでなく次をサイト別に記録する。

- 管理者: 新規サイト作成時に編集するファイル数、共通修正の反映箇所数、エラーメッセージから解決までの操作数
- 変換品質: 連続空行、記号だけの段落、未処理HTML、構造化できなかった定義、手修正件数
- 閲覧性: 代表タスクで目的のページ・APIへ到達する時間、モバイルの横overflow、長い目次の操作性
- 表示性能: 実ブラウザのFCP／LCP、転送量、初期JavaScript、検索索引の遅延読込量
- 生成性能: サイト別ページ数、ファイル数、容量、ビルド時間、最大ファイル
- 多言語: 定本と翻訳の構造差、欠落ページ、誤った言語リンク、UIの未翻訳visible／accessible label
- 保守性: 重複レイアウト・スキーマ数、実行可能な文書例の検査率、上流更新時の再生成差分

## 9. 総括

Luaパイロットで得た最大の示唆は、libxが大量のMarkdownを扱えるだけでは十分ではなく、**取り込んだ構造を読みやすいHTMLへ安定して写し、管理者向け文書と実装を同じ契約で保つ必要がある**ということである。

Markdownの表現力は増やせるが、MDXコンポーネントを本文へ増やすこと自体を目的にしない。移植可能なMarkdownを基礎に、技術文書で本当に必要な意味構造だけを共通変換し、UIはその表示を担当する。この方針なら、上流追従、多言語の同一構造、軽い静的配信、サイト単位の選択的ビルドを保ちながら、管理しやすさと読みやすさを改善できる。
