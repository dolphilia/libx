# Awesome編集の実務ガイド

2026-10-01開始。正規方針は [全ページ編集計画](../../../../plans/AWESOME_FULL_CONTENT_EDITORIAL_REVIEW_PLAN.md)。機械棚卸しとAI全文レビューを別に扱う。

- 対象は版とsourceIdの英日1組。過去版の独立確認を省略しない。
- 固定原文、編集前英語、編集前日本語は `baseline/blobs/<sha256>.gz` に保存する。ファイル全体のハッシュで識別し、読み出し時にも検証する。`.tmp` を正本にしない。
- ページ別判断記録は `.json` または `.json.gz` に保存する。読み込み・更新・存在確認には `scripts/importers/awesome/editorial-utils.mjs` の `json` / `save` / `jsonExists` を使い、呼出側の論理パスは `<version>/<sourceId>.json` のままとする。圧縮済み記録の更新はgzip形式を維持する。同名の非圧縮版を再作成せず、両形式が存在する場合は内容を照合して解決する。2026-10-06にDeveloper FirstとLidarの2件を原バイトのSHA-256を保持してgzipへ移行した。移行記録は `docs/notes/repository-audit/2026-10-06-gzip-migration.json`。
- `INVENTORY.json` は実ファイル・経路・ロック・所有子との照合結果を持つ。検出候補は削除命令や内容確認の証拠ではない。
- `enAnalysis` / `jaAnalysis` はMarkdown AST由来の位置付き単位、節、主リンク、付随リンク、コード、HTMLのURL・IDを含むJSONの保存ハッシュ。単位IDは編集前の位置に固定し、同一URLの繰り返しも別項目として扱う。
- 編集は序文とdescriptionを主題に合わせる。本文をキーワード検索だけで削除しない。判断は `keep / rewrite / remove / relocate / textualize / needs-decision` とし、範囲・根拠・行先を記録する。
- 本文のライセンス節を移す前に、出典設定・通知・表示を確認する。項目別の料金、ライセンス、警告、コード、数値は保持する。
- 日本語の見出し・案内ラベル・一般語を翻訳する。名称・API・識別子・書籍等の正式題名を残す場合は理由を記録する。汎用説明による意味の置換を認めない。
- 編集後の別パスで原文→英語→日本語を最後まで読み直す。ファイルハッシュ、節・項目・読了範囲、指摘を保存する。省略された出力は未読。`human-reviewed` を今回のAIレビュー状態として使用しない。
- 状態は `inventoried → classified → edited-en → translated-ja → content-reviewed → verified`。ハッシュ変更はstale、検証失敗はblocked、根拠不足はneeds-decision。verifiedには再生成、保全検査、英日照合、ビルド・ローカル表示が必要。
- 原則3〜5組、長大なリストは1組。バッチのレビュー・検証を終えて次へ進む。最初は台帳のpilot集合を全件処理する。
- Codexで編集・翻訳・レビューする。標準指定はGPT-6.1 Sol。実際のモデル識別子が取得できない場合は制約を明記する。ローカルLLMや既存のLLM翻訳呼び出しは禁止。
- import / publishは再現用差分のハッシュゲートを整備してから実行する。外部公開、Cloudflare Workersの使用は行わない。

RST由来構文とHTML表は独立に内容を読む。Markdown ASTだけで原構文の意味が解釈できたとしない。パイロットで得た判断・用語をこのガイドに追記する。

## パイロットで確認した判断

- Whisperの24/7は24時間・週7日まで保持し、speech/non-speechを発話／発話以外と区別する。作者の製品でも主題の収録対象なら保持する。Communityの利用者資源を投稿・寄付の運営案内と混同しない。
- ReactのContributionにある無料資料の収録条件は序文へ抽出する。リストの歴史、投稿依頼、感謝、広告禁止等は運営案内として整理する。ライセンス画像のaltとURLが矛盾するときは固定コミットの既存判断・証拠・出典表示を照合する。ReactはCC-BY-4.0の帰属とリンクを保持して画像を集約した。
- persistentを持続可能、portableを軽量、carouselをカーネル、unopinionatedを無偏見と直訳しない。永続的、移植性、カルーセル、特定の設計を強制しない、という文脈に応じた意味を確認する。比喩だけの説明は根拠のある機能説明へ直す。
- 日本語の既存英語アンカーを保持する。`anchorAliases`には空の見出し内`<a id="..."></a>`の開閉単位、旧ID、理由・証拠を記録する。構造比較の例外はこの位置・空要素を厳密に検証できた単位だけ。表示本文・URL・任意HTMLを除外しない。本文対応表、全文読了範囲、生成HTMLの重複ID・参照検査は引き続き必要。
- 生成HTMLの全件参照検査は全子アプリのビルド終了後に実行する。ビルド中の一時的な出力欠落を合格扱いにしない。目次の移動確認ではsmooth scrollの途中画像ではなく、到達後のURLと見出し位置・表示を確認する。
- タイトル変更で旧H1のIDを保つ場合も、空の見出し内別名を記録する。title/H1の比較では、根拠・位置・空要素の検証に合格した別名だけを除く。未記録のHTMLや表示文字を持つアンカーは除外しない。
- FastAPIの末尾スポンサー画像とref付き誘導を除く場合も、本文の通常の有料講座は保持する。dependenciesは依存性、out of the boxは標準提供、Redis-backedはRedisを基盤とするという意味を確認する。定型的な「資料」への置換を合格にせず、原文のメール添付・一括送信、コンテントネゴシエーション、依存性注入などの具体的機能を戻す。原文に説明のない正式記事題名や製品リンクは、推測で説明を足さず理由を記録する。
- metadata-onlyの再生成も固定された英日と編集差分から行う。旧テンプレートへの戻しや未記録の差分の上書きを拒否する。現在の外部リンク報告は各版の`EXTERNAL_LINK_REPORT.json`へ生成し、本文URLを変えたバッチでは更新・checkする。移行時の`external-links-before.json`や取得・ライセンス証拠は上書きしない。報告はローカルのURL列挙であり、外部サイトへのライブ検査は行わない。

## 固定原文のSPDX著作権通知

原文に明示的な著作権者・年があり出典の所有者名だけでは保持できない場合、PROVENANCE_NOTICES.jsonに固定sourceId・commit・path・document hash・SPDX実在行を記録し、出典レジストリとcopyrightNoticeへ反映する。ライセンス判定やURLをこの記録で変更しない。出典欄の実表示を確認し、生成し直しても通知が保持されることを検証する。

## RST由来ページ

SQLAlchemyのように未変換のRSTがMarkdown本文に残る場合、元の定義リストと参照定義を読んでから、項目名・説明・補助リンク・機能箇条書きを通常のMarkdownへ移す。ドット下線の小分類はH3へ、contentsディレクティブは自動目次へ置換する。移動する参照URLの順序・重複と、誤ってコード扱いされた説明箇条書きは理由を明示し、コード一致検査を一括無効にしない。

Markdown ASTではRSTの項目名と参照URLが離れた別単位になるため、節ごとの全旧単位の対応に加え、固定原文の各項目へ位置・ハッシュ・定義URL・英日行先IDを付けたrstCorrespondenceを保存する。生のlistItem数を資料件数と見なさない。SQLAlchemyは74資料と34機能点を別々に確認した。原文の100%保証や「性能に影響しない」は原文の主張と分かる表現へ整え、古い対応DB・版・条件を現在の保証へ変えない。

## Unicode・文字教材と長い表

文字・絵文字・顔文字が主題やコード識別子である場合は、装飾候補の機械検出だけで消さない。残す単位・具体的な文字・原文の教材の意味をresidualExceptionsに記録する。不可視の双方向上書き文字は、表示を乱す実制御の代わりにコードポイントとエスケープ例で意味を保てる。コードポイント、Unicodeスカラー値、UTF-16コード単位、書記素、グリフを区別する。

図版は構成要素・コードポイント列・合成結果・凡例・数量・関係を文章や表へ移し、元の画像URLを通常リンクとして保持する。Unicodeでは2つのZWJ列、5つの肌色修飾子、BOYとTYPE-5の組み合わせ、灰色一般顔と5色のパレット、BMP図の16×16格子と15凡例を個別に確認した。壊れた画像URLを推測置換せず、作者の同時期の保存版をファイル履歴から同定して補助リンクへ加える。

原文の技術的な誤りは固定版の一次資料と照合して修正し、原値・修正理由・根拠を残す。262ブロックの表では範囲と原記載値を保持し、両端を含む位置数を別列にした。誤った原記載値を現在の割当数へ更新しない。104行の大小対応はUnicode 9.0の完全ケースフォールディングであり、大文字化と小文字化の混在ではない。

実コードの保全は編集前Markdownだけでなく固定原文とも照合する。旧importがHTML教材のコメントを落としていた例では、head内の配置先とエラー・成功例を原文通り復元した。11コードブロックの原文一致を確認し、表示用の修正と区別して記録する。HTMLのbrが偽の表行として解析される場合も、表行数の差だけで意味の欠落と判定せず実データを確認する。

## 入口ディレクトリ

一般的な主題名は日本語へ翻訳し、製品・言語・標準識別子・正式リスト名を残す理由を項目ごとに記録する。原文に説明のない項目へ用途を推測追加しない。27分類の手動目次を除く際も分類順・入れ子項目・日本語の既存英語IDを保持する。

固定原文にあるSoftware Patreonsは、ソフトウェア開発への資金提供を扱う通常の主題項目として復元した。作者のスポンサー募集とキーワードだけで同一視しない。What is an awesome list?も定義資料として関連節へ移し、相対リンクを固定コミットの元ファイルへ解決した。安全性・最速・引用数・保守状況などの原文評価は、現在の保証へ変えず帰属を示す。

publishは一時的に配信ファイルを再配置するため、翻訳・HTML検査は生成の正常終了を確認してから実行する。生成途中のファイル欠落を内容不備や検証済みとして記録しない。

## 分野名が太字の長い資源一覧

Pythonのように汎用Projects見出しの下で分野名を太字、各資源節をH3とする原文は、太字分野をH2へ移して階層を保持する。手動Categoriesを除去しても、分野名・資源順・入れ子の関連リストを失わない。ハイフンを含むPre-trained ModelsやFine-tuningも一般分類なので翻訳する。

同じライブラリの複数用途掲載、分類だけの親項目、説明内の派生元リンクを保持し、URLの重複と入れ子も位置付きで照合する。原文の検索・絞り込みサイト案内をスポンサー案内と混同しない。訳文への他項目説明の混入、in-process、implicit feedback、sorted、concurrent/parallel、obfuscationの誤訳は全文を原文と照合して判断する。

## 主題のコミュニティと曖昧な説明

Node.js公式Twitterや通常の有料講座、開発アイデア資料は主題の資源として保持し、作者個人のSNS・広告・スポンサー募集と区別する。HTMLに埋め込まれた主題の定義や解説リンクは、広告ブロック全体と一緒に捨てず通常序文へ復元する。

固定原文の「上記」が直前の資源と一致しない場合、参照先や現行APIを推測しない。neat-csvのcallbackという記述は固定原文に帰属させ、曖昧な参照語を除去した理由を記録する。画像のminifyは圧縮であり、リサイズとは区別する。fluent interfaceは処理を連鎖できるインターフェースとして訳す。

## セルフホスト用の長いリストと帰属リンク

Free softwareは利用・改変等の自由を表し、無料とは区別する。SaaSS、network service、web applicationの定義は原文へ結び付けて序文に保持する。non-freeの別リストへの案内と、個々の項目がプロプライエタリ外部サービスへ依存する警告も区別する。警告は全出現の位置と英日表示トークンを記録し、ライセンス・実装言語・実行コードの一致検査から一括除外しない。

項目ごとのライセンス凡例は読者の選択条件なので残す。リスト自体の著者一覧やLICENSE本文へのリンクが既存出典にない場合、PROVENANCE_ATTRIBUTIONS.jsonへ固定commit/path/raw hash/該当証拠行と英日ラベルを保存してレジストリと共通出典へ追加する。削除前の実表示確認と、再生成・最終英日モバイル表示が必要。本文内に同じURLがあっても出典欄のリンクを代替した扱いにしない。

説明文の修正後は、リンク後の単一ライセンスも含め各項目のメタデータを照合する。全角括弧による境界誤認に注意する。商標記号は絵文字候補と分け、名称の表示として保持する根拠を記録する。サービス名をスラッシュで長く連結した原文は、通常の列挙へ直すことで読みやすさとモバイルの折返しを改善できる。

## 本文非収録の案内

metadata-onlyは転載対象外README全体の翻訳・レビュー対象ではない。固定された参照元索引の主題説明と既存収録判定を読み、何の資料を探せるかを短く具体化する。READMEを取得できたか、本文に適用するライセンスが確認できたかという既存判定を編集のために変更しない。固定READMEへのリンクは「元のリストを読む」、README未取得でcommitのtreeを指すリンクは「記録されたコミットの元のリポジトリを開く」等、実際のリンク先に合わせる。共通出典がCC0の参照元索引であることを記録し、対象リスト本文へCC0を適用したと判断しない。

READMEの取得可否はsourceIdの接頭辞ではなく既存判定のreadmePath/readmeSha256と実URLで判断する。metadata-edobashira-speech-language-processingはREADME.rst取得済みでblobリンクを指すため、tree入口の案内へ変えない。固定索引に名称しかない案内は、親分類と名称の範囲で説明し、具体的分野・機能・資料種別を推測しない。バッチ22のDeep Visionではこの根拠制約を判断記録へ保存した。

publish --checkは配信元の版ディレクトリへ一時的に.en-check-*等の検査用フォルダーを作る。グループの本文収集を伴うAstroビルドと並行実行すると、その一時文書を未登録経路として拾うことがある。publish --check終了0と検査用フォルダー不在を確認してからビルドを実行する。バッチ26の衝突は編集内容の不備と区別し、失敗ログ・保留状態・順次再ビルドの結果を保存する。

入力ハッシュには対象子アプリだけでなく共通のpackages/config/scriptsとグループの文書目録も含まれる。別作業のスクリプトがビルド中に更新され、最終入力照合が失敗した場合は、その変更を巻き戻さない。変更時刻・パス・ハッシュ、ビルド入力照合のコード、失敗ログを保存し、編集成果物のハッシュが維持されているかを確認する。別作業の変更後に全7子を再ビルドし、開始時・現在・成果物目録の入力ハッシュ一致と最終exit0を確認してからHTML・実表示検証へ進む。バッチ28のLuaページマップ更新による停止はこの手順で解消した。

## 配信本文から失われた原文資料の復元

バッチの大きさは現行本文の行数だけで決めない。固定原文と比べて資料や条件が消えている場合は、原文の実際の長さ・構造に合わせて独立バッチへ分ける。Accessibilityの既存本文は支援案内だけ、Material Designは投稿案内だけだった。固定原文の項目・説明・分類を復元し、baseline単位の判断に加えて原文の全単位へ判断・行先と根拠を記録する。既存配信ファイルの短さを内容の少なさとみなさない。

Table of Contentsというラベルでも、別のtopicsファイルを指すリンクは資料の入口であり、ページ内ジャンプ目次として除去しない。元の相対パスを同じ固定コミットのファイルへ解決し、外部topics本文のレビューとは区別する。分類親のlistItemが子資料を含む場合、資料数へ重複計上せず、必要なら分類をH3へ移して全子項目を保持する。Material Designは原文listItem54に対し資料53件と確認した。
