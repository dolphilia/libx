# Awesomeリスト取得・定本化・翻訳パイロット総括

- 総括日: 2026-08-22
- 対象: `v2026-08-20`、既知取得元660件、英日各365ページ
- 状態: 全フェーズ完了。416/416レビュー済み、Production公開・検証済み

## 結果

一つの公式文書を変換したGLFW、Luaと異なり、Awesomeでは起点索引から再帰的に発見した660取得元を、ライセンス証拠と固定commitごとに管理した。365件を全文定本化し、295件はmetadata-onlyとして索引上の外部リンクに留めた。英日各365ページ、28カテゴリ、2除外断片を単一Awesomeアプリへ統合した。

## GLFW・Lua・Awesomeで共通化できた処理

- 版、取得元、SHA-256、ライセンスを本文生成前に固定する。
- 一時出力で生成・検査してから公開領域を置換する。
- 英語定本と翻訳のページ集合、構造、URL、コードを機械比較する。
- source IDを本文frontmatter、lock、判断記録、帰属表示まで通す。
- 個別・選択的・統合ビルド、成果物予算、Preview、明示承認を段階ゲートにする。
- 翻訳の機械完了と人手内容レビューを別状態にする。
- 実ブラウザ確認をビルド成功とは別の品質ゲートにする。

この共通部分は取得形式ではなく、証拠、状態遷移、安全な出力、比較、公開制御である。

## Awesome固有として残す処理

- 起点索引からの深さ制限付き再帰発見、候補上限、安全停止、管理者判断。
- repositoryごとの既定branch、document path、commit、license evidenceの固定。
- `included`、`metadata-only`、`pending-license-review`、`excluded`の分類。
- 広告・スポンサー・寄付断片の除外と、正規リスト項目の誤除外防止。
- 25取得元単位の取得バッチ、最大10ページの翻訳バッチ、カテゴリ横断の標本抽出。
- 数百の異種Markdown、巨大表、画像、details、裸URLを同一UIへ収める処理。

これらをGLFW/Lua用変換器へ押し込まず、Awesome importerのドメイン規則として維持する。

## 得られた知見

### 分類はページ生成より先に閉じる

metadata-only本文を一度公開領域へ入れてから除く方式では、法的・運用上の境界が曖昧になる。lockのstatusを生成入力フィルターにしたことで、本文非複製を構造的に保証できた。

### 件数は生成データからPreviewへ渡す

READMEへ手入力した進捗はGLFW/Luaでも陳腐化した。Awesomeではlock、除外、英日ファイル集合から`awesome-preview-status.json`を生成し、入口と生成チェックを同じ値にした。

### 実ブラウザは多言語派生の不整合を見つける

機械検査と735ページビルドが成功していても、日本語検索索引欠落、日本語サイドバー空表示、派生リンクの英語化、長いURLのモバイル横あふれが残っていた。さらに外部Previewでは12ページのカードに古い作業状態の説明が残っていた。ルート数だけでなく、実際のhref、表示文言、現在表示、検索操作、scrollWidthまで確認し、表示状態語も回帰検査へ固定する必要がある。

### 機械的な「翻訳完了」は意味品質を証明しない

構造、URL、コード、英語残存候補は機械提示できるが、推薦理由、制限、否定、専門用語、固有名詞、説明の忠実性は人が固定原文と照合する必要がある。このため416件の最終レビューキューをProduction承認の前提とした。全件合格の包括証明をキュー全体の証拠ハッシュへ結び付けたため、416件の個別結果を重複記録せず、本文変更後に旧判定が残ることも防げる。

### 規模に応じて表示と検索を生成物として固定する

365ページでは、実行時の本文探索ではなく、版・言語別のsidebar/search JSONが適切だった。修正後の日本語索引185,460 bytes、初回ローカル検索6.4 msで、成果物予算内に収まった。

## 次回改善

1. route manifestを言語別派生まで含む共通生成形式にし、レイアウト側のMarkdown glob重複を減らす。
2. カテゴリ代表URL、最大ページ、metadata-only、404、検索を宣言したブラウザsmokeを自動化する。
3. upstream差分から影響source ID、翻訳バッチ、レビュー失効を自動生成する。
4. 英語残存候補を固有名詞・書誌・コード・要レビュー文へ分類し、最終レビューの負荷を下げる。
5. Preview集計と機械監査のschemaを共通化し、同じ件数定義を一か所にする。

## 結論

GLFWとLuaで成立した固定入力、安全生成、構造比較、段階公開は、多数の独立リポジトリを扱うAwesomeにも適用できた。一方、再帰発見、ライセンス別分類、広告断片、異種Markdown、大規模レビューキューはAwesome固有である。最終的に416件の内容レビュー、全機械ゲート、同一成果物によるPreview・Production検証まで完了し、パイロット全体の完了条件を満たした。
