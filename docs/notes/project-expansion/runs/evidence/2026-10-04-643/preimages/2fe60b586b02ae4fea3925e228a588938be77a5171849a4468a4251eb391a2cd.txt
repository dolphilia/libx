# 公式文書プロジェクトの継続追加と更新の運用計画

作成日: 2026-10-01。運用方針更新日: 2026-10-02。台帳に基づく継続運用中。2026-10-02のユーザー指示により、文書専用ライセンス未発見時の注釈付きソフトウェアライセンス適用と、正規の公開待ち案件の追加承認なしの公開を認める。新規プロジェクトの作成・公開を公開済みプロジェクトの定期再確認より優先する。定期実行の設定は引き続き別途指示が必要。

対象は `templates/docs-site/` から作成する通常の `apps/<project>/`。GLFW・Luaの実例を継承し、原則として原文言語と日本語、初回は安定版1版を扱う。大規模なAwesomeリストの編集・翻訳は別計画で実行中のため、本計画の進捗や変更へ混ぜない。

目的は、日本語資料が不足する有用な公式文書を、内容の正確さと更新可能性を保って増やすこと。追加数をノルマにせず、調査、選定、取得、変換、翻訳、レビュー、検証、公開、保守を別の段階として管理する。

## 採用した運用上の決定

| 項目 | 初期設定 |
| --- | --- |
| 選定単位 | プロジェクト、対象版、文書範囲の組。プロジェクト名だけでは採用しない |
| 発見と調査 | 1サイクルで候補を最大10件補充し、上位最大3件を詳細調査 |
| 新規着手 | 1サイクル最大1件。新規取り込みの作業中案件も最大1件 |
| 全体の作業上限 | 新規と既存保守を合わせて作業中最大2件。並列実行を必須にはしない |
| 公開待ち上限 | 検証済みで未公開の候補が2件あれば、新規取り込みを止める |
| 通常候補の規模 | 原文本文が数千〜3万語程度を探索の目安とする。ページ数に一律の上限を設けない |
| 自動選定の基準 | 必須条件をすべて通過し、評価70点以上、追加価値と実用性が各3点以上 |
| モデル | 進行、候補調査、採否判断、翻訳、内容レビューを原則GPT-6.1 SolのCodexで実施 |
| 作業の再開 | 台帳と実ファイルを照合し、最後の有効な段階から再開 |
| 文書専用ライセンス未発見時 | ソフトウェア本体の固定版ライセンスを注釈付きで適用する。文書専用表記の不在だけで保留しない |
| 公開承認 | 正規工程で検証済みとなり、台帳・実ファイル照合に合格した公開待ち案件は追加承認なしで公開できる |
| 定期確認 | 着手可能な新規作成・公開がない場合または余力がある場合に、前回確認から7日以上経過した対象を古い順に確認。1サイクル最大10件・15分を目安とする |
| 初期評価 | 新規3件を検証済みにした段階で方式を評価。各案件完了時にも振り返る |

値は初期設定であり、3件の実績から調整する。閾値や上限を変える場合は理由と適用日を運用設定へ記録する。候補がないときに採用件数を埋めるための基準引き下げはしない。ライセンスの根拠、全文確認、未確認を完了としない条件は、効率化のために省略しない。

## 既存の基盤と本計画の位置付け

- [外部公式文書の取得・定本化・翻訳ガイド](../guides/UPSTREAM_DOCUMENT_IMPORT_AND_TRANSLATION_GUIDE.md) の固定入力、原文保全、ページ別翻訳、検証ゲートを継承する。
- [GLFWの振り返り](../notes/document-import/glfw/RETROSPECTIVE.md) と [Luaの振り返り](../notes/document-import/lua/RETROSPECTIVE.md) を基準実績とする。GLFWは36組、Luaは56組という記録があり、コンパクトさをページ数だけで判定しない。
- [正規テンプレート](../../templates/README.md) と [プロジェクト作成器](../../scripts/create-project.js) を利用する。アプリを手作業で複製しない。
- [安全な単一出力](../../scripts/importers/safe-import-output.js) と [一括出力](../../scripts/importers/batch-import-output.js) の既存実装を確認し、検査前に公開用本文を置換しない。
- 古い資料にある「人手翻訳・人手判断」は、今回承認された運用ではCodexによる逐次翻訳とAI内容レビューで実施する。人手レビューを実施したと記録せず、OllamaやローカルLLM、翻訳API、無検査の一括翻訳は使用しない。

通常の公式文書は意味と構造を忠実に保つ。Awesome向けの序文再執筆、項目削減、画像一律除去を適用しない。サイトUI、重複ナビゲーション、広告などを除く場合も、本文との区別と除外理由を記録する。図表・注意書き・例・ライセンス通知は内容と条件に応じて保持する。

## 候補の発見経路

候補は公式URLとリポジトリの同一性で重複排除する。移転先やミラーを別プロジェクトとして数えず、発見元は複数記録できるようにする。通常の探索は発見元から公式文書へ到達するところまでとし、依存先を際限なく再帰収集しない。

| 優先 | 発見元 | 調べる内容 |
| --- | --- | --- |
| 1 | 既存収録プロジェクトの関連技術 | 一緒に使うライブラリ、ツール、公式ガイドから、読者の用途がつながる候補を探す |
| 2 | 分野別Awesomeリスト | 関連する分野から名前を拾い、公式文書へ移動する。掲載は採用根拠や権利証拠にしない |
| 3 | パッケージ登録情報 | vcpkgなどの用途・依存関係・公式URLを使い、目立たない基盤ライブラリも拾う |
| 4 | 公式文書の目録 | GNUのマニュアル一覧などから、まとまった文書を起点に探す |
| 5 | GitHub等の検索、人気情報 | 未収録分野の探索に使う。スター数やTrendingだけで採用しない |
| 6 | 読者の要望と利用実績 | 記録が得られるようになったら、具体的な用途や不足を候補の優先順位へ反映する |

1回の候補集合には原則3種類以上の発見経路と3分野以上を含める。件数が不足する場合はその理由を記録する。最終選定は用途と証拠で決め、分野ごとの採用ノルマは設けない。直近3件が同じ分野に偏った場合は、次の探索で別分野を優先する。

GitHub以外の公式Git、公式配布サイト、バージョン付きのマニュアルも対象とする。公式性、固定可能性、ライセンスを確認できれば、ホスティングサービスの違いで減点しない。

## 必須条件と証拠

各条件は `pass`、`fail`、`unknown` で記録する。1つでもunknownなら採用できず、failならその範囲・版を通常工程へ入れない。点数で必須条件の不足を相殺しない。

| 条件 | passに必要な証拠 |
| --- | --- |
| ライセンスの運用判断と履行方法が記録済み | 文書専用ライセンス、または注釈付きで適用するソフトウェア本体の固定版ライセンス。対象範囲、判断根拠、帰属・通知・変更表示等の履行方法 |
| 文書境界が明確 | 公式目次、入力ディレクトリ、生成設定等と照合した全ファイル一覧。採用・参照・除外の分類と理由 |
| 版と入力を固定できる | リリースとコミット、または公式配布物の版表示・取得URL・SHA-256。生成文書の版対応も確認 |
| 内容が自立している | 利用に必要な主要説明が収録範囲内にあり、Issue、チャット、動画等を組み合わせて新規執筆する必要がない |
| 忠実に移植できる | 通常ページ、最大ページ、表・コード・図・参照を含む難しいページで変換試験が成立する |
| 作業量を管理できる | 総語数、API項目、図表、リンク、独自構文、初回工数・更新工数の見積もりと担当範囲 |

ライセンス判断では文書ディレクトリ、各ファイルの指定、別サイトの条件を確認する。文書専用のライセンスが見つからない場合は、同じ公式プロジェクトのソフトウェア本体の固定版ライセンスを、注釈付きで文書にも適用する。文書への明示的許諾を発見した事実と、このユーザー承認に基づく運用判断を区別して記録する。文書専用表記の不在だけで調査や取り込みを止めず、通常の選定判断は大らかに進める。

この適用では、確認先・固定ライセンス原文・対象版と範囲・専用表記が未発見であること・注釈文・通知の配置先を候補台帳と出典記録へ保存する。各掲載ページの出典欄に「文書専用ライセンスの表記が確認できないため、ソフトウェア本体の〈ライセンス名〉を文書にも適用する運用判断で掲載しています」と表示し、原文の著作権・許諾条件・免責全文へのリンク、非公式翻訳と変更表示を付ける。この判断と履行方法が揃えばrightsをpassにできる。注釈を付けたことを権利者からの新たな許諾と記録しない。

明示された文書固有の条件や第三者素材の別条件がある場合はそれを優先する。ソフトウェア本体のライセンスも不明、明示的な禁止と矛盾する、条件の履行方法を定められない、といった案件は理由と再開条件を記録して保留する。過去に専用表記の不在だけで保留した候補もこの方針で再評価するが、変換試験・採点・全文レビューの未実施は合格へ変更しない。外部への問い合わせは、ユーザーの送信指示がある場合にのみ行う。

収録範囲は「特定版の利用ガイドと公開API一式」など、読者が理解できる単位で定める。巨大プロジェクト内の独立した公式マニュアルは採用できる。作業量に収めるために必要な章を切り捨てたり、コードから不足文書を生成して補ったりしない。3万語を超える候補は通常枠で即着手せず、実測、再利用可能な変換器、保守負荷の根拠を伴う別枠判断を残す。

試験変換はライセンスと対象範囲を確認してから、一時領域で行う。初期スクリーニングでは移植性・工数を暫定評価できるが、試験の結果を反映するまでeligibleにはしない。

## 日本語資料の調査と順位付け

日本語の有無は対象版と収録範囲に対して判定する。公式の言語一覧、翻訳用ディレクトリ・リポジトリ、公式が案内するコミュニティ訳、一般検索を調べる。検索にはプロジェクトの正式名・別名と、日本語、翻訳、対象版を組み合わせ、同名の別製品を除く。

| 状態 | 判断 |
| --- | --- |
| 対象版・対象範囲のまとまった訳がある | 追加価値を原則低く評価。重複する理由がなければ選ばない |
| 旧版のみ | 差分と、その版を日本語で読める価値を評価する |
| 部分訳・入門記事のみ | 公式文書一式を提供する追加価値を評価する |
| 調査範囲では未発見 | 探索先、検索語、確認日とともに記録。不存在を断定しない |
| 調査不足 | needs-evidenceとし、未翻訳として加点しない |

見つかった訳文の品質を、AIの印象だけで低評価しない。古い版、未訳節、仕様との不一致など、確認できた不足を根拠にする。既存訳を再利用する場合は、原文の利用許諾とは別に、その翻訳の権利と条件を確認する。

必須条件を満たした候補を各項目0〜5点で採点する。0は価値や適合性が確認できない、3は具体的な根拠がある、5は複数の強い根拠がある状態。未調査は0点として採用判定に流さずunknownにする。

| 評価項目 | 重み | 評価の根拠 |
| --- | ---: | --- |
| 日本語で提供する追加価値 | 30 | 版や範囲の不足、体系的な資料の不足 |
| 読者の実用性 | 25 | 想定読者、利用場面、既存収録との関連、具体的な需要 |
| 文書のまとまりと原文品質 | 20 | 自立性、目次と構成、用語の一貫性、説明の充足 |
| 継続保守のしやすさ | 15 | 版対応、文書差分、安定アンカー、更新履歴 |
| 取り込み方式の再利用性 | 10 | 既存形式・変換器・検査との適合 |

合計は `各得点 ÷ 5 × 重み` の和で100点満点とする。70点以上かつ追加価値・実用性が各3点以上をeligibleの条件とし、同点なら、保守負荷が小さいもの、次に文書変換を再利用できるものを優先する。点数に加え、採用理由を具体的な2〜3文で残す。

採用直前に、調査とは別の確認パスで、各passと得点を引用先・取得証拠へたどれるか照合する。対象範囲、試験結果、日本語訳の不足のいずれかが説明と食い違えば順位付けをやり直す。同じCodexで実施できるが、推薦文を読むだけで承認済みにしない。

詳細調査は上位最大3件。通常は1件30分程度を初期の調査枠とし、根拠が揃わなければ保留へ移す。短い時間で権利や品質を推測してpassにしない。追加調査の必要性と見込みが明確なら、時間枠の延長理由を記録して継続できる。

候補が尽きたサイクルは、採用0件で正常終了できる。落選・保留も理由を保存し、新しい証拠や再調査日が来るまで同じ調査を繰り返さない。

## 台帳と状態の正本

新設予定の運用記録は `docs/notes/project-expansion/` へ置く。以下は実行準備で作る成果物であり、計画策定時点で実装済みという意味ではない。

| 成果物 | 役割 |
| --- | --- |
| `POLICY.json` | 本計画の版、採点基準、件数上限、再調査間隔、モデル方針 |
| `CANDIDATES.json` | 公式URL、発見元、対象版・範囲、必須条件、翻訳調査、採点、採否、次回確認日 |
| `OPERATIONS.json` | 取り込み・修正・更新・公開待ちの共通一覧。担当、作業場所、状態、依存、次の操作 |
| `runs/<run-id>.json` | 入力と成果物のハッシュ、実行段階、実モデル、使用ツール、検査結果、判断 |
| `REPORT.md` | 上記JSONと実ファイルから生成する人向け進捗。件数を手作業で二重管理しない |

プロジェクト別の出典、content map、用語、ページ進捗、レビュー証拠は、既存様式に合わせ `docs/notes/document-import/<project>/` の版別領域に置く。全体台帳はその正本への参照を持ち、ページ進捗を別の場所へ複製しない。今回の方式を適用するためだけに、GLFW・Luaの既存記録を一括移動しない。

候補IDは公式プロジェクトの同一性に対応させ、作業IDは候補ID・固定版・範囲ハッシュで一意にする。新しい版や範囲は別作業として関連付ける。重複発見から同じappsを二度作らない。

候補の状態は `discovered → screening → qualifying → eligible → selected`。不足は `needs-evidence`、見送りは `deferred`、不適合は `rejected` とし、再調査条件を添える。

作業の状態は `planned → source-locked → canonical-ready → translating → content-reviewed → verified`。公開は別フィールドで `not-requested / awaiting-release / preview-verified / published` とする。更新対象がない状態は `no-change`、障害は `blocked`、証拠失効は `stale`、条件を記録して作業枠から外した長期保留は `deferred` とし、最後に合格した段階を併記する。

すべての状態更新は、期待する入力ハッシュ・台帳のリビジョンと照合し、書き込み競合があれば再読込する。異常終了で担当が残った場合は、プロセスの終了と最後の成果物を確認してから担当を引き継ぐ。経過時間だけで他プロセスの作業を上書きしない。

## サイクルの実行手順

### 開始時と再開時

1. AGENTS.md、本計画、運用設定、台帳を読む。実行設定からモデルを確認し、実モデルを記録する。取得できない場合は設定上のモデル名と確認不能を区別し、推測で埋めない。GPT-6.1 Solを利用できない場合は制約を報告し、ローカルLLMへ自動代替しない。
2. Git差分、作業場所、担当、入力・出力ハッシュを確認する。既存のユーザー変更やAwesome作業を取り込まない。
3. 未完了の新規作成・公開を優先し、その他は下記の作業順位で選ぶ。staleなら失効した段階へ戻る。既に合格した変更のないページを理由なく再翻訳しない。
4. 公開済みプロジェクトの定期再確認は、新規作成・公開の着手可能な作業がない場合または余力がある場合に行う。7日以上未確認の対象を古い順に最大10件・15分を目安に調べ、未処理分は低優先の確認待ちへ残す。実際に確認していない確認日時は更新しない。既知の重大不具合はこの巡回を待たず優先する。
5. 次の優先順位と件数上限に従って作業を選ぶ。

### 作業の優先順位

1. 読者への重大な影響が確認された誤訳・欠落・主要リンク破損・通知不足などの緊急修正。理由と影響範囲を記録する。
2. 着手済み新規プロジェクトの取得・定本化・翻訳・全文レビュー・検証と、正規の公開待ち案件の公開。
3. 次の新規候補の調査・選定と、件数上限内の新規プロジェクトの作成・公開。
4. 公開済み文書の通常の修正・上流更新と、その未完了案件の再開。
5. 公開済みプロジェクトの定期再確認。着手可能な新規作業がない場合または余力がある場合に進める。

緊急修正がある場合、新規作業は再開可能な状態で保存して中断できる。通常の更新の待機件数や経過日数だけを理由に新規追加を止めない。従来の「着手可能な更新2件以上／30日以上の更新1件で新規停止」は新規優先運用では適用しない。POLICYのreadyUpdates・oldUpdateDaysは旧方針互換の設定として残す。着手可能な新規作業がない場合は、独立して進められる更新・保留解消・定期再確認を行う。新規採用の必須条件・採点、全文レビュー、公開前の証拠再検証と回帰検査は省略しない。

作業中上限には、未完了の新規取り込みを含める。blockedへ状態名を変えて新規1件制限を回避しない。長期保留に移す場合は、理由、復帰条件、保存成果物を記録し、配信対象から外したことを確認してから作業枠を解放する。

### 発見から採用まで

台帳に有効なeligible候補があれば、毎回10件を調べ直さずその候補を使う。候補が不足するときだけ補充する。選定直前に必須条件の証拠、正式版、日本語訳の状況を確認し、調査から30日以上経過していれば再調査する。

eligibleの待機枠は最大3件とし、枠が埋まっている間は詳細調査を追加しない。公開待ちで新規を始められない間も、この上限を超えて採用待ちを積み上げない。調査枠内に確認できなかったページや更新は未確認のまま残し、確認日時を進めて見かけ上の滞留を消さない。

詳細調査と試験変換を終えた候補から最大1件をselectedにする。通常の条件内での選定、ページ分割、用語、翻訳順序はCodexが判断する。候補ごとにユーザーの採用承認を要求しない。注釈付きライセンス適用を含む運用判断でも条件が定まらない候補や、確定した範囲を大きく拡張する案は保留にする。uthash 2.4.0とfmt 12.2.0は候補台帳へ各1件登録済みで、ユーザー指定候補として不足する変換・工数評価を進める。

### 固定入力と内容対応表

正式版を選び、タグが指すコミット、公式配布物のURL・取得日・SHA-256、文書の版表示、ライセンスの適用範囲と証拠を保存する。正式リリースがない文書でも、版付き文書やコミットと対象仕様を固定できれば、例外理由を記録して評価できる。移動するlatestやブランチ名だけで固定済みにしない。

固定後に上流の新しい版へ切り替えない。同じタグの内容が変わった場合も別の入力として扱い、無言で更新しない。上流が消えても検証できるよう、権利条件に従って取得物を保管し、保管場所とハッシュを記録する。`.tmp` だけに復元不能な原資料や翻訳成果物を置かない。

全上流物を採用、分割、統合、検査参照、外部参照、除外へ分類し、配置先と理由を記録する。段落・API・表・コード・アンカーを照合できる単位へ分ける。1シンボル1ページを強制せず、上流の意味単位を基本とする。

### アプリ作成と定本化

別プロセスと衝突する可能性がある場合は、実行開始時に適切な専用チェックアウトまたはworktreeを用意する。現在の共有チェックアウトで新規アプリ生成、pnpm install、統合ビルドを同時に走らせない。台帳へ作業場所を記録する。

プロジェクト作成器のdry-runで、アプリだけでなくlanding設定などの変更先を確認し、テンプレートから生成する。次は既存の操作例であり、本計画作成時には実行しない。

```bash
pnpm create:project <project> "English name" "日本語名" --dry-run --confirm
pnpm create:project <project> "English name" "日本語名" --confirm
```

テンプレートのサンプル本文・版を削除し、固定版、言語、カテゴリ、出典を設定する。未検証のアプリは専用作業場所に置き、共有の公開対象へ統合しない。`apps/` が自動検出されることを踏まえ、台帳の状態だけで公開を防げるとは考えない。

上流形式ごとの変換器とページマップを作り、固定入力から同じ英語定本を再生成できるようにする。原文が英語以外なら原文言語を定本として明示し、英語へ中間翻訳して原文扱いしない。初期の実証は英語定本・日本語訳を基本とする。

元の説明を要約・補筆して定本化しない。未処理構文、図表欠落、参照切れ、API欠落を解消してからcanonical-readyにする。生成器のために上流のビルドが必要なら、必要な文書生成部分と依存を確認して実行する。

### 翻訳と内容レビュー

Codexが定本から1ページずつ翻訳し、そのページの原文照合を終えてから次へ進む。用語、規範語、否定・例外、前後関係、単位・数値、対応版を保持する。見出し、表セル、注意書き、説明用リンクラベルも確認し、固有名詞やAPI名を無理に訳さない。

編集とは別のレビュー工程で、原文→定本の保全、定本→日本語の意味、日本語単独での読みやすさを確認する。同じCodexで実施できるが、初稿の自己申告だけでレビュー済みとしない。全ページを確認し、難しい規範表現だけの抜き取りで代替しない。

ページごとに原文・定本・翻訳のハッシュ、確認範囲、指摘と修正、モデル、日時を記録する。長文は節単位に分け、確認範囲が全体を覆うことを検査する。省略されたツール出力は読了扱いにしない。定本を変更した場合は対応訳とレビューを失効させる。

翻訳成果物と検証結果はGitで追跡できる形で保存する。再生成時にLLMへ再翻訳させることを再現性の条件にしない。自動証拠検査、AI内容レビュー、人手確認は別の状態として記録する。

### 検証と統合

ページ検査では、ファイル集合、対応する全節、API識別子・コード・数値・URL・アンカー、未処理構文、用語、出典を確認する。URLの内部化や見出し翻訳など正当な差分は対応表で検査し、完全一致検査を外すだけで合格にしない。

プロジェクトに読み取り専用の `check:content` を設け、定本再生成差分、翻訳欠落、構造、内部リンク、ライセンス参照を検査する。既存のGLFW・Luaの方式を参照するが、プロジェクト固有変換を無理に共通化しない。

```bash
pnpm --filter=<実際のpackage名> check:content
pnpm build:selective --projects=<project>
pnpm check:links
pnpm check:integrity
git diff --check
```

新設する台帳・選定検査のコマンド名は実装時に確定し、存在しないコマンドを実行済みと記録しない。共有パッケージやテンプレートを変更した場合は関連テスト、テンプレートビルド、GLFW・Luaなど複数アプリの確認を加える。

ローカルAstroプレビューで、入口、各カテゴリ、最大ページ、API、図表、コード、英日切替、版切替、サイドバー、前後移動、404、出典を確認する。デスクトップ・モバイルとキーボード操作を確認し、未実施項目を合格として埋めない。

定本と日本語が確定範囲について全件合格してからverifiedにする。部分翻訳を許す基盤は維持するが、この新規追加サイクルでは部分訳を案件完了にしない。専用作業場所からの統合時は最新の共有状態との差分を確認し、landing、依存ロック、生成物を整合させ、必要な検査を再実行する。

### 公開と公開待ち

2026-10-02のユーザー指示を継続的な公開承認として扱う。正規の選定・取得・定本化・翻訳・別工程の全文内容レビュー・機械検査・表示検証・統合を経てverifiedとなり、OPERATIONS.jsonへ公開待ちとして登録された案件は、追加の承認確認なしで外部Preview・Productionへ公開できる。この方針は既存の正規公開待ち案件にも適用する。公開待ちというラベルだけでは許可対象にせず、公開直前に台帳・現行本文・レビュー・検査証拠の有効性と対象差分を照合する。継続目標が一時停止中なら、方針更新だけで公開処理を起動せず再開時の次の操作へ記録する。

正規の公開待ち案件は、上記の作業優先順位と作業上限に従って公開まで進める。配信障害や証拠失効で待機する場合は理由と次の操作を保存する。待機中も上限内の新規候補調査と、独立した既存文書の保守は進められるが、公開待ちが2件に達したら新規取り込みを始めない。

公開待ちの件数は、verifiedでProduction未反映の新規・更新作業IDから算出する。not-requestedやpreview-verifiedも数え、状態名の変更で件数から外さない。同じ成果物の公開再試行は別件として増やさない。この条件は新規着手を止めるためのものであり、公開中の文書に対する必要な修正を止める理由にはしない。

外部Preview・Productionは統合Cloudflare Pagesのみを使用する。Workersは開発・検証を含め使わない。[配信workflow](../../.github/workflows/cloudflare-pages-deploy.yml) はpush等からPreviewが起動し得るため、許可対象の検証済み変更だけを専用のクリーンな公開候補へ入れてからpushする。既存ガイドの個別承認待ちより、この計画の継続的な承認を優先する。具体的な差分、内容レビュー、統合成果物の検証結果を記録して公開へ進み、公開後に結果を報告する。別プロセスのAwesome作業、ユーザーの未完了変更、未検証案件はこの承認の対象に含めない。

公開時は対象変更を限定したクリーンな候補から統合成果物を生成し、他プロセスの未完了内容を混入させない。検証済み成果物のハッシュと実際の配信物を対応付け、公開後に主要URL、言語・版切替、出典、404を確認する。公開状態と配信IDは内容のverified状態とは別に記録する。

## 既存文書の更新と再調査

更新確認は上流の正式版、文書ファイルの差分、訂正文、リンク移転、ライセンス変更を対象とする。コミット数が少ない成熟プロジェクトを、それだけで保守不良と判断しない。

文書に差分がなければno-changeとして確認日時を更新する。差分があれば、章・API・リンク・ライセンス・翻訳への影響を分類し、修正または新版追加を作業一覧へ入れる。未調査の新リリースをただちに最新版として表示しない。

新しい上流版は新しいLibx版として取り込み、旧版の内容を黙って置換しない。同じ固定原文に対する誤訳や変換不具合は、修正履歴を残して既存版を直せる。上流の訂正で入力が変わる場合は、版の表示と出典で区別できる訂正版として扱う。

変更のない訳文は再利用できるが、定本のハッシュ、周辺の前提、用語、参照先を確認する。変更ページと依存するページは再レビューし、全体の機械検査を通す。ライセンス条件が変わった場合は新版の判定をやり直し、過去のpassを継承しない。

履歴版・プロジェクトの削除は通常サイクルへ含めない。上流終了や新しい公式日本語訳の登場は保守方針の見直し候補にし、既存URLを自動削除しない。候補の翻訳状況も、新規採用前と30日以上経過後に見直す。

## 中断と障害からの復帰

1操作ごとに、対象作業ID、現在の段階、最後に合格したハッシュ、未解決点、次の具体的な操作を保存する。外部障害は影響案件だけをblockedにし、独立した作業を進める。同じ失敗の無限再試行はせず、原因と次回条件を記録する。

復帰時は、保存状態ではなく実ファイルと入力ハッシュから整合性を確認する。基準と異なる場合はstaleとして依存する検査を失効させる。範囲変更、版変更、変換器変更、用語の意味変更も影響レビューを失効させる。整形だけの変更でも構造検査を行い、内容レビューを再利用した理由を記録する。

失敗時は当該案件の変更だけを戻し、既存のユーザー変更やAwesome作業を巻き戻さない。原資料、中間物、翻訳、生成物、台帳を対応付けて復元する。検証済み版は新しい版の失敗で壊さない。

## 初期導入の工程

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 0 運用準備 | 設定、台帳スキーマ、状態更新・検査・報告の最小実装。GLFW・Luaの固定版と監視入口を登録 | 件数上限、重複、根拠不足、ハッシュ失効、再開を検査できる。既存ページを再レビュー済みと誤登録しない |
| 1 候補選定の実証 | 最大10件の比較、上位最大3件の詳細調査、代表ページの変換試験 | 適格な1件を根拠付きで選定、または採用0件と理由を説明できる |
| 2 最初の1件 | 取得、定本化、テンプレート生成、逐次翻訳、内容レビュー、表示検証 | 確定した収録範囲が英日ともverified。更新確認方法と再開手順がある |
| 3 異なる条件で反復 | 次の2件を同じサイクルで処理。少なくとも2種類の上流形式を試す | 新規3件の実績と、1件以上の文書差分分類・訳文失効・更新検証の実証が揃う |
| 4 通常運用へ移行 | 閾値、工数、上限、保守負荷を振り返り、手順と設定を修正 | 各ゲート・再生成・再開が機能し、未解決の共通欠陥がない |

公開待ちが2件に達した場合は、正規の公開条件を満たす案件を追加承認なしで公開へ進める。障害で公開できなければ暫定評価と保守作業を行い、公開待ち上限は外さない。公開後に枠が空いた時点で3件目へ進み、正式な初期導入完了を判定する。未実施の3件目は完了扱いにしない。

段階0の検査では、少なくとも、ライセンスunknownの候補が採用されないこと、同じプロジェクトが重複生成されないこと、公開待ち上限で新規着手が止まること、訳文や定本の変更でレビューが失効すること、中断した台帳と実ファイルの不一致を検出できることを確認する。最初の案件では再生成を二度行い、二度目で差分が増えないことと、失敗した生成が既存本文を壊さないことを検証する。

更新の実証では、実際の上流差分を使う。新しい公開がなければ、過去2版を隔離領域で比較して試験できる。試験を実際の新版公開と記録しない。候補条件を満たす別形式が見つからない場合は、その検証項目を未完了として保持する。

共通ツールは設定、台帳、固定証拠、安全出力、検査、進捗報告へ限定して始める。2種類以上の上流形式で再利用できた変換だけを共通化する。初回から汎用クローラーや任意文書変換器を完成させることを前提にしない。

## 完了条件と運用評価

1案件のverified条件は、権利と範囲の確定、固定入力からの定本再生成一致、範囲内全ページの翻訳・AI内容レビュー、構造・リンク・ビルド・表示検証、進捗台帳との一致である。証拠が現在の内容に対応し、未解決の欠落・重大誤訳・表示破損がないことを要求する。

1サイクルの完了は、作業結果、採用・保留の理由、確認日時、次の処理IDを保存できた状態。案件を終えられなければサイクル結果をpartialとし、次回その案件から再開する。候補なしや更新なしは正常なno-changeである。

継続運用そのものには全件終了という終点を設けない。初期導入の完了と、その後の各案件・各サイクルの完了を分ける。

評価には、検証済み件数と公開件数に加え、次を使う。

- 選定理由と権利証拠が揃った案件の割合、保留理由の内訳。
- 全ページ確認率、レビューで見つかった意味欠落・誤訳、公開後の修正件数。
- 1件当たりの調査、変換、翻訳、レビュー、更新の実作業量。
- 更新待ち・公開待ちの件数と待機日数、未解決案件の滞留。
- 再利用できた変換処理と、再生成差分・再開失敗の件数。

件数を増やすために同じ文書を細分化したり、未完了範囲を分母から外したりしない。工数が見積もりを大きく上回った案件は、次回の採点と作業枠に反映する。
