Description</h2>&#10;<div class="textblock"><p>Various macros to control xxHash's behavior. </p>&#10;</div><a name="doc-define-members" id="doc-define-members"></a><h2 id="header-doc-define-members" class="groupheader">Macro Definition Documentation</h2>&#10;<a id="ga9cc731558db44d378e6dde975236d4ab" name="ga9cc731558db44d378e6dde975236d4ab"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#ga9cc731558db44d378e6dde975236d4ab">◆&nbsp;</a></span>XXH_SCALAR</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH_SCALAR&nbsp;&nbsp;&nbsp;0</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>Possible values for <a class="el" href="#gab216d0cd3d35dcfd7c6860ea296cdd86" title="XXH_VECTOR">XXH_VECTOR</a>. </p>&#10;<p>Unless set explicitly, determined automatically. Portable scalar version </p>&#10;&#10;</div>&#10;</div>&#10;<a id="ga7e738bf7fb8249e8a834a8c8a8581d80" name="ga7e738bf7fb8249e8a834a8c8a8581d80"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#ga7e738bf7fb8249e8a834a8c8a8581d80">◆&nbsp;</a></span>XXH_NO_LONG_LONG</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH_NO_LONG_LONG</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>Define this to disable 64-bit code. </p>&#10;<p>Useful if only using the <a class="el" href="/docs/xxhash/v0-8-4/en/02-api/12-group___x_x_h32__family/" title="XXH32 family">XXH32 family</a> and you have a strict C90 compiler. </p>&#10;&#10;</div>&#10;</div>&#10;<a id="ga04b48241beb7c34e5929d328cf5cc71a" name="ga04b48241beb7c34e5929d328cf5cc71a"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#ga04b48241beb7c34e5929d328cf5cc71a">◆&nbsp;</a></span>XXH_FORCE_MEMORY_ACCESS</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH_FORCE_MEMORY_ACCESS&nbsp;&nbsp;&nbsp;0</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>Controls how unaligned memory is accessed. </p>&#10;<p>By default, access to unaligned memory is controlled by <span class="tt">memcpy()</span>, which is safe and portable.</p>&#10;<p>Unfortunately, on some target/compiler combinations, the generated assembly is sub-optimal.</p>&#10;<p>The below switch allow selection of a different access method in the search for improved performance.</p>&#10;<dl class="section user"><dt>Possible options:</dt><dd></dd></dl>&#10;<ul>&#10;<li><span class="tt"><a class="el" href="#ga04b48241beb7c34e5929d328cf5cc71a" title="Controls how unaligned memory is accessed.">XXH_FORCE_MEMORY_ACCESS</a>=0</span> (default): <span class="tt">memcpy</span> <dl class="section user"><dt></dt><dd>Use <span class="tt">memcpy()</span>. Safe and portable. Note that most modern compilers will eliminate the function call and treat it as an unaligned access.</dd></dl>&#10;</li>&#10;<li><span class="tt"><a class="el" href="#ga04b48241beb7c34e5929d328cf5cc71a" title="Controls how unaligned memory is accessed.">XXH_FORCE_MEMORY_ACCESS</a>=1</span>: <span class="tt">__attribute__((aligned(1)))</span> <dl class="section user"><dt></dt><dd>Depends on compiler extensions and is therefore not portable. This method is safe <em>if</em> your compiler supports it, and <em>generally</em> as fast or faster than <span class="tt">memcpy</span>.</dd></dl>&#10;</li>&#10;<li><span class="tt"><a class="el" href="#ga04b48241beb7c34e5929d328cf5cc71a" title="Controls how unaligned memory is accessed.">XXH_FORCE_MEMORY_ACCESS</a>=2</span>: Direct cast <dl class="section user"><dt></dt><dd>Casts directly and dereferences. This method doesn't depend on the compiler, but it violates the C standard as it directly dereferences an unaligned pointer. It can generate buggy code on targets which do not support unaligned memory accesses, but in some circumstances, it's the only known way to get the most performance.</dd></dl>&#10;</li>&#10;<li><span class="tt"><a class="el" href="#ga04b48241beb7c34e5929d328cf5cc71a" title="Controls how unaligned memory is accessed.">XXH_FORCE_MEMORY_ACCESS</a>=3</span>: Byteshift <dl class="section user"><dt></dt><dd>Also portable. This can generate the best code on old compilers which don't inline small <span class="tt">memcpy()</span> calls, and it might also be faster on big-endian systems which lack a native byteswap instruction. However, some compilers will emit literal byteshifts even if the target supports unaligned access.</dd></dl>&#10;<dl class="section warning"><dt>Warning</dt><dd>Methods 1 and 2 rely on implementation-defined behavior. Use these with care, as what works on one compiler/platform/optimization level may cause another to read garbage data or even crash.</dd></dl>&#10;See <a href="https://fastcompression.blogspot.com/2015/08/accessing-unaligned-memory.html">https://fastcompression.blogspot.com/2015/08/accessing-unaligned-memory.html</a> for details.</li>&#10;</ul>&#10;<p>Prefer these methods in priority order (0 &gt; 3 &gt; 1 &gt; 2) </p>&#10;&#10;</div>&#10;</div>&#10;<a id="ga1e9850064fc149181cce7431f40a990a" name="ga1e9850064fc149181cce7431f40a990a"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#ga1e9850064fc149181cce7431f40a990a">◆&nbsp;</a></span>XXH_SIZE_OPT</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH_SIZE_OPT&nbsp;&nbsp;&nbsp;0</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>Controls how much xxHash optimizes for size. </p>&#10;<p>xxHash, when compiled, tends to result in a rather large binary size. This is mostly due to heavy usage to forced inlining and constant folding of the <a class="el" href="/docs/xxhash/v0-8-4/en/02-api/14-group___x_x_h3__family/" title="XXH3 family">XXH3 family</a> to increase performance.</p>&#10;<p>However, some developers prefer size over speed. This option can significantly reduce the size of the generated code. When using the <span class="tt">-Os</span> or <span class="tt">-Oz</span> options on GCC or Clang, this is defined to 1 by default, otherwise it is defined to 0.</p>&#10;<p>Most of these size optimizations can be controlled manually.</p>&#10;<p>This is a number from 0-2.</p><ul>&#10;<li><span class="tt"><a class="el" href="#ga1e9850064fc149181cce7431f40a990a" title="Controls how much xxHash optimizes for size.">XXH_SIZE_OPT</a></span> == 0: Default. xxHash makes no size optimizations. Speed comes first.</li>&#10;<li><span class="tt"><a class="el" href="#ga1e9850064fc149181cce7431f40a990a" title="Controls how much xxHash optimizes for size.">XXH_SIZE_OPT</a></span> == 1: Default for <span class="tt">-Os</span> and <span class="tt">-Oz</span>. xxHash is more conservative and disables hacks that increase code size. It implies the options <a class="el" href="#gae980c41901d840d8909aa74d603ad4f1" title="XXH_NO_INLINE_HINTS">XXH_NO_INLINE_HINTS</a> == 1, <a class="el" href="#gaee35763869a969d5576e70dac1c08b8d" title="XXH_FORCE_ALIGN_CHECK">XXH_FORCE_ALIGN_CHECK</a> == 0, and <a class="el" href="#gac799ce966f18e4837f7fdc3d51917e9c" title="XXH3_NEON_LANES">XXH3_NEON_LANES</a> == 8 if they are not already defined.</li>&#10;<li><span class="tt"><a class="el" href="#ga1e9850064fc149181cce7431f40a990a" title="Controls how much xxHash optimizes for size.">XXH_SIZE_OPT</a></span> == 2: xxHash tries to make itself as small as possible. Performance may cry. For example, the single shot functions just use the streaming API. </li>&#10;</ul>&#10;&#10;</div>&#10;</div>&#10;<a id="gaee35763869a969d5576e70dac1c08b8d" name="gaee35763869a969d5576e70dac1c08b8d"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#gaee35763869a969d5576e70dac1c08b8d">◆&nbsp;</a></span>XXH_FORCE_ALIGN_CHECK</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH_FORCE_ALIGN_CHECK&nbsp;&nbsp;&nbsp;0</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>If defined to non-zero, adds a special path for aligned inputs (<a class="el" href="/docs/xxhash/v0-8-4/en/02-api/12-group___x_x_h32__family/#ga310c01be2371883ad3bb37930626ec86" title="Calculates the 32-bit hash of input using xxHash32.">XXH32()</a> and <a class="el" href="/docs/xxhash/v0-8-4/en/02-api/16-group___x_x_h64__family/#ga9651d864dea7e0755ae3935bf6bf7082" title="Calculates the 64-bit hash of input using xxHash64.">XXH64()</a> only). </p>&#10;<p>This is an important performance trick for architectures without decent unaligned memory access performance.</p>&#10;<p>It checks for input alignment, and when conditions are met, uses a "fast&#10;path" employing direct 32-bit/64-bit reads, resulting in <em>dramatically faster</em> read speed.</p>&#10;<p>The check costs one initial branch per hash, which is generally negligible, but not zero.</p>&#10;<p>Moreover, it's not useful to generate an additional code path if memory access uses the same instruction for both aligned and unaligned addresses (e.g. x86 and aarch64).</p>&#10;<p>In these cases, the alignment check can be removed by setting this macro to 0. Then the code will always use unaligned memory access. Align check is automatically disabled on x86, x64, ARM64, and some ARM chips which are platforms known to offer good unaligned memory accesses performance.</p>&#10;<p>It is also disabled by default when <a class="el" href="#ga1e9850064fc149181cce7431f40a990a" title="XXH_SIZE_OPT">XXH_SIZE_OPT</a> &gt;= 1.</p>&#10;<p>This option does not affect XXH3 (only XXH32 and XXH64). </p>&#10;&#10;</div>&#10;</div>&#10;<a id="gae980c41901d840d8909aa74d603ad4f1" name="gae980c41901d840d8909aa74d603ad4f1"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#gae980c41901d840d8909aa74d603ad4f1">◆&nbsp;</a></span>XXH_NO_INLINE_HINTS</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH_NO_INLINE_HINTS&nbsp;&nbsp;&nbsp;0</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>When non-zero, sets all functions to <span class="tt">static</span>. </p>&#10;<p>By default, xxHash tries to force the compiler to inline almost all internal functions.</p>&#10;<p>This can usually improve performance due to reduced jumping and improved constant folding, but significantly increases the size of the binary which might not be favorable.</p>&#10;<p>Additionally, sometimes the forced inlining can be detrimental to performance, depending on the architecture.</p>&#10;<p>XXH_NO_INLINE_HINTS marks all internal functions as static, giving the compiler full control on whether to inline or not.</p>&#10;<p>When not optimizing (-O0), using <span class="tt">-fno-inline</span> with GCC or Clang, or if <a class="el" href="#ga1e9850064fc149181cce7431f40a990a" title="XXH_SIZE_OPT">XXH_SIZE_OPT</a> &gt;= 1, this will automatically be defined. </p>&#10;&#10;</div>&#10;</div>&#10;<a id="gaa6d5f6ddf0a7d14b90a63cb6a9d34c26" name="gaa6d5f6ddf0a7d14b90a63cb6a9d34c26"></a>&#10;<h2 class="memtitle"><span class="permalink"><a href="#gaa6d5f6ddf0a7d14b90a63cb6a9d34c26">◆&nbsp;</a></span>XXH3_INLINE_SECRET</h2>&#10;&#10;<div class="memitem">&#10;<div class="memproto">&#10;      <table class="memname">&#10;        <tbody><tr>&#10;          <td class="memname">#define XXH3_INLINE_SECRET&nbsp;&nbsp;&nbsp;0</td>&#10;        </tr>&#10;      </tbody></table>&#10;</div><div class="memdoc">&#10;&#10;<p>Determines whether to inline the XXH3 withSecret code. </p>&#10;<p>When the secret size is known, the compiler can improve the performance of <a class="el" href="/docs/xxhash/v0-8-4/en/02-api/14-group___x_x_h3__family/#gac3b0a46f4a38befb3c8fa122f5d74dbb" title="Calculates 64-bit variant of XXH3 with a custom &quot;secret&quot;.">XXH3_64bits_withSecret()</a> and <a class="el" href="/docs/xxhash/v0-8-4/en/02-api/14-group___x_x_h3__family/#gaa7f6e73421e0be9abd7181991ba8030f" title="Calculates 128-bit variant of XXH3 with a custom &quot;secret&quot;.">XXH3_128bits_withSecret()</a>.</p>&#10;<p>However, if the secret size is not known, it doesn't have any benefit. This happens when xxHash is compiled into a global symbol.
