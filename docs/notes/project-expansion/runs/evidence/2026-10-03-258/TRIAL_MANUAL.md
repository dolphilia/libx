<div class="sect1">&#10;<h2 id="_introduction">Introduction</h2>&#10;<div class="sectionbody">&#10;<div class="paragraph"><p>Ninja is yet another build system.  It takes as input the&#10;interdependencies of files (typically source code and output&#10;executables) and orchestrates building them, <em>quickly</em>.</p></div>&#10;<div class="paragraph"><p>Ninja joins a sea of other build systems.  Its distinguishing goal is&#10;to be fast.  It is born from&#10;<a href="http://neugierig.org/software/chromium/notes/2011/02/ninja.html">my&#10;work on the Chromium browser project</a>, which has over 30,000 source&#10;files and whose other build systems (including one built from custom&#10;non-recursive Makefiles) would take ten seconds to start building&#10;after changing one file.  Ninja is under a second.</p></div>&#10;<div class="sect2">&#10;<h3 id="_philosophical_overview">Philosophical overview</h3>&#10;<div class="paragraph"><p>Where other build systems are high-level languages, Ninja aims to be&#10;an assembler.</p></div>&#10;<div class="paragraph"><p>Build systems get slow when they need to make decisions.  When you are&#10;in an edit-compile cycle you want it to be as fast as possible — you&#10;want the build system to do the minimum work necessary to figure out&#10;what needs to be built immediately.</p></div>&#10;<div class="paragraph"><p>Ninja contains the barest functionality necessary to describe&#10;arbitrary dependency graphs.  Its lack of syntax makes it impossible&#10;to express complex decisions.</p></div>&#10;<div class="paragraph"><p>Instead, Ninja is intended to be used with a separate program&#10;generating its input files.  The generator program (like the&#10;<span class="monospaced">./configure</span> found in autotools projects) can analyze system&#10;dependencies and make as many decisions as possible up front so that&#10;incremental builds stay fast.  Going beyond autotools, even build-time&#10;decisions like "which compiler flags should I use?"  or "should I&#10;build a debug or release-mode binary?"  belong in the <span class="monospaced">.ninja</span> file&#10;generator.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_design_goals">Design goals</h3>&#10;<div class="paragraph"><p>Here are the design goals of Ninja:</p></div>&#10;<div class="ulist"><ul>&#10;<li>&#10;<p>&#10;very fast (i.e., instant) incremental builds, even for very large&#10;  projects.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;very little policy about how code is built.  Different projects and&#10;  higher-level build systems have different opinions about how code&#10;  should be built; for example, should built objects live alongside&#10;  the sources or should all build output go into a separate directory?&#10;  Is there a "package" rule that builds a distributable package of&#10;  the project?  Sidestep these decisions by trying to allow either to&#10;  be implemented, rather than choosing, even if that results in&#10;  more verbosity.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;get dependencies correct, and in particular situations that are&#10;  difficult to get right with Makefiles (e.g. outputs need an implicit&#10;  dependency on the command line used to generate them; to build C&#10;  source code you need to use gcc’s <span class="monospaced">-M</span> flags for header&#10;  dependencies).&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;when convenience and speed are in conflict, prefer speed.&#10;</p>&#10;</li>&#10;</ul></div>&#10;<div class="paragraph"><p>Some explicit <em>non-goals</em>:</p></div>&#10;<div class="ulist"><ul>&#10;<li>&#10;<p>&#10;convenient syntax for writing build files by hand.  <em>You should&#10;  generate your ninja files using another program</em>.  This is how we&#10;  can sidestep many policy decisions.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;built-in rules. <em>Out of the box, Ninja has no rules for&#10;  e.g. compiling C code.</em>&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;build-time customization of the build. <em>Options belong in&#10;  the program that generates the ninja files</em>.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;build-time decision-making ability such as conditionals or search&#10;  paths. <em>Making decisions is slow.</em>&#10;</p>&#10;</li>&#10;</ul></div>&#10;<div class="paragraph"><p>To restate, Ninja is faster than other build systems because it is&#10;painfully simple.  You must tell Ninja exactly what to do when you&#10;create your project’s <span class="monospaced">.ninja</span> files.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_comparison_to_make">Comparison to Make</h3>&#10;<div class="paragraph"><p>Ninja is closest in spirit and functionality to Make, relying on&#10;simple dependencies between file timestamps.</p></div>&#10;<div class="paragraph"><p>But fundamentally, make has a lot of <em>features</em>: suffix rules,&#10;functions, built-in rules that e.g. search for RCS files when building&#10;source.  Make’s language was designed to be written by humans.  Many&#10;projects find make alone adequate for their build problems.</p></div>&#10;<div class="paragraph"><p>In contrast, Ninja has almost no features; just those necessary to get&#10;builds correct while punting most complexity to generation of the&#10;ninja input files.  Ninja by itself is unlikely to be useful for most&#10;projects.</p></div>&#10;<div class="paragraph"><p>Here are some of the features Ninja adds to Make.  (These sorts of&#10;features can often be implemented using more complicated Makefiles,&#10;but they are not part of make itself.)</p></div>&#10;<div class="ulist"><ul>&#10;<li>&#10;<p>&#10;Ninja has special support for discovering extra dependencies at build&#10;  time, making it easy to get <a href="#ref_headers">header dependencies</a>&#10;  correct for C/C++ code.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;A build edge may have multiple outputs.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Outputs implicitly depend on the command line that was used to generate&#10;  them, which means that changing e.g. compilation flags will cause&#10;  the outputs to rebuild.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Output directories are always implicitly created before running the&#10;  command that relies on them.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Rules can provide shorter descriptions of the command being run, so&#10;  you can print e.g. <span class="monospaced">CC foo.o</span> instead of a long command line while&#10;  building.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Builds are always run in parallel, based by default on the number of&#10;  CPUs your system has.  Underspecified build dependencies will result&#10;  in incorrect builds.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Command output is always buffered.  This means commands running in&#10;  parallel don’t interleave their output, and when a command fails we&#10;  can print its failure output next to the full command line that&#10;  produced the failure.&#10;</p>&#10;</li>&#10;</ul></div>&#10;</div>&#10;</div>&#10;</div>&#10;<div class="sect1">&#10;<h2 id="_using_ninja_for_your_project">Using Ninja for your project</h2>&#10;<div class="sectionbody">&#10;<div class="paragraph"><p>Ninja currently works on Unix-like systems and Windows. It’s seen the&#10;most testing on Linux (and has the best performance there) but it runs&#10;fine on Mac OS X and FreeBSD.</p></div>&#10;<div class="paragraph"><p>If your project is small, Ninja’s speed impact is likely unnoticeable.&#10;(However, even for small projects it sometimes turns out that Ninja’s&#10;limited syntax forces simpler build rules that result in faster&#10;builds.)  Another way to say this is that if you’re happy with the&#10;edit-compile cycle time of your project already then Ninja won’t help.</p></div>&#10;<div class="paragraph"><p>There are many other build systems that are more user-friendly or&#10;featureful than Ninja itself.  For some recommendations: the Ninja&#10;author found <a href="http://gittup.org/tup/">the tup build system</a> influential&#10;in Ninja’s design, and thinks <a href="https://github.com/apenwarr/redo">redo</a>'s&#10;design is quite clever.</p></div>&#10;<div class="paragraph"><p>Ninja’s benefit comes from using it in conjunction with a smarter&#10;meta-build system.</p></div>&#10;<div class="dlist"><dl>&#10;<dt class="hdlist1">&#10;<a href="https://gn.googlesource.com/gn/">gn</a>&#10;</dt>&#10;<dd>&#10;<p>&#10;The meta-build system used to&#10;generate build files for Google Chrome and related projects (v8,&#10;node.js), as well as Google Fuchsia.  gn can generate Ninja files for&#10;all platforms supported by Chrome.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<a href="https://cmake.org/">CMake</a>&#10;</dt>&#10;<dd>&#10;<p>&#10;A widely used meta-build system that&#10;can generate Ninja files on Linux as of CMake version 2.8.8.  Newer versions&#10;of CMake support generating Ninja files on Windows and Mac OS X too.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<a href="https://github.com/ninja-build/ninja/wiki/List-of-generators-producing-ninja-build-files">others</a>&#10;</dt>&#10;<dd>&#10;<p>&#10;Ninja ought to fit perfectly into other meta-build software&#10;like <a href="https://premake.github.io/">premake</a>.  If you do this work,&#10;please let us know!&#10;</p>&#10;</dd>&#10;</dl></div>&#10;<div class="sect2">&#10;<h3 id="_running_ninja">Running Ninja</h3>&#10;<div class="paragraph"><p>Run <span class="monospaced">ninja</span>.  By default, it looks for a file named <span class="monospaced">build.ninja</span> in&#10;the current directory and builds all out-of-date targets.  You can&#10;specify which targets (files) to build as command line arguments.</p></div>&#10;<div class="paragraph"><p>There is also a special syntax <span class="monospaced">target^</span> for specifying a target&#10;as the first output of some rule containing the source you put in&#10;the command line, if one exists. For example, if you specify target as&#10;<span class="monospaced">foo.c^</span> then <span class="monospaced">foo.o</span> will get built (assuming you have those targets&#10;in your build files).</p></div>&#10;<div class="paragraph"><p><span class="monospaced">ninja -h</span> prints help output.  Many of Ninja’s flags intentionally&#10;match those of Make; e.g <span class="monospaced">ninja -C build -j 20</span> changes into the&#10;<span class="monospaced">build</span> directory and runs 20 build commands in parallel.  (Note that&#10;Ninja defaults to running commands in parallel anyway, so typically&#10;you don’t need to pass <span class="monospaced">-j</span>.)</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_gnu_jobserver_support">GNU Jobserver support</h3>&#10;<div class="paragraph"><p>Since version 1.13., Ninja builds can follow the&#10;<a href="https://www.gnu.org/software/make/manual/html_node/Job-Slots.html">GNU Make jobserver</a>&#10;client protocol. This is useful when Ninja is invoked as part of a larger&#10;build system controlled by a top-level GNU Make instance, or any other&#10;jobserver pool implementation, as it allows better coordination between&#10;concurrent build tasks.</p></div>&#10;<div class="paragraph"><p>This feature is automatically enabled under the following conditions:</p></div>&#10;<div class="ulist"><ul>&#10;<li>&#10;<p>&#10;Dry-run (i.e. <span class="monospaced">-n</span> or <span class="monospaced">--dry-run</span>) is not enabled.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;No explicit job count (e.g. <span class="monospaced">-j&lt;COUNT&gt;</span>) is passed on the command&#10;  line.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;The <span class="monospaced">MAKEFLAGS</span> environment variable is defined and describes a valid&#10;  jobserver mode using <span class="monospaced">--jobserver-auth=SEMAPHORE_NAME</span> on Windows, or&#10;  <span class="monospaced">--jobserver-auth=fifo:PATH</span> on Posix.&#10;</p>&#10;</li>&#10;</ul></div>&#10;<div class="paragraph"><p>In this case, Ninja will use the jobserver pool of job slots to control&#10;parallelism, instead of its default parallel implementation.</p></div>&#10;<div class="paragraph"><p>Note that load-average limitations (i.e. when using <span class="monospaced">-l&lt;count&gt;</span>)&#10;are still being enforced in this mode.</p></div>&#10;<div class="admonitionblock">&#10;<table><tbody><tr>&#10;<td class="icon">&#10;<div class="title">Important</div>&#10;</td>&#10;<td class="content">On Posix, only the FIFO-based version of the protocol, which is&#10;implemented by GNU Make 4.4 and higher, is supported. Ninja will detect&#10;when a pipe-based jobserver is being used (i.e. when <span class="monospaced">MAKEFLAGS</span> contains&#10;<span class="monospaced">--jobserver-auth=&lt;read&gt;,&lt;write&gt;</span>) and will print a warning, but will&#10;otherwise ignore it.</td>&#10;</tr></tbody></table>&#10;</div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_environment_variables">Environment variables</h3>&#10;<div class="paragraph"><p>Ninja supports two environment variables to control its behavior:&#10;<span class="monospaced">NINJA_STATUS</span>, the progress status printed before the rule being run.</p></div>&#10;<div class="paragraph"><p>Several placeholders are available:</p></div>&#10;<div class="dlist"><dl>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%s</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The number of started edges.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%t</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The total number of edges that must be run to complete the build.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%p</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The percentage of finished edges.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%r</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The number of currently running edges.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%u</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The number of remaining edges to start.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%f</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The number of finished edges.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span default)&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%e</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;Elapsed time in seconds. <em>(Available since Ninja 1.2.)</em>&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%E</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;Remaining time (ETA) in seconds. <em>(Available since Ninja 1.12.)</em>&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%w</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;Elapsed time in [h:]mm:ss format. <em>(Available since Ninja 1.12.)</em>&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%W</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;Remaining time (ETA) in [h:]mm:ss format. <em>(Available since Ninja 1.12.)</em>&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%P</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;The percentage (in ppp% format) of time elapsed out of predicted total runtime. <em>(Available since Ninja 1.12.)</em>&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">%%</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;A plain <span class="monospaced">%</span> character.&#10;</p>&#10;</dd>&#10;</dl></div>&#10;<div class="paragraph"><p>The default progress status is <span class="monospaced">"[%f/%t] "</span> (note the trailing space&#10;to separate from the build rule). Another example of possible progress status&#10;could be <span class="monospaced">"[%u/%r/%f] "</span>.</p></div>&#10;<div class="paragraph"><p>If <span class="monospaced">MAKEFLAGS</span> is defined in the environment, if may alter how&#10;Ninja dispatches parallel build commands. See the GNU Jobserver support&#10;section for details.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_extra_tools">Extra tools</h3>&#10;<div class="paragraph"><p>The <span class="monospaced">-t</span> flag on the Ninja command line runs some tools that we have&#10;found useful during Ninja’s development.  The current tools are:</p></div>&#10;<div class="hdlist"><table>&#10;<tbody><tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">query</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;dump the inputs and outputs of a given target.&#10;</p>&#10;</td>&#10;</tr>&#10;<tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">browse</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;browse the dependency graph in a web browser. date.&#10;</p>&#10;</td>&#10;</tr>&#10;<tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">inputs</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;given a class="monospaced">multi-inputs</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;print one or more sets of inputs required to build targets.&#10;Each line will consist of a target, a delimiter, an input and a terminator character.&#10;The list produced by the tool can be helpful if one would like to know which targets&#10;that are affected by a certain input.&#10;</p>&#10;<div class="paragraph"><p>The output will be a series of lines with the following elements:</p></div>&#10;<div class="listingblock">&#10;<div class="content Additional arguments are&#10;targets, which removes the given targets and recursively all files&#10;built for them.&#10;</p>&#10;<div class="paragraph"><p>If used like <span class="monospaced">ninja -t clean -r <em>rules</em></span> it removes all files built using&#10;the given rules.</p></div>&#10;<div class="paragraph"><p>Files created but not referenced in the graph are not removed. The resulting compilation database contains&#10;all commands required to build the indicated targets, and <em>only</em> those&#10;commands.&#10;</p>&#10;</td>&#10;</tr>&#10;<tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">deps</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;show all dependencies stored in the <span class="monospaced">.ninja_deps</span> file. When given a&#10;target, show just the target’s dependencies. <em>Available since Ninja 1.4.</em>&#10;</p>&#10;</td>&#10;</tr>&#10;<tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">missingdeps</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;given a list of targets, look for targets that depend on&#10;a generated file, but do not have a properly (possibly transitive) dependency&#10;on the generator.  Such targets may cause build flakiness on clean builds.&#10;</p>&#10;<div class="paragraph"><p>The broken targets can be found assuming deps log / depfile dependency&#10;information is correct.  Any target that depends on a generated file (output&#10;of a generator-target) implicitly, but does not have an explicit or order-only&#10;dependency path to the generator-target, is considered broken.</p></div>&#10;<div class="paragraph"><p>The tool’s findings can be verified by trying to build the listed targets in&#10;a clean outdir without building any other targets. It can be used to know which rule name&#10;to pass to <span class="monospaced">ninja -t targets rule <em>name</em></span> or <span class="monospaced">ninja -t compdb</span>. Adding the <span class="monospaced">-d</span>&#10;flag also prints the description of the rules.&#10;</p>&#10;</td>&#10;</tr>&#10;<tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">msvc</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;Available on Windows hosts only.&#10;Helper tool to invoke the <span class="monospaced">cl.exe</span> compiler with a pre-defined set of&#10;environment variables, as in:&#10;</p>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>ninja&#32;-t&#32;msvc&#32;-e&#32;ENVFILE&#32;--&#32;cl.exe&#32;&lt;arguments&gt;</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Where <span class="monospaced">ENVFILE</span> is a binary file that contains an environment block suitable&#10;for CreateProcessA() on Windows (i.e. a series of zero-terminated strings that&#10;look like NAME=VALUE, followed by an extra zero terminator). Note that this uses&#10;the local codepage encoding.</p></div>&#10;<div class="paragraph"><p>This tool also supports a deprecated way of parsing the compiler’s output when&#10;the <span class="monospaced">/showIncludes</span> flag is used, and generating a GCC-compatible depfile from it:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>ninja&#32;-t&#32;msvc&#32;-o&#32;DEPFILE&#32;[-p&#32;STRING]&#32;--&#32;cl.exe&#32;/showIncludes&#32;&lt;arguments&gt;</pre>&#10;</div></div>&#10;<div class="paragraph"><p>When using this option, <span class="monospaced">-p STRING</span> can be used to pass the localized line prefix&#10;that <span class="monospaced">cl.exe</span> uses to output dependency information. For English-speaking regions&#10;this is <span class="monospaced">"Note: including file: "</span> without the double quotes, but will be different&#10;for other regions.</p></div>&#10;<div class="paragraph"><p>Note that Ninja supports this natively now, with the use of <span class="monospaced">deps = msvc</span> and&#10;<span class="monospaced">msvc_deps_prefix</span> in Ninja files. Native support also avoids launching an extra&#10;tool process each time the compiler must be called, which can speed up builds&#10;noticeably on Windows.</p></div>&#10;</td>&#10;</tr>&#10;<tr>&#10;<td class="hdlist1">&#10;<span class="monospaced">wincodepage</span>&#10;<br>&#10;</td>&#10;<td class="hdlist2">&#10;<p style="margin-top: 0;">&#10;Available on Windows hosts (<em>since Ninja 1.11</em>).&#10;Prints the Windows code page whose encoding is expected in the build file.&#10;The output has the form:&#10;</p>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>Build&#32;file&#32;encoding:&#32;&lt;codepage&gt;</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Additional lines may be added in future versions of Ninja.</p></div>&#10;<div class="paragraph"><p>The <span class="monospaced">&lt;codepage&gt;</span> is one of:</p></div>&#10;<div class="dlist"><dl>&#10;<dt class="hdlist1">&#10;<span class="monospaced">UTF-8</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;Encode as UTF-8.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">ANSI</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;Encode to the system-wide ANSI code page.&#10;</p>&#10;</dd>&#10;</dl></div>&#10;</td>&#10;</tr>&#10;</tbody></table></div>&#10;</div>&#10;</div>&#10;</div>&#10;<div class="sect1">&#10;<h2 id="_writing_your_own_ninja_files">Writing your own Ninja files</h2>&#10;<div class="sectionbody">&#10;<div class="paragraph"><p>The remainder of this manual is only useful if you are constructing&#10;Ninja files yourself: for example, if you’re writing a meta-build&#10;system or supporting a new language.</p></div>&#10;<div class="sect2">&#10;<h3 id="_conceptual_overview">Conceptual overview</h3>&#10;<div class="paragraph"><p>Ninja evaluates a graph of dependencies between files, and runs&#10;whichever commands are necessary to make your build target up to date&#10;as determined by file modification times.  If you are familiar with&#10;Make, Ninja is very similar.</p></div>&#10;<div class="paragraph"><p>A build file (default name: <span class="monospaced">build.ninja</span>) provides a list of <em>rules</em> — short names for longer commands, like how to run the compiler — along with a list of <em>build</em> statements saying how to build files&#10;using the rules — which rule to apply to which inputs to produce&#10;which outputs.</p></div>&#10;<div class="paragraph"><p>Conceptually, <span class="monospaced">build</span> statements describe the dependency graph of your&#10;project, while <span class="monospaced">rule</span> statements describe how to generate the files&#10;along a given edge of the graph.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_syntax_example">Syntax example</h3>&#10;<div class="paragraph"><p>Here’s a basic <span class="monospaced">.ninja</span> file that demonstrates most of the syntax.&#10;It will be used as an example for the following sections.</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>cflags&#32;=&#32;-Wall&#10;&#10;rule&#32;cc&#10;&#32;&#32;command&#32;=&#32;gcc&#32;$cflags&#32;-c&#32;$in&#32;-o&#32;$out&#10;&#10;build&#32;foo.o:&#32;cc&#32;foo.c</pre>&#10;</div></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_variables">Variables</h3>&#10;<div class="paragraph"><p>Despite the non-goal of being convenient to write by hand, to keep&#10;build files readable (debuggable), Ninja supports declaring shorter&#10;reusable names for strings.  A declaration like the following</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>cflags&#32;=&#32;-g</pre>&#10;</div></div>&#10;<div class="paragraph"><p>can be used on the right side of an equals sign, dereferencing it with&#10;a dollar sign, like this:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;cc&#10;&#32;&#32;command&#32;=&#32;gcc&#32;$cflags&#32;-c&#32;$in&#32;-o&#32;$out</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Variables can also be referenced using curly braces like <span class="monospaced">${in}</span>.</p></div>&#10;<div class="paragraph"><p>Variables might better be called "bindings", in that a given variable&#10;cannot be changed, only shadowed.  There is more on how shadowing works&#10;later in this document.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_rules">Rules</h3>&#10;<div class="paragraph"><p>Rules declare a short name for a command line.  They begin with a line&#10;consisting of the <span class="monospaced">rule</span> keyword and a name for the rule.  Then&#10;follows an indented set of <span class="monospaced">variable = value</span> lines.</p></div>&#10;<div class="paragraph"><p>The basic example above declares a new rule named <span class="monospaced">cc</span>, along with the&#10;command to run.  In the context of a rule, the <span class="monospaced">command</span> variable&#10;defines the command to run, <span class="monospaced">$in</span> expands to the list of&#10;input files (<span class="monospaced">foo.c</span>), and <span class="monospaced">$out</span> to the output files (<span class="monospaced">foo.o</span>) for the&#10;command.  A full list of special variables is provided in&#10;<a href="#ref_rule">the reference</a>.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_build_statements">Build statements</h3>&#10;<div class="paragraph"><p>Build statements declare a relationship between input and output&#10;files.  They begin with the <span class="monospaced">build</span> keyword, and have the format&#10;<span class="monospaced">build <em>outputs</em>: <em>rulename</em> <em>inputs</em></span>.  Such a declaration says that&#10;all of the output files are derived from the input files.  When the&#10;output files are missing or when the inputs change, Ninja will run the&#10;rule to regenerate the outputs.</p></div>&#10;<div class="paragraph"><p>The basic example above describes how to build <span class="monospaced">foo.o</span>, using the <span class="monospaced">cc</span>&#10;rule.</p></div>&#10;<div class="paragraph"><p>In the scope of a <span class="monospaced">build</span> block (including in the evaluation of its&#10;associated <span class="monospaced">rule</span>), the variable <span class="monospaced">$in</span> is the list of inputs and the&#10;variable <span class="monospaced">$out</span> is the list of outputs.</p></div>&#10;<div class="paragraph"><p>A build statement may be followed by an indented set of <span class="monospaced">key = value</span>&#10;pairs, much like a rule.  These variables will shadow any variables&#10;when evaluating the variables in the command.  For example:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>cflags&#32;=&#32;-Wall&#32;-Werror&#10;rule&#32;cc&#10;&#32;&#32;command&#32;=&#32;gcc&#32;$cflags&#32;-c&#32;$in&#32;-o&#32;$out&#10;&#10;#&#32;If&#32;left&#32;unspecified,&#32;builds&#32;get&#32;the&#32;outer&#32;$cflags.&#10;build&#32;foo.o:&#32;cc&#32;foo.c&#10;&#10;#&#32;But&#32;you&#32;can&#32;shadow&#32;variables&#32;like&#32;cflags&#32;for&#32;a&#32;particular&#32;build.&#10;build&#32;special.o:&#32;cc&#32;special.c&#10;&#32;&#32;cflags&#32;=&#32;-Wall&#10;&#10;#&#32;The&#32;variable&#32;was&#32;only&#32;shadowed&#32;for&#32;the&#32;scope&#32;of&#32;special.o;&#10;#&#32;Subsequent&#32;build&#32;lines&#32;get&#32;the&#32;outer&#32;(original)&#32;cflags.&#10;build&#32;bar.o:&#32;cc&#32;bar.c</pre>&#10;</div></div>&#10;<div class="paragraph"><p>For more discussion of how scoping works, consult <a href="#ref_scope">the reference</a>.</p></div>&#10;<div class="paragraph"><p>If you need more complicated information passed from the build&#10;statement to the rule (for example, if the rule needs "the file&#10;extension of the first input"), pass that through as an extra&#10;variable, like how <span class="monospaced">cflags</span> is passed above.</p></div>&#10;<div class="paragraph"><p>If the top-level Ninja file is specified as an output of any build&#10;statement and it is out of date, Ninja will rebuild and reload it&#10;before building the targets requested by the user.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_generating_ninja_files_from_code">Generating Ninja files from code</h3>&#10;<div class="paragraph"><p><span class="monospaced">misc/ninja_syntax.py</span> in the Ninja distribution is a tiny Python&#10;module to facilitate generating Ninja files.  It allows you to make&#10;Python calls like <span class="monospaced">ninja.rule(name='foo', command='bar',&#10;depfile='$out.d')</span> and it will generate the appropriate syntax.  Feel&#10;free to just inline it into your project’s build system if it’s&#10;useful.</p></div>&#10;</div>&#10;</div>&#10;</div>&#10;<div class="sect1">&#10;<h2 id="_more_details">More details</h2>&#10;<div class="sectionbody">&#10;<div class="sect2">&#10;<h3 id="_the_span_class_monospaced_phony_span_rule">The <code>phony</code> rule</h3>&#10;<div class="paragraph"><p>The special rule name <span class="monospaced">phony</span> can be used to create aliases for other&#10;targets.  For example:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>build&#32;foo:&#32;phony&#32;some/file/in/a/faraway/subdir/foo</pre>&#10;</div></div>&#10;<div class="paragraph"><p>This makes <span class="monospaced">ninja foo</span> build the longer path.  Semantically, the&#10;<span class="monospaced">phony</span> rule is equivalent to a plain rule where the <span class="monospaced">command</span> does&#10;nothing, but phony rules are handled specially in that they aren’t&#10;printed when run, logged (see below), nor do they contribute to the&#10;command count printed as part of the build process.</p></div>&#10;<div class="paragraph"><p>When a <span class="monospaced">phony</span> target is used as an input to another build rule, the&#10;other build rule will, semantically, consider the inputs of the&#10;<span class="monospaced">phony</span> rule as its own. Therefore, <span class="monospaced">phony</span> rules can be used to group&#10;inputs, e.g. header files.</p></div>&#10;<div class="paragraph"><p><span class="monospaced">phony</span> can also be used to create dummy targets for files which&#10;may not exist at build time.  If a phony build statement is written&#10;without any dependencies, the target will be considered out of date if&#10;it does not exist.  Without a phony build statement, Ninja will report&#10;an error if the file does not exist and is required by the build.</p></div>&#10;<div class="paragraph"><p>To create a rule that never rebuilds, use a build rule without any input:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;touch&#10;&#32;&#32;command&#32;=&#32;touch&#32;$out&#10;build&#32;file_that_always_exists.dummy:&#32;touch&#10;build&#32;dummy_target_to_follow_a_pattern:&#32;phony&#32;file_that_always_exists.dummy</pre>&#10;</div></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_default_target_statements">Default target statements</h3>&#10;<div class="paragraph"><p>By default, if no targets are specified on the command line, Ninja&#10;will build every output that is not named as an input elsewhere.&#10;You can override this behavior using a default target statement.&#10;A default target statement causes Ninja to build only a given subset&#10;of output files if none are specified on the command line.</p></div>&#10;<div class="paragraph"><p>Default target statements begin with the <span class="monospaced">default</span> keyword, and have&#10;the format <span class="monospaced">default <em>targets</em></span>.  A default target statement must appear&#10;after the build statement that declares the target as an output file.&#10;They are cumulative, so multiple statements may be used to extend&#10;the list of default targets.  For example:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>default&#32;foo&#32;bar&#10;default&#32;baz</pre>&#10;</div></div>&#10;<div class="paragraph"><p>This causes Ninja to build the <span class="monospaced">foo</span>, <span class="monospaced">bar</span> and <span class="monospaced">baz</span> targets by&#10;default.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_log">The Ninja log</h3>&#10;<div class="paragraph"><p>For each built file, Ninja keeps a log of the command used to build&#10;it.  Using this log Ninja can know when an existing output was built&#10;with a different command line than the build files specify (i.e., the&#10;command line changed) and knows to rebuild the file.</p></div>&#10;<div class="paragraph"><p>The log file is kept in the build root in a file called <span class="monospaced">.ninja_log</span>.&#10;If you provide a variable named <span class="monospaced">builddir</span> in the outermost scope,&#10;<span class="monospaced">.ninja_log</span> will be kept in that directory instead.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_versioning">Version compatibility</h3>&#10;<div class="paragraph"><p><em>Available since Ninja 1.2.</em></p></div>&#10;<div class="paragraph"><p>Ninja version labels follow the standard major.minor.patch format,&#10;where the major version is increased on backwards-incompatible&#10;syntax/behavioral changes and the minor version is increased on new&#10;behaviors.  Your <span class="monospaced">build.ninja</span> may declare a variable named&#10;<span class="monospaced">ninja_required_version</span> that asserts the minimum Ninja version&#10;required to use the generated file.  For example,</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>ninja_required_version&#32;=&#32;1.1</pre>&#10;</div></div>&#10;<div class="paragraph"><p>declares that the build file relies on some feature that was&#10;introduced in Ninja 1.1 (perhaps the <span class="monospaced">pool</span> syntax), and that&#10;Ninja 1.1 or greater must be used to build.  Unlike other Ninja&#10;variables, this version requirement is checked immediately when&#10;the variable is encountered in parsing, so it’s best to put it&#10;at the top of the build file.</p></div>&#10;<div class="paragraph"><p>Ninja always warns if the major versions of Ninja and the&#10;<span class="monospaced">ninja_required_version</span> don’t match; a major version change hasn’t&#10;come up yet so it’s difficult to predict what behavior might be&#10;required.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_headers">C/C++ header dependencies</h3>&#10;<div class="paragraph"><p>To get C/C++ header dependencies (or any other build dependency that&#10;works in a similar way) correct Ninja has some extra functionality.</p></div>&#10;<div class="paragraph"><p>The problem with headers is that the full list of files that a given&#10;source file depends on can only be discovered by the compiler:&#10;different preprocessor defines and include paths cause different files&#10;to be used.  Some compilers can emit this information while building,&#10;and Ninja can use that to get its dependencies perfect.</p></div>&#10;<div class="paragraph"><p>Consider: if the file has never been compiled, it must be built anyway,&#10;generating the header dependencies as a side effect.  If any file is&#10;later modified (even in a way that changes which headers it depends&#10;on) the modification will cause a rebuild as well, keeping the&#10;dependencies up to date.</p></div>&#10;<div class="paragraph"><p>When loading these special dependencies, Ninja implicitly adds extra&#10;build edges such that it is not an error if the listed dependency is&#10;missing.  This allows you to delete a header file and rebuild without&#10;the build aborting due to a missing input.</p></div>&#10;<div class="sect3">&#10;<h4 id="_depfile">depfile</h4>&#10;<div class="paragraph"><p><span class="monospaced">gcc</span> (and other compilers like <span class="monospaced">clang</span>) support emitting dependency&#10;information in the syntax of a Makefile.  (Any command that can write&#10;dependencies in this form can be used, not just <span class="monospaced">gcc</span>.)</p></div>&#10;<div class="paragraph"><p>To bring this information into Ninja requires cooperation.  On the&#10;Ninja side, the <span class="monospaced">depfile</span> attribute on the <span class="monospaced">build</span> must point to a&#10;path where this data is written.  (Ninja only supports the limited&#10;subset of the Makefile syntax emitted by compilers.)  Then the command&#10;must know to write dependencies into the <span class="monospaced">depfile</span> path.&#10;Use it like in the following example:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;cc&#10;&#32;&#32;depfile&#32;=&#32;$out.d&#10;&#32;&#32;command&#32;=&#32;gcc&#32;-MD&#32;-MF&#32;$out.d&#32;[other&#32;gcc&#32;flags&#32;here]</pre>&#10;</div></div>&#10;<div class="paragraph"><p>The <span class="monospaced">-MD</span> flag to <span class="monospaced">gcc</span> tells it to output header dependencies, and&#10;the <span class="monospaced">-MF</span> flag tells it where to write them.</p></div>&#10;</div>&#10;<div class="sect3">&#10;<h4 id="_deps">deps</h4>&#10;<div class="paragraph"><p><em>(Available since Ninja 1.3.)</em></p></div>&#10;<div class="paragraph"><p>It turns out that for large projects (and particularly on Windows,&#10;where the file system is slow) loading these dependency files on&#10;startup is slow.</p></div>&#10;<div class="paragraph"><p>Ninja 1.3 can instead process dependencies just after they’re generated&#10;and save a compacted form of the same information in a Ninja-internal&#10;database.</p></div>&#10;<div class="paragraph"><p>Ninja supports this processing in two forms.</p></div>&#10;<div class="olist arabic"><ol class="arabic">&#10;<li>&#10;<p>&#10;<span class="monospaced">deps = gcc</span> specifies that the tool outputs <span class="monospaced">gcc</span>-style dependencies&#10;   in the form of Makefiles.  Adding this to the above example will&#10;   cause Ninja to process the <span class="monospaced">depfile</span> immediately after the&#10;   compilation finishes, then delete the <span class="monospaced">.d</span> file (which is only used&#10;   as a temporary).&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;<span class="monospaced">deps = msvc</span> specifies that the tool outputs header dependencies&#10;   in the form produced by the Visual Studio compiler’s&#10;   <a href="http://msdn.microsoft.com/en-us/library/hdkef6tk(v=vs.90).aspx"><span class="monospaced">/showIncludes</span>&#10;   flag</a>.  Briefly, this means the tool outputs specially-formatted lines&#10;   to its stdout.  Ninja then filters these lines from the displayed&#10;   output.  No <span class="monospaced">depfile</span> attribute is necessary, but the localized string&#10;   in front of the header file path should be globally defined. For instance,&#10;   <span class="monospaced">msvc_deps_prefix = Note: including file:</span>&#10;   for an English Visual Studio (the default).&#10;</p>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>msvc_deps_prefix&#32;=&#32;Note:&#32;including&#32;file:&#10;rule&#32;cc&#10;&#32;&#32;deps&#32;=&#32;msvc&#10;&#32;&#32;command&#32;=&#32;cl&#32;/showIncludes&#32;-c&#32;$in&#32;/Fo$out</pre>&#10;</div></div>&#10;</li>&#10;</ol></div>&#10;<div class="paragraph"><p>If the include directory directives are using absolute paths, your depfile&#10;may result in a mixture of relative and absolute paths. Paths used by other&#10;build rules need to match exactly. Therefore, it is recommended to use&#10;relative paths in these cases.</p></div>&#10;</div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_pool">Pools</h3>&#10;<div class="paragraph"><p><em>Available since Ninja 1.1.</em></p></div>&#10;<div class="paragraph"><p>Pools allow you to allocate one or more rules or edges a finite number&#10;of concurrent jobs which is more tightly restricted than the default&#10;parallelism.</p></div>&#10;<div class="paragraph"><p>This can be useful, for example, to restrict a particular expensive rule&#10;(like link steps for huge executables), or to restrict particular build&#10;statements which you know perform poorly when run concurrently.</p></div>&#10;<div class="paragraph"><p>Each pool has a <span class="monospaced">depth</span> variable which is specified in the build file.&#10;The pool is then referred to with the <span class="monospaced">pool</span> variable on either a rule&#10;or a build statement.</p></div>&#10;<div class="paragraph"><p>No matter what pools you specify, ninja will never run more concurrent jobs&#10;than the default parallelism, or the number of jobs specified on the command&#10;line (with <span class="monospaced">-j</span>).</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>#&#32;No&#32;more&#32;than&#32;4&#32;links&#32;at&#32;a&#32;time.&#10;pool&#32;link_pool&#10;&#32;&#32;depth&#32;=&#32;4&#10;&#10;#&#32;No&#32;more&#32;than&#32;1&#32;heavy&#32;object&#32;at&#32;a&#32;time.&#10;pool&#32;heavy_object_pool&#10;&#32;&#32;depth&#32;=&#32;1&#10;&#10;rule&#32;link&#10;&#32;&#32;...&#10;&#32;&#32;pool&#32;=&#32;link_pool&#10;&#10;rule&#32;cc&#10;&#32;&#32;...&#10;&#10;#&#32;The&#32;link_pool&#32;is&#32;used&#32;here.&#32;Only&#32;4&#32;links&#32;will&#32;run&#32;concurrently.&#10;build&#32;foo.exe:&#32;link&#32;input.obj&#10;&#10;#&#32;A&#32;build&#32;statement&#32;can&#32;be&#32;exempted&#32;from&#32;its&#32;rule's&#32;pool&#32;by&#32;setting&#32;an&#10;#&#32;empty&#32;pool.&#32;This&#32;effectively&#32;puts&#32;the&#32;build&#32;statement&#32;back&#32;into&#32;the&#32;default&#10;#&#32;pool,&#32;which&#32;has&#32;infinite&#32;depth.&#10;build&#32;other.exe:&#32;link&#32;input.obj&#10;&#32;&#32;pool&#32;=&#10;&#10;#&#32;A&#32;build&#32;statement&#32;can&#32;specify&#32;a&#32;pool&#32;directly.&#10;#&#32;Only&#32;one&#32;of&#32;these&#32;builds&#32;will&#32;run&#32;at&#32;a&#32;time.&#10;build&#32;heavy_object1.obj:&#32;cc&#32;heavy_obj1.cc&#10;&#32;&#32;pool&#32;=&#32;heavy_object_pool&#10;build&#32;heavy_object2.obj:&#32;cc&#32;heavy_obj2.cc&#10;&#32;&#32;pool&#32;=&#32;heavy_object_pool</pre>&#10;</div></div>&#10;<div class="sect3">&#10;<h4 id="_the_span_class_monospaced_console_span_pool">The <code>console</code> pool</h4>&#10;<div class="paragraph"><p><em>Available since Ninja 1.5.</em></p></div>&#10;<div class="paragraph"><p>There exists a pre-defined pool named <span class="monospaced">console</span> with a depth of 1. It has&#10;the special property that any task in the pool has direct access to the&#10;standard input, output and error streams provided to Ninja, which are&#10;normally connected to the user’s console (hence the name) but could be&#10;redirected. This can be useful for interactive tasks or long-running tasks&#10;which produce status updates on the console (such as test suites).</p></div>&#10;<div class="paragraph"><p>While a task in the <span class="monospaced">console</span> pool is running, Ninja’s regular output (such&#10;as progress status and output from concurrent tasks) is buffered until&#10;it completes.</p></div>&#10;</div>&#10;</div>&#10;</div>&#10;</div>&#10;<div class="sect1">&#10;<h2 id="ref_ninja_file">Ninja file reference</h2>&#10;<div class="sectionbody">&#10;<div class="paragraph"><p>A file is a series of declarations.  A declaration can be one of:</p></div>&#10;<div class="olist arabic"><ol class="arabic">&#10;<li>&#10;<p>&#10;A rule declaration, which begins with <span class="monospaced">rule <em>rulename</em></span>, and&#10;   then has a series of indented lines defining variables.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;A build edge, which looks like <span class="monospaced">build <em>output1</em> <em>output2</em>:&#10;   <em>rulename</em> <em>input1</em> <em>input2</em></span>.<br>&#10;   Implicit dependencies may be tacked on the end with <span class="monospaced">|&#10;   <em>dependency1</em> <em>dependency2</em></span>.<br>&#10;   Order-only dependencies may be tacked on the end with <span class="monospaced">||&#10;   <em>dependency1</em> <em>dependency2</em></span>.  (See <a href="#ref_dependencies">the reference on    dependency types</a>.)&#10;   Validations may be tacked on the end with <span class="monospaced">|@ <em>validation1</em> <em>validation2</em></span>.&#10;   (See <a href="#validations">the reference on validations</a>.)&#10;</p>&#10;<div class="paragraph"><p>Implicit outputs <em>(available since Ninja 1.7)</em> may be added before&#10;the <span class="monospaced">:</span> with <span class="monospaced">| <em>output1</em> <em>output2</em></span> and do not appear in <span class="monospaced">$out</span>.&#10;(See <a href="#ref_outputs">the reference on output types</a>.)</p></div>&#10;</li>&#10;<li>&#10;<p>&#10;Variable declarations, which look like <span class="monospaced"><em>variable</em> = <em>value</em></span>.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Default target statements, which look like <span class="monospaced">default <em>target1</em> <em>target2</em></span>.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;References to more files, which look like <span class="monospaced">subninja <em>path</em></span> or&#10;   <span class="monospaced">include <em>path</em></span>.  The difference between these is explained below&#10;   <a href="#ref_scope">in the discussion about scoping</a>.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;A pool declaration, which looks like <span class="monospaced">pool <em>poolname</em></span>. Pools are explained&#10;   <a href="#ref_pool">in the section on pools</a>.&#10;</p>&#10;</li>&#10;</ol></div>&#10;<div class="sect2">&#10;<h3 id="ref_lexer">Lexical syntax</h3>&#10;<div class="paragraph"><p>Ninja is mostly encoding agnostic, as long as the bytes Ninja cares&#10;about (like slashes in paths) are ASCII.  This means e.g. UTF-8 or&#10;ISO-8859-1 input files ought to work.</p></div>&#10;<div class="paragraph"><p>Comments begin with <span class="monospaced">#</span> and extend to the end of the line.</p></div>&#10;<div class="paragraph"><p>Newlines are significant.  Statements like <span class="monospaced">build foo bar</span> are a set&#10;of space-separated tokens that end at the newline.  Newlines and&#10;spaces within a token must be escaped.</p></div>&#10;<div class="paragraph"><p>There is only one escape character, <span class="monospaced">$</span>, and it has the following&#10;behaviors:</p></div>&#10;<div class="dlist"><dl>&#10;<dt class="hdlist1">&#10;<span class="monospaced">$</span> followed by a newline&#10;</dt>&#10;<dd>&#10;<p>&#10;escape the newline (continue the current line&#10;across a line break).&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">$</span> followed by text&#10;</dt>&#10;<dd>&#10;<p>&#10;a variable reference.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">${varname}</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;alternate syntax for <span class="monospaced">$varname</span>.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">$</span> followed by space&#10;</dt>&#10;<dd>&#10;<p>&#10;a space.  (This is only necessary in lists of&#10;paths, where a space would otherwise separate filenames.  See below.)&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">$:</span> &#10;</dt>&#10;<dd>&#10;<p>&#10;a colon.  (This is only necessary in <span class="monospaced">build</span> lines, where a colon&#10;would otherwise terminate the list of outputs.)&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">$$</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;a literal <span class="monospaced">$</span>.&#10;</p>&#10;</dd>&#10;</dl></div>&#10;<div class="paragraph"><p>A <span class="monospaced">build</span> or <span class="monospaced">default</span> statement is first parsed as a space-separated&#10;list of filenames and then each name is expanded.  This means that&#10;spaces within a variable will result in spaces in the expanded&#10;filename.</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>spaced&#32;=&#32;foo&#32;bar&#10;build&#32;$spaced/baz&#32;other$&#32;file:&#32;...&#10;#&#32;The&#32;above&#32;build&#32;line&#32;has&#32;two&#32;outputs:&#32;"foo&#32;bar/baz"&#32;and&#32;"other&#32;file".</pre>&#10;</div></div>&#10;<div class="paragraph"><p>In a <span class="monospaced">name = value</span> statement, whitespace at the beginning of a value&#10;is always stripped.  Whitespace at the beginning of a line after a&#10;line continuation is also stripped.</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>two_words_with_one_space&#32;=&#32;foo&#32;$&#10;&#32;&#32;&#32;&#32;bar&#10;one_word_with_no_space&#32;=&#32;foo$&#10;&#32;&#32;&#32;&#32;bar</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Other whitespace is only significant if it’s at the beginning of a&#10;line.  If a line is indented more than the previous one, it’s&#10;considered part of its parent’s scope; if it is indented less than the&#10;previous one, it closes the previous scope.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_toplevel">Top-level variables</h3>&#10;<div class="paragraph"><p>Two variables are significant when declared in the outermost file scope.</p></div>&#10;<div class="dlist"><dl>&#10;<dt class="hdlist1">&#10;<span class="monospaced">builddir</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;a directory for some Ninja output files.  See <a href="#ref_log">the   discussion of the build log</a>.  (You can also store other build output&#10;  in this directory.)&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">ninja_required_version</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;the minimum version of Ninja required to process&#10;  the build correctly.  See <a href="#ref_versioning">the discussion of versioning</a>.&#10;</p>&#10;</dd>&#10;</dl></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_rule">Rule variables</h3>&#10;<div class="paragraph"><p>A <span class="monospaced">rule</span> block contains a list of <span class="monospaced">key = value</span> declarations that&#10;affect the processing of the rule.  Here is a full list of special&#10;keys.</p></div>&#10;<div class="dlist"><dl>&#10;<dt class="hdlist1">&#10;<span class="monospaced">command</span> (<em>required</em>)&#10;</dt>&#10;<dd>&#10;<p>&#10;the command line to run.  Each <span class="monospaced">rule</span> may&#10;  have only one <span class="monospaced">command</span> declaration. See <a href="#ref_rule_command">the next   section</a> for more details on quoting and executing multiple commands.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">depfile</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;path to an optional <span class="monospaced">Makefile</span> that contains extra&#10;  <em>implicit dependencies</em> (see <a href="#ref_dependencies">the reference on   dependency types</a>).  This is explicitly to support C/C++ header&#10;  dependencies; see <a href="#ref_headers">the full discussion</a>.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">deps</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;<em>(Available since Ninja 1.3.)</em> if present, must be one of&#10;  <span class="monospaced">gcc</span> or <span class="monospaced">msvc</span> to specify special dependency processing.  See&#10;   <a href="#ref_headers">the full discussion</a>.  The generated database is&#10;   stored as <span class="monospaced">.ninja_deps</span> in the <span class="monospaced">builddir</span>, see <a href="#ref_toplevel">the    discussion of <span class="monospaced">builddir</span></a>.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">msvc_deps_prefix</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;<em>(Available since Ninja 1.5.)</em> defines the string&#10;  which should be stripped from msvc’s /showIncludes output. Only&#10;  needed when <span class="monospaced">deps = msvc</span> and no English Visual Studio version is used.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">description</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;a short description of the command, used to pretty-print&#10;  the command as it’s running.  The <span class="monospaced">-v</span> flag controls whether to print&#10;  the full command or its description; if a command fails, the full command&#10;  line will always be printed before the command’s output.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">dyndep</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;<em>(Available since Ninja 1.10.)</em> Used only on build statements.&#10;  If present, must name one of the build statement inputs.  Dynamically&#10;  discovered dependency information will be loaded from the file.&#10;  See the <a href="#ref_dyndep">dynamic dependencies</a> section for details.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">generator</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;if present, specifies that this rule is used to&#10;  re-invoke the generator program.  Files built using <span class="monospaced">generator</span>&#10;  rules are treated specially in two ways: firstly, they will not be&#10;  rebuilt if the command line changes; and secondly, they are not&#10;  cleaned by default.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">in</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;the space-separated list of files provided as inputs to the build line&#10;  referencing this <span class="monospaced">rule</span>, shell-quoted if it appears in commands.  (<span class="monospaced">$in</span> is&#10;  provided solely for convenience; if you need some subset or variant of this&#10;  list of files, just construct a new variable with that list and use&#10;  that instead.)&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">in_newline</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;the same as <span class="monospaced">$in</span> except that multiple inputs are&#10;  separated by newlines rather than spaces.  (For use with&#10;  <span class="monospaced">$rspfile_content</span>; this works around a bug in the MSVC linker where&#10;  it uses a fixed-size buffer for processing input.)&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">out</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;the space-separated list of files provided as outputs to the build line&#10;  referencing this <span class="monospaced">rule</span>, shell-quoted if it appears in commands.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">restat</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;if present, causes Ninja to re-stat the command’s outputs&#10;  after execution of the command.  Each output whose modification time&#10;  the command did not change will be treated as though it had never&#10;  needed to be built.  This may cause the output’s reverse&#10;  dependencies to be removed from the list of pending build actions.&#10;</p>&#10;</dd>&#10;<dt class="hdlist1">&#10;<span class="monospaced">rspfile</span>, <span class="monospaced">rspfile_content</span>&#10;</dt>&#10;<dd>&#10;<p>&#10;if present (both), Ninja will use a&#10;  response file for the given command, i.e. write the selected string&#10;  (<span class="monospaced">rspfile_content</span>) to the given file (<span class="monospaced">rspfile</span>) before calling the&#10;  command and delete the file after successful execution of the&#10;  command.&#10;</p>&#10;<div class="paragraph"><p>This is particularly useful on Windows OS, where the maximal length of&#10;a command line is limited and response files must be used instead.</p></div>&#10;<div class="paragraph"><p>Use it like in the following example:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;link&#10;&#32;&#32;command&#32;=&#32;link.exe&#32;/OUT$out&#32;[usual&#32;link&#32;flags&#32;here]&#32;@$out.rsp&#10;&#32;&#32;rspfile&#32;=&#32;$out.rsp&#10;&#32;&#32;rspfile_content&#32;=&#32;$in&#10;&#10;build&#32;myapp.exe:&#32;link&#32;a.obj&#32;b.obj&#32;[possibly&#32;many&#32;other&#32;.obj&#32;files]</pre>&#10;</div></div>&#10;</dd>&#10;</dl></div>&#10;<div class="sect3">&#10;<h4 id="ref_rule_command">Interpretation of the <code>command</code> variable</h4>&#10;<div class="paragraph"><p>Fundamentally, command lines behave differently on Unixes and Windows.</p></div>&#10;<div class="paragraph"><p>On Unixes, commands are arrays of arguments.  The Ninja <span class="monospaced">command</span>&#10;variable is passed directly to <span class="monospaced">sh -c</span>, which is then responsible for&#10;interpreting that string into an argv array.  Therefore, the quoting&#10;rules are those of the shell, and you can use all the normal shell&#10;operators, like <span class="monospaced">&amp;&amp;</span> to chain multiple commands, or <span class="monospaced">VAR=value cmd</span> to&#10;set environment variables.</p></div>&#10;<div class="paragraph"><p>On Windows, commands are strings, so Ninja passes the <span class="monospaced">command</span> string&#10;directly to <span class="monospaced">CreateProcess</span>.  (In the common case of simply executing&#10;a compiler this means there is less overhead.)  Consequently, the&#10;quoting rules are determined by the called program, which on Windows&#10;are usually provided by the C library.  If you need shell&#10;interpretation of the command (such as the use of <span class="monospaced">&amp;&amp;</span> to chain&#10;multiple commands), make the command execute the Windows shell by&#10;prefixing the command with <span class="monospaced">cmd /c</span>. Ninja may error with "invalid parameter"&#10;which usually indicates that the command line length has been exceeded.</p></div>&#10;</div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_outputs">Build outputs</h3>&#10;<div class="paragraph"><p>There are two types of build outputs which are subtly different.</p></div>&#10;<div class="olist arabic"><ol class="arabic">&#10;<li>&#10;<p>&#10;<em>Explicit outputs</em>, as listed in a build line.  These are&#10;   available as the <span class="monospaced">$out</span> variable in the rule.&#10;</p>&#10;<div class="paragraph"><p>This is the standard form of output to be used for e.g. the&#10;object file of a compile command.</p></div>&#10;</li>&#10;<li>&#10;<p>&#10;<em>Implicit outputs</em>, as listed in a build line with the syntax <span class="monospaced">|&#10;   <em>out1</em> <em>out2</em></span> before the <span class="monospaced">:</span> of a build line <em>(available since&#10;   Ninja 1.7)</em>.  The semantics are identical to explicit outputs,&#10;  the only difference is that implicit outputs don’t show up in the&#10;  <span class="monospaced">$out</span> variable.&#10;</p>&#10;<div class="paragraph"><p>This is for expressing outputs that don’t show up on the&#10;command line of the command.</p></div>&#10;</li>&#10;</ol></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_dependencies">Build dependencies</h3>&#10;<div class="paragraph"><p>There are three types of build dependencies which are subtly different.</p></div>&#10;<div class="olist arabic"><ol class="arabic">&#10;<li>&#10;<p>&#10;<em>Explicit dependencies</em>, as listed in a build line.  These are&#10;   available as the <span class="monospaced">$in</span> variable in the rule.  Changes in these files&#10;   cause the output to be rebuilt; if these files are missing and&#10;   Ninja doesn’t know how to build them, the build is aborted.&#10;</p>&#10;<div class="paragraph"><p>This is the standard form of dependency to be used e.g. for the&#10;source file of a compile command.</p></div>&#10;</li>&#10;<li>&#10;<p>&#10;<em>Implicit dependencies</em>, either as picked up from&#10;   a <span class="monospaced">depfile</span> attribute on a rule or from the syntax <span class="monospaced">| <em>dep1</em>&#10;   <em>dep2</em></span> on the end of a build line.  The semantics are identical to&#10;   explicit dependencies, the only difference is that implicit dependencies&#10;   don’t show up in the <span class="monospaced">$in</span> variable.&#10;</p>&#10;<div class="paragraph"><p>This is for expressing dependencies that don’t show up on the&#10;command line of the command; for example, for a rule that runs a&#10;script that reads a hardcoded file, the hardcoded file should&#10;be an implicit dependency, as changes to the file should cause&#10;the output to rebuild, even though it doesn’t show up in the arguments.</p></div>&#10;<div class="paragraph"><p>Note that dependencies as loaded through depfiles have slightly different&#10;semantics, as described in the <a href="#ref_rule">rule reference</a>.</p></div>&#10;</li>&#10;<li>&#10;<p>&#10;<em>Order-only dependencies</em>, expressed with the syntax <span class="monospaced">|| <em>dep1</em>&#10;   <em>dep2</em></span> on the end of a build line.  When these are out of date, the&#10;   output is not rebuilt until they are built, but changes in order-only&#10;   dependencies alone do not cause the output to be rebuilt.&#10;</p>&#10;<div class="paragraph"><p>Order-only dependencies can be useful for bootstrapping dependencies&#10;that are only discovered during build time: for example, to generate a&#10;header file before starting a subsequent compilation step.  (Once the&#10;header is used in compilation, a generated dependency file will then&#10;express the implicit dependency.)</p></div>&#10;</li>&#10;</ol></div>&#10;<div class="paragraph"><p>File paths are compared as is, which means that an absolute path and a&#10;relative path, pointing to the same file, are considered different by Ninja.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="validations">Validations</h3>&#10;<div class="paragraph"><p><em>Available since Ninja 1.11.</em></p></div>&#10;<div class="paragraph"><p>Validations listed on the build line cause the specified files to be&#10;added to the top level of the build graph (as if they were specified&#10;on the Ninja command line) whenever the build line is a transitive&#10;dependency of one of the targets specified on the command line or a&#10;default target.</p></div>&#10;<div class="paragraph"><p>Validations are added to the build graph regardless of whether the output&#10;files of the build statement are dirty are not, and the dirty state of&#10;the build statement that outputs the file being used as a validation&#10;has no effect on the dirty state of the build statement that requested it.</p></div>&#10;<div class="paragraph"><p>A build edge can list another build edge as a validation even if the second&#10;edge depends on the first.</p></div>&#10;<div class="paragraph"><p>Validations are designed to handle rules that perform error checking but&#10;don’t produce any artifacts needed by the build, for example, static&#10;analysis tools.  Marking the static analysis rule as an implicit input&#10;of the main build rule of the source files or of the rules that depend&#10;on the main build rule would slow down the critical path of the build,&#10;but using a validation would allow the build to proceed in parallel with&#10;the static analysis rule once the main build rule is complete.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_variable_expansion">Variable expansion</h3>&#10;<div class="paragraph"><p>Variables are expanded in paths (in a <span class="monospaced">build</span> or <span class="monospaced">default</span> statement)&#10;and on the right side of a <span class="monospaced">name = value</span> statement.</p></div>&#10;<div class="paragraph"><p>When a <span class="monospaced">name = value</span> statement is evaluated, its right-hand side is&#10;expanded immediately (according to the below scoping rules), and&#10;from then on <span class="monospaced">$name</span> expands to the static string as the result of the&#10;expansion.  It is never the case that you’ll need to "double-escape" a&#10;value to prevent it from getting expanded twice.</p></div>&#10;<div class="paragraph"><p>All variables are expanded immediately as they’re encountered in parsing,&#10;with one important exception: variables in <span class="monospaced">rule</span> blocks are expanded&#10;when the rule is <em>used</em>, not when it is declared.  In the following&#10;example, the <span class="monospaced">demo</span> rule prints "this is a demo of bar".</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;demo&#10;&#32;&#32;command&#32;=&#32;echo&#32;"this&#32;is&#32;a&#32;demo&#32;of&#32;$foo"&#10;&#10;build&#32;out:&#32;demo&#10;&#32;&#32;foo&#32;=&#32;bar</pre>&#10;</div></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="ref_scope">Evaluation and scoping</h3>&#10;<div class="paragraph"><p>Top-level variable declarations are scoped to the file they occur in.</p></div>&#10;<div class="paragraph"><p>Rule declarations are also scoped to the file they occur in.&#10;<em>(Available since Ninja 1.6)</em></p></div>&#10;<div class="paragraph"><p>The <span class="monospaced">subninja</span> keyword, used to include another <span class="monospaced">.ninja</span> file,&#10;introduces a new scope.  The included <span class="monospaced">subninja</span> file may use the&#10;variables and rules from the parent file, and shadow their values for the file’s&#10;scope, but it won’t affect values of the variables in the parent.</p></div>&#10;<div class="paragraph"><p>To include another <span class="monospaced">.ninja</span> file in the current scope, much like a C&#10;<span class="monospaced">#include</span> statement, use <span class="monospaced">include</span> instead of <span class="monospaced">subninja</span>.</p></div>&#10;<div class="paragraph"><p>Variable declarations indented in a <span class="monospaced">build</span> block are scoped to the&#10;<span class="monospaced">build</span> block.  The full lookup order for a variable expanded in a&#10;<span class="monospaced">build</span> block (or the <span class="monospaced">rule</span> is uses) is:</p></div>&#10;<div class="olist arabic"><ol class="arabic">&#10;<li>&#10;<p>&#10;Special built-in variables (<span class="monospaced">$in</span>, <span class="monospaced">$out</span>).&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Build-level variables from the <span class="monospaced">build</span> block.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Rule-level variables from the <span class="monospaced">rule</span> block (i.e. <span class="monospaced">$command</span>).&#10;   (Note from the above discussion on expansion that these are&#10;   expanded "late", and may make use of in-scope bindings like <span class="monospaced">$in</span>.)&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;File-level variables from the file that the <span class="monospaced">build</span> line was in.&#10;</p>&#10;</li>&#10;<li>&#10;<p>&#10;Variables from the file that included that file using the&#10;   <span class="monospaced">subninja</span> keyword.&#10;</p>&#10;</li>&#10;</ol></div>&#10;</div>&#10;</div>&#10;</div>&#10;<div class="sect1">&#10;<h2 id="ref_dyndep">Dynamic Dependencies</h2>&#10;<div class="sectionbody">&#10;<div class="paragraph"><p><em>Available since Ninja 1.10.</em></p></div>&#10;<div class="paragraph"><p>Some use cases require implicit dependency information to be dynamically&#10;discovered from source file content <em>during the build</em> in order to build&#10;correctly on the first run (e.g. Fortran module dependencies).  This is&#10;unlike <a href="#ref_headers">header dependencies</a> which are only needed on the&#10;second run and later to rebuild correctly.  A build statement may have a&#10;<span class="monospaced">dyndep</span> binding naming one of its inputs to specify that dynamic&#10;dependency information must be loaded from the file.  For example:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>build&#32;out:&#32;...&#32;||&#32;foo&#10;&#32;&#32;dyndep&#32;=&#32;foo&#10;build&#32;foo:&#32;...</pre>&#10;</div></div>&#10;<div class="paragraph"><p>This specifies that file <span class="monospaced">foo</span> is a dyndep file.  Since it is an input,&#10;the build statement for <span class="monospaced">out</span> can never be executed before <span class="monospaced">foo</span> is built.&#10;As soon as <span class="monospaced">foo</span> is finished Ninja will read it to load dynamically&#10;discovered dependency information for <span class="monospaced">out</span>.  This may include additional&#10;implicit inputs and/or outputs.  Ninja will update the build graph&#10;accordingly and the build will proceed as if the information was known&#10;originally.</p></div>&#10;<div class="sect2">&#10;<h3 id="_dyndep_file_reference">Dyndep file reference</h3>&#10;<div class="paragraph"><p>Files specified by <span class="monospaced">dyndep</span> bindings use the same <a href="#ref_lexer">lexical syntax</a>&#10;as <a href="#ref_ninja_file">ninja build files</a> and have the following layout.</p></div>&#10;<div class="olist arabic"><ol class="arabic">&#10;<li>&#10;<p>&#10;A version number in the form <span class="monospaced">&lt;major&gt;[.&lt;minor&gt;][&lt;suffix&gt;]</span>:&#10;</p>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>ninja_dyndep_version&#32;=&#32;1</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Currently the version number must always be <span class="monospaced">1</span> or <span class="monospaced">1.0</span> but may have&#10;an arbitrary suffix.</p></div>&#10;</li>&#10;<li>&#10;<p>&#10;One or more build statements of the form:&#10;</p>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>build&#32;out&#32;|&#32;imp-outs...&#32;:&#32;dyndep&#32;|&#32;imp-ins...</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Every statement must specify exactly one explicit output and must use&#10;the rule name <span class="monospaced">dyndep</span>.  The <span class="monospaced">| imp-outs...</span> and <span class="monospaced">| imp-ins...</span> portions&#10;are optional.</p></div>&#10;</li>&#10;<li>&#10;<p>&#10;An optional <span class="monospaced">restat</span> <a href="#ref_rule">variable binding</a> on each build statement.&#10;</p>&#10;</li>&#10;</ol></div>&#10;<div class="paragraph"><p>The build statements in a dyndep file must have a one-to-one correspondence&#10;to build statements in the <a href="#ref_ninja_file">ninja build file</a> that name the&#10;dyndep file in a <span class="monospaced">dyndep</span> binding.  No dyndep build statement may be omitted&#10;and no extra build statements may be specified.</p></div>&#10;</div>&#10;<div class="sect2">&#10;<h3 id="_dyndep_examples">Dyndep Examples</h3>&#10;<div class="sect3">&#10;<h4 id="_fortran_modules">Fortran Modules</h4>&#10;<div class="paragraph"><p>Consider a Fortran source file <span class="monospaced">foo.f90</span> that provides a module&#10;<span class="monospaced">foo.mod</span> (an implicit output of compilation) and another source file&#10;<span class="monospaced">bar.f90</span> that uses the module (an implicit input of compilation).  This&#10;implicit dependency must be discovered before we compile either source&#10;in order to ensure that <span class="monospaced">bar.f90</span> never compiles before <span class="monospaced">foo.f90</span>, and&#10;that <span class="monospaced">bar.f90</span> recompiles when <span class="monospaced">foo.mod</span> changes.  We can achieve this&#10;as follows:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;f95&#10;&#32;&#32;command&#32;=&#32;f95&#32;-o&#32;$out&#32;-c&#32;$in&#10;rule&#32;fscan&#10;&#32;&#32;command&#32;=&#32;fscan&#32;-o&#32;$out&#32;$in&#10;&#10;build&#32;foobar.dd:&#32;fscan&#32;foo.f90&#32;bar.f90&#10;&#10;build&#32;foo.o:&#32;f95&#32;foo.f90&#32;||&#32;foobar.dd&#10;&#32;&#32;dyndep&#32;=&#32;foobar.dd&#10;build&#32;bar.o:&#32;f95&#32;bar.f90&#32;||&#32;foobar.dd&#10;&#32;&#32;dyndep&#32;=&#32;foobar.dd</pre>&#10;</div></div>&#10;<div class="paragraph"><p>In this example the order-only dependencies ensure that <span class="monospaced">foobar.dd</span> is&#10;generated before either source compiles.  The hypothetical <span class="monospaced">fscan</span> tool&#10;scans the source files, assumes each will be compiled to a <span class="monospaced">.o</span> of the&#10;same name, and writes <span class="monospaced">foobar.dd</span> with content such as:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>ninja_dyndep_version&#32;=&#32;1&#10;build&#32;foo.o&#32;|&#32;foo.mod:&#32;dyndep&#10;build&#32;bar.o:&#32;dyndep&#32;|&#32;&#32;foo.mod</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Ninja will load this file to add <span class="monospaced">foo.mod</span> as an implicit output of&#10;<span class="monospaced">foo.o</span> and implicit input of <span class="monospaced">bar.o</span>.  This ensures that the Fortran&#10;sources are always compiled in the proper order and recompiled when&#10;needed.</p></div>&#10;</div>&#10;<div class="sect3">&#10;<h4 id="_tarball_extraction">Tarball Extraction</h4>&#10;<div class="paragraph"><p>Consider a tarball <span class="monospaced">foo.tar</span> that we want to extract.  The extraction time&#10;can be recorded with a <span class="monospaced">foo.tar.stamp</span> file so that extraction repeats if&#10;the tarball changes, but we also would like to re-extract if any of the&#10;outputs is missing.  However, the list of outputs depends on the content&#10;of the tarball and cannot be spelled out explicitly in the ninja build file.&#10;We can achieve this as follows:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>rule&#32;untar&#10;&#32;&#32;command&#32;=&#32;tar&#32;xf&#32;$in&#32;&amp;&amp;&#32;touch&#32;$out&#10;rule&#32;scantar&#10;&#32;&#32;command&#32;=&#32;scantar&#32;--stamp=$stamp&#32;--dd=$out&#32;$in&#10;build&#32;foo.tar.dd:&#32;scantar&#32;foo.tar&#10;&#32;&#32;stamp&#32;=&#32;foo.tar.stamp&#10;build&#32;foo.tar.stamp:&#32;untar&#32;foo.tar&#32;||&#32;foo.tar.dd&#10;&#32;&#32;dyndep&#32;=&#32;foo.tar.dd</pre>&#10;</div></div>&#10;<div class="paragraph"><p>In this example the order-only dependency ensures that <span class="monospaced">foo.tar.dd</span> is&#10;built before the tarball extracts.  The hypothetical <span class="monospaced">scantar</span> tool&#10;will read the tarball (e.g. via <span class="monospaced">tar tf</span>) and write <span class="monospaced">foo.tar.dd</span> with&#10;content such as:</p></div>&#10;<div class="listingblock">&#10;<div class="content monospaced">&#10;<pre>ninja_dyndep_version&#32;=&#32;1&#10;build&#32;foo.tar.stamp&#32;|&#32;file1.txt&#32;file2.txt&#32;:&#32;dyndep&#10;&#32;&#32;restat&#32;=&#32;1</pre>&#10;</div></div>&#10;<div class="paragraph"><p>Ninja will load this file to add <span class="monospaced">file1.txt</span> and <span class="monospaced">file2.txt</span> as implicit&#10;outputs of <span class="monospaced">foo.tar.stamp</span>, and to mark the build statement for <span class="monospaced">restat</span>.&#10;On future builds, if any implicit output is missing the tarball will be&#10;extracted again.  The <span class="monospaced">restat</span> binding tells Ninja to tolerate the fact&#10;that the implicit outputs may not have modification times newer than&#10;the tarball itself (avoiding re-extraction on every build).</p></div>&#10;</div>&#10;</div>&#10;</div>&#10;</div>&#10;
