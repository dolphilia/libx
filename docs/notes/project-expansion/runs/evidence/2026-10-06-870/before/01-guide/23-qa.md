<h1 id="page-title">Q&amp;A</h1>
<h2>なぜWrenを作ったのですか？ <a class="header-anchor" href="#why-did-you-create-wren" name="why-did-you-create-wren">#</a></h2>
<p>ほかの創作活動は、始めた途端に存在意義を問われたりしませんが、なぜかプログラマーは、新しい言語を好まないようです。私が埋めようとしている分野は、次のとおりです。</p>
<p>アプリケーションへ組み込むために使う、スクリプト言語はいくつかあります。中心はLuaです。以前はTCLでした。Guileもあり、JavaScriptも増えていて、Pythonを組み込むアプリケーションもあります。私は元ゲーム開発者なので、「スクリプト」と聞くと、「ゲームのスクリプト」を考えがちです。</p>
<p>Luaは良い言語です。小さく、単純で、高速です。しかし、批判するつもりではありませんが、C++やJavaなどに慣れていると、変わった言語でもあります。構文が違います。意味論、特にオブジェクトのモデルは独特です。1から始まるインデックスには誰でも慣れますが、メタテーブルなどを見ると、Luaへ後からオブジェクトを付け加えたことが、よく分かります。</p>
<p>Luaと同じくらい単純で、オブジェクト指向の経験がある人に自然に感じられる言語には、余地があると思います。Wrenは、それを目指す私の試みです。</p>
<h2>なぜクラスなのですか？ <a class="header-anchor" href="#why-classes" name="why-classes">#</a></h2>
<p>JavaScriptの人気のおかげで、多くの人が今、プロトタイプを知り、その方式の人気が高まっています。プロトタイプは面白いと思いますが、<a href="http://finch.stuffwithstuff.com/">数年間試した</a>後、プロトタイプを考案した元のSelfプロジェクトの多くの人々と同様に、クラスの方が使いやすいと結論付けました。</p>
<p>Luaで、そのようなオブジェクト指向のプログラミングを行う例を示します。</p>
<pre class="snippet"><code>&#10;-- account.lua&#10;&#10;Account = {}&#10;Account.__index = Account&#10;&#10;function Account.create(balance)&#10;   local acnt = {}             -- our new object&#10;   setmetatable(acnt,Account)  -- make Account handle lookup&#10;   acnt.balance = balance      -- initialize our object&#10;   return acnt&#10;end&#10;&#10;function Account:withdraw(amount)&#10;   self.balance = self.balance - amount&#10;end&#10;&#10;-- create and use an Account&#10;account = Account.create(1000)&#10;account:withdraw(100)&#10;</code></pre>
<p>同じ例をWrenで示します。</p>
<pre class="snippet"><code>&#10;//account.wren&#10;&#10;class Account {&#10;  construct new(balance) { _balance = balance }&#10;  withdraw(amount) { _balance = _balance - amount }&#10;}&#10;&#10;// create and use an Account&#10;var account = Account.new(1000)&#10;account.withdraw(100)&#10;</code></pre>
<p>クラスは複雑だと言われますが、それは、クラスを持つ広く使われた言語のほとんど、C++、Java、C#、Ruby、Pythonが、とても複雑だからです。複雑なのは、その言語であり、クラス自身ではないことを、Wrenで示したいと思います。</p>
<p>それらの多くに影響を与えたSmalltalkは、単純なことで有名です。構文は、<a href="http://www.jarober.com/blog/blogView?showComments=true&amp;title=Readability+is+Key&amp;entry=3506312690">索引カードに収まります</a>。私の目標は、Wrenをそれほど小さく保ちながら、<a href="/docs/wren/v0-4-0/en/01-guide/10-classes/">クラス</a>の表現力も持たせることです。</p>
<h2>なぜバイトコードへコンパイルするのですか？ <a class="header-anchor" href="#why-compile-to-bytecode" name="why-compile-to-bytecode">#</a></h2>
<p>詳しくは<a href="/docs/wren/v0-4-0/en/01-guide/22-performance/">性能のページ</a>にありますが、短く言えば、バイトコードは性能と単純さの良い折り合いだからです。ほかにも、次の理由があります。</p>
<ul>
<li><p>iPhoneやゲーム機などの多くの機器は、実行時に生成したコードの実行を許可しないため、JITコンパイルを使えません。</p></li>
<li><p><a href="/docs/wren/v0-4-0/en/01-guide/12-concurrency/">ファイバー</a>は、とても強力な道具だと思います。ネイティブスタックを使わないバイトコードVMなら、その実装は簡単です。</p></li>
</ul>
<h2>なぜVMはレジスター方式ではなく、スタック方式なのですか？ <a class="header-anchor" href="#why-is-the-vm-stack-based-instead-of-register-based" name="why-is-the-vm-stack-based-instead-of-register-based">#</a></h2>
<p>バイトコードVMには、二つの方式があります。スタック方式のVMは、短い、通常1バイトの命令を持ち、そのオペランドは暗黙にスタックの先頭にあると分かります。そのため、何かをスタックへプッシュするいくつかの命令と、その後に何かを行う命令が並ぶことがよくあります。</p>
<p>レジスター方式のVMには、大きな、通常32ビットの命令があり、オペコードと、スタック内のオペランドの場所を示すいくつかの数値を含みます。便利なのは、例えば次のLuaの文を、</p>
<pre class="snippet"><code>&#10;a = b + c&#10;</code></pre>
<p>一つのバイトコード命令にできることです。スタック方式の言語なら、<code>b</code>をプッシュ、<code>c</code>をプッシュ、加算、<code>a</code>へ保存、という四つになります。（ただし、どちらもコードは合計32ビットである点に注意してください。）</p>
<p>Luaは、以前はスタック方式でしたが、レジスター方式へ変えて高速になりました。なぜWrenもレジスターを使わないのでしょうか？</p>
<p>私は、<a href="http://finch.stuffwithstuff.com/">以前、レジスター方式のVMを実装しました</a>。良いモデルだと思いますが、Wrenには大きな利点をもたらさないと思います。コンパイルにより多くの手間がかかり、私は、Wrenの実装をできるだけ単純に保とうとしています。</p>
<p>その複雑さと引き換えに、命令数を減らせます。しかし、Wrenは、その利点を使えないと思います。現在、Wrenには算術演算専用の命令がありません。演算子は通常のメソッド呼び出しであり、利用者が定義した手続きを呼び出すこともできます。</p>
<p>メソッドの呼び出し規約は、すべての引数を呼び出し元のスタック先頭へ置くことを必要とします。それを、呼び出し先のスタックフレーム領域の底にできるようにするためです。Wrenで<code>+</code>を呼び出すには、やはり引数をスタックの先頭へプッシュする必要があります。同様に、呼び出し規約は、戻り値を最初の引数があった場所へ置くので、呼び出し後、それを宛先スロットへ戻す必要があります。</p>
<p>利用者定義の演算子メソッドへフォールバックする前に、組み込み型を特別扱いする算術命令を用意する価値はあるかもしれません。（Luaは、言語の開発後期に演算子のオーバーロードを追加したので、そうしていると推測します。）そうなれば、レジスター方式へ移れるかもしれません。</p>
<p>しかし、実際に性能上の利点になるとは確信していません。レジスター方式のVMが有利かどうかは、言語の細かな仕様の多くに左右されます。例えば、代入はLuaでは文ですが、Wrenでは式なので、効率的なレジスター方式のコードへコンパイルするのが難しくなります。</p>
<h2>ほかに作った言語は、どうするのですか？ <a class="header-anchor" href="#what-about-your-other-languages" name="what-about-your-other-languages">#</a></h2>
<p><a href="http://journal.stuffwithstuff.com">私が誰か</a>を知らなければ、奇妙な質問でしょう。以前、<a href="http://finch.stuffwithstuff.com/">Finch</a>や<a href="http://magpie-lang.org/">Magpie</a>など、ほかにも趣味の言語を作り、ブログへ書きました。</p>
<p>Finchは、インタープリターの実装と、プロトタイプ方式を、もっと知るために始めました。どちらについても、多くを学びました。特に、私はプロトタイプよりクラスを強く好むと分かりました。Finchへクラスを後付けし始めましたが、大きすぎる変更だと気付き、こうしてWrenが生まれました。</p>
<p>私にとって、WrenはFinchの代わりです。名前を変えた主な理由は、ほかの人がFinchを引き継いで何かしたい場合に、残しておくためです。私には、もうFinchで作業する意図はありません。</p>
<p>Magpieは、もう少し難しい話です。私は、Magpieの考え方がとても好きです。多くの場面で、こんな汎用言語が欲しいと思う言語です。パターンマッチングと多重ディスパッチが大好きです。<a href="https://github.com/joyent/libuv">libuv</a>のイベント駆動IOを、ファイバーの単純さと結び付けるところも気に入っています。</p>
<p>しかし、はるかに難しいプロジェクトでもあります。汎用言語なので、何かに使えるようになるまでに、大量のライブラリー作業が必要です。GCには、未解決の問題があります。そして、正直なところ、今の私には、多重ディスパッチを効率的に実装するだけの技量がありません。</p>
<p>その間、Magpieを作り始めてから、<a href="http://julialang.org/">Julia</a>が現れ、<a href="http://opendylan.org/">Dylan</a>が<em>再び</em>現れました。Magpieを作った理由の一つは、多重ディスパッチの火を受け継ぐことでしたが、今は、ほかの人たちが、その光を広げ始めています。</p>
