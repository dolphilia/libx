## 1. 結論

`apps/awesome`は一つの閲覧サイトとして維持し、内部の生成単位を「リスト × 版 × 言語」に分けることを推奨する。リストごとに`apps/`やCloudflareプロジェクトを増やす必要はない。

短期はサイドバーHTMLの重複削減とCI成果物の再利用を優先する。次に、入力を限定した個別ビルドと再利用可能な成果物を導入する。リスト単位で独立した公開まで必要なら、Awesome部分だけをWorker＋R2に移し、生成済みHTMLを配信する。

libx全体では「閲覧サイト」「生成単位」「公開単位」を区別できる設計へ進める。ただし、小規模アプリは現在のサイト単位の静的ビルド・Pages配信を既定とする。すべてのアプリに増分ビルドやR2を必須化しない。

今から共通化する価値が高いのは、計測、出力の所有範囲、変更依存関係、生成物の識別、検証済み成果物の公開という契約である。これらは配信先を変えなくても有効である。

## 2. 背景と既存方針との関係

libxは複数の文書群をアプリへ分散し、変更していないサイトの再ビルドを避けることを重視している。一方、Awesomeでは多数のリストを一つのナビゲーション・検索・言語／版選択の下で閲覧できることに価値がある。

既存の[単一アプリ構成](./document-import/awesome/SINGLE_APP_ARCHITECTURE.md)は、大きなcontent collectionのdata-layer assetを避けるため、Markdownの遅延importを採用している。この判断には最大ファイルサイズを抑えた実績がある。ただし、遅延importはサイト内の一部だけをビルド・公開できることまでは保証しない。

関係する既存方針は次のとおり。

- [正式原則](../spec/PROJECT_PRINCIPLES.md): ファイル正本、静的HTML、変更範囲への処理限定、単純な運用を維持する。
- [ADR-0006](../adr/0006-deployment-asset-budget-and-edge-compression.md): 成果物の予算管理、事前gzipの廃止、当時の規模でR2全面移行を見送る判断。
- [ADR-0008](../adr/0008-site-scoped-static-search.md): サイト・版・言語別の遅延読込検索。現行は1索引2 MiBの予算。
- [ADR-0009](../adr/0009-synchronize-doc-site-layouts.md): 正規テンプレートから共通レイアウトを同期する。
- [既存の配信規模調査](./DEPLOYMENT_FILE_COUNT_SCALING_RESEARCH.md): ファイル数上限を中心に、サイト分割を優先する段階的方針。
- [性能測定ガイド](../guides/PERFORMANCE_MEASUREMENT_GUIDE.md): サイト別ビルドの予算超過時に文書単位の増分処理よりサイト分割を優先する。

今回の提案は、ファイル数上限への到達だけでなく、閲覧上は分割したくない文書群の個別更新と障害範囲の縮小をR2検討の理由に加えるものになる。実装前に、新ADRで適用条件と既存原則への影響を明確にする。承認済みADRや過去の計測値を、このメモで遡って書き換えない。

## 3. 実測結果と限界

### 3.1 Awesomeの生成物

計測対象は既存のローカル`dist`であり、この調査でクリーンビルドした成果物ではない。HEADと生成物の対応、本番公開物との一致、処理時間、最大RSS、アップロード量、失敗原因は未検証である。

| 項目 | 結果 |
| --- | ---: |
| `apps/awesome/dist`のディスク使用量（`du -sh`表示） | 620M |
| ファイル内容のバイト数合計 | 611.84 MiB |
| ファイル数 | 4,188 |
| HTML | 2,082ファイル、434.65 MiB |
| HTML中のサイドバー領域 | 2,074ページ分、276.01 MiB |
| JavaScript（`sw.js`を含む） | 2,090ファイル、約175.81 MiB |
| 検索・サイドバーJSON | 10ファイル、約1.30 MiB |
| `dist/docs/awesome`のディスク使用量 | 440M |
| 統合`dist`のディスク使用量 | 461M |

MiBは1,048,576 bytes。`du`の値にはファイルシステムの割当量が含まれ、内容のバイト数合計とは一致しない。いずれも圧縮後のネットワーク転送量ではない。

サイドバー領域は各HTMLの`<aside class="sidebar-column…">`から対応する最初の`</aside>`までを抽出し、UTF-8のバイト数を合計した。HTML全体の約63.5%に相当する。これは領域全体の容量であり、削減可能量の保証ではない。

ルート目録の英語エントリは旧版365、新版672、合計1,037。両版を通じた`sourceId`は672種類。日本語を含む本文ページは2,074件で、入口等を含むHTML総数が2,082件になっている。

### 3.2 未参照JSの解釈

[統合ビルド](../../scripts/build-integrated.js)と[選択ビルド](../../scripts/build-selective.js)は、統合後に[未参照JS削除](../../scripts/prune-unreferenced-javascript-assets.js)を行う。公開パスと一致する一時的な`docs/awesome/`配置で読み取り検査した結果、アセットJS 2,089件中、到達可能7件、未参照2,082件、未参照容量175.80 MiBだった。

したがって「620Mすべてを毎回Cloudflareへアップロードしている」とは断定できない。既存の統合出力が440Mであることとも整合する。ただし、生成後の削除では、そのJSを生成するビルド処理・一時ディスクの負担はなくならない。

検査器は公開URLを統合出力ルートから解決する。`apps/awesome/dist`をそのまま渡すと`/docs/awesome/assets/…`を解決できず、使用中のJSまで未参照扱いになるため、その結果を削除判断に使わない。既存検査は静的な参照抽出であり、動的URLなども含めたブラウザ検証の代替ではない。

### 3.3 他のapps

同じ方法で既存ローカル出力を測定した。アプリ間でビルド時点が揃っている保証はなく、厳密な性能比較ではない。

| アプリ | ファイル数 | HTML数 | 全内容MiB | HTML MiB | サイドバー領域MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| awesome | 4,188 | 2,082 | 611.84 | 434.65 | 276.01 |
| glfw | 106 | 77 | 14.33 | 6.58 | 1.25 |
| lua | 145 | 117 | 10.38 | 6.75 | 2.54 |
| sample-docs | 186 | 44 | 7.53 | 2.68 | 0.48 |
| test-verification | 102 | 26 | 1.39 | 0.70 | 0.16 |

他のappsにも共通ナビゲーションをHTMLへ埋め込む構造がある。ただし、この値から全面的な遅延読込やR2移行が必要とは判断しない。小規模なサイドバーは初期HTMLに含める方が単純で、追加通信も要らない。

## 4. ソースから確認できる負荷の構造

### 4.1 サイドバーの反復

[AwesomeのDocLayout](../../apps/awesome/overview/src/layouts/DocLayout.astro)は版・言語に属する全カテゴリ／リストを各ページで組み立て、[Sidebar](../../packages/ui/src/components/Sidebar.astro)へ渡してHTML化する。同一版・言語のページ数をNとすると、全N項目をNページへ出力する部分は概ねN²で増える。タイトル変更も多数のHTMLの差分につながる。

全サイトのサイドバーを毎ページに出しているわけではない。版・言語ごとの集合について、この増加が発生する。

### 4.2 全コンテンツの取り込み

[Awesomeのルート](../../apps/awesome/overview/src/pages/[version]/[lang]/[...slug].astro)には全Markdownを対象とする`import.meta.glob`があり、`getStaticPaths()`も全ルートを生成する。パスだけを絞っても入力モジュールの処理が残り得るため、個別ビルドではimport対象自体の限定が必要である。

同じページ内で全ルートのfilter／find、同じ版・言語の隣接ページ探索も行っている。版・言語・カテゴリ・slugのMapを一度構築して再利用する候補になるが、効果はプロファイル後に判断する。

### 4.3 CIと統合出力

[CloudflareのCI](../../.github/workflows/cloudflare-pages-deploy.yml)はquality-checkで統合ビルドし、preview／productionジョブで再度ビルドしている。検証済み出力を同じコミットのartifactとして引き継ぐ余地がある。

[選択出力の統合](../../scripts/selective-output.js)は既存distをステージへ複製し、対象を置換してから切り替える。失敗時の保全には意味がある一方、対象外アプリが巨大化すると、小さい変更でも全体コピーのI/O・一時容量が増える。単に直接上書きへ変えて安全性を失わず、将来はアプリ別成果物と公開目録でこの依存を減らす。

### 4.4 共有実装の境界

[レイアウト同期](../../scripts/sync-docs-layouts.js)の対象はLua、GLFW、sample-docs、test-verificationの固定4件で、Awesomeは含まれない。ADR-0009の一般方針と現在の例外を整理する必要がある。Awesomeをそのまま同期対象に追加すると専用ルート目録の処理を失うため、ナビゲーションの入力契約を先に設ける。

[検索生成](../../scripts/build-search-index.js)は通常の文書に本文・見出し・API識別子を含む索引を生成する。一方、[Awesome公開処理](../../scripts/importers/awesome/publish-awesome.mjs)の索引はタイトル・説明・リポジトリ・カテゴリを中心とし、本文全文検索ではない。共通化時に検索範囲を暗黙に変えない。

## 5. Awesomeの推奨構造

### 5.1 閲覧・生成・公開を分ける

| 単位 | 責務 | Awesomeでの例 |
| --- | --- | --- |
| 閲覧サイト | URL、見た目、ナビ、検索のまとまり | `apps/awesome`、`/docs/awesome/` |
| 生成単位 | 独立して変換・検証・再利用できる入力 | `sourceId × version × lang` |
| 公開単位 | 検証済み生成物を公開する切替範囲 | 変更リスト＋関連目録、必要に応じ複数リスト |

既存の`sourceId`、ルート目録、`CONTENT_MAP`、`CONTENT_PARTITIONS`を起点にし、同じ分類の手書き設定を増やさない。旧`SITE_SHARDS`を新たな正本へ戻さない。カテゴリは閲覧上の分類とし、識別子や必須のデプロイ境界にしない。

### 5.2 ビルド入力と出力

対象リストだけのimportモジュールを生成するか、隔離した作業ディレクトリに必要な入力を用意する。並行ビルドで共通の生成ファイルや`dist`を上書きしない。Astroの起動コストを考え、単独指定に加えて複数指定・バッチ処理を用意する。

公開済みルート一覧はリンク解決用に全体を参照できるようにする。「今回ビルドしない」と「存在しない」を区別する。共通CSS／JSは内容ハッシュで参照し、個別出力が依存するアセットを明示する。

初期段階は現行レイアウトを使った完全なHTMLページを成果物とする。本文、目次、出典、canonical、lang／dirを初期HTMLに残す。WorkerでリクエストごとにMarkdownを変換する方式や、本文をJSで取得するSPA化は推奨しない。

### 5.3 ナビゲーション

大規模モードでは現在のカテゴリ・現在地と全体一覧へのリンクを初期HTMLに含め、全体ツリーは共有JSONから取得する。必要ならカテゴリ別に分割し、展開時に取得する。表示位置を確保し、現在地・展開・スクロール・キーボード操作を維持する。

JavaScript無効時や取得失敗時も、通常のカテゴリ一覧・全体一覧ページから移動できるようにする。全リストをnoscript内へ再度埋め込むと容量削減にならない。隣接ページリンクは小さいため初期HTMLに残せるが、並び変更時は前後ページも更新対象になる。

### 5.4 配信先の比較

| 案 | 利点 | 制約・採用判断 |
| --- | --- | --- |
| Pages継続＋差分ビルド | 運用変更が小さく、まず試せる | 完全な公開ファイル集合を復元・管理する必要がある |
| 少数のStatic Assets配信単位＋Worker | 公開・障害範囲を分けやすい | 各配信単位内はまとまったデプロイ。境界とルーティングの管理が必要 |
| Worker＋R2 | リスト別生成物を独立して保存・公開できる | ルート解決、キャッシュ、公開切替、復旧を実装する |
| リスト別apps／Cloudflareプロジェクト | 単位が明示的 | 設定・監視・デプロイ数がリスト数に比例し、今回の要件に合いにくい |

Pagesのデプロイはファイル集合のマニフェストを持つ。変更分だけを通常の`pages deploy`へ渡して、既存ファイルへ追記する運用にはしない。Workers Static Assetsも未変更ファイルのアップロードを省けるが、公開はWorkerバージョン単位である。「差分転送」「差分ビルド」「独立した公開」は別々に評価する。[Pages API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/methods/create/)、[Static Assets Direct Uploads](https://developers.cloudflare.com/workers/static-assets/direct-upload/)

### 5.5 R2を採用する場合の公開契約

R2は配信用の生成物置き場とし、Git管理の本文・設定・出典情報を正本として維持する。既存URLをWorkerが生成物へ解決し、他のappsはPages配信を継続できるようにする。Cloudflareのzone、既存Pagesドメイン、`/docs/awesome/*`の経路競合は実環境で検証する。プロキシを使う場合は同じ公開URLへの再fetchによるループを避ける。

1. 新生成物を内容ハッシュ付きの不変キーへアップロードする。
2. HTML、アセット、ナビ・検索、出典、リンクの検証を完了する。
3. 未変更生成物への参照を引き継いだ不変の公開マニフェストを作る。
4. 公開先を指す小さな参照を切り替える。切替を直列化するか条件付き更新にして、競合で他の更新を失わないようにする。
5. 旧マニフェストと旧アセットを保持し、参照を戻してロールバックする。
6. 保持期間とキャッシュ寿命を過ぎ、どの保持マニフェストからも参照されない物だけ回収する。

全体マニフェストが小さい間は、変更本文だけを送信し、小さな全体マニフェストを再生成する方式で十分。毎要求で巨大な目録を取得・解析する設計にしない。成長したら版・言語・区画別目録とルート目録に分ける。

R2の強整合性は複数オブジェクトの一括トランザクションやCDNキャッシュの即時失効を意味しない。公開参照のキャッシュ時間、旧世代が見える許容時間、世代を含むキャッシュキーを定義する。新旧どちらの応答でも依存アセットが揃うことを保証する。[R2 Consistency](https://developers.cloudflare.com/r2/reference/consistency/)

WorkerのR2 bindingによる取得は、自動的なCDNキャッシュを意味しない。Cache API等でキャッシュ方針を明示し、ヒット率、Worker呼出、R2読取、保存世代数を測る。料金削減を未計測で約束しない。プレビューは本番と別の公開参照を使い、検索索引やService Workerも混在させない。

末尾スラッシュ、index解決、404のHTTPステータス、リダイレクト、Content-Type、ETag、HEAD、キャッシュ制御もPagesから引き継ぐ対象である。削除・URL変更は公開マニフェストとリダイレクトに反映し、古いキャッシュで削除済みページがいつまで見えるかを管理する。

## 6. libx全体で今からできること

### 6.1 出力と処理時間を段階別に測る

既存の[性能予算](../../config/performance-budgets.json)、[管理者性能測定](../../scripts/performance/measure-management.js)、[成果物検査](../../scripts/check-deployment-assets.js)を拡張し、別系統の予算設定を乱立させない。

計測対象は、入力文書数／バイト数、変換時間、HTML出力、公開出力、最大ファイル、サイドバー反復量、参照されるJS、最大RSS、一時ディスク、統合コピー、アップロード、公開完了までの時間とする。アプリ・版・言語別内訳と前回からの増分も残す。

現在の成果物検査は合計容量を報告するが、容量自体の停止予算は持たない。既存の件数・最大ファイル検査に加え、容量と増加率の予算を検討する。新しい閾値は同条件のクリーン／キャッシュあり計測を複数回行ってから定める。既存閾値を理由なく引き上げない。

1,000件のサイドバー生成fixtureだけでなく、100／1,000／10,000文書、複数言語・版、巨大な1ページを含む生成fixtureを用意する。全HTML生成と読者側DOM数も測り、N²の増加や単一巨大ファイルを早く検出する。規模の大きい測定は通常の小変更CIから分ける。

### 6.2 検証済み成果物を一度だけ作る

同一コミット・同一公開設定でビルドした出力をCI artifactへ保存し、検証・プレビュー・本番公開で使う。出力マニフェストにコミット、設定、ロックファイル、生成器、出力ハッシュを記録する。環境によりcanonical等が変わる場合は設定ごとに一度生成する。

再利用キャッシュと公開対象artifactは役割を区別する。キャッシュ消失時は正本から再生成でき、公開対象は検証済みの正確なバイト列を追跡できるようにする。失敗したビルドや不完全なキャッシュを完成成果物として採用しない。

### 6.3 変更グラフを段階的に導入する

最初は既存の`--projects`を生かし、Git差分から影響アプリを自動選択する。次にAwesome内の生成単位へ詳細化する。共通パッケージ、CSS、設定、変換プラグイン、テンプレート、ロックファイルから利用アプリへの依存も含める。

入力ハッシュには本文だけでなくfrontmatter、翻訳状態、出典、リンク解決に必要な情報、レイアウト、生成器と依存バージョンを含める。ルート目録全体を全ページのキャッシュキーへ無条件に入れると、一件の変更ですべて失効する。参照している情報を追跡するか、追跡できない段階は保守的に広く再生成し、判断理由を表示する。

削除・改名、隣接ページ、逆リンク、検索・ナビの更新も対象とする。差分なしなら不要なビルド・公開を省く。不明な依存がある場合は全体ビルドへ戻れる経路を維持する。定期的な全体検証で増分処理の漏れを検出する。

### 6.4 共通の成果物契約を小さく作る

各アプリが「公開パス → ファイルハッシュ・サイズ・Content-Type・依存アセット」の目録を出せるようにする。所有パスの衝突を検査し、通常SSGと分割SSGが同じ公開層へ渡せる形を目指す。

入力の取得・翻訳・レビューは各インポーターに残し、公開目録の組立、差分アップロード、検証、切替は共有候補とする。最初から汎用の分散ビルド基盤や巨大な新パッケージを作らず、既存`scripts/`に明確な契約を置き、Awesomeで実証してから抽出する。

### 6.5 過去版と資産を再利用する

過去版は毎回再生成せず、入力と描画処理が同じなら成果物を再利用する。旧版を削除して軽量化することを既定にしない。共通UIの修正や出典訂正時は、必要な旧版も再生成できるようにする。

異なる版で本文が同じでも、canonical、版表示、前後リンクが違う完全HTMLは同一とは限らない。本文中間成果物の再利用と公開HTMLの同一性を区別する。共有CSS／JSの集約も、同名ではなく内容と参照関係で判断し、旧版が参照する資産を保持する。

### 6.6 並列化はメモリ予算から決める

各アプリ・バッチの最大RSSを測り、CIのメモリとディスクに余裕が残る同時実行数にする。巨大アプリを無制限に並列化しない。まず重複処理を減らし、その後に並列化する。全体ビルド・リスト単体・複数リストの各経路で中断後の再実行を検証する。

### 6.7 新規ドキュメント取り込み時に規模を見積もる

取り込み計画に、文書数、最大本文、版数、言語数、画像・添付容量、更新頻度、検索範囲、出典単位を追加する。おおよその出力は本文HTML合計＋各ページに反復されるUI＋共有資産で見積もり、単なるソース容量やページ数だけで判断しない。

最小・代表・最大ページで試験ビルドし、1リスト更新と1版追加の処理を先に確認する。大規模化が見込まれる文書群では、公開前から安定した文書IDとルート目録を持つ。通常アプリは既存slugを利用し、不要なID移行を強制しない。

## 7. 他のappsとテンプレートへの適用

| 改善 | 適用方針 |
| --- | --- |
| 段階別計測・出力予算 | 全appsと統合出力へ適用 |
| CI成果物再利用・影響アプリ選択 | libx共通として適用 |
| 公開パスの所有・衝突検査 | 全apps／sitesへ適用 |
| ナビのデータ契約 | テンプレートと共有UIへ導入し、Awesome専用データも接続可能にする |
| ナビの遅延読込 | Awesomeで先行。Lua／GLFW等は実測と閲覧テストを踏まえて選択 |
| ページ単位の増分ビルド | Awesomeで実証。通常の小規模appsはサイト単位を維持 |
| 検索索引の分割 | 既存予算に近づいた版・言語から検討 |
| Worker＋R2配信 | 独立公開や規模上の必要があるアプリだけに適用 |

レイアウトはまずナビ項目の供給と描画を分離する。通常appsは既存`getSidebarAsync`、Awesomeは専用目録から同じ入力契約を作れるようにする。サイトCSSやcontent collectionを不用意にUIパッケージへ移さず、テンプレートのProps／slot等で接続できる範囲から進める。同期対象の固定リストと新規アプリの扱いも整理する。

検索は当面、既存のサイト・版・言語単位を維持する。大規模化したら生成側は文書別に中間結果をキャッシュし、配信側は適度な数の区画にまとめる。生成単位と通信単位を一致させる必要はない。カテゴリだけで絞った結果をサイト全体の検索結果として扱わず、検索範囲・ランキング・日本語検索の品質を維持する。

[Service Worker](../../scripts/service-worker/sidebar-sw.js)は同一originの`sidebar-cache-v3`を使い、旧名のキャッシュを削除している。CacheStorageはアプリのパスごとに分離されないため、将来の独立リリースではアプリ・環境・スキーマを含む名前と、自分のキャッシュだけを回収する範囲を検討する。キャッシュ済みナビとHTMLの世代が合わない場合の回復も確認する。

共有UI変更時はAwesomeに加えてLua・GLFW・sample-docs・test-verification・テンプレートを検証する。特に長いAPIリファレンス、RTL、モバイル、キーボード、JS無効・通信失敗の回帰を確認する。小規模サイトの初期表示を追加JSのために悪化させない。

## 8. 推奨する実施順序と完了条件

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 0 | 同一コミットの計測基準を作る | クリーン／再利用時の時間・RSS・容量・公開処理を比較できる |
| 1 | CI成果物再利用、未参照JSの生成経路調査 | 検証と公開の出力が一致し、二重ビルドがなくなる。JS削減で必要な機能が壊れない |
| 2 | Awesomeのナビ共有化とテンプレートの接続契約 | HTML重複を削減し、全リストへの到達、現在地、no-JS、アクセシビリティを維持 |
| 3 | Awesomeの個別／バッチビルド、ハッシュ・依存目録 | 一件の本文更新で対象外本文を再変換せず、必要な関連更新を漏らさない |
| 4 | Pages上で成果物再利用を運用 | クリーンCIでも完全な公開集合を復元し、差分ビルドの時間短縮を確認 |
| 5 | 独立公開が必要ならWorker＋R2をプレビュー実証 | 既存URL互換、削除、失敗時保全、競合、世代整合、ロールバックを確認 |
| 6 | Awesomeの配信切替と他appsへの選択展開 | 他appsの経路に影響せず、運用・監視・復旧手順が揃う |

段階4は恒久解にも中間段階にもなる。Pages用の全体集合復元が過大になると分かった場合は、段階3の契約を使って段階5を先行検証してよい。改善率や完了期限は未計測のため設定しない。

増分処理の受け入れケースは、本文一件、日本語だけ、タイトル変更、カテゴリ移動、URL改名、削除、共通テーマ変更、ロックファイル変更、新版追加、変更なし、キャッシュ欠損、アップロード途中失敗、同時公開、ロールバックを含める。旧版・別言語・他appsが意図せず消えないことを確認する。

公開基盤変更前にはADRを作成し、必要に応じて正式原則、性能ガイド、ビルド／デプロイガイド、Awesome単一アプリ構成、CLIヘルプを更新する。本メモの作成はそれらの承認や実装完了を意味しない。
