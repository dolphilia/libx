# libx 正式原則準拠状況の再調査メモ

- 調査日: 2026-08-11
- 対象: リポジトリ全体
- 評価基準: `docs/spec/PROJECT_PRINCIPLES.md`
- 文書種別: 調査メモ（修正方針を決めるための入力であり、仕様やADRではない）

## 1. 調査目的

正式化した「libx コンセプト・方針・方向性・開発原則」を、現在の実装がどの程度満たしているか再評価した。単なる未実装機能の列挙ではなく、原則が重視する安全性、読者体験、管理者体験、表示・生成性能、一元管理、自動検査の順で、実害または将来の拡張時に負債となる箇所を抽出した。

## 2. 調査方法

- `apps/`、`sites/`、`templates/`、`packages/`、`scripts/`、`config/`、`tests/`、`.github/`、`docs/` の構造と主要ファイルを確認した。
- 設定スキーマ、設定読込経路、言語・版・ライセンス設定、生成スクリプト、統合・選択的ビルドをコード上で追跡した。
- 共有コンポーネントと各サイトのレイアウト、ルーティング、CSS、クライアントスクリプトの重複と国際化対応を検索した。
- `pnpm check`、カテゴリ構造検査、Markdown相対リンク検査、設定参照の簡易監査を実行した。
- 統合出力をローカルHTTPサーバーで配信し、Chrome DevToolsのトレースとLighthouseで代表ページを測定した。
- 英語ページとRTLのアラビア語ページを実際に開き、ネットワーク要求とアクセシビリティツリーを確認した。

## 3. 総括

libxの基礎構造は正式原則と概ね同じ方向を向いている。静的生成、サイト単位のワークスペース、共有パッケージ、JSONC設定、テンプレート分離、サイドバー生成、複数言語・複数バージョン、RTL属性、ライセンス表示、回帰テストはすでに存在する。代表ページのローカル無制限環境での表示性能も良好だった。

一方、原則を「継続的に保証する契約」として見ると、現状は品質ゲート、安全な選択的ビルド、管理CLI、アクセシビリティ、法的整合性、設定の正本に重要な不足がある。特に、ランディングだけを選択的ビルドすると統合済み文書を失う実装と、CIが検査失敗を許容する設定は、正式原則の中核保証を直接破るため優先対応が必要である。

優先度別の件数は次のとおりである。

| 優先度 | 意味 | 件数 |
| --- | --- | ---: |
| P0 | 公開物や中核保証を壊し得るため最優先 | 1 |
| P1 | 日常操作、国際化、安全性、品質保証へ明確な実害 | 6 |
| P2 | 拡張時の負債、重複、検査不足 | 7 |
| P3 | 整理・再現性・文書品質の改善 | 3 |

## 4. 原則に適合している点

### 4.1 構造と生成単位

- 配信対象を `apps/`、ポータルを `sites/`、共有機能を `packages/`、生成処理を `scripts/`、正規テンプレートを `templates/` に分けている。
- `templates/docs-site` は通常の統合ビルドから分離され、専用ビルドと構造テストで保護されている。
- `apps/sample-docs` と `apps/test-verification` は独立してビルドできる。

### 4.2 静的・軽量な閲覧経路

- Astroの静的出力を採用し、代表ページの初期表示で要求されたのは文書、CSS、6個の小さなJavaScriptの計8要求だった。
- ローカル、CPU・ネットワーク制限なしの単一測定では、英語代表ページのLCPは490ms、CLSは0.00だった。
- 初期表示で読み込まれたJavaScriptは合計約4.8KB、CSSは約84.7KB、HTMLは約39.1KBだった。

この値は良好だが、本番環境、低速回線、低性能端末、複数回の中央値ではなく、比較対象も用意していない。正式な性能基準値としては扱わない。

### 4.3 多言語の欠落許容

- `sample-docs` のアラビア語はv2だけに存在するが、全体ビルドは成功する。
- サイドバー生成は版ごとの実在言語を検出し、存在しない組合せの出力を省略できる。
- `lang` と `dir` は文書・ランディングの主要レイアウトへ渡されている。

### 4.4 現在の自動検査

- `pnpm check` はlint、型検査、単体テスト、実行時テスト、テンプレート・実サイトビルド、生成物スモークテストを通過した。
- 単体テスト6件、実行時テスト4件、生成物スモークテスト3件が成功した。
- `node scripts/validate-category-structure.js` は、2サイトのカテゴリ翻訳キーが一致していることを確認した。

## 5. 修正すべき点

### P0-1: ランディングの選択的ビルドが他サイトの統合出力を削除する

根拠:

- `scripts/build-selective.js:99` で `landing` の出力先をリポジトリ直下の `dist/` 自体にしている。
- 同ファイル `268-272` では対象の既存出力先を再帰削除してからコピーする。
- したがって `--projects=landing` は、保持すると説明されている `dist/docs/*` も削除する。

違反する原則:

- 7.5「選択したサイト以外の生成物を維持する」
- 13「破壊的操作の対象を事前に確定する」「途中失敗で半端な状態を残さない」

改善案:

1. ランディング出力を一時ディレクトリへ生成する。
2. `dist/` 全体ではなく、ランディングが所有するルートファイルと共通アセットだけを置換する。
3. 更新前後で `dist/docs/*` のハッシュが不変であることを自動テストする。
4. 失敗時に旧出力を維持する原子的な置換へ変更する。

### P1-1: CIの品質ゲートが失敗を止めず、フォーマット検査自体も実行不能

根拠:

- `.github/workflows/cloudflare-pages-deploy.yml` のlintとformatに `continue-on-error: true` が指定されている。
- deployはこのジョブへ依存するが、検査失敗でもジョブが成功扱いになる。
- `.prettierrc` は `prettier-plugin-astro` を要求するが、`package.json` に依存関係がない。
- 実際に `pnpm prettier --check .` は「Cannot find package 'prettier-plugin-astro'」で終了コード1になった。
- CIは `pnpm check`、型検査、テスト、テンプレート検査、生成物スモークテストを実行していない。

改善案:

- Astro用Prettierプラグインを依存関係へ追加し、format検査を復旧する。
- `continue-on-error` を除去する。
- CIの正規品質ゲートを `pnpm check` に統一し、deployは成功した品質ゲートだけに依存させる。

### P1-2: 管理CLIの設定正本と安全な変更手順が揃っていない

根拠:

- `scripts/add-language.js:428` は `landingConfig.siteConfig.supportedLangs.includes(...)` を無条件に呼ぶ。
- 現在の `sites/landing/src/config/projects.config.jsonc` の `siteConfig` には `supportedLangs` がない。
- ランディングの対応言語の正本は `sites/landing/src/config/site.config.jsonc` の `i18n.locales` である。
- 言語追加スクリプトには `--dry-run` がなく、安全に変更予定を確認できない。
- `create-version` の非対話実行にもdry-runや確認がなく、設定を書き換えた後にコンテンツをコピーする。言語別コピーの失敗は警告だけで継続するため、設定上は完成しているがコンテンツが一部欠けた状態を成功として残し得る。
- `create-document` の非対話実行は、文書作成とカテゴリ翻訳設定の更新を別々に書き込み、全体を一つのトランザクションとして戻す手段がない。

違反する原則:

- 7.2、8.1「一つの意味には一つの正本」
- 8.3、10.1「標準スクリプトで日常操作を完了できる」
- 10.2「実行前に結果を理解できる」

改善案:

- プロジェクトへの言語追加と、ポータル自体のUI言語追加を別操作として扱う。
- `projects.config.jsonc` へ対応言語を書き戻す処理を廃止し、必要な場合だけ `site.config.jsonc` の共通ローダー・検証APIを使う。
- `--dry-run`、確認、失敗時ロールバックのテストを追加する。

### P1-3: BCP 47形式の対応言語を文書作成CLIとURL補正が扱えない

根拠:

- `scripts/document-utils.js:298` は言語コードを `/^[a-z]{2}$/` に限定する。
- libxは `zh-Hans`、`zh-Hant`、`pt-BR` を正式な対応ロケールとして持つため、これらの文書を `create-document` で追加できない。
- `scripts/build-integrated.js:133-166` と `scripts/build-selective.js:158-189` のURL置換も `[a-z]+` を前提とし、ハイフン付きロケールに一致しない。

改善案:

- 独自正規表現ではなく `@docs/i18n` のロケール集合または共有ロケール検証関数を使用する。
- `zh-Hans`、`pt-BR`、RTL言語を含むCLI・ルーティングテストを追加する。
- 実質的に不要になっている `/libx` 前提のHTML後処理は削除可否を検証する。

### P1-4: アクセシビリティの実測不具合とUI文言の言語不一致がある

代表英語ページのLighthouse結果:

- Accessibility: 87
- `SidebarResizer.astro` の `aria-hidden="true"` 要素内にフォーカス可能なボタンが存在する。
- Shikiのコードコメント色 `#6a737d` と背景 `#24292e` のコントラスト比が3.04:1だった。
- MDXタスクリストの無効化チェックボックスにラベルがない。

RTLページの確認結果:

- アラビア語ページのテーマ切替ボタンが日本語の「テーマを切り替える」と読み上げられる。
- 共有UIとレイアウトに「メインナビゲーション」「閉じる」「言語選択」など日本語固定の `aria-label` が残る。
- CSSの物理方向プロパティを25箇所検出した。すべてが問題とは限らないが、`VersionDiff`、`Banner`、`Card`、`ProjectCard`、`SidebarResizer`、`AnchorHeading` などはRTL目視確認が必要である。

改善案:

- 3件のLighthouse失敗を共有レイヤーで修正する。
- アクセシブル名を `@docs/i18n` の翻訳キーへ移す。
- 英語、アラビア語、モバイル幅を対象にaxe/Lighthouseとキーボード操作を品質ゲートへ追加する。
- 物理方向指定を分類し、意味上固定でないものを論理プロパティへ変更する。

### P1-5: 欠落を許容しているが、存在しないサイドバーへ実際にアクセスする

根拠:

- アラビア語は `sample-docs` のv2にだけ存在する。
- アラビア語v2ページを開くと `/docs/sample-docs/sidebar/sidebar-ar-v1.json` が要求され、404とブラウザコンソールエラーが発生した。

ビルドを止めない点は原則6.6に適合するが、「リンク切れや誤った言語への暗黙遷移を発生させない」という後半を満たしていない。

改善案:

- 言語ごとに利用可能な版だけを版選択UIへ渡す。
- 存在確認のためのクライアント側HEAD/JSON要求を減らし、ビルド時に対応表を生成する。
- 欠落言語・版の組合せで404要求が発生しないブラウザテストを追加する。

### P1-6: ライセンス設定を必須契約として検証していない

根拠:

- `ProjectConfigJSON.licensing` は省略可能である。
- `licenseUrl`、`sourceUrl`、`sourceLanguage` も省略可能で、空文字も通過し得る。
- `sourceLanguage` が `language.supported` に含まれるか、文書の `licenseSource` が存在するsourceを参照するかを正式な品質ゲートで検査していない。
- `apps/test-verification` には `sourceLanguage` がない。

改善案:

- 配信サイトでは `licensing`、原著者、出典、ライセンス、既定sourceを必須にする。
- `sourceLanguage` と対応言語、Frontmatterの `licenseSource` とsource IDを参照整合性検査へ追加する。
- テンプレート、全アプリ、生成スクリプトで同じスキーマを使用する。

## 6. 改善すべき点

### P2-1: レガシー設定APIがリポジトリ内部の標準経路になっている

`getLegacyProjectConfig`、`initializeConfig`、`LegacyProjectConfig`、旧 `basic.*` 形式などの参照をコード・文書から約120件検出した。主要レイアウト、ページ、UI、content-utilsがレガシー型へ依存しているため、現在は削除できない。

正式原則15.5に従い、まず内部利用を `ProjectConfig` と非同期 `loadProjectConfig` / `getProjectConfig` へ移行し、リポジトリ内参照がなくなった段階でレガシー変換、同期キャッシュ、旧JSON形式のfallback、移行専用関数を削除するのが妥当である。

### P2-2: 同じ設定・解析ロジックの正本が複数ある

主な重複:

- `config/global-defaults.jsonc` に `defaultLang` と `language.default` が併存する。
- `scripts/global-defaults.js` と `packages/project-config/src/global-defaults.ts` が同じURL・言語既定値解決を別実装する。
- JSONCコメント除去が `scripts/jsonc-utils.js`、`packages/project-config/src/jsonc.ts`、`packages/config/src/index.ts` に存在する。
- 15ロケールの一覧が `locale-types.ts`、`locales/index.ts`、`language-names.json`、ランディング設定、`packages/config` のfallbackへ重複する。
- `document-utils.js`、サイドバー生成、landing URL生成が共有設定スキーマを通さず独自に設定を解釈する。

改善案は、言語レジストリと設定スキーマを正本にし、型、表示名、fallback、CLI検証、設定リファレンスを生成または共有APIから解決することである。

### P2-3: 設定スキーマの参照整合性が不足する

現在のスキーマは基本的な型を検査するが、次を保証しない。

- version IDの重複禁止と `isLatest` がちょうど1件であること
- `language.supported` の全言語に表示名とtranslationsがあること
- 設定上の版・言語と実ディレクトリの対応
- `projectSlug` とアプリID、生成URL、ランディング装飾IDの対応
- ライセンス参照整合性

実際に `sites/landing/src/config/projects.config.jsonc` には、存在しない `libx-docs` の装飾が残っている。明確に測れるため、原則14の自動検査対象にできる。

### P2-4: 生成物を追跡しつつ、再生成経路がビルド入口ごとに異なる

- `public/sidebar/*.json`、`.gz`、`public/sw.js` がGit追跡対象である。
- Service Workerは各アプリの `prebuild` で同期される。
- テンプレートの `prebuild` はサイドバーも生成するが、実アプリの `prebuild` はサイドバーを生成しない。
- そのためアプリ単体の `pnpm --filter=... build` は、構造変更後の古いサイドバーを使用し得る。

生成物を追跡するか否かを統一し、どの正式ビルド入口でも正本から必ず再生成されるようにする必要がある。追跡を続ける場合は、生成後差分がないことをCIで検査する。

### P2-5: サイト固有シェルの複製が多い

テンプレートと2アプリに、`content/config.ts`、`MainLayout.astro`、`DocLayout.astro`、ルートページ、版・言語ページ、文書ページが合計20ファイル存在する。多くは同じ責務を持つが差分があり、テンプレート修正が既存サイトへ自動反映されない。

すべてを一度に抽象化する必要はないが、安定した共通責務である設定読込、ルートリダイレクト、レイアウト骨格、版・言語の静的パス生成は共有パッケージへ寄せる候補である。サイト固有差分はslot、Props、設定で表す。

### P2-6: 性能契約と大規模フィクスチャがない

現状の代表ページは高速だが、原則11.3が求める次の仕組みはない。

- 代表ページと大規模文書フィクスチャ
- LCP、CLS、転送量、JavaScript/CSS、ビルド時間、最大メモリの予算
- 初回・キャッシュ済み・低速回線・低性能CPUの継続測定
- 類似ジェネレーター、最小静的HTML、変更前libxとの相対比較

また `dist/docs/sample-docs/assets` には約4.13MB、102個のJavaScriptファイルが出力されている。代表ページが初期読込したのはその一部だけなので、直ちに読者転送量の問題ではないが、静的配信物として不要なサーバー側・ページ固有チャンクが含まれていないか確認する価値がある。

### P2-7: Astroの主要バージョンがワークスペース内で分裂している

`apps`、`sites`、`config`、`content-utils`、`project-config` はAstro 5.7.12を使用する一方、`i18n`、`ui`、`versioning` はAstro 3.6.5を別途導入している。共有コンポーネントはAstro 5アプリから利用されるため、依存の重複、型や実行時前提の不一致、インストール量増加につながる。

共有パッケージがAstroを実行時所有する必要があるか確認し、同一バージョンへ揃えるか、適切なpeer dependencyへ変更する。

## 7. その他の整理事項

### P3-1: 主要文書に参照切れと現状不一致がある

確認できた実参照切れ:

- `docs/spec/PROJECT_PRINCIPLES.md` の調査メモ参照が `./LIBX_CONCEPT_AND_DIRECTION_RESEARCH.md` になっている。正しくは `../notes/...`。
- `docs/guides/BACKUP_OPERATIONS_GUIDE.md` の `../CLAUDE.md` は階層が不足する。
- `docs/guides/BUILD_AND_DEPLOYMENT_GUIDE.md` が存在しない `TROUBLESHOOTING_GUIDE.md` を参照する。

現状不一致:

- `README.md` は `config/global-defaults.json` と記載するが実体は `.jsonc`。
- `README.md` は `sample-docs` をlocale-firstの例として説明するが、現在のコンテンツとルートはversion-firstである。

コード例として意図的に存在しないリンクもあるため、リンク検査にはコードブロック・例示と実ナビゲーションを区別する仕組みが必要である。

### P3-2: パッケージ公開境界をVite aliasが迂回する

`packages/config/src/index.ts` は `@docs/ui`、`@docs/theme`、`@docs/i18n` などを各パッケージの `src` ディレクトリへ直接aliasする。ワークスペースのexportsより内部構造が優先されるため、原則7.4の公開API境界が弱くなる。

必要なサブパスを各packageのexportsへ明示し、通常のワークスペース解決を使えるか検証する。

### P3-3: ツールチェーンの再現条件が固定されていない

- READMEはpnpm 8以上、CIはpnpm 9、今回のローカルロック更新環境はpnpm 10系だった。
- ルート `package.json` に `packageManager` やNode engineがない。

動作範囲を広く保つ意図がなければ、CIと開発環境で同じpnpm・Node系統を宣言し、ロックファイルの再現性を上げる。

## 8. 推奨する対応順

### 第1段階: 公開安全性と品質ゲート

1. ランディングの選択的ビルドで他サイトを保持する。
2. CIのformat依存を直し、`pnpm check` を失敗時停止の品質ゲートにする。
3. 選択的ビルドの保存性、失敗時復旧、統合出力を自動テストする。

### 第2段階: 管理CLIと国際化

1. `add-language` の設定正本とdry-runを修正する。
2. BCP 47ロケールを全CLI・URL処理で共通検証する。
3. 欠落版のサイドバー要求をなくす。
4. `create-version` と `create-document` に変更予定表示、dry-run、原子的更新を導入する。

### 第3段階: 読者安全性

1. Lighthouseで検出したアクセシビリティ不具合を修正する。
2. 共有UIのアクセシブル名を多言語化する。
3. ライセンス設定とFrontmatter参照を品質ゲートへ追加する。

### 第4段階: 正本と保守境界

1. 内部コードを現行 `ProjectConfig` APIへ移行してレガシーAPIを削除する。
2. 言語レジストリ、JSONC、既定値、URL解決の重複を統合する。

## 10. 結論

現状のlibxは、正式原則が目指す構造をすでに相当程度備えており、通常のビルドと代表ページ表示も成立している。しかし、保証の中心に置くべき選択的ビルド、CI、管理CLI、アクセシビリティ、ライセンス整合性がまだ「動く場合が多い」段階に留まり、「壊れないことを測定する契約」にはなっていない。

次の改善では機能追加より先に、P0・P1の不整合を解消して正式原則を品質ゲートへ落とし込むべきである。その後、レガシー経路と設定重複を減らし、大規模化しても管理者の理解・設定・生成時間・公開リスクが増えない構造へ寄せていくのが妥当である。
