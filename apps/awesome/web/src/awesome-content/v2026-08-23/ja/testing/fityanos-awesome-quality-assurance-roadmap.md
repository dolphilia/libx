# Awesome Quality Assurance Roadmap

品質保証とソフトウェアテストの基礎を学び、フロントエンド、バックエンド、モバイルの自動化へ進むためのロードマップです。テスト計画書の例、ツールやテスト手法を含む学習の道筋、著者の助言を紹介します。

## はじめに

食品、自動車、ソフトウェアを含め、製品のライフサイクルにはテストが必要です。結果が期待と一致し、その製品を作った目的を満たすかを確認します。QAエンジニアには、ソフトウェアの構成要素の動作や連携を理解し、不具合を引き起こす使い方を試し、意図しない挙動や望ましくない状況を見つける技能が求められます。

以下の学習の道筋を、QAやソフトウェアテストを学び始める際の参考にできます。原文には別の[ロードマップページ](https://fityanos.github.io/anasfitiani/qaroadmap.html)への案内もあります。

## テスト計画書のサンプル

テスト計画書では、判断基準、開始点、各種テストを実施する時期を定めます。計画がなければ、チームは明確な方針を持たずに作業し、品質の低いコードを提供するおそれがあります。

計画書の構成や内容は、プロジェクトや提供物の性質によって変わります。原文ではソフトウェアテスト全般向けのPDF例を紹介しており、プロジェクトの必要に合わせて使えます。

[test_plan_sample.pdfをダウンロード](https://github.com/anas-qa/Quality-Assurance-Road-Map/blob/master/Test_Plan_Sample.pdf)。

## ロードマップ

原文の図2点には「QA Engineer Road Map 2022」という名称が付いています（[1枚目](https://i.imgur.com/cM9cM8T.png)、[2枚目](https://i.imgur.com/meodAKp.png)）。以下の表は、その学習順序と分岐を文章にしたものです。図の赤は「高い採用率」、青は「個人的な好み」を示します。これらは図の評価であり、現在の採用率を測定した結果ではありません。ほかの項目にはこの印はありません。

図の略語：STLCはソフトウェアテストのライフサイクル、SDLCはソフトウェア開発のライフサイクル、TDDはテスト駆動開発、RPAはロボティック・プロセス・オートメーション、UATはユーザー受け入れテスト。

### 基礎とフロントエンドの自動化

| 段階 | 学ぶ内容とツール |
| --- | --- |
| テストのアプローチ | ホワイトボックス、グレーボックス、ブラックボックスの各テスト。 |
| テストの種類 | 機能テスト：UAT、探索的テスト、サニティテスト、回帰テスト、スモークテスト、単体テスト、結合テスト。非機能テスト：負荷テスト、性能テスト、ストレステスト、セキュリティテスト。 |
| テスト管理 | qTest、TestRail（個人的な好み）、TestLink（高い採用率）、Zephyr。 |
| プロジェクト管理 | Atlassian（高い採用率）と、その配下のJira・Confluence。ほかにAssembla、YouTrack、Trello。 |
| SDLCの進め方 | ウォーターフォール：工程間で引き継ぐ。アジャイル：同期しながら反復する。Vモデル：順に進める。 |
| 手動テストとTDD | 手動テストを理解し、テスト駆動開発へ進む。図では、テストとユースケースに基づく開発を勧め、明確な受け入れ基準によって生産性を高め、回帰テストに費やす時間と労力を減らせると説明。 |
| テスト計画 | テスト対象、提供範囲、方針、実施方法を決める。 |
| テストケースとシナリオ | 必須とされている項目。明確に記述・文書化したケースをテストの土台とし、あらゆる可能性をカバーして、より自信を持ってリリースすることを目指す。 |
| 報告 | QAやテストの結果が多様に解釈されることを避け、関係者や管理者の意思決定に役立つ、明確な報告の流れを作る。 |
| 互換性 | ハードウェアやソフトウェアの構成要素を含め、さまざまな利用者の行動や利用能力を再現する。 |
| 検証と妥当性確認 | 違いと使い分けを理解する。検証では製品を正しい方法で作っているか、妥当性確認では作るべき製品を作っているかを問う。 |
| 自動化の分野 | 自動テストを理解し、モバイル、バックエンド、フロントエンドの自動化を検討する。図は続いてフロントエンドを詳しく扱い、2枚目でバックエンドとモバイルへ進む。 |
| フロントエンドのブラウザー拡張 | フロントエンドのテスト対象はブラウザー上のUI。拡張機能：Selenium IDE、CodeCeption add-on、Ghost Inspector、Bug Magnet、Check my links。 |
| フロントエンドの自動化フレームワーク | qaWolf、Mocha.js、Webdriver IO（高い採用率）、Jasmine JS、2つ目のWebdriver IO、Protractor JS、Nightwatch JS、CodeCeption、Robot、Jest、Cypress.io（個人的な好み。Selenium不要と記載）。 |

## 助言

著者は次のように助言しています。

- 失敗するところを確認していないテストコードを信用しない。

- 自動化へ進む前にソフトウェアテストを理解する。まずテストの判断基準を設計し、その後、反復作業を効率よく進めるために自動化する。

- 自動化は、手作業で記述したテストを文書化し、読みやすく、理解しやすく、再利用できるコードにするものと捉える。

- テストコードが実際に何かをテストしていることを確認する。

- テストコード自体にテストが必要な状態にしない。

- 200~OKでも問題がないとは限らない。サーバーのステータスだけに頼らず、許可されていないAPI呼び出しに200が返ることは、ソフトウェアのセキュリティを危険にさらすと認識する。
