<h3 class="section" id="Linking-executables-1">3.3 実行可能ファイルのリンク</h3>
<a class="index-entry-id" id="index-linking-against-installed-libraries"></a>
<p>この時点で、実行可能ファイルをリンクする前にライブラリをインストールする（恒久的な場所に置く）ことにした場合、リンクに libtool を使う必要はありません。適切な <samp>-L</samp> と <samp>-l</samp> フラグでライブラリの場所を指定するだけです。</p>
<a class="index-entry-id" id="index-buggy-system-linkers"></a>
<p>システムのリンカーによっては、生成する実行可能ファイルに、各共有ライブラリの完全なディレクトリ名を埋め込むものがあります。Libtool はこの困った機能を特別な方法で回避し、インストールされる実行可能ファイルには、恒久的なディレクトリ名だけが入るようにします。</p>
<a class="index-entry-id" id="index-security-problems-with-buggy-linkers"></a>
<a class="index-entry-id" id="index-bugs_002c-subtle-ones-caused-by-buggy-linkers"></a>
<p>この不具合の重要性を見落としてはいけません。プログラムが分かりやすくクラッシュするわけではありませんが、セキュリティ上の穴が生まれます。さらに悪いことに、パッケージをインストールした後でライブラリのソースコードを変更すると、インストール済みのプログラムの動作まで変わってしまうことがあります。</p>
<p>したがって、ライブラリをインストールする前にプログラムをリンクしたい場合は、リンクに libtool を使う必要があります。</p>
<a class="index-entry-id" id="index-linking-against-uninstalled-libraries"></a>
<p>未インストールのライブラリにリンクする従来の方法は、次のとおりです。</p>
<div class="example">
<pre class="example-preformatted">burger$ <kbd class="kbd">gcc -g -O -o hell.old main.o libhello.a -lm</kbd>&#10;burger$&#10;</pre></div><p class="gnu-libtool-code-note">従来の方法で、main.o と静的ライブラリ、数学ライブラリをリンクして hell.old を作成します。</p>
<p>libtool を使う方法もほとんど同じです<a class="footnote" href="#FOOT2" id="DOCF2"><sup>2</sup></a>（<a class="pxref" href="/docs/gnu-libtool/source/v2-6-2/manual.html#Link-mode">Link mode</a> を参照）。</p>
<div class="example">
<pre class="example-preformatted">a23$ <kbd class="kbd">libtool --mode=link gcc -g -O -o hell main.o libhello.la</kbd>&#10;gcc -g -O -o hell main.o  ./.libs/libhello.a -lm&#10;a23$&#10;</pre></div><p class="gnu-libtool-code-note">libtool が .la を静的アーカイブへ置き換え、保存済みの数学ライブラリ依存 -lm も gcc に渡しています。</p>
<p>あまりに単純で、本当とは思えないかもしれません。libtool が行ったのは <samp>libhello.la</samp> を <samp>./.libs/libhello.a</samp> に置き換えることだけですが、<samp>a23</samp> には共有ライブラリがないことを思い出してください。また、Libtool は <samp>libhello.la</samp> が <samp>-lm</samp> に依存していることも覚えていました。そのため、libtool のコマンド行で <samp>-lm</samp> を指定しなかったにもかかわらず<a class="footnote" href="#FOOT3" id="DOCF3"><sup>3</sup></a>、<code>gcc</code> のリンク行に加えてくれています。</p>
<p><samp>burger</samp> では、Libtool は未インストールの共有ライブラリにリンクします。</p>
<div class="example">
<pre class="example-preformatted">burger$ <kbd class="kbd">libtool --mode=link gcc -g -O -o hell main.o libhello.la</kbd>&#10;gcc -g -O -o .libs/hell main.o -L./.libs -R/usr/local/lib -lhello -lm&#10;creating hell&#10;burger$&#10;</pre></div><p class="gnu-libtool-code-note">本体を .libs/hell に作成し、現在のディレクトリにラッパー hell を生成します。</p>
<a class="index-entry-id" id="index-linking-with-installed-libtool-libraries"></a>
<p>今度は <samp>libhello.la</samp> がすでにインストールされていて、新しいプログラムをそれにリンクしたいとします。場所を自分で調べて、次のように実行できます。</p>
<div class="example">
<pre class="example-preformatted">burger$ <kbd class="kbd">gcc -g -O -o test test.o -L/usr/local/lib -lhello -lm</kbd>&#10;</pre></div><p class="gnu-libtool-code-note">インストール済みのライブラリの場所と名前を、コンパイラに直接指定する例です。</p>
<p>しかし、<samp>/usr/local/lib</samp> が標準のライブラリ検索パスに入っていなければ、<code>test</code> を実行できません。代わりに libtool を使ってインストール済みの libtool ライブラリにリンクすれば、適切に処理してくれます。</p>
<div class="example">
<pre class="example-preformatted">burger$ <kbd class="kbd">libtool --mode=link gcc -g -O -o test test.o \&#10;                /usr/local/lib/libhello.la</kbd>&#10;gcc -g -O -o .libs/test test.o -Wl,--rpath \&#10;        -Wl,/usr/local/lib /usr/local/lib/libhello.a -lm&#10;creating test&#10;burger$&#10;</pre></div><p class="gnu-libtool-code-note">libtool が実行時の検索パスと -lm を補ってリンクし、ラッパー test を作成します。</p>
<p>libtool が必要な実行時パスのフラグと、libhello.la が依存しているライブラリ <samp>-lm</samp> を追加した点に注目してください。便利でしょう？</p>
<a class="index-entry-id" id="index-wrapper-scripts-for-programs"></a>
<a class="index-entry-id" id="index-program-wrapper-scripts"></a>
<p>実行可能ファイル <code>hell</code> は実際には <samp>.libs</samp> サブディレクトリに作成され、その後、現在のディレクトリにラッパースクリプト（プラットフォームによってはラッパー実行形式。<a class="pxref" href="/docs/gnu-libtool/v2-6-2/ja/01-guide/06-wrapper-executables/#Wrapper-executables">未インストールのプログラムのラッパー実行形式</a> を参照）が作成された点に注意してください。</p>
<p>libtool がラッパースクリプトを作成したので、インストールとデバッグにも libtool を使うべきです。ただし、プログラムが未インストールの libtool ライブラリに依存していなければ、ラッパースクリプトなしでもおそらく利用できます。</p>
<p>NetBSD 1.2 では、libtool はコンパイラフラグ <samp>-R/usr/local/lib</samp> を使って <samp>libhello</samp> のインストール先ディレクトリを埋め込みます。その後、ラッパースクリプトが、実行可能ファイルが正しい共有ライブラリ（<samp>./.libs</samp> にあるもの）を見つけるようにし、正しくインストールできるようにします。</p>
<p>二つのプログラムを比較しましょう。</p>
<div class="example">
<pre class="example-preformatted">burger$ <kbd class="kbd">time ./hell.old</kbd>&#10;Welcome to GNU Hell!&#10;** This is not GNU Hello.  There is no built-in mail reader. **&#10;        0.21 real         0.02 user         0.08 sys&#10;burger$ <kbd class="kbd">time ./hell</kbd>&#10;Welcome to GNU Hell!&#10;** This is not GNU Hello.  There is no built-in mail reader. **&#10;        0.63 real         0.09 user         0.59 sys&#10;burger$&#10;</pre></div><p class="gnu-libtool-code-note">出力は「GNU Hell へようこそ。これは GNU Hello ではなく、組み込みメールリーダーはない」という挨拶です。続く real・user・sys は各実行の実時間・ユーザーCPU時間・システムCPU時間で、ここではラッパー経由の方が長くなっています。</p>
<p>ラッパースクリプトを実行するとかなり時間がかかりますが、共有ライブラリがまだインストールされていなくても、少なくとも結果は正しくなります。</p>
<p>では、共有ライブラリによって得られるはずの容量の節約はどうなっているのでしょうか。</p>
<div class="example">
<pre class="example-preformatted">burger$ <kbd class="kbd">ls -l hell.old libhello.a</kbd>&#10;-rwxr-xr-x  1 gord  gord  15481 Nov 14 12:11 hell.old&#10;-rw-r--r--  1 gord  gord   4274 Nov 13 18:02 libhello.a&#10;burger$ <kbd class="kbd">ls -l .libs/hell .libs/libhello.*</kbd>&#10;-rwxr-xr-x  1 gord  gord  11647 Nov 14 12:10 .libs/hell&#10;-rw-r--r--  1 gord  gord   4274 Nov 13 18:44 .libs/libhello.a&#10;-rwxr-xr-x  1 gord  gord  12205 Nov 13 18:44 .libs/libhello.so.0.0&#10;burger$&#10;</pre></div><p class="gnu-libtool-code-note">ls の出力で、実行可能ファイルと静的・共有ライブラリのサイズ、アクセス権、日時を比較しています。</p>
<p>これはひどいですね。このプロジェクトは捨てて、かご編みでも始めた方がよいのかもしれません。</p>
<p>実は、これは重要な点を示しています。共有ライブラリには、相対的な複雑さによるオーバーヘッドがあります。この場合、動的にする代償は8キロバイトで、得られる節約は約4キロバイトです。したがって、少なくともあと数個のプログラムをリンクするまでは、共有 <samp>libhello</samp> を使う利点はありません。</p>
