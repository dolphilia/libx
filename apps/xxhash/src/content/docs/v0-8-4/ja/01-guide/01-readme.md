xxHash — 非常に高速なハッシュアルゴリズム
======================================

[ウェブサイト](https://xxhash.com/) · [APIドキュメント](/docs/xxhash/v0-8-4/ja/02-api/32-xxhash_8h/) · [`xxhsum`マニュアル](/docs/xxhash/v0-8-4/ja/01-guide/06-cli-xxhsum1/) · [形式仕様](/docs/xxhash/v0-8-4/ja/01-guide/08-doc-xxhash_spec/)

xxHashは、RAMの速度限界に達するほど高速な非暗号学的ハッシュアルゴリズムです。移植性が高く、リトルエンディアンとビッグエンディアンを含む、あらゆるプラットフォームで同一のハッシュを生成します。アルゴリズムが確定すると、その出力はxxHashのリリースをまたいでも変わりません。

このライブラリには次のアルゴリズムが含まれます。

- XXH32は32ビット演算を使って32ビットのハッシュを生成します。
- XXH64は64ビット演算を使って64ビットのハッシュを生成します。
- v0.8.0以降で利用できるXXH3は、ベクトル演算を使って64ビットまたは128ビットのハッシュを生成します。128ビット版はXXH128と呼ばれます。

新しいアプリケーションでは、標準の選択として`XXH3_64bits()`を推奨します。128ビットのハッシュが必要な場合は`XXH3_128bits()`を使用してください。

### 小さいデータ

大きいデータでの性能は、全体像の一部にすぎません。ハッシュ処理は、ハッシュテーブルやブルームフィルターなどの構造でも非常に役立ちます。こうした用途では、多数の小さい入力をハッシュすることが一般的で、入力が数バイトしかないこともあります。この場合、初期化と終了処理のコストが固定的にかかるため、アルゴリズムの性能は大きく異なり得ます。分岐予測の失敗も、はるかに大きな影響を及ぼします。

XXH3は、長い入力でも小さい入力でも優れた性能を発揮するよう設計されています。次のグラフでその様子を確認できます。

![XXH3、レイテンシー、ランダムなサイズ](https://user-images.githubusercontent.com/750081/61976089-aedeab00-af9f-11e9-9239-e5375d6c080f.png)

詳しい分析は、[wikiの性能比較](https://github.com/Cyan4973/xxHash/wiki/Performance-comparison#benchmarks-concentrating-on-small-data-)を参照してください。

**xxHashは暗号学的ハッシュ関数ではありません。** 署名、パスワードの保存、その他の攻撃への耐性が必要な用途には使用しないでください。

使い始める
---------------

デフォルトの`make`ターゲットは、ライブラリとコマンドラインユーティリティ`xxhsum`の両方をビルドします。

```sh
make
./xxhsum -H3 README.md
```

その後、ライブラリを`libxxhash`としてリンクするか、`xxhash.c`から直接コンパイルできます。ヘッダーだけで組み込むには、`xxhash.h`をインクルードする前に`XXH_INLINE_ALL`を定義します。

```c
#define XXH_INLINE_ALL
#include "xxhash.h"
```

CMakeでの組み込みは、[CMakeガイド](/docs/xxhash/v0-8-4/ja/01-guide/03-build-cmake-readme/)を参照してください。[`xxhsum`マニュアル](/docs/xxhash/v0-8-4/ja/01-guide/06-cli-xxhsum1/)では、チェックサムの生成、検証、ベンチマーク、高度なコマンドラインオプションを説明しています。

### 例

最も単純なAPIは、連続したメモリブロックを1回の呼び出しでハッシュします。

```c
#include <stddef.h>
#include "xxhash.h"

XXH64_hash_t hash_buffer(const void* buffer, size_t size)
{
    return XXH3_64bits(buffer, size);
}
```

APIは、サイズが不明なストリームの逐次的なハッシュ処理にも対応しています。1回の呼び出しとストリーミングの完全な例は、説明付きの[APIヘッダー](/docs/xxhash/v0-8-4/ja/02-api/32-xxhash_8h/)にあります。

品質
-------------------------

重要なのは速度だけではありません。攻撃を意図しない入力に対し、xxHashは均一な分布を目指しています。これにより、出力ビットの任意の部分集合を使って、テーブルやインデックス内の要素を均等に分散できます。固定幅のハッシュである以上、衝突や[誕生日のパラドックス]の影響は受けます。

すべてのバリアントは、Austin Applebyの[SMHasher](https://www.google.com/search?q=SMHasher)テストスイートを正常に完了しています。これは統計的な品質を測る基準となります。速度や衝突特性をより詳しく評価する追加テストも[提供されています](https://github.com/Cyan4973/xxHash/tree/c87183a77d67f7d37e3d2d1b7eaac5e7c695e4f0/tests)。

さらにxxHashは、独自の[大規模な衝突テスター](https://github.com/Cyan4973/xxHash/tree/c87183a77d67f7d37e3d2d1b7eaac5e7c695e4f0/tests/collisions)を提供しています。数十億個のハッシュを生成・比較し、64ビットハッシュアルゴリズムの限界を検証できます。この面でも、xxHashは[誕生日のパラドックス]と整合する良好な結果を示しています。詳しい分析は[wiki](https://github.com/Cyan4973/xxHash/wiki/Collision-ratio-comparison)に記載されています。

[誕生日のパラドックス]: https://en.wikipedia.org/wiki/Birthday_problem

パッケージ
--------

xxHashは多くのパッケージマネージャーから利用できます。[vcpkg](https://github.com/microsoft/vcpkg)では、次のコマンドでライブラリをインストールします。

```sh
vcpkg install xxhash
```

コマンドラインユーティリティもインストールするには、`xxhsum`機能を追加します。

```sh
vcpkg install "xxhash[xxhsum]"
```

各ディストリビューションで現在利用できるパッケージのバージョンは、[Repology](https://repology.org/project/xxhash/versions)で追跡されています。

高度なビルドオプション
----------------------

### ライブラリのマクロ

次のマクロは、コンパイル時に設定して`libxxhash`の動作を変更できます。通常、デフォルトでは無効です。

- `XXH_INLINE_ALL`：すべての関数を`inline`にし、実装を`xxhash.h`に直接含めます。関数のインライン化は速度向上に役立ち、特に小さいキーで効果があります。キーの長さが*コンパイル時定数*で表される場合は*非常に効果的*で、+200%程度の性能向上が観測されています。詳しくは[この記事](https://fastcompression.blogspot.com/2018/03/xxhash-for-small-keys-impressive-power.html)を参照してください。
- `XXH_PRIVATE_API`：`XXH_INLINE_ALL`と同じ結果になります。従来との互換性のため引き続き利用できます。この名前は、`XXH_*`というシンボル名がエクスポートされないことを強調しています。
- `XXH_STATIC_LINKING_ONLY`：静的確保に必要な内部状態の宣言にアクセスできるようにします。ABI変更のリスクがあるため、動的リンクとは互換性がありません。
- `XXH_NAMESPACE`：すべてのシンボルに`XXH_NAMESPACE`の値を接頭辞として付けます。このマクロにはコンパイル可能な文字集合しか使えません。xxHashのソースコードを複数回取り込む場合などに、シンボル名の衝突を避けるのに役立ちます。`xxhash.h`を通じてシンボルが自動的に変換されるため、クライアントアプリケーションでは通常の関数名を使います。
- `XXH_FORCE_ALIGN_CHECK`：入力がアラインされている場合に、より高速な直接読み取り経路を使います。アラインされていないアドレスからメモリをロードできないアーキテクチャでは、ハッシュ対象の入力が偶然32ビットまたは64ビット境界にアラインされている場合に、性能が大幅に改善することがあります。アラインされていないメモリアクセスの性能が高いプラットフォーム（アラインの有無にかかわらず同じ命令を使用）では、わずかに性能を悪化させます。このオプションは`x86`、`x64`、`aarch64`では自動的に無効になり、それ以外のすべてのプラットフォームでは有効になります。
- `XXH_FORCE_MEMORY_ACCESS`：デフォルトの方式`0`は、移植性のある`memcpy()`記法を使います。方式`1`はgcc固有の`packed`属性を使い、一部の対象で性能を改善することがあります。方式`2`は非アライン読み取りを強制します。標準には準拠しませんが、より高い読み取り性能を得る唯一の方法になる場合もあります。方式`3`はバイトシフト演算を使います。`memcpy()`をインライン化しない古いコンパイラーや、バイトスワップ命令のないビッグエンディアンシステムに適しています。
- `XXH_CPU_LITTLE_ENDIAN`：デフォルトでは、コンパイル時に解決される実行時テストによってエンディアンを判定します。何らかの理由でコンパイラーがこの実行時テストを簡略化できない場合、性能上のコストがかかることがあります。このマクロを1に設定してアーキテクチャがリトルエンディアンだと明示すれば、自動検出を省略できます。0にするとビッグエンディアンを示します。
- `XXH_ENABLE_AUTOVECTORIZE`：CPUのベクトル機能やコンパイラーのバージョンによっては、XXH32とXXH64で自動ベクトル化が行われることがあります。注：最近の`clang`では自動ベクトル化がより起こりやすい傾向があります。XXH32ではSSE4.1または同等の機能（NEON）で十分ですが、XXH64にはAVX512が必要です。残念ながら、自動ベクトル化は一般にXXHの性能を悪化させます。このため、xxhashのソースコードはデフォルトで自動ベクトル化を防ぐようにしています。ただし、システムは進歩しており、この結論は変わる可能性があります。たとえば、最近のZen4 CPUではベクトル化によって性能が改善する可能性が高いと報告されています。そのため、ベクトル化したコードを使いたい、または試したい場合は、このフラグを有効にできます。これによりベクトル化を防ぐコードが取り除かれ、XXH32とXXH64が自動ベクトル化される可能性が高まります。
- `XXH32_ENDJMP`：XXH32の複数分岐による終了処理段階を、1回のジャンプに置き換えます。一般に性能面では望ましくなく、特にランダムなサイズの入力をハッシュする場合に不利です。ただし、アーキテクチャやコンパイラーによっては、ジャンプによって小さい入力での性能がわずかに改善することがあります。デフォルトでは無効です。
- `XXH_IMPORT`：MSVC固有です。リンクエラーを防ぐため、動的リンクの場合だけ定義すべきです。
- `XXH_NO_STDLIB`：`<stdlib.h>`の関数、特に`malloc()`と`free()`の呼び出しを無効にします。`libxxhash`の`XXH*_createState()`は常に失敗して`NULL`を返すようになります。ただし、`XXH32()`などによる1回のハッシュ処理や、静的に確保した状態を使うストリーミングは、従来どおり動作します。このビルドフラグは、動的確保を使わない組み込み環境で役立ちます。
- `XXH_memcpy`、`XXH_memset`、`XXH_memcmp`：コンパイル時に`memcpy()`、`memset()`、`memcmp()`をユーザーが選んだシンボルへ転送します。3つすべてを転送すると、標準ライブラリの`<string.h>`をインクルードする必要がなくなります。
- `XXH_NO_EXTERNC_GUARD`：`xxhash.h`をC++モードでコンパイルするとき、`extern "C" { .. }`のブロックガードを取り除きます。
- `XXH_DEBUGLEVEL`：1以上の値に設定すると、`assert()`文を有効にします。実行速度はわずかに低下しますが、デバッグ時のバグ発見に役立つことがあります。

### バイナリーサイズの制御

- `XXH_NO_XXH3`：生成するバイナリーから、`XXH3`に関連するシンボル（64ビットと128ビットの両方）を取り除きます。`libxxhash`のサイズへの寄与は`XXH3`が突出して大きいため、`XXH3`を使わないアプリケーションのバイナリーサイズを小さくするのに役立ちます。
- `XXH_NO_LONG_LONG`：64ビットの`long long`型に依存するアルゴリズムをコンパイル対象から外します。対象には`XXH3`と`XXH64`が含まれ、`XXH32`だけがコンパイルされます。64ビットに対応しない対象（アーキテクチャやコンパイラー）で役立ちます。
- `XXH_NO_STREAM`：ストリーミングAPIを無効にし、ライブラリを1回の呼び出しによるバリアントだけに制限します。
- `XXH_NO_INLINE_HINTS`：デフォルトでは、xxHashは`__attribute__((always_inline))`と`__forceinline`を使い、コードサイズを犠牲にして性能を改善します。このマクロを1に定義すると、すべての内部関数を`static`にし、関数をインライン化するかどうかをコンパイラーが決められるようにします。最小のバイナリーサイズを目指す場合に非常に役立ちます。GCCとClangで`-O0`、`-Os`、`-Oz`、`-fno-inline`を指定してコンパイルすると、自動的に定義されます。コンパイラーのバージョンによっては、`-Og`でコンパイルを成功させるためにも必要です。
- `XXH_SIZE_OPT`：`0`はデフォルトで、速度を最適化します。`1`は`-Os`と`-Oz`でのデフォルトで、サイズ最適化のために速度向上のための一部の工夫を無効にします。`2`はコードを可能な限り小さくしますが、性能は大きく低下するかもしれません。

### XXH3固有のビルド設定

- `XXH_VECTOR`：ベクトル命令セットを手動で選びます（デフォルトではコンパイル時に自動選択）。利用できる命令セットは、`XXH_SCALAR`、`XXH_SSE2`、`XXH_AVX2`、`XXH_AVX512`、`XXH_NEON`、`XXH_VSX`です。正しく対応させるため、コンパイラーが追加のフラグを必要とすることがあります。たとえばx86_64上の`gcc`では、`AVX2`に`-mavx2`、`AVX512`に`-mavx512f`が必要です。
- `XXH_PREFETCH_DIST`：プリフェッチ距離を選びます。特定のハードウェアプラットフォームに合わせて低水準で調整するための設定です。XXH3だけに適用されます。
- `XXH_NO_PREFETCH`：プリフェッチを無効にします。プラットフォームや状況によっては、プリフェッチなしの方が性能がよい場合があります。XXH3だけに適用されます。

### `xxhsum` CLIのビルド設定

- `XXH_1ST_SPEED_TARGET`：ベンチマークモードの最初の速度テストに対して、MiB/sで初期の目標速度を選びます。ベンチマークは以後の反復で目標を調整しますが、最初のテストでは事前に実測せず、この速度を目標にします。現在は、非常に遅い（エミュレーションされた）プラットフォームにも対応するため、控えめな10 MiB/sに設定されています。

### Makefileの変数

次の変数は、`make`でビルドするときの実行時ディスパッチを制御します。

- `DISPATCH=1`：コマンドラインインターフェース`xxhsum`で`xxh_x86dispatch.c`を使い、`scalar`、`sse2`、`avx2`、`avx512`の命令セットから実行時に選びます。このオプションは`x86`/`x64`システムでのみ有効です。`x86`/`x64`ターゲットを検出するとデフォルトで有効になります。`DISPATCH=0`で強制的に無効にできます。
- `LIBXXH_DISPATCH=1`：静的ライブラリと動的ライブラリの両方の`libxxhash`で、同じ実行時ディスパッチを有効にします。このオプションは`x86`/`x64`システムでのみ有効で、デフォルトでは無効です。ライブラリの利用者は短い入力を頻繁にハッシュすると一般に想定されます。その場合はインライン化が重要で、実行時ディスパッチが性能を悪化させる可能性があるため、デフォルトでは無効です。それでも明示的に選ぶことはできます。有効にすると、`xxh_x86dispatch.h`で宣言されたシンボルがライブラリに含まれ、ヘッダーもインストールされます。アプリケーションは、このヘッダーをインクルードし、XXH3のエントリーポイントをディスパッチ対応版へ転送する必要があります。
- `NODE_JS=1`：Emscriptenを使ってNode.js用の`xxhsum`をコンパイルするとき、ファイルシステムへ制限なくアクセスするために`NODERAWFS`ライブラリをリンクし、コマンドラインユーティリティが端末を正しく検出できるように`isatty`を修正します。この設定により、バイナリーはNode.js専用になります。
